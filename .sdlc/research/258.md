## Decisions
**A — plan hash source.** NOT `publish_generation` (see claim table; measured). `plan_hash =
hashlib.sha256(<plan file bytes>).hexdigest()`, which is also the 64-hex shape the contract's
`plans` kind documents. One small helper beside the resolver (e.g. `review_context.plan_sha256(path)`
or a `work.py` private) used by BOTH `record-plan-review` and `pr`. Do not name it `content_hash`:
`tests/test_mirror.py:674` string-matches that name across `skills/`. At `pr`, hash the plan
**as it is on the branch**: `rel` from `phase_doc_file` (BR-4); if `git ls-files -- rel` in the
worktree is non-empty, read `<worktree>/<rel>` bytes from disk (the porcelain check at `:2760` just
proved the tree clean, so it equals HEAD); if the repo ignores plans there is no branch copy, so
hash the main-checkout file. **Do not hash `git show` output via `run`**: `_run` returns
`stdout.strip()` (`work.py:1024`), which drops the trailing newline and never matches a file-bytes
hash.

**B — contract.** (b) purely local state, no MINOR bump, no golden. `.sdlc/state/` is in
`RUNTIME_IGNORES` (`sigma-setup/scripts/setup.py:51`), never published or synced, like the existing unversioned
`state/work/`, `state/review-results/`, `state/review-manifests/`. The journal mirror reuses
`gate` with `gate=plan_review`, `verdict=pass|warn|block` (BR-13): no new kind, no new field.
Adding `plan_hash` to the event WOULD be a new field → MINOR bump + `vocabulary.json` regen +
golden update. Recommend not doing it. Write the mirror as a literal
`ledger.safe_append(sdlc_dir, "gate", goal, config=config, stream=ledger.EVENTS, gate="plan_review", verdict=...)`
and delete the prose emit, so there is only one emitter (the #1013/#1626 double-emission lesson).

**C — config registration.** Local-only key read straight from `config` with the total
`_gate_block`/`hard_plan_gate_on` rules. **Not** routed through `managed_settings.gated_check`
and **not** added to `LOCKABLE_KEYS`: probed, an adopted checkout whose org file is `status: ok`
but does not lock a key turns a local ON into OFF (TD-1). A future lockable version must fall
back to local config when `outcome["locked"]` is False. Files: `config.json.tmpl` (BR-17),
`work.py` registry row with `enabled_by=("work.enabled","gates.plan_review.enabled")` (BR-5), regen
`docs/enforcement.md` (BR-16), README flag table (BR-20), optional doctor row (BR-29). There is no
config schema/validator (`state.load_config` is plain `json.loads`, `state.py:36-50`) and
`contract/golden/config.json` has no `gates`.

**D — plan shapes covered.** Covered: the goal's plan `.sdlc/plans/<stem>.md` (plus the
`phase_doc_file` slug and `<n>-*.md` variants). Not covered: `.sdlc/plans/<stem>.slices.json`
(`slices.py:92`, not hashed: a manifest edit after review is not caught) and design PRs.
Design PRs DO go through `work.py pr` on `sdlc/<n>` (`dossier-pipeline.md:549`,
`writing-the-artifact.md:293`). They carry `.sdlc/design/<n>.md` and no plan, and goal-review
(`sdlc:designed`) is their review. Recommendation: with no plan resolved, this gate says nothing
and `_hard_plan_gate_refusal` owns the no-plan case. That exempts design PRs and docs-only goals
by construction and avoids a second `.allow-direct-edits` interaction. The refusal text names
both uncovered shapes.

## Constraints & unknowns
- Unverified: whether the contract golden `plans.json` `hash` is sha256 of raw bytes. No code computes it and `.sdlc/plans/100.md` is not on disk here.
- Unverified end to end: the Cursor/Codex parity claim rests on the check living in `pr()` (plain Python), as the hard gate's does. No live non-Claude host run is in scope.
- Blocking: none. The issue delegated the hash choice to Research, and Decision A settles it with a measured control.
- Non-blocking, for Plan:
  1. Verdict CLI vocabulary. Accept `SOUND|SOUND-WITH-REFINEMENTS|FIX-FIRST` and map to `pass|warn|block`, or accept `pass|warn|block` directly? Approving = `pass` and `warn`.
  2. SOUND-WITH-REFINEMENTS applied to the plan after review changes the hash, so `pr` refuses. Should the skill say to re-review, or to re-record after applying refinements? Re-recording binds an approval to bytes the reviewer never saw.
  3. `reviewer_route`: a `--resolution <file>` re-checked against `reviewer.resolve()` (house pattern, BR-12), or an internal `resolve()` stored as `{mechanism, host}`. Either way the record is agent-written and cannot prove an independent reviewer ran; it needs the same honesty caveat as `record_subagent_review`'s docstring (`work.py:612-616`).
  4. Keep the control label "Plan review before implementation" (the issue says the row *moves*), but the gate proves "approving record for the plan bytes on the branch at PR push", not "before any edit". Say so in `mechanism`/`condition`.
  5. Refusal must say which file was hashed (branch copy vs main checkout) and give the re-record gesture.
- Review must run `/sigma-contract-check`: new CLI verb, new config key, new persisted state shape (`contract` risk).
- Sizing at 10x/100x: one ≤300-byte JSON per goal, one read plus one sha256 of one plan per `pr()` call (1+N review cycles). Bounded by `finish()` unlink (BR-7).
