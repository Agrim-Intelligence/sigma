# Research: red_green.py can't attribute assertion reds when any failing test has captured output
**Goal**: #956 · **Lane**: medium · **Date**: 2026-10-10

## Goal in one paragraph
`red_green.observe` (the planned-pytest red-before-green proof behind `work.py pr`'s test-first
gate) credits a node as an "assertion red" from two text sources in pytest's terminal report: the
short-summary reason (`FAILED <node> - assert…`) and, failing that, `_split_traceback_assertions`,
which joins traceback report blocks to failed nodes. The split bails out for the whole run as soon as
any `Captured stdout/stderr/log` header appears before the summary. Most real node ids are too long
for the summary reason to survive pytest's 80-column trim, so one logging test drops every red in the
run. The gate can then only be passed with `--no-tests`. The fix must attribute reds per node,
without depending on terminal width (#414) and without letting test-controlled text forge an
assertion red (AC3/AC4).

## Recommended approach
Option (c): attribute the failure kind from JUnit XML. Keep the summary's `FAILED` set as the
membership authority, and credit a node only when it is in that set **and** its unique JUnit testcase
has a direct `<failure>` child whose `message` first line matches `^(AssertionError\b|assert\b)`.
- Add `--junitxml=<tempfile.TemporaryDirectory()>/red_green.xml --junit-prefix=` to the observe argv.
  The XML goes outside the repo, so the worktree content fingerprint is untouched.
- Parse it with stdlib `xml.etree.ElementTree` (`flake_census.py` prior art).
- Map each collected node to `(classname, name)` with pytest's `mangle_test_address` rule:
  split the part before `[` on `::`, turn `/` into `.`, strip `.py`, and re-attach `[params]`.
- Fail closed when a JUnit key is repeated (`record_xml_attribute`) or two planned nodes share one key.
- Fail closed, and say so loudly, when the XML is missing or unparseable (junitxml disabled in
  addopts). The run never fails because of it, and green proof is unaffected.
- Delete `_split_traceback_assertions` and the Captured guard.
- Why not (a) or (b): the end of a captured section cannot be found from text, because a forged header
  inside captured output has the same shape as a real one (scratch excerpt above). (b) alone credits 2
  false nodes and stays width-, CI- and `-s`-dependent.

**Tests the plan should add.** Every node listed in `## Tests` must be red against pre-fix code
(`refusal` needs a red for every planned node), and **must emit no captured stdout/stderr/log in the
outer run**: the installed 1.0.2 gate would otherwise drop every red. Keep each test function name
≤72 chars (1.0.2's header split) and never `print`/`log` in the outer test. Write inner pytest files
as strings under `tmp_path`. The inner run's output is captured by red_green's own subprocess, so the
inner tests may log. Pin `COLUMNS=80` and remove `CI`/`BUILD_NUMBER` with `monkeypatch` so the
pre-fix red is deterministic.
- **Red, listed:**
  - an inner logging assertion red (node id ≥68 chars) is credited, real pytest (AC1);
  - a mixed run of a logging red and a silent red (both credited), plus a passing test that logs (AC2);
  - a RuntimeError block followed by a >72-char-named assertion block: the RuntimeError node is not credited (TD-1);
  - a RuntimeError whose message carries `\nAssertionError:` is not credited (TD-2/AC4);
  - with junitxml blocked (`PYTEST_ADDOPTS=-p no:junitxml`), observe reports that attribution is unavailable instead of crediting.
- **Green on pre-fix code, unlisted controls:**
  - ImportError, fixture/setup error and a non-assertion exception, each with captured output, are not credited (AC3);
  - captured forgery (the existing 344-354 test) (AC4);
  - a duplicate JUnit name is not credited;
  - a long node id at `COLUMNS=80` and at `COLUMNS=1000` is credited (#414, AC5).
- Update the BR-12 fakes to write JUnit so BR-14 keeps testing something.

## Constraints & unknowns
- Unverified: pytest 7.x output and JUnit `message` (only 8.4.1 and 9.0.2 are installed locally;
  installing 7.x needs a download, which was not done). From the pytest source, `append_failure` has
  used `reprcrash.message` across 7–9.
- Unverified: pytest-xdist (`-n` in a target's addopts) with `--junitxml`; xdist is not installed locally.
- Unverified: run-time overhead of `--junitxml`; it was not measured.
- Scale: the XML grows with nodes × failure text (plus captured output only if a repo enables
  `junit_logging`), the same order as the `proc.stdout` already held in memory. Parsing is linear in
  that size, and planned scope is capped at 25 selectors (`red_green.py:25`).
- Blocking: none.
- Non-blocking Q-1: keep `PROVENANCE = 'planned-pytest-v1'`? Recommendation: yes. A bump fails
  `refusal` (`red_green.py:199,222`) for every in-flight goal fleet-wide, whose reds cannot be
  re-observed after green.
- Non-blocking Q-2: drop the summary-reason crediting path (one source of truth for failure kind;
  closes TD-4; costs fake-runner churn) or keep it intersected with JUnit? Recommendation: drop it.
- Non-blocking Q-3: TD-5 (green forgery via skip/xfail reasons) is the same root cause, test text
  read as report text. Moving membership to JUnit too would close it, but it re-expresses the #912
  XFAIL accounting and touches every fake. Recommendation: a separate follow-up goal. The user owns
  this scope call.
- Non-blocking Q-4: link or close #414 from this PR.
- North-star: `absent` (`north_star.py`), so it was skipped. No conditional review (no
  auth/PII/migration/public contract). Review should still run the forgery controls as gate-integrity checks.

## Lane rationale
**medium.**
- **Production code:** 1 module (`red_green.py`). It replaces about 33 lines (`_split_traceback_assertions`), changes the argv, and adds a JUnit reader of about 30–40 lines.
- **Callers:** 0 signature changes (loop.py:5328, work.py:3184 untouched).
