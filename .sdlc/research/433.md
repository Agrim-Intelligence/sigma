## 0. Findings that change the plan (read first)

1. **The issue's "measured fix direction", read literally, is wrong in three ways I measured.**
   a. *Exemption = "matching END follows the run".* Per-line qualification splits a run at any 64-char line lacking
      upper/lower/digit, and real certificate bodies have them (ASCII subject text). Three real CA bundles
      (`/etc/ssl/cert.pem`, certifi, botocore; ~890 KB) give **19 new findings** (10/6/3) because the sub-run is not
      next to the END. Fix that works: exempt the whole `BEGIN <kind w/o PRIVATE>` .. `END <kind>` **span** (0 new).
   b. *Qualify per line* (split at non-mixed lines). One sibling repo (a mail-fixture QA repo, 590 files, MIME `.eml` fixtures,
      two checkouts on this machine): old 4 findings, per-line **30 (+26 each)**, because base64 of ASCII text is full of
      digit-less lines. Fix that works: count a *block* of consecutive base64 lines, tolerate <=1 non-mixed line
      (`B1-tol1`): +0 there. Real key bodies have 0 non-mixed lines (P ~2e-5/line).
   c. *"2 qualifying + 28-39 tail" plus today's adjacent-header exemption* flags PGP `SIGNATURE` / clearsigned blocks
      (4 corpus files); the exemption must change in the same PR, not separately.
2. **Acceptance bullet 1 cannot be met for Ed25519 shape (c) by any line-count rule.** Ed25519 PKCS8 is ONE 64-char
   line (measured). A lone 64-char mixed base64 line is the base64 of 48 random bytes: indistinguishable from a sha384
   digest or token. Only a structural recogniser can: every Ed25519 PKCS8 starts with the public DER constant
   `MC4CAQAwBQYDK2VwBCIEI` (X25519 `...K2VuBCIEI`, Ed448 `MEcCAQAwBQYDK2VxBDsEO`). A hermetic "random base64 of the real
   line lengths" fixture would need that 21-char prefix + 43 random chars. Same for a truncated RSA paste as shape (c).
   Shapes (a) and (b) for Ed25519 / truncated RSA ARE closed by a header anchor (section 4).
3. **Quadratic ReDoS trap.** A natural header regex (`-{4,5} ?BEGIN (.*?) ?-{4,5}`) took **31.5 s** on 0.22 MB and **518 s**
   on 0.9 MB of `-----BEGIN ` x N on one line (<= `MAX_BYTES` 4 MB). Bounding the label (`{0,63}`, no `-`) gives 0.18 s on
   4.2 MB. The shipped gate takes 1.0 s on 3.85 MB of the same input. Control: run that input.
4. **This tree is an empty domain for FP evidence.** No line in 798 tracked files (17.4 MB) is a whole-line base64 run of
   >= 12 chars (641 lines >= 8). "0 -> 0 on this tree" proves nothing about thresholds; the corpus and sibling repos do.
5. `scrub.py`'s `private-key` rule ALREADY catches `BEGIN` + body with **no armor line** and `BEGIN`..`END` (shapes a0/a3,
   measured on all three key sizes). Open today: armor/blank line between header and body without END (a, a2), prose (b), (c).
6. The existing allow marker is not a designed waiver for a header-less multi-line body (section 2): a marker on a body line makes it non-base64 and splits the block, so a short body (3 lines, or 64/64/36) that the split leaves under the thresholds goes green by accident (measured in P5), and a longer one stays flagged.
7. A structural DER recogniser (not in the issue) closes almost every re-wrap/flatten/truncate/prefix evasion with 0 FP
   in 29,413 files, but in token mode it flags **4 fabricated key literals in this repo's own tests** (section 3.3).

## 6. Constraints and risks
- **Runtime:** linear, section 3.4. Adversarial timings (prototype, one file, 3.12): 380k `-----BEGIN ` on one line (4.2 MB) 0.18 s bounded vs
  518 s unbounded at 0.9 MB; one 4 MB base64 line 0.13 s; 100k x 64-char lines 0.31 s; 50k (`BEGIN PUBLIC KEY` + line, no END) 0.36 s; 100k armor lines 0.07 s;
  4 MB `M`+base64 token 0.11 s; 4 MB space/tab line 0.22 s. The span scan stops at the next non-base64 line so it cannot go quadratic.
  Must ship with a test for the BEGIN-flood input.
- **Decoding:** text is UTF-8-sig / UTF-16 (BOM or NUL parity) / Latin-1 (`_decode`, 336-355). Trailing spaces and `\r\n` are tolerated by the old
  and candidate line regexes; lone CR and UTF-32 are not (B06, C26). `scan_text` line numbers count `\n` only.
- **PEM labels** are not `[A-Z0-9 ]` only (`X9.42 DH PARAMETERS`, SSH2 uses `---- BEGIN SSH2 PUBLIC KEY ----` with spaces and 4 dashes, with `Comment:`
  armor that may be quoted). Label match must be case-sensitive-upper like scrub's; lower-case `begin rsa private key` (E10) is already out of scope.
- **Mislabelled body inside a matching public span (E02)** is a documented limit of an exemption-only design; only a DER cross-check removes it, and
  that edits the existing certificate-body test fixture.
- **Hermeticity:** fixtures must be built at run time from a seeded `random.Random` (deterministic CI), stdlib only, no openssl; assert each generated
  line has upper+lower+digit. The gate scans `tests/` and `tools/readiness/exposure_scan.py` scans tracked files too, so no literal key-shaped line may appear in test source.
  Gesture must be `[sys.executable, "tools/leak_scan.py"]` in a `_scratch` repo, as today.
- **Mutation control** fits the existing pattern (patch the scratch copy, re-run, assert the test goes red): e.g. disable the anchor / armor skip in the copy and
  require shape (a) to turn clean.
- **Python:** CI is 3.10-3.13; the prototype uses no 3.11+ feature (checked on 3.10.20 and 3.12). The system `python3` here is 3.9.6 and also ran the gate.

### Open design questions for the plan phase (not settled here)
1. Shape (c) for Ed25519 / truncated RSA: add a DER-prefix recogniser (and put the 21-char public prefix in the fixture) or amend acceptance bullet 1 to claim (c) only where a line-count rule can reach it?
2. DER recogniser scope: constants only (Ed25519/X25519/Ed448/X448/OpenSSH) vs generic first-24-bytes parse; line-start vs any-token (token = +4 in-repo fixtures to fragment/mark, +86 TPs in the largest sibling repo).
3. Exemption: BEGIN..END span (needed) vs literal; PRIVATE-blacklist vs public-kind whitelist (`SECRET KEY`, `TSIG` labels); accept E02 as a documented limit or cross-check DER.
4. Run semantics: block + tolerance (1 abs? 2%?) vs per-line (+26 .eml FPs per repo); keep 40 as the line floor (30 -> 28 costs ID-list FPs) and 28 as the tail floor.
5. Anchor: gap (blank/armor lines), min body width (40 vs 28), whether prose containing the header counts as shape (b) (it must), PuTTY `Private-Lines:` anchor in or out.
6. Finding location and waiver: first body line (as today) vs header line; what is the documented way to waive a header-less body (marker on the preceding line? tolerate trailing comments?).
7. Lone-CR support and `starts` change in `scan_text`; UTF-32 in `_decode` (affects all rules; probably its own issue).
8. How much of the 2-line / short-tail space to claim: the table in section 5 lists real keys that stay undetected under any choice without a recogniser; docstring must say so in the same sentence as the claim.
9. Which evaded shapes become follow-up issues (acceptance bullet 4): hex bodies, base64-wrapped PEM, JSON/shell-escaped bodies (if no token mode), PuTTY, UTF-32 decode, one-word allow reason, the 21 non-key harness evaders (homoglyph paths, percent-encoded owner, etc.).
