# Research: #615 — migrated repos and teammate clones are told to trust their verify command

Inputs: issue #615 (epic #613), validation evidence G10 (executed at cc0f68e), the tree at cc0f68e.

## The defect (executed in the validation, re-run in P5 as AC-4)
`loop.py verify` refuses a repository-configured shell command unless the Git-LOCAL key
`sigma.allowRepositoryShellCommands` is true (`skills/sigma-loop/scripts/shell_policy.py`; deliberate, #422). The key is set only by
`verify_detect.py confirm|set` (`trust_confirmed_repository_shell_commands`). A repo whose COMMITTED `.sdlc/config.json` already
has `verify.command` (every migrated repo; every teammate clone, because git-local config is not cloned) re-runs `/sigma-init`
and gets `[ok] verify: ... (enforce ON)` (`init_flow.py` `verify_step`, the `verify.get("command")` branch), writes no trust,
then `loop.py verify` exits 2. With `enforce` on, `record done` needs a green verify, so every goal stalls.

## Surfaces
- `skills/sigma-init/scripts/init_flow.py` `verify_step` (line ~479): the false `[ok]`.
- `skills/sigma-init/scripts/verify_detect.py` decline message (~line 527): "...or put the command in verify.command and set
  verify.enforce true" is a hand edit that cannot work without the trust step.
- `skills/sigma-doctor/scripts/doctor.py` `check()` near "verify command present (enforce is on)": no row for trust.
- `docs/upgrading.md` line 4-5 "carry on with no migration" is false for verify; no section on per-checkout trust.
- `docs/threat-model.md:72` and `skills/sigma-setup/references/public-repo.md` already name the key (unchanged).

## Constraints found
- `[ask]` lines are parsed by `tools/onboarding_control.py` (`parse_asks`): a line with no ` -> --flag` machine part, or an id
  with no `ASK_POLICY`, is red "unanswerable [ask]". The new line therefore has no ` -> ` machine part; if a control scenario
  ever meets this state it goes loudly red rather than guessing. Control scenarios confirm a command (trust set) or have none,
  so they never reach it (verified by running the control's test file in P5).
- `verify_detect.py confirm` needs a detected candidate id; a committed command (e.g. `echo PROVED`) is not a candidate, so
  `confirm` cannot trust it. A new verb would widen the CLI surface (effects table in onboarding control, write-surface docs).
  The one gesture that works for ANY committed command is the policy's own documented one,
  `git -C <project> config --local sigma.allowRepositoryShellCommands true` (shell_policy.refusal_message, threat-model.md).
  The init line prints that, plus the command to inspect first. DEVIATION from the issue text ("`verify_detect.py confirm`"),
  stated in the PR.
- doctor.py is a standalone diagnostic that avoids cross-skill imports; the trust read is duplicated (a fixed `git config
  --local --type=bool` call) with a parity test against `shell_policy`.
- A repo-controlled command string is printed only through `_vd.printable` (existing helper); never spliced into a runnable gesture.

## Blast radius / scale
Per-checkout, one git subprocess (5s timeout) per init run and per doctor run. No growth, no state, no network.
Failure mode: git missing / not a worktree / read error -> "not trusted" (fail closed, same as shell_policy).
