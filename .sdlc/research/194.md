## Measurement (coverage.py with subprocess support)

Throwaway venv outside the repo: `python3.12 -m venv`, `pip install pytest coverage`: coverage 7.16.2,
pytest 9.1.1. Rcfile (scratch): `source` = the worktree `skills` and `hooks`, `parallel = True`,
`patch = subprocess`, absolute `data_file`. Command: `python -m coverage run -m pytest tests/ -q`, then
`coverage combine` and `coverage report` (PATH puts the venv first so child `python`/`python3` is the venv's).

- Run 1 (aborted by `-x` on one environment artifact: started under `nohup`, so SIGHUP was ignored and
  `test_slack_commands_listen` saw `SIG_IGN`): 80% on a partial run. Not used.
- Run 2 (no `-x`, not under `nohup`): 11,569 passed, 24 skipped, 2 xfailed in 2,489 s. 780 data files
  combined. TOTAL 37,806 statements, 3,436 missed = 90.91% line coverage (`coverage json`:
  34,370 covered lines, 10 excluded).
- Scope is `skills/` and `hooks/` only (what the issue named); `tools/`, `evals/`, `contract/`, `tests/` excluded.

## What the number does not measure (and which way it errs)

- Scripts copied elsewhere by tests (6 test files `copytree`/copy `.py` files into `tmp_path`) run from a
  path outside `source`, so they are not attributed. Understates by an amount not measured.
- Children started with an environment that drops `COVERAGE_PROCESS_START` are not traced. Understates, not measured.
- `evals/run.py` runs as its own CI step, not in this run. Line coverage only; branch coverage not measured.
- The 24 skips and 2 xfails are platform/optional-dependency dependent; the Linux skip set differs from macOS.
  Linux, Python 3.10/3.11/3.13 and the hosted macOS runner were not measured by this run; the CI log of the
  gated leg is the Linux measurement.
- Coverage says lines ran, not that anything was checked (`skills/agrim-loop/scripts/mutation.py` says the same).

## Design consequences

1. The number is high enough that a floor with real headroom is meaningful: floor 85 (measured 90.9, 5 points).
2. CI cost is the real question: this run was 41 min under load for the whole suite, plain pytest on the CI
   ubuntu legs is 24-31 min. The added cost cannot be measured here without a plain run on the same machine
   state, so the PR's own CI leg is the measurement (baseline ubuntu 3.12: 1481 s). One leg only (ubuntu 3.12).
3. A `.coveragerc` with relative `source = skills, hooks` and `data_file = .coverage` measured the same as the
   absolute-path scratch rcfile on a subprocess-using subset (`tests/test_readme_first_run.py`: 17,755 statements,
   14,491 missed under both) and attributed a scratch project's child process correctly when started from another
   working directory (coverage resolves relative config paths against the rcfile). No env-var expansion is needed.
   Children whose test passes a scrubbed environment (e.g. `tests/test_script_help.py`, which builds `env` from
   scratch) lose `COVERAGE_PROCESS_START` and are not traced: that subset measured 0% under both configs.
4. The existing guard `test_control_a_planted_coverage_claim_is_red_and_an_enforcing_ci_clears_it` runs its
   first assertion against the REAL config files; once `fail_under` exists it would go green-to-red. It must
   use an empty config list for that assertion.
5. Coverage tooling is test-only (CI pip install, pinned), never imported by shipped code.
