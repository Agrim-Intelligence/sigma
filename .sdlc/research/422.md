# Research — #422 repository-configured shell commands

## Finding

Three product paths execute strings sourced from repository-controlled `.sdlc`
files with `shell=True`:

| Path | Source | Existing behaviour |
| --- | --- | --- |
| `pipeline._run_check` | `.sdlc/pipeline.json` stage `checks.*[].run` | executes in the repository root |
| `backlog_check._run_embedder` | `.sdlc/config.json` `backlog_check.embed.command` | executes with issue text on stdin |
| `loop.verify_goal` | goal frontmatter / `.sdlc/config.json` verify command | executes in the goal worktree |

An allow flag stored in the repository would not be an operator decision: a
malicious clone can ship both the command and the flag.  Git's local config is
not versioned or cloned, is shared by a project's linked worktrees, and gives
the operator one explicit project-level trust decision.  The proposed gesture
is therefore:

```sh
git -C <trusted-project> config --local sigma.allowRepositoryShellCommands true
```

No config, no Git repository, malformed value, an unavailable Git binary, or
any command error is refusal.  This is intentionally strict: a trusted
operator must make the decision after cloning, rather than a repository making
it for them.

## Scope

Add one small shared policy module that reads only the local Git setting above;
route all three shell-string call sites through it; add hermetic controls that
first prove an untrusted command is not run and then prove the documented
gesture permits it.  Document the gesture and the compatibility trade-off.

## Non-goals

This does not remove shell support for trusted projects, reinterpret commands
as argv, or govern Sigma-owned fixed argv subprocesses.  It also does not
attempt to make a hostile existing `.git/config` trustworthy: the protection
is for an ordinary clone/adopted checkout before the operator opts in.
