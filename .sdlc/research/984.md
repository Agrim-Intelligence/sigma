## Goal in one paragraph
The issue (filed 2026-10-10) says `protection()` in `work.py` reads only classic branch protection, so a repo that enforces through rulesets reads "`main` is not protected — nothing is enforced on merge". It asks for (1) the rulesets for the base to be read and combined with the classic result, and (2) "protection could not be determined" - failing closed like `merge_rights` - when neither source can be read, never "not protected". The acceptance record (`.sdlc/acceptance/984.md`, `drafted: false`) has four criteria: AC-1 ruleset-only requirements are reported; AC-2 both sources report nothing -> "nothing is enforced"; AC-3 neither source readable -> "could not be determined", never "unprotected"; AC-4 PROCESS: the classic-404 + rules-review fixture is seen misreported with the rules read removed, by the documented test gesture. **Finding: half of the issue was fixed after it was filed (the union landed in e4da3cdb, #895 slice 4b-2 / #1110). AC-1, AC-2 and AC-4 are already met and tested. AC-3 is the live gap, and it is also a documented, deliberate behaviour today that the change must reverse (docs/cloud-sessions.md:568, tests/test_work.py:4681-4695, :4769-4771).**

### Measured here (read-only GETs against Agrim-Intelligence/sigma, 2026-10-28)
Three DIFFERENT classic 404 bodies on the same endpoint family, so a bare "404" is not one thing:
- branch exists, no classic protection: `gh: Branch not protected (HTTP 404)` (body `{"message":"Branch not protected",...,"status":"404"}`)
- branch absent on the remote (`sdlc/984`, `zz-no-such-branch-984`): `gh: Branch not found (HTTP 404)`
- repo absent or invisible to the caller's credentials (`gh: Not Found (HTTP 404)`)
And `rules/branches/<b>` answered 200 + a JSON list for a branch name that does not exist at all (the ruleset conditions apply to the pattern, not to an existing ref), i.e. the rules endpoint says nothing about branch existence.
How `work._run` surfaces each: always `RuntimeError("<argv joined>: gh: <message> (HTTP <n>) -- fix: <remedy>")`; NO `.hint`, NO status attribute (`work.py:1689-1736`). `gh_api.classify` on it returns `(404, 'not_found')` for all three, so the three 404s are told apart ONLY by the message text. `gh_api.classify` is safe to call on the exception only through `_pr_api_run` (`work.py:1739-1754`), which sets `.hint` to the text after the argv prefix, so a branch named `timeout-x` cannot decide the kind.
NOT measured (say so, do not assume): the real rules reply for a repo with no rulesets (expected `[]` 200 - this repo's ruleset matches every branch name I could try); the classic read's status/text for a non-admin token, a GitHub App token, a fine-grained token without Administration:read, or a private free-plan repo (`skills/sigma-status/scripts/merge_queue.py:114-117` states a 403 there, from an earlier observation; I did not reproduce it); the cloud-session token path.

- Non-blocking, decision D2 (what counts as "neither source can be read"): classic 404 "Branch not protected" is an ANSWER ("nothing"). The existing test name `test_protection_both_unreadable_is_unchanged_not_protected` calls classic-404 + rules-403 "both unreadable". Recommended default: nothing is enforced is reported ONLY when BOTH sources ANSWERED nothing (classic 404 with the `Branch not protected` message or a readable empty protection object, AND a rules reply that is a JSON list with no counted requirement); any unreadable source with no requirement found -> "could not be determined". A requirement found from either source still reports `enforces` (the other source failing only undercounts: the documented safe direction). This is stricter than the AC's literal text and satisfies AC-1..AC-3 and the issue's intent.
- Non-blocking, decision D3 (how malformed is "unreadable"): a rules reply that is a JSON list is "answered" even when an item is malformed (that item contributes nothing - the existing `_ruleset_requirements` contract); a reply that is not a JSON list (empty, `null`, object, number, text) is unreadable. A recognised rule type (`pull_request`, `required_status_checks`) with unparseable parameters could alternatively be treated as unreadable; recommended default: keep the existing "contributes nothing" contract for in-list items, say so in the docstring.
- In-repo precedent for the empty-body question (decision D3, and the 38+10+2+1 tests above): `work.py:2250-2254` already rules that "an EMPTY or non-object reply counts as a failed read rather than an absent declaration: a real REST reply is always a JSON object ... so an empty body, a `null` or a `[]` is a signal that something went wrong, not an answer" - and cites `protection()`'s own non-object-JSON fix as the origin of that rule. ## Lane rationale
**medium** (sized by measured footprint, no calendar figure): one function and one call site in one module (`work.py:4675-4751`, `:7727-7744`: BR-1..BR-5), no new source of truth, no new boundary - which alone reads as small. Not large: no new structure, nothing contradicts a numbered rule (none exist for this project), and it is not a candidate for splitting. The issue's own estimate ("small build") holds for the code; it understates the tests and docs. Resource/scale: per-call cost is unchanged - the same two REST reads per merge on `protected`/`always`, zero on `off`; no loop, no paging, no new state to prune; at 10x/100x merges the cost is linear in merges at 2 reads each, with the existing `per_page=100` ceiling (docstring `work.py:4713-4715`) unchanged.
