## Findings that shape the design

**F1. This repo has no publish runbook, no files leak gate and no snapshot builder.** `tools/`
contains only `generate_vocabulary.py` and `onboarding_control.py`. The history starts at the
`public snapshot` commit, and `git log --all` over the paths tools/leak_scan.py and docs/superpowers
is empty. The "publish build" (`build_public_snapshot.py`), its files leak scan (`leak_scan.py`
under tools/) and the
runbook (`2026-09-26-sigma-publish-runbook.md`, cited in the body of epic #193) all live in the
private predecessor. This tree mentions them only in comments (BR-8). `.sdlc/research/231.md:55-57`
recorded the same absence. So the runbook the goal names must be created here. The nearest in-repo
patterns are the owner-runbook sections at `docs/board.md:121`, `docs/onboarding-control.md:255` and
`docs/board-fields.md:181`, and the per-tool page `docs/onboarding-control.md`. Issue #221 (the
publish human gate) is where the owner's checklist lives today. The repo is `PRIVATE`
(`gh repo view --json visibility`) and was created 2026-09-26.

**F2. Rewriting a body does not remove the old text from GitHub.** Every edit keeps the prior
revision in the edit history (GraphQL `userContentEdits`, fields `diff`, `deletedAt`, `deletedBy`),
and anyone with read access can view it. GraphQL introspection lists no mutation that deletes a
revision: the edit-related mutations are only `deleteIssue`, `deleteIssueComment`,
`deletePullRequestReview`, `deletePullRequestReviewComment` and `minimizeComment`. Deleting a
revision is a web-UI action only. Measured today: 157 of 299 issues already have edit history
(321 revisions); 24 of those revisions, across 13 issues, carry a foreign `owner/repo#N`; 1 issue
has a clean current body but still carries the reference in its history.

Applying the rewrite to about 60 issues would add at least 60 more revisions that hold the removed
text. So the done-when "a rescan reports zero" is only honest if the scanner reads history too, and
then apply alone cannot reach zero. Clearing history needs a human, per revision, in the web UI.
This is SAFETY: refuse loudly rather than accept a silent half-guarantee. The plan must choose, as a
Block C decision for the owner: scan history and hand the owner a purge list, or declare history out
of scope in the runbook.

**F3. The blocker regex already reads a cross-repo reference as a local blocker.** `_compile`
(`blocker_scan.py:122-127`) builds `(?i)\b(<triggers>)\b[^\n#,;.!?]{0,40}?#(\d+)`, and its character
class admits `/`. Run against the real module:

| Input | Result |
| --- | --- |
| `**Blocked by:** acme-corp/secret-repo#12` | local ref `12` (a phantom edge) |
| `**Blocked by:** acme-corp/secret.repo#12` | no match (the class excludes `.`) |
| `**Blocked by:** https://github.com/acme-corp/secret-repo/issues/12` | no match |

Measured: 2 open issues carry such a phantom edge today. The apply would remove them, which changes
the pick order. State that in the dry-run summary.

There are two scans:
- `_BLOCK_RE` (all 7 `TRIGGERS`, `:115`) runs at check time over the excerpt plus comment text
  (`backlog_check.py:352,380`).
- `_EXPLICIT_BLOCK_RE` (the first 3 triggers, `:119,131`) runs over whole bodies at fetch time,
  through `extract_refs` (`:224`).

Rewrite invariant, checked for every edit with both regexes, loaded by path:
`refs(after) ⊆ refs(before) − {refs whose match spans a foreign slug}`. Replacement text must also
carry nothing GitHub autolinks or notifies: no `#\d`, no `GH-\d`, no `owner/repo#N`, no URL, no
`@name`, and no bare hex SHA of 7 or more characters. A replacement such as "the predecessor's #12"
would plant an explicit edge to an unrelated local issue.

**F4. Ownership (the goal's Pitfalls).** Every issue, PR and comment object carries
`author_association` (OWNER, MEMBER, COLLABORATOR, CONTRIBUTOR, FIRST_TIME_CONTRIBUTOR, FIRST_TIMER,
MANNEQUIN, NONE) and `user.type` (User or Bot). In an org repo the org's owner reads as MEMBER.
Today all 327 issue and PR items and all 241 comments are MEMBER, from 2 accounts, so the rule
changes nothing now but must be built and tested. Proposed rule:

- Rewrite only where `author_association ∈ {OWNER, MEMBER, COLLABORATOR}`.
- Report every other match as `manual`: a human asks the author, or minimizes the comment.
- Never PATCH third-party text. The scan still exits 1 while any match remains.

The association cannot tell text the loop posted apart from text a human typed. Both use the
owner's token, and both count as owned.

**F5. Apply mode, specified only (this goal never runs it).** Endpoints:

| Surface | Endpoint |
| --- | --- |
| issue or PR title and body | `PATCH repos/{o}/{r}/issues/{n}` |
| issue or PR conversation comment | `PATCH repos/{o}/{r}/issues/comments/{id}` |
| review comment | `PATCH repos/{o}/{r}/pulls/comments/{id}` |
| review body | `PUT repos/{o}/{r}/pulls/{n}/reviews/{id}` |
| release | `PATCH repos/{o}/{r}/releases/{id}` |

GitHub REST offers no `If-Match` on writes, so apply uses compare-and-skip. The dry-run records
`(surface, id, updated_at, sha256(before), sha256(after))` for each edit. Apply re-reads the
current text; skips it as already applied when its hash is `after`; skips it as changed since the
dry-run when the hash is neither `before` nor `after`; otherwise PATCHes, then re-reads and checks
the hash now equals `after`.

A re-run is therefore idempotent. The window between the read and the PATCH remains; see R5.
Mutations are paced at 1/s or slower, because GitHub's secondary limit for content writes is about
80/min and 500/h. Retries after a 403 or 429 honour `Retry-After` and are bounded.

**F6. The scanner's own output must not become the leak.** `scrub.py:3-4` sets the house rule:
report the location, never the matched value. Scan mode prints surface, id or URL, offset and the
pattern's line number in the patterns file (for example `pattern#1`), never the matched text.
The before/after text goes only to the dry-run file:
- outside the repo toplevel (refuse an `--out` path inside it),
- written with mode 0600,
- and never printed.

Read the goal's "prints the exact before and after" as "writes to that file". A loop session relays
stdout, and `.sdlc/research/` and `.sdlc/plans/` are tracked (`.gitignore` re-includes them), so
text from a phase can be committed. Other refusals, each exit 2: no `--patterns` and no
`SIGMA_LEAK_PATTERNS` (no default path under `~`); a patterns file inside the repo; a file that
yields zero usable patterns (a vacuous green).

The file's format is the tool's to define. Suggested: one case-insensitive literal per line, `#`
comments allowed, `re:` prefix for a regex. The tool derives the URL and `#N` variants. The owner
confirms that the existing 2-line file matches (R2).

## Risks

- **R1 (blocking, owner decision):** edit history (F2). Apply cannot reach "rescan zero" if the
  scanner reads history, and the scanner is dishonest if it does not.
- **R2:** the patterns file format is unknown to the author by design. A mismatch reads as a false
  green, unless the tool refuses a file with zero patterns and the plan adds a control that plants a
  pattern known to match.
- **R3:** leakage through the tool's output. Keep the scan location-only (F6). Also check any comment
  the goal posts, and its PR text, before posting (the self-scan done-when).
- **R4:** tests reading the real `~` patterns file or reaching the real `gh` (see the guard table).
- **R5:** concurrent writers. `sources.append_to_body` and `unpark._append_block` read and then
  write a body without atomicity. A loop running during apply can revert an edit, or be reverted by
  one. Run apply with the loop stopped, then rescan.
- **R6:** the counts drift while the repo is live (326 to 327 items during this research). The
  dry-run hashes and compare-and-skip (F5) absorb that drift.
- **R7:** BR-8's stale comments cite a leak gate this repo lacks. A reader may assume a files leak
  scan runs here, and none does. Out of scope, but a follow-up should record that the only files
  gates are the three boundary guards and `test_self_contained`.

## Lane

**Medium.** The footprint is all new: 1 tool module, 1 test file, 1 doc page and a CHANGELOG bullet,
0 edits to existing modules. It reuses two contracts read-only: `blocker_scan`'s vocabulary and the
`gh` REST/GraphQL shapes. It does not reach small, because it spans 6 or more GitHub surfaces plus
the tree, needs a new external config input (the patterns file and its env var), and specifies a
bulk live write with idempotency and ownership rules. It stops short of large because no existing
structure changes. Escalate to large, or split, if the owner rules at R1 that edit history is in
scope. The history purge would then need its own goal, or at least an owner-runbook step.
