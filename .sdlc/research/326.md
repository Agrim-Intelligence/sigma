# #326 research -- a partial migrate must not turn the newer unit record into a delta

Follow-through of parked goal #314 (PR #319, branch `sdlc/314`). The whole reviewed #314 change is
merged onto `sdlc/326` (clean `git merge --no-ff origin/sdlc/314` over current main; no conflicts).

## The defect (reproduced)

`migrate.apply()` wrote `Plan.changes` in the order `_candidate_json` walks them: `os.walk` yields
`features/index.json` before descending into `features/units/`. So the index took Sigma's schema id
first. If a unit record was then refused ("it changed after it was read", or a symlink), it stayed
in the previous plugin's schema. The previous plugin writes its unit record first and rebuilds its
index only on demand, so that record can be the complete, NEWER record. Beside a Sigma-schema
index, `feature_registry.read` merges a legacy-id record as a DELTA (`_delta_base`, #314): the
older index entry wins every field, so the record's owner/priority/branch/grants are dropped from
what is served. `feature_sync.py repair` (recommended by `delta_recovery`, "nothing is lost")
rewrites the record from the merged view in Sigma's schema, and a second migrate finds nothing.

Reviewer's repro (`.sdlc/evidence/314/me/{race.py,mk2.sh,pred.py,sig.py,env.sh}`) runs the REAL
predecessor scripts (1.4.24 `6f41743a`, 1.4.25 `9d2f40fd`) from scratch copies: plan, predecessor
`claim` + `set-priority` on alpha, apply.

## Findings that shaped the fix

- A plan-time refusal list is not enough: the previous plugin can CREATE a legacy record after the
  plan (set-priority on an index-only unit copies the whole entry). So the index write re-scans
  `features/units/` at write time for any record still in a KNOWN previous-schema id (an unknown id
  is unreadable either way and must not block the index forever).
- The stand-in predecessor (Sigma's registry with the old schema id) also ran Sigma's #314 delta
  rule, so against an old-schema index it merged its OWN records as deltas -- a fidelity bug in the
  test harness that surfaced only because the new tests use an old-schema index. Neutralised.
- The registry carries no timestamp; file mtime is the only "newer" signal. It cannot detect the
  original race (the index is rewritten after the record), which is why the migrate ordering is
  the fix and repair's mtime refusal is the backstop for the remaining gap (a record written in the
  milliseconds between the last check and the replace, or an index Sigma itself rewrote).
- Measured: the predecessor's own `feature_sync.py fold` (1.4.25) on a converted repository wrote
  `{"features": {}}` in its schema -- an emptied index (`.sdlc/evidence/326-predecessor-fold.txt`).
- Not fixed (pre-existing, non-blocking): `normalise_entry` drops unknown extra entry fields.
