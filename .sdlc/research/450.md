# Research: leak_scan decodes UTF-32 text

**Goal**: #450 · **Lane**: medium · **Date**: 2026-10-03

## Goal in one paragraph

`tools/leak_scan.py::_decode` has UTF-8, UTF-16 (BOM or NUL parity) and Latin-1 branches and no UTF-32 branch. A UTF-32 little-endian file with its byte-order mark begins `FF FE 00 00`; its first two bytes are the UTF-16 LE mark, so it is decoded as UTF-16 LE and every plant in it scans CLEAN. The other three spellings already fail closed as `opaque-binary`.

## Claim verification

| Claim | Verdict | Evidence |
| --- | --- | --- |
| LE+BOM scans CLEAN, BE+BOM and both BOM-less are `opaque-binary` | confirmed, re-measured | `tests/test_utf32.py` run against the pre-fix gate: le-key and le-home report `0 finding(s)`, be-* report `notes.md:0: opaque-binary` |
| Extra silent variants beyond the issue | found | LE+BOM with two stray trailing bytes keeps an even length, so the UTF-16 read succeeds: CLEAN. LE+BOM with a group above U+10FFFF: CLEAN. A file valid as both UTF-32 and UTF-16 (`FF FE 00 00` + UTF-16 LE text) is a UTF-16 file starting with U+0000 |

## Decisions per case

- UTF-32 LE or BE with BOM: decode (`utf-32-le`/`-be` on the bytes after the mark, `errors="replace"` so a truncated tail or a group above U+10FFFF cannot hide the rest).
- A file valid under two readings (UTF-32 BOM then UTF-16 LE text): scan BOTH decodings and union the findings; a reader may honour either.
- BOM-less UTF-32 (either order, any NUL parity): width unknowable; stays a named `opaque-binary` finding, exit 1. Never CLEAN.
- Unchanged: secret values are never printed; exit 2 REFUSED paths untouched.

## Unscannable remaining (to document)

BOM-less UTF-32, UTF-7, EBCDIC, other legacy multibyte codecs (GB18030, Shift-JIS read as Latin-1), and anything encrypted or compressed. The first is named; the rest read as Latin-1 text or opaque-binary.
