# Research: #460 Slack listener and supervisor logs (B6)

Revision: origin/main 12c7b26 (the producing code). Measured with the real functions in a scratch `.sdlc`, not a live deployment.

## Writers (from source)
- `.sdlc/state/slack-commands.log`: `slack_commands_listen._log` (one scrubbed line per call, append, open-per-write, errors swallowed). Called per inbound event/mention, per driven dispatch (stdout tail capped at 4,000 chars), at start/stop/refusal. The heartbeat never logs. The listener is multi-threaded (`threading` is imported), so concurrent `_log` calls are real.
- `.sdlc/state/supervisor.log`: `supervise_daemon._append` and one direct `open(log, "a")` that copies the whole `supervisor.run.out` of every session into it, per iteration. One supervisor process runs at most `SIGMA_SUPERVISE_MAX_RUNS` (default 48) sessions; restarts accumulate into the same file. Not scrubbed today (out of scope here, see follow-up).
- `.sdlc/state/supervisor.run.out`: opened `"wb"` per iteration and handed to the child as stdout/stderr: truncated every run, so it is bounded by ONE session's output, not cumulative.
- `.sdlc/state/supervisor.tail`: `write_text(last 50 lines of run.out)` per iteration: rewritten whole, never appended.
- `.sdlc/state/slack-commands.launchd.log`: NOT written by Sigma. It appears only inside the documented operator-authored plist (`StandardOutPath`/`StandardErrorPath` in `skills/agrim-loop/SLACK_COMMANDS.md`); launchd opens and writes it. `ensure` spawns the listener with DEVNULL streams. Because `_log` also echoes to stderr, a launchd-run listener's stderr duplicates every `_log` line there.
- Precedent in the repo: `watch_daemon.rotate_log` (#2499): one `os.replace` to `.1`, cap derived from free disk (`sync.watch_log_cap_bytes`).

## Measured (command: python script calling `slack_commands_listen._log` and `supervise_daemon.main` with a 41-line fake session, SLEEP_SCALE=0, MAX_RUNS=3)
- slack-commands.log bytes/line: start 83, mention 119, ignored event 90, driven stdout with 200 chars 288, driven stdout at the 5,000-char input 4,089 (cap holds). Lines/hour on a live listener: NOT measured (no live listener in this environment); it is one line per Slack event plus one per dispatch, so growth = event rate x ~100 B (+ up to ~4 KB per dispatch).
- supervisor.log: 12,114 B for 3 iterations = ~4,038 B/iteration with a 3,863 B synthetic session; the non-session part is ~175 B (run marker, verdict, pausing). Real session output size: NOT measured (a real `claude -p` transcript was not run); the copy into the log is unbounded in that size. Cadence floor is the verdict sleep (300-3600 s on the crash/limit ladders, 120 s after a clean relaunch as seen above), so iterations/hour <= 30.
- run.out == tail == 3,863 B in the sample (50-line tail of a 41-line session).
- 10x/100x: linear and unbounded today for slack-commands.log and supervisor.log. Per write cost after the change: one stat.

## Decision
Add a bounded, tested size-capped rotation (new `logroll.py`), used by the two Sigma-written append logs; document run.out/tail as bounded by truncation; document launchd.log as the host service manager's file that Sigma never touches.
- Cap derived from the machine like `sync.watch_log_cap_bytes`: min(1 MiB, max(free/100, 64 KiB)); 3 predecessor generations => at most 4 x cap per log.
- Rotate at write time, before the append; shift oldest-first with `os.replace` (atomic per step); a crash leaves the live file in place and the next write recreates/rotates; a `.rotating` O_EXCL lock with stale takeover (60 s) serialises rotators, and a rotator that cannot take the lock just writes (the line lands in the current file or its predecessor, never nowhere).
- supervisor.log copy of run.out bounded to the cap (tail kept, marker line), since one run could exceed the cap.
