### The `_run` chokepoint and what routing around it loses
`_run` (sources.py:1282-1303) does exactly two things: (1) `feature_labels.creates_a_feature_label(args)` returns
True only for `args[0]=="label" and args[1]=="create"` with a `feature:*` arg (feature_labels.py:363-375), then
no-ops with one stderr line; (2) a bounded transient retry for `project` verbs only. REST argv starts with `"api"`,
so neither fires: no project retry is lost (none of these are `project`), but the feature refusal does not apply to
REST at all. Passing `self._run` as the helpers' `run` keeps recording fakes and the chokepoint seam; it does not
restore the refusal.

The concrete leaks if nothing is added: `POST /issues` with `labels[]=feature:x` and `POST /issues/n/labels` with a
missing label CREATE the label (documented GitHub behaviour; NOT reproduced here, no scratch repo/writes allowed:
UNMEASURED). `gh issue create --label feature:x` / `gh issue edit --add-label feature:x` instead FAIL when the label
is absent (sources.py:1281 states this as the intended loud outcome). Reachable today by: `handoff track --label
feature:voice` -> `create_dependency` (site 14) and a triage plan `add-label feature:x` (site 8; `triage.py:2262`
docstring says its guard "lives in ANOTHER MODULE").

Decision: guard in two layers.
1. Inside gh_api (defence in depth, closes R5 for every future caller): `create_issue` and `add_labels` raise
   `GhApiError(kind="refused")` for any `feature_labels.is_feature_label(name)` unless called with
   `feature_labels_exist=True`. Load via the existing `_load("feature_labels")` idiom (lazy).
2. In `GitHubSource` (the only legitimate caller): new methods `_issue_comment/_issue_edit_body/_issue_add_labels/
   _issue_remove_label/_issue_add_assignees/_issue_create/_issue_close` call `self._require_feature_labels(names)`:
   for each feature-prefixed name one `GET repos/R/labels/<quoted>` (new `gh_api.label_exists`, 404 -> False); any
   False or any failed lookup (fail closed) -> raise `RuntimeError("refusing to create the label ...")` with the
   same stderr wording as `_run`'s. Cost: +1 REST read per feature label, only when one is present.
   Non-feature labels keep REST's mint-on-write (they matched gh only because `create_dependency`/triage
   pre-create them). Stricter alternative (existence check for ALL labels) is one `_existing_label_names()` call
   (sources.py:1700) per write batch; I do not recommend it: label-model section 5 flags only the feature tier.
Callers (dossier/blockers/promote/unpark/assign/triage) stop touching `_run`/`_repo_args` and call the source
methods; their `hasattr` guards become `hasattr(source, "_issue_comment")` etc. (LocalSource has neither).

Two more REST-vs-gh differences that must be handled in the helpers, found by reading call sites:
- `@me`: dossier.py:348 passes `"@me"`; `gh --add-assignee @me` resolves it client-side, REST would send a literal
  login. `add_assignees` strips one leading `@`, resolves `me` through `GET user` (one extra REST read), and
  refuses any value containing `/` (CODEOWNERS teams: handoff.py:905 comment says gh rejects them and the
  "Could not assign" note path depends on the raise).
- REST `POST /assignees` returns 201 and silently ignores a non-assignable login. After the call compare
  `resp["assignees"][].login` (case-insensitive) with the request and raise `GhApiError(kind="invalid")` if absent,
  otherwise `last_assignee_applied=True` becomes a false claim. 
- `remove_label` treats ANY 404 as a no-op (`"404" in str(exc)`, gh_api.py:647), which also swallows "issue not
  found". Tighten to `exc.kind=="not_found"` plus a message check; UNMEASURED which message GitHub returns for each.
- Body `-f body=` is a raw field (no `@file` expansion; `-F` is the magic one), and the helpers already use `-f`.
- `create_issue` returns the dict; REST also returns `html_url`. Keep `_create_issue` signature but make it accept the
  dict form (new `_create_issue_rest`), so `test_create_dependency_still_raises_when_issue_create_itself_fails` keeps its meaning.

## 3. Policy machinery and the WRITE variant
Existing (gh_api.py): `classify(exc)` (:112) -> (status, kind) with kinds `proxy, rate_limit, permission, server,
auth, not_found, invalid, transport, other`; `FALLBACK_KINDS = {rate_limit, server, transport}` (:103); read policy
`_rest_first` (:465) = REST, then ONE gh fallback on a FALLBACK_KIND while `graphql_available(env)`, shared
breaker (`state/gh-rest-breaker.json`, threshold 3, cooldown 300s) and bounded log (`state/gh-fallback.json`,
cap 200, no text/argv/body). Reads fall back on 5xx/transport because a read has no side effect. A write does not
get that for free, so `_rest_first` is reused only for the log/stderr conventions, not its predicate:

`_rest_write(op, number, what, cmd, rest, fallback, *, idempotent, env, sdlc_dir, now)`:
```
try: return rest()
except GhApiError as e:
    if not _write_fallback_ok(e, idempotent) or not graphql_available(env)["available"]: raise
    log(...) ; stderr "fell back to <cmd> once"; return fallback()      # exactly one
```
```
_write_fallback_ok(e, idempotent):
  kind in {auth, not_found, invalid, permission, proxy, other}      -> False   # response arrived or unparseable-after-send
  kind == rate_limit:  True iff text lacks /secondary|abuse/       # primary REST core exhausted; request pre-empted
  kind in {server, transport}:  idempotent                          # request may have committed
```
Taxonomy:
| failure | idempotent write (add_labels, remove_label, close, edit body, add_assignees) | non-idempotent (comment, create) |
|---|---|---|
| 429 / 403 "API rate limit exceeded" (primary) | one fallback | one fallback (provably not executed; UNMEASURED) |
| 403/429 "secondary rate limit"/abuse | RAISE: content-creation limits are per-user across REST and GraphQL, fallback burns the same pool | RAISE, same |
| 5xx | one fallback | RAISE, no retry (may have committed: a fallback would duplicate) |
| timeout / transport after send | one fallback | RAISE, no retry |
| 401, 404, 422, permission 403, proxy block, malformed 2xx body | RAISE | RAISE |
| cloud session / `SIGMA_GH_GRAPHQL=off` | RAISE (no fallback) | RAISE |
Honest ceiling: `classify` decides 403 by TEXT only (no headers via `gh api`), the wording is inferred, and a 5xx can
have committed server-side; hence the default for ambiguity on non-idempotent writes is no fallback and no retry.
Breaker: writes only LOG (op names `comment`, `labels_add`, ...) and neither open nor close the read breaker (an
ambiguous-5xx or secondary-limit stream on writes is not a read outage; coupling them could flip reads to GraphQL
for 300 s on an unrelated cause). Log cap stays 200, now shared with writes: say so in the docstring.

Fallback argvs (all are today's exact argv, so already available, built INSIDE gh_api.py which the ratchet exempts):
- comment: `issue comment <n> [--repo R] --body <text>`; add_labels: `issue edit <n> [--repo R] --add-label a --add-label b`;
  remove_label: `issue edit <n> --remove-label a`; add_assignees: `issue edit <n> --add-assignee a` (gh does resolve `@me`);
  edit body: `issue edit <n> --body <text>`; close: `issue close <n> [--reason completed]` (never repeats `--comment`);
  create: `issue create --title t --body b --label l...` returning the URL, number parsed as `_create_issue` does today.
- Parent combos: close-with-comment = `comment_issue` (non-idempotent policy) then `close_issue` (idempotent policy). If
  the comment lands and close fails, the issue stays open and loop parks, exactly as today with gh's two mutations.
- Any fallback goes through the same injected `run` (= `self._run`), so the label refusal and recording fakes still see it.
