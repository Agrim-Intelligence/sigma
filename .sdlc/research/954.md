# Research: work.py start refuses on a dirty root that its own registry sync just wrote
**Goal**: #954 · **Lane**: medium · **Date**: 2026-10-10

Code read in the goal worktree `.sdlc/work/954` (branch `sdlc/954`, HEAD `5f25b99`, release 1.0.5).
Acceptance: `.sdlc/acceptance/954.md` (AC-1..AC-5). North star: `north_star.py` printed `absent`, so
there was nothing to check.

## Goal in one paragraph
`work.start()` refuses when the ROOT checkout is on `work.base` with tracked, uncommitted edits
(`_dirty_root_refusal`). The same `start()` then runs the registry sync, and it rewrites
`.sdlc/features/units/<unit>.json` and `.sdlc/features/<unit>.md` in the ROOT checkout. Once a human
has committed the registry (docs §14 step 3 says to), those writes are tracked dirt. So the next
`start()` refuses on Sigma's own write, and the refusal text tells the operator to `git stash push -u`.
**Reproduced red with real git (below).** The fix must stop Sigma's own registry writes from tripping
the guard. It must not hide a human's uncommitted edit, must not use stash, and must hold when
several goal slots start at once in one root.

## Seen red: real-git repro (the AC-1 control, run 2026-10-10 against the worktree code)
The test is a bare remote plus a root on `main`. The `.gitignore` lists `.sdlc/state/`, `.sdlc/work/`,
`.sdlc/ledger/` and `.sdlc/events/` (the `RUNTIME_IGNORES` shape). `.sdlc/features/units/` exists,
`feature/voice` was pushed at main's tip, and the config is
`{"work":{"enabled":true,"base":"main"},"discovery":{"source":"github","github":{"repo":"acme/app"}}}`.
The runner sends `git` to `work._run` and answers `gh api …/issues/<n>` with
`{"body":"Feature: voice\nBranch: feature/voice\n","labels":[{"name":"feature:voice"}]}`.
1. `work.start(sdlc, cfg, "100", run=run)` cut a worktree. `git status --porcelain` showed `?? .sdlc/features/` (untracked, so no refusal yet).
2. The human commits it (`git add .sdlc/features && git commit`, per §14 step 3). Then `start(…"101")` cut a worktree. Status showed ` M .sdlc/features/units/voice.json` and ` M .sdlc/features/voice.md`.
3. `start(…"102")` returned `REFUSED — the root checkout at … is on 'main', its own configured base, w…`. **This is the bug.**

The run wrote **0 lines to stderr**, so a test built this way has no captured-output section and
stays clear of #956. No `gh` or network calls were needed beyond the canned issue read.

## Q1 — what the guard checks and why it exists
- Its command, filter, base gate and fail-open behaviour are in the table above. The docstring
  (`work.py:2142-2163`) says root dirt "can only mean an edit landed straight in root instead of a
  worktree (#2014)". The reason given: `commit()`'s `git add -A` runs only in a worktree, so dirt in
  root would otherwise go unseen. Untracked `??` is excluded "NARROW ON PURPOSE". That premise is now
  false, because Sigma itself edits tracked files in root.
- **Introduced by internal #2014.** `git log -S_dirty_root_refusal` finds only `d378333 public
  snapshot` (squashed history), so the issue number comes from the docstring and the tests.
- It is registered in the enforcement table at `work.py:228-231`. `docs/enforcement.md:33` is GENERATED
  from that table by `skills/sigma-doctor/scripts/enforcement_table.py`, and
  `tests/test_enforcement_table.py:92-99` pins the function name.
- **The refusal text tells the operator to stash**: ``git -C {base_root} stash push -u``
  (`work.py:2183-2184`). That is the gesture behind the 17 unpopped stashes. `-u` also sweeps up
  untracked, non-ignored files, which in an adopter can include other slots' plans and research.
  Related: #53, which asks for a stash ban.

## Q2 — what the writes are, where they land, and the safety holes they carry today
- **Shard**: `amend` takes the per-unit flock and runs a read-modify-write of the WHOLE entry
  (`feature_sync.py:340-483`). It writes only when the normalised entry changed (`:438-443`), so a
  re-pick of an already recorded goal is a no-op. The write is ASCII, sorted and indented
  (`feature_registry.py:499-528`).
- **Page**: `feature_doc.sync` splices the managed block and leaves the human region outside it
  byte-identical (`feature_doc.py:14-27`). An edit inside the block is overwritten and ledgered as
  `block-diverged`. `_sync_doc` runs on every pick, but writes nothing when the block is unchanged
  (`feature_sync.py:1034-1038`).
- **Not-adopted**: if there is no `.sdlc/features/` directory, the sync returns at
  `feature_sync.py:979-986` with no writes.
- **The sync does change a human's uncommitted shard edit today. MEASURED (scratch script, worktree
  code):** a shard carried an uncommitted out-of-schema key `notes` and an in-schema edit
  `authorized: true`, then `amend` appended a goal. Result: `notes kept: False | authorized kept:
  True | goals: [1, 2]`.
  So (a) `normalise_entry` **silently drops** out-of-schema fields (`feature_registry.py:398-428`;
  `write_unit`'s own docstring admits it at `:1174-1178`), and (b) in-schema human edits are
  **folded into Sigma's write**. That second point matters for the fix: a check of "content equals
  Sigma's last write" would then **vouch for the human's edit and hide it**.
- `.sdlc/features/rebase-acks/<unit>.json` is also tracked. It is written only by the human-run
  `feature_rebase.py ack` (`feature_rebase.py:480-493`), so it is not Sigma's automatic write.

## Q3 — concurrency
- `work.py` takes **no lock** anywhere on `start()` (`rg -n "flock|_acquire\(|lock_path" work.py`
  returns nothing). The loop's claim lock is per GOAL (`loop.py:411-416`), so two slots for different
  goals run `start()` fully in parallel in one root.
- `amend` holds a per-UNIT `flock` across the read-modify-write (`feature_sync.py:399`, lock at
  `.sdlc/state/features/<unit>.lock`, `:273-288`). It is bounded at 10 s and fails open
  (`:291-324`).
- **`_sync_doc` runs after `amend` has released the lock** (`feature_sync.py:1015` vs `:1038`), so
  `.md` writes for the same unit are not serialised.
- **Today's race:** slot B's sync can write a shard at any moment between slot A's `git status` and
  slot A's next start. A refuses whenever B wrote first, whether or not its own unit changed. That is
  AC-4's failure, and it gets worse with more slots.

**Recommended design (for the Plan to refine):**
1. **Record provenance at the two write chokepoints**: `feature_registry.write_unit` (shards) and
   `feature_doc._atomic_write_bytes` (pages). For each path, keep a gitignored record under
   `.sdlc/state/features/` holding a set of TRUSTED content hashes. On each write, hash the
   pre-image P and the post-image W. If P is already trusted, add W. Otherwise reset the set to
   `{P, W}`.
   Update the record **before** `os.replace`, under a per-path flock. That way a concurrent observer
   sees either old content (already trusted) or new content (trusted). Recording after the replace
   would reopen the AC-4 window.
2. **Check in `_dirty_root_refusal`**: a dirty line is exempt only if all of these hold. It is a
   worktree-only modification (` M`; staged, deleted, renamed and type-changed lines still refuse,
   because Sigma never stages or deletes). Its path is a registry shard or page under this root's
   `.sdlc/features/` (not `index.json`, not `rebase-acks/`). The current bytes' hash is trusted.
   **The HEAD/index version's hash is also trusted.**
   The HEAD condition is what catches the folded-in human edit: if Sigma wrote on top of a human's
   uncommitted edit X, the set was reset to `{X, W}` and HEAD is not in it, so the guard refuses.
   After a human commits, the next Sigma write chains from the committed content and is exempt
   again. Any non-registry dirt still refuses exactly as today.
3. **Cost**: zero new git calls when the porcelain shows no registry dirt, so
   `tests/test_docs.py:788-797`'s pinned **4 and 17** calls are unchanged. One extra git read (HEAD
   or index blob for the dirty registry paths) is made only when registry dirt is present.
4. **Scale**: the trusted set grows by one hash per Sigma write between human commits. Cap it; on
   overflow, drop the oldest post-images and fail closed, which costs a refusal and never a hidden
   edit. State the 10x/100x numbers in the plan.
5. **Rewrite the refusal text** with no stash advice. Name each offending path. For a registry path,
   point at docs §15's maintainer gesture `git add .sdlc/features && git commit` (AC-3; #53).

## Lane rationale
**Medium.** It fits the existing structure: per-unit `flock`, a record under the already-ignored
`.sdlc/state/features/`, and the two existing write chokepoints. It spans 4 code modules
(`work.py`, `feature_registry.py`, `feature_doc.py`, possibly `feature_sync.py`) and a contract between
them (the provenance record that one writes and the other reads). 26 sites are listed: 14 in-scope,
9 verify, 3 out-of-scope. It changes the committed registry layout for no one and adds no new
committed source of truth, and the §6e call counts are preserved. **Escalate to large** if the Plan
moves registry writes into worktrees or a dedicated branch, or automates committing them; the docs
call that undesigned.
