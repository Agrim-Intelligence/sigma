# Research: #459 — review generation, manifest, post and result evidence (B6)

Base: origin/main 757efaf (the revision that produces every store below). Worktree `.sdlc/work/459`.

## Writers and ownership (all under the project `.sdlc/state/`, none under a host configuration root)
- `review-generations/<gen>/brief.md`: `review_context.publish_generation`, one NEW generation per `review_context.py brief --output` call
  (id = hash of goal, artifact, brief digest, time and a random nonce, so a re-review never reuses one). `_atomic_bytes`.
- `review-manifests/<goal>.json`: same function; ONE pointer per goal at the path the caller names (documented gesture: `$goal.json`),
  atomically REPLACED each publish. The generation it used to name is superseded and nothing ever removes it.
- `review-generations/<gen>/resolution.json`: written by the documented shell redirect `reviewer.py resolve .sdlc > "$REVIEW_RESOLUTION"`
  (not by Python; the scan does not see it, it is pruned only as part of its generation directory).
- `review-results/<gen>.json`: `work._write_review_result` (create-once). `review-generations/<gen>/evidence.json`: `work.review_evidence` (create-once).
- `review-posts/<evidence_id>.json`: `work._review_post_request` (create-once; carries `goal`, `pr`, `evidence_id`).
- `review-queue.md`: `state._queue`, local-goals mode only, appended at park/fail: a human work queue.

## Who re-reads what, and for how long (the gate question)
- `merge()` / the review gate read the PR's COMMENTS on GitHub (`sigma:approve|block|unblock` directive), and `merge_observation` reads the
  `review_posted` JOURNAL event. Neither opens any `review-*` file.
- Local readers: `post_review` (scans every `review-manifests/*.json` for the goal's current generation, then reads that generation's
  evidence and `review-results/<gen>.json`; refuses a superseded generation) and `reconcile_review_post` (reads `review-posts/<id>.json` + evidence).
  Both start with `_record(goal)` = `state/work/<goal>.json` carrying the PR number; `work.finish` unlinks that record (work.py:6016). So the files
  are live exactly while the goal's work record exists. After `record done` + `finish`, nothing reads them. A parked or failed goal keeps its
  record/worktree and can resume, so it is NOT terminal here.
