# #363 research — knowledge-graph launch control

The repository already persists failed automatic refresh results in
`.sdlc/state/kg-refresh.json`, has doctor reporting for absent and stale graphs, and tests its
fail-open behavior. The remaining live defect is #132: `graphify --version` succeeds while warning
that its installed skill and package versions differ. Doctor currently treats any nonempty version
output as an installed, healthy builder, hiding the actionable mismatch.

On this machine, `graphify --version` reports a skill at 0.8.14 and a package at 0.8.39, followed
by `graphify 0.8.39`. No supported backend environment variable is configured, so an extraction
cannot be run without introducing an unauthorised model call. The control must therefore exercise
the real CLI's read-only version probe and use a deterministic executable for extraction, query,
and refresh behavior; it must state that limitation rather than inventing a cost measurement.

The implementation can reuse doctor's injectable runner. A successful version command returns its
combined stdout and stderr, allowing a narrow parser to recognize only graphify's documented
`skill is from graphify X, package is Y` mismatch warning. A nonmatching warning remains an
installed builder; a match produces a failing doctor row with `graphify install`.

The public control uses a disposable executable that implements only graphify's `extract` and
`--version` boundary. Its first measured run processed one 22-byte corpus document in 1.382
seconds. That measures Sigma's orchestration path, not a provider extraction: no backend is
selected, so no claim about a live graph build's cost or throughput is made.
