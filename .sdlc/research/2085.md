## Goal in one paragraph
Under the environment verify approval (`SIGMA_TRUSTED_VERIFY_SHA256`, #2066), a goal whose acceptance record carries its own `verify_command` can never run: `acceptance.py record` accepts and posts it, then `loop.py verify` refuses, and the refusal names only the git-local grant. The goal needs (1) an up-front record-time refusal, (2) a supported clear/replace of `verify_command` before any verify evidence exists, (3) a verify refusal that names the goal's own command first, (4) tests with the approval set and unset.

## Findings by question
**AC-1 (record-time check).**
- The predicate can be called from `acceptance.py`. `shell_policy.py` is stdlib-only (4 ms import), has no import of acceptance/state/loop, and `acceptance.py` already loads siblings with `_load(name)` (`:22-26`); a lazy `_load('shell_policy')` inside `record()` keeps `contract/validate.py:232`'s bare import cheap. Owner stays `shell_policy` (trust), `state` owns the list builder (BR-5).
- Input: `path` = project root `Path(sdlc_dir).resolve().parent` (what `loop.py` already passes as `roots`); `commands` = the state-built list from `config["verify"]["command"]` and the resolved `verify_command`. The root differs from verify's goal worktree only in the `repository-sourced` tracked-file scan; verify-time stays authoritative, so record-time can wrongly accept but never wrongly refuse a command verify would run.
- Behaviour matrix at record time: git-local granted → accept. Variable unset (no trust at all) → accept (today's behaviour, zero cost, no git spawn). Variable set and the approval covers the repository command alone but not the combined list → REFUSE before writing or posting. Variable set but malformed, empty, vetoed, no-identity, location-variable, repository-sourced, or approving something other than the repository command → accept (trust does not come from the approval; verify will explain). Variable approves the goal command with no `verify.command` → covered, accept.
- The same check must guard the replace path of the new verb.

**AC-2 (clear/replace).**
- Predicate: `state.evidence_path(sdlc_dir, goal).exists()` (BR-6). Conservative on purpose (also true for a failed verify, whose digest-bound evidence a rewrite would void: `state.py:1764-1770`).
- Home: `acceptance.py set-verify-command <sdlc> <goal> (--verify-command CMD | --clear)`. It owns the file format, the atomic write and the 32 KiB cap, runs on any host, and adds no script file. The alternative, a `loop.py` verb (`USAGE` at `loop.py:7460`, `waive-phases` at `:8154` is the shape), would make the acceptance writer's invariants live in loop.py.
- Mechanics: read and `parse()` the record (`FileNotFoundError` → refuse, "run record"); refuse if evidence exists; replace ONLY the header line `verify_command: <json>` (insert if absent), keeping criteria, `drafted` and footer bytes identical; re-`parse()`; temp file + `os.replace`. Idempotent: clearing an already-null field is a no-op, exit 0, no write.
- Action log: a new INTERNAL kind, fields `action` (clear|replace), `result` (changed|refused-evidence), and sha256 prefixes of old and new commands, never the command text (secrets must not enter logs; the text is also repository input). Written on the change and on the evidence refusal. Only effective when `action_log.enabled` (`/sigma-init` ships it true).
- Issue copy: not needed. Verify reads `.sdlc/acceptance/<stem>.md` from the main checkout (`state.py:1637`). The github comment is posted only for drafted criteria and nothing reads it back (`legacy.py:73` only registers the marker). It will show the old command; the action log is the record of the change.
- Local `.md` goals: `state.py:1641` is `acceptance["verify_command"] or cmd`, so clearing the record leaves a goal-file frontmatter `verify_command` running. A `--clear` for such a goal would be a half-guarantee.

**AC-3 (attribution and text).** "The goal's own command caused the mismatch" ≡ the reason would be `mismatch`, the goal added at least one command not in the repository list, and the env value equals the hash of every repository command. That is pure hashing on the `mismatch` branch (`environment_approval` returns the identity in `detail`, `:276`), so no second git pass. Put the text in `shell_policy.verify_refusal_message` (BR-1) so verify and red share it; `loop.py` supplies the concrete clear gesture because only it knows goal, sdlc dir and interpreter. Message shape: reason (approval covers only the repository's `verify.command`; the goal adds its own; keep the existing clause `does not approve every command about to run in <id>`), then remedy 1 (clear or replace the goal's command, allowed only before the first verify), then remedy 2 (git-local grant, operator only, never an unattended run). The unset text must not change (BR-11).

**Sealed-acceptance / hash checks (#2069).** Nothing seals the acceptance bytes except verify evidence's `acceptance_sha256` (`loop.py:6806`, compared in `state.py:1764-1770`) and the ledger event (BR-24). So a clear/replace before evidence cannot be refused by a hash gate, and after evidence the evidence predicate refuses first. The sealed-test gate (`work.py:4078`) is separate and untouched.
