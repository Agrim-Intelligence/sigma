## 4. Decisions for the plan (all recommendations are DEFAULTS, not rulings)

### (a) The 3-word reason rule and `N/A: small lane`
Count: the reason in `N/A: small lane` is `small lane`, which is 2 words, so the plain "reason of fewer
than 3 words" rule would reject the one literal the design wants accepted in the small lane.
Default: order the clauses so the exact literal is tested first. If `_norm(reason).lower() == "small lane"`:
accepted in `small`; a violation in `medium` and `large` (distinct message naming the category and the
lane, so clause vii goes red on its own). Otherwise apply the word-count rule (reason must have at least 3
whitespace-separated words) and the blocklist. Test it three ways: small accepts it, medium rejects it,
and `N/A: big lane` (2 words, not the literal) is rejected everywhere.
Parse `Answer` as: `scenario` | `N/A: <reason>` | `open: D-n` (case-sensitive on `scenario`, accept
`N/A` with exactly `N/A:` prefix; a bare `N/A` or `N/A:` with empty reason is "N/A without a reason").

### (b) Large-lane security row and STRIDE
Default rule: in `large`, the `security` row may NOT be `N/A` (violation naming `security`), and the
STRIDE table is required (D-7's "silence is not allowed"). The row itself may be `scenario` or
`open: D-n`. Do not require the row's Evidence to cite the STRIDE table (that would be unverifiable
free text); the checker clause is "large + security N/A is a violation" plus "large + no STRIDE table is
a violation". Medium and small keep `N/A` legal for security.

STRIDE table shape contradiction in the design to resolve in the plan: D-7 says each container's six
threats; D-13 says "six rows per declared container"; control (xii) says "a container with five
threats". Default: LONG FORM, columns `Container | Threat | Mitigation`, one row per (container,
threat) where Threat is one of S, T, R, I, D, E. Then "five threats" is a missing row, the D-13 row
count holds, and the escape row is a single row with Container `—`. Header starts with `Container`
(D-6). Mitigation must be non-empty and either text or `ruled out: <reason>` (apply the same 3-word and
blocklist rule to the reason). Container name must equal a first-column cell of `## Components`
exactly (violation xiii). Duplicate (container, threat) is a violation. The `—` row must carry a
reason of at least 3 words. Count distinct containers for the warning.

### (c) Blocklisted reason tokens
Default: after `_norm` and lowercasing and stripping trailing punctuation, a reason that equals one of
`n/a`, `na`, `none`, `nil`, `tbd`, `todo`, `-`, `—`, `–`, `...`, `?`, `unknown`, `not applicable`,
`no`, `later` is a violation even before the word count (most are 1 word anyway, so the blocklist is
chiefly for the clear message and to catch multi-word fillers: `not applicable`, `to be determined`,
`not applicable here`). Each blocklisted token gets its own red control (the issue demands this).
The words test rejects less than 3 words; blocklist only changes the message for 3+ word fillers, so
include at least `not applicable`, `to be determined`, `n/a n/a n/a` style repetition is out of scope.
Keep the list small and declared as one module constant.

### (d) Evidence, measure, warn and exit contract
- `Response measure` (scenario rows only): passes if it contains an ASCII digit, OR matches
  `^test:\s*\S` followed by at least one more token (a named test, command or observable check). A bare
  `test:` or `test:  ` fails. This is form, not truth (state in the docstring, once).
- `Evidence` (scenario rows): non-empty; split on commas and whitespace-separated list; every token must
  be one of: `BR-n` (exists in the parsed `## Blast radius` ids), `D-n` (exists in `## Doubts`),
  `Dossier:<id>` (id charset `[A-Za-z0-9_-]+`, not verified), `file:line` (regex
  `^[\w./-]+:\d+(-\d+)?$`, existence of the file NOT checked, no filesystem access), or the literal
  `agent-proposed`. Anything else is a violation naming the category and the token. `—` is a violation
  on a scenario row.
  Where to find `BR-n` and `D-n` ids: scan the `## Blast radius` and `## Doubts` sections for
  `BR-\d+` / `D-\d+` as the first token of table first cells or `**D-n.**` bullet markers. Use the same
  anchored patterns the design skeleton uses, and add a control where an id appears only in prose (not as a
  row id) so a looser regex is seen red.
- Small lane extra rule: an answered (`scenario`) row's evidence must contain at least one `BR-n`
  (control x). Warn (stderr, not a violation) when `Lane` is `small` and the slice table has more than one
  data row (D-1). The slice table is found by the existing `_parse_table`; reuse it read-only.
- Warn when the number of distinct STRIDE containers exceeds 20 (`CONTAINER_WARN = 20`); the 20th does
  not warn, the 21st does (boundary control).
- 1 MiB: `_read_artifact` already refuses; add a quality-verb test at cap (ok to read) and cap+1
  (exit 2, nothing on stdout, message names the cap).
- Missing or unrecognised `Lane` header: violation (`Lane: missing or not one of small, medium, large`)
  and proceed as `discovery.DEFAULT_LANE` (medium), never weaker. A `--lane` flag, if given, overrides
  the header for the rules but a header mismatch is not itself reported (the flag is the test hook and
  the documented override); an invalid `--lane` value is a usage error, exit 2, nothing on stdout.
- Each violation line begins with the category slug then `: `, so every line names the category (AC-5
  needs `observability` in the missing-row line).
- Exit codes: 0 clean (warnings allowed), 2 on any violation, refusal or usage error. Stdout: the JSON
  result `{"ok","lane","rows","violations","warnings"}` printed with `indent=2` only when the artifact
  was read; nothing on stdout on refusal/usage. Stderr: `goal_design.py quality: warning: ...` and
  `goal_design.py quality: VIOLATION: ...` exactly mirroring the `requirements` verb's prefixes.
- `nfr-bank`: no arguments; prints one JSON object with `indent=2`: `version`, `categories`
  (id, label, origin, ask), `scenario_fields`, `stride`, `answer_forms` per design D-9; exit 0; the
  category order is a literal tuple, accessed by `quality` so there is one copy. Return copies from a
  function so a caller mutating the result cannot alter the data (the design's "returned as copies"; the
  control is mutate-the-result-then-call-again).
  Version string from D-9: `iso-iec-25010-2023+sigma-ext/1` (flag D-12: not checkable in the repo).
- Table parse rules for the main table (decisions the design leaves open): header must be the exact
  eight names in D-6 order, case-insensitive match after `_norm`; a wrong header is a single
  violation and stops row checks (otherwise column mismatch gives noise). Rows with a cell count not equal
  to eight are a violation per row. Any cell over `SENTENCE_CAP` (2000) is a violation (reuse the
  constant) checked before any regex. The five scenario cells on `N/A` and `open` rows must all be `—`
  (violation otherwise: design D-6 says they are `—`).
  Row key (first cell) is the slug; unknown slug, duplicate slug, missing slug are three separate
  clauses. Row order is NOT enforced (D-6) so no weakened-to-membership control is needed for the
  main table; the order pin lives on the bank data only.
- Missing `## Quality requirements` section altogether: one violation, plus (so every category is named)
  a "missing row" line per category, so AC-5 style output stays uniform.
- Table not found under the section: violation.

## 6. Sizing and scale

Lane: medium. Files: 1 edited source, 1 new test file (plus verify-only scans). Estimate: source +250 to
+330 lines (data tuple ~40, parser ~60, checks ~120, mains ~50, usage/docstring ~30), tests +450 to +600
lines (about 55-70 tests incl. parametrised blocklist and evidence forms). Complexity low, risk
concentrated in the table cell-count and header-order handling.

10x / 100x: cost is linear in rows (11 fixed plus 6 per declared container in large). No lock, writer,
daemon or shared state; each machine reads its own file. The ceilings are: the 1 MiB read cap (refuses
loudly), the 2000-char cell cap, and the 20-container warning (about 120 STRIDE rows). Parse time is
NOT measured for this goal. Measurement plan for the implementer: build synthetic artifacts with
11 + 100 and 11 + 1000 STRIDE container rows (and a 1 MiB boundary file), time `check_quality` in-process
(best of 5, `time.perf_counter`) and the subprocess wall time including interpreter start, record the
numbers in the module comment next to the caps the way the 659 block does, and state the machine and
Python version. Until then write "unmeasured" in the same sentence as any performance claim. The
sibling's figures (0.9 ms at 100 rows, 4.6 ms at 1000) are the prior for the same parser shape but are
not evidence for this verb.

## 7. Traps

- Heading and id schema: do not mint any `XX-n` id family in slice 1 test fixtures that live in shipped
  docs; the pinned id regex in the plan compiler accepts only `BR`, `PC`, `D`, `B`, `X`, `S`, plus `FR`
  from the sibling. Rows are keyed by bank slugs (design D-8), never `Q-n`. In tests it is fine to use
  `BR-n`/`D-n` ids in fixtures (they are the existing families).
- Do not hand-type any `#<digits>` in test fixtures or docstrings that end up in text pasted into
  ticket bodies; a hash-number near words like needs/after/requires/depends on mints a blocker edge.
  (Source comments citing issue numbers for provenance, the module's habit, are fine in code, not in
  slice rows or compiled bodies.)
- `tests/test_no_private_sdlc_citations.py`: no concrete design/plans/research file path in
  `goal_design.py`'s docstring or comments. Cite behaviour, not the private artifact.
- Shipped docs and prose (slices 2 and 3, and any research file that lands on a branch) must not contain
  a bare skill-dir variable followed by `scripts/...` nor test-path tokens that
  `tests/test_skill_structure.py::test_every_path_a_shipped_doc_names_ships` cannot resolve. This
  dossier names only existing files, with no such token form.
- `tests/test_script_help.py` runs `goal_design.py --help` and `-h` as a subprocess: the new verbs must
