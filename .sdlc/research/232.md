# #232 research — what "done" means when the PR has not merged

**Owner decision (recorded on the issue, 2026-09-29):** done only after merge. `record done` and the
issue close require the PR merged; an unmerged PR leaves the goal in review/QC.

## The defect, traced on shipped defaults

Template: `work.enabled: true`, `work.auto_merge: "off"`, `work.require_review: "changes"`.

1. `work.py merge` (`merge()`): verify evidence → `gate()` → `if chosen == OFF: return "... auto_merge
   is off, leaving PR #N for a human"`. This return sits BEFORE `effective_review_mode` /
   `review_gate`, so on defaults the review gate never runs: a `sigma:block` on the PR is invisible.
2. SKILL.md step 6 and `references/landing.md` route `leaving PR #N for a human`, `PR #N opened`,
   `auto-merge armed`, `merging it is yours to make` → `record done`.
3. `loop.py record ... done` → `work.done_refusal()`: `policy == OFF` → `None` (allowed), also None for
   fork/insufficient rights/armed/unreadable/protected-unguarded (non-unit base).
4. `_record(..., "done")` → `GitHubSource.complete()` → `gh issue close` + strips `sdlc:goal` /
   `sdlc:in-progress`, board → Done. Issue closed, PR still OPEN.
5. `_release_checkout` → `finish()` refuses (`_open_pr_refusal`, "loop: kept ...") so the worktree
   survives, but nothing ever revisits the goal: no code path observes the later merge.

`tests/test_public_bootstrap_control.py::test_a_goal_goes_from_filed_to_merged_on_the_public_profile`
pins the defect as expected behaviour: `issue1_state_before_merge == "closed"` with
`pr_state_before_merge == "OPEN"`. That is the RED control for this goal.

## Existing vocabulary to reuse (label model)

- `sdlc:in-progress` overlay stays on while the PR awaits merge — `_fetch_pending` excludes any issue
  carrying it, so the goal is never re-picked. `sdlc:goal` membership stays (the goal is not done).
- Board: `mark_qc()` → the existing QC column ("Review / QC quality stage"). No new label, no new
  board column.
- Ledger: no new kind (adding one touches `ledger.KINDS`, `SHARED_KINDS`, `contract/vocabulary.json`).
  The #1394 `mark_blocked` precedent records ledger `parked` for "left the active queue pending
  something" and lets labels carry the distinction; that ends the lease so
  `_auto_reclaim_stale_claims` (ledger on) cannot release the goal back to Ready while it waits.
  The later merge writes `done` (and `merged` via `_record_confirmed_merge`).

## Merge observation

`work._record_confirmed_merge` / `_observe_confirmed_merge` (receipt adapter over
`merge_observation.py`) are replayed by `done_refusal` on a MERGED read — already idempotent via
per-merge delivery receipts with stable keys. The reconcile pass reuses that path by calling
`done_refusal` and, on None, `_record(..., "done")`.

REST, not GraphQL: `gh api repos/{owner}/{repo}/pulls/<n>` returns `state` (open/closed), `merged`,
`merged_at`. GraphQL has a separate, previously-exhausted budget (#1209); the sweep must not draw on it.

## Cost at scale (per pass)

State lives in `.sdlc/state/work/<goal>.json` (one file per started goal). A pass lists that
directory (O(records), local) and makes at most `MERGE_RECONCILE_MAX_PER_PASS` = 10 REST GETs,
oldest-checked first, skipping records checked within the last 120 s. At 10x (≈50 awaiting PRs) a
pass is ≤10 REST calls and every PR is re-read within 5 passes; at 100x (≈500) still ≤10 calls per
pass (≈600/h at one pass per minute, 12% of the 5,000/h REST budget), and a merged PR's close
latency grows to ≤50 passes — a latency ceiling, stated, not a data loss. Each close then costs the
existing `complete()` writes (issue close + label swap + board move) once. Measured numbers are in
the plan's verification section.
