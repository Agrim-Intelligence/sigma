## Findings

1. **Pin is honoured, but only within the first 100 boards.** `_find_project` matches a pinned
   number only inside the single `--limit 100` page. An owner with >100 boards whose pinned board is
   outside that page gets "mirroring OFF". Fix (the "a pinned number is honoured" exception the goal
   allows): when a pinned number is not in the page, read that one board with
   `gh project view N --owner O --format json` (one read, only then).
2. **Title fallback makes the pin redundant while the title is untouched.** The loop also matches
   `<repo> — SDLC` by title, so "unset the number → warning fires" does NOT hold for a board still
   carrying the default title (verified against the fake in the acceptance transcript). The pin is
   load-bearing once the board is renamed (humans do) or when `--title` is custom, or past 100
   boards. The CONTROL is therefore run on the renamed board, and the title-intact case is recorded
   as its own transcript rather than claimed.
3. **Latent case bug on fresh boards.** GitHub's default Status options are `Todo / In progress /
   Done` (#1492 comment: lowercase p). `_options_mutation` keeps the existing spelling on a
   case-only match, so a loop-created board ends with `In progress` while `_set_board_status`
   looks up `In Progress` exactly — the In-Progress move silently no-ops. board_setup avoids it by
   passing `rename={"Todo": Backlog, "In progress": In Progress}` (rule 2, id-preserving, so
   workflows survive). The loop's own path is NOT changed here (out of scope; flagged in the report).
4. **REST covers every read** (core quota, not the shared GraphQL 5000/h), measured live read-only:
   `GET orgs/{o}/projectsV2?per_page=100` (Link-header cursor pagination, `--paginate`),
   `GET orgs/{o}/projectsV2/{n}`, `GET orgs/{o}/projectsV2/{n}/fields` (field `node_id`, option
   `id` + `name.raw`), `users/{u}/projectsV2...` for user owners, `users/{o}` (`type`, `node_id`),
   `repos/{o}/{r}` (`node_id`). Evidence: `evidence/235/rest-projectsv2-probe.txt`,
   `rest-fields-probe-board17.json`. Only mutations and the workflow read need GraphQL.

## Empirical verification (schema introspection, READ-ONLY — no mutation was run)

Evidence files: `.sdlc/evidence/235/introspection-{1..5}-*.json` (GitHub caps `__Type.fields` at 2
uses per query, hence five queries; GraphQL remaining 4992 → ~4990 after).

| Question | Schema says | Verdict |
|---|---|---|
| Can a view be created via API? | `Mutation.createProjectV2View(projectId, name, layout, configuration)` and `updateProjectV2View`, `deleteProjectV2View` exist | YES (schema). The older "views have no public create mutation" claim is outdated. |
| Can a workflow be created/enabled via API? | Only `deleteProjectV2Workflow`; `ProjectV2Workflow` exposes `enabled` as a read field; `ProjectV2.workflows` is a read connection; no create/update/enable mutation | NO. Manual step required when a workflow is off. |

GitHub's UI docs say a copy carries views, custom fields and workflows except auto-add; whether the API mutation does the same needs one mutation. |
| `createProjectV2` links a repo? | `CreateProjectV2Input.repositoryId` "The repository to link the project to." | YES in one call. |
| Option ids preserved on rewrite? | `ProjectV2SingleSelectFieldOptionInput.id`: "Include this to preserve the option's identity during updates" | YES (matches #720's measurement). |

**Could NOT be verified without a mutation** (so the code handles both outcomes):
- whether `copyProjectV2` copies views and workflows (template path re-ensures Status/Priority
  field-by-field afterwards regardless, and reads the workflow states and reports them);
- whether a fresh API-created board has "Item closed" enabled (#720 measured all six workflows
  enabled on a fresh board; board_setup READS `workflows { name enabled }` after setup and, if
  "Item closed" is off or unreadable, prints the manual step with the deep link
  `https://github.com/{orgs|users}/<owner>/projects/<n>/workflows`).

### Owner's 5-line manual verification runbook (also in skills/agrim-init/references/board.md)

1. `gh auth refresh -s project` then create a throwaway board by hand in the UI with one extra view and "Item closed" ON; note its number T.
2. In a throwaway repository whose `.sdlc` pins no board: `python3 <sigma>/skills/agrim-init/scripts/board_setup.py create .sdlc --owner <you> --title "copy-probe" --template T --yes`
3. Open `https://github.com/users/<you>/projects/<new>/views/1` and `.../workflows`: note which views and which workflows (enabled?) came across.
4. Record the answer on #235 (views copied? workflows copied? enabled state kept?).
5. Delete both throwaway boards (Settings → Delete project) and unset the pin board_setup wrote.

## Cost / scale

Per `create` (fresh, field-by-field), MEASURED against the fake (test_cost_per_create_and_per_rerun):
`gh auth status` 1; REST reads — `users/{o}` 1, `repos/{o}/{r}` 1, boards list ceil(B/100) pages
(one `gh --paginate` call), `fields` 2 (before/after), board 1; GraphQL — `createProjectV2` 1,
`updateProjectV2Field` 1, `createProjectV2Field` 1, workflow/link read 1 = **4 GraphQL +
5+ceil(B/100) REST + 1 auth**. Re-run on a
complete board: 0 mutations, 1 GraphQL read. Steady state (the loop): **zero** new calls — init
prints an offer and makes no call; the only loop change is one `gh project view` read, only when a
pinned number is absent from the first page of 100 boards. At 10x/100x boards the list costs
ceil(B/100) REST pages inside one `gh --paginate` call (B=10 000 → 100 pages), bounded by the
per-call timeout (`SIGMA_WATCH_CALL_TIMEOUT`, default 120 s); a list that fails or times out is
REFUSED (a duplicate cannot be ruled out), never guessed.
