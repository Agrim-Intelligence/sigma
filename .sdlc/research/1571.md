## 1. How `flake_check.py` works (166 lines, `skills/sigma-loop/scripts/flake_check.py`)

- **Picking tests.** `check(root, test_files, runs=3, run=None, seed=None, node_ids=None)` (:105). When
  `node_ids` is given it is used as is (:136). Otherwise `_collect` (:71-92) runs
  `python3 -m pytest --collect-only -q <file>` once per file and rebuilds `path::rest` ids, which
  guards against rootdir drift. `MAX_SCOPED_FILES = 25` (:48) bounds the FILE count only and returns
  `absent` with a loud stderr line (:128-135). **The node-id count has no bound** (1052 went through).
- **Ordering.** No plugin is used. `random.Random(seed)` with `rng.shuffle(order)` for each run (:140-144).
  The ordering relies on pytest honouring argv order, which the module docstring says was verified
  (:14-17). There is no reversal. Every run gets a fresh `tempfile.mkdtemp(prefix="sigma-flake-%d-")`
  passed as `--basetemp` (:145-148).
- **Invocation.** `subprocess.run(["python3", "-m", "pytest", "-q", "--basetemp=…", *order])` (:149, :66-68).
  The calls are sequential, with no `-n`, no `-p no:xdist`, no `-p no:cacheprovider`, no timeout, and
  no `COLUMNS` override (red_green sets `COLUMNS=4000` because of #414, `red_green.py:66-70`).
  `_failed_ids` reads `FAILED <id>` lines (:95-102).
- **Verdict.** `_measured` (:51-59) treats exit codes 2/3/4/5 and any negative code as nothing measured.
  If any run is unmeasured the verdict is `absent` (:159-161). If every run gives the same
  `(code==0, failed-tuple)` the verdict is `verified`, so consistent failure also counts as verified
  (:162-163). Otherwise it is `unverified`, with `disagreement` listing the union of failed ids (:164-166).
  Each per-run record is `{"exit", "failed"}`. There is no per-run ms and no order or seed record.
- **Records.** The module itself writes nothing durable; its only write is the mkdtemp dirs. loop.py
  stores the dict under the `flake` key of the goal's verify evidence JSON (`loop.py:5829`) and the
  `ms` as a `timing_store` record, `kind=verify name=flake` (`loop.py:5859-5868`). Exit 5 on
  `unverified` (`loop.py:5870-5875`). Witness is a separate pass (`_witness_verdict`, `loop.py:5389+`).
- **Stated ceiling** (docstring :25-27): three runs catch a ~50% flake with p=0.75. A 5% flake usually
  passes. The check "raises the cost of shipping a flake; it does not eliminate it."
- **Callers.** `loop.py:54` binds the module. `_flake_verdict` (`loop.py:5313-5348`) is called once from
  `_verify_goal_body` (`loop.py:5800`), after the proving command and red_green's observation and
  before `_diff_revert_verdict` and `_witness_verdict`. `_changed_tests` (`loop.py:5361-5386`) and
  `loop.py:5473` reuse `flake_check._collect` and `_run`; `loop.py:5404` reuses `_failed_ids`. Those
  private seams must keep their signatures.

## 3. Interpreters, xdist and `-n`

- The proving command (the main checkout's config, `verify.command`) is
  `$HOME/.sigma-venv312/bin/python -m pytest tests -q -n 4 -p no:cacheprovider`.
  That venv is Python 3.12.13 with pytest 9.1.1 and **pytest-xdist 3.8.0**. No random-order or
  rerun plugin is installed.
- **The flake runs and red_green do not use that interpreter.** They call bare `python3`, which on PATH
  here resolves to the system Python 3.9.6:, pytest 8.4.2, **no xdist**. The flake docstring's
  "pytest 8.4.2" matches that interpreter. So "xdist when available" has to be probed **for the
  interpreter the flake runs actually use**, not assumed from the verify command. Changing the
  interpreter (for example to the proving command's own, or `sys.executable`) is a behaviour change the
  plan has to decide explicitly. Flag it to Plan-Review.
- `-n` appears only in the configured verify command. No Python under `skills/` passes `-n` or
  `-p xdist` (grep). Done-when requires the use to be explicit: pass `-p no:xdist` when not
  parallelising inside a run, and `-p xdist -n K` when you are.

## 4. Tests that cover the flake check, and seams

- `tests/test_flake_check.py` (202 lines, 14 tests, all fake-runner). The controls: stable gives
  verified (:31), coin-flip gives unverified (:40), **order dependence caught by the shuffle** (:49,
  runs=8, seed=1, asserting more than one distinct order was seen), a distinct basetemp per run (:72),
  absent cases (:87, :93, :132, :143, :160), consistent red counts as verified (:100), rootdir rebuild
  (:112), the over-widening control (:168), and the scope bound (:180, :197).
- **Concurrency breaks the fakes.** `_fake` (:18-29) hands out `results[i]` by *call order* through a
  shared counter, and the other fakes append to shared lists. Under a thread or process pool, call order
  is not run order. The fakes need thread safety, or (better) results have to be keyed by run index:
  the runner receives a run index or the basetemp, and the check assembles `results[i]` by index,
  never by completion order.
- In `tests/test_loop.py`: :7322-7362 (timing records for flake ms and absent ms 0), :8700-8775 (key
  placement, no changed files, red verify skips flake), :8797-8916 (`_failed_ids` reuse).
  `tests/test_test_first_gate.py:387-391` covers planned node ids reaching flake.
- Seams for deterministic in-process controls (AGENTS.md: a port across a performance boundary disarms
  probabilistic controls):
  1. **Disagreement judge.** Factor out a pure `_judge(results)` and test it directly. Break each clause
     on its own: `any` to `all` on the unmeasured check, set equality to "first equals last", and a
     dropped failed-tuple. Done-when 4's "control seen red" lives here: one red run in three gives
     `unverified`, and the test must go red when `len(set(observations)) == 1` is weakened.
  2. **Scope selection.** `_flake_verdict` labels the three paths (nodes, files, diff).
  3. **Parallel runner.** It must keep a distinct order and a distinct basetemp per run, and its result
     slot must not depend on completion order. Use a fake runner that sleeps in reverse index order, so
     completion order is the inverse of submission order.
  4. **Parallelism derivation.** A pure `_workers(cpu_count, load1, runs)` with an injectable
     cpu and load. Controls: a loaded machine gives 1 (serial), a missing `getloadavg` falls back
     safely, and the result never exceeds `runs × per-run`.

## 6. Interactions

- **#1650 receipt and lock.** `verify_goal` (`loop.py:5622-5638`) wraps the whole body in
  `_CallGuard` (`loop.py:5545+`), using a per-goal kernel flock and the running receipt with
  `VERIFY_RECEIPT_SECONDS = 14400` (`loop.py:5539-5541`), and returns exit 6 on a concurrent verify of
  the *same goal*. Flake parallelism is internal to one verify call, so it does not touch the lock. A
  shorter flake pass only moves the receipt's final write earlier. Do not import
  `skills/sigma-loop/scripts/run_receipt.py` into flake_check (it stays standalone, as `diff_revert.py:72-74`
  notes about that posture).
- **The machine-wide cap of two concurrent verifies** is operator-side (the owner's serial-verify launcher in the ops directory,
  flock slots, default 2, "`-n 4` workers each"), not repo code. The flake pass runs *after* the proving
  command has exited, so that verify's own 4-worker share is idle during flake. The derivation should be
  min(runs × per-run-workers, free cores) where free = `cpu_count - ceil(load1)`. On a 12-core machine
  carrying the other verify (load about 4-5) that leaves 3 to 4 workers. The live load when this
  dossier was written was **21-24 on 12 cores**, where a load-derived bound must collapse to serial.
  Say so in the output line.
- **Content fingerprint** (`loop.py:5810-5823`): flake runs happen between `content_before` and
  `content_after`. Concurrent runs write `.pytest_cache` and `__pycache__`. The flake argv lacks
  `-p no:cacheprovider` (the proving command has it), and three concurrent writers of
  pytest's lastfailed cache file race. Add `-p no:cacheprovider` to the flake argv.
- **Timing store.** One record per verify (`name: flake`, `loop.py:5863-5868`). A "distribution" in
  done-when 3 means across at least 3 verifies (min, median, max of those records). Adding a per-run
  `ms` to each `runs[i]` entry also gives the within-check spread at no new write site.
- **Docs.** `docs/enforcement.md` has no flake text (grep empty) and is generated by
  `skills/sigma-doctor/scripts/enforcement_table.py` (`tests/test_enforcement_table.py:18`). Exit 5's
  refusal text does not need to change. `skills/sigma-time/SKILL.md:26` mentions flake as background time
  and is unaffected. No other doc under `docs/` describes the serial mechanism.
  `docs/launch/review-units.json:454-457` pins `flake_check.py` lines 1-166 as a frozen review unit; run
  `tests/test_readiness_review_units.py` to confirm it does not re-check live line counts.
- **Write surface and shared paths.** flake_check has no entry in `docs/launch/write-surface.json`, and
  mkdtemp is not a scanned write rule. If the change adds no durable writer, no edits are needed in
  `docs/launch/write-surface.json` or the `tests/test_shared_sdlc_paths.py` ratchet. Keep it that way:

## 8. Risks

1. **xdist weakens the order-dependence control.** Under `-n K` the given order splits across worker
   processes, so a pair (a, b) whose interaction is the bug may land on different workers and never
   interact. The per-worker order is a subsequence of the shuffle, but `--dist load` scheduling is
   nondeterministic, so a seed no longer reproduces an order. Prefer **3 concurrent serial runs** as the
   primary mechanism, keeping intra-run order intact. Add per-run `-n` only when the derived budget
   exceeds `runs`, and consider `--dist loadfile` (keeps a file's tests on one worker). Re-run the
   real-pytest order control (the docstring's `cab`/`bca` check) under xdist before trusting it.
   Record `workers` per run.
2. **Isolation under concurrency.** The suite already passes under `-n 4`, but xdist never runs the
   *same* test twice at once, and the flake check does. Shared state: the `.pytest_cache` race
   (mitigated by `-p no:cacheprovider`), tests that write fixed paths (29 test files reference
   `Path.home()`, `expanduser`, a literal tmp root or sockets; the #1550 files are mostly clean, `tests/test_loop.py`
   has 5 literal tmp-rooted sdlc paths used as path arguments only), and `conftest.py`'s autouse `gh` guard is
   per process, which is fine. A collision would show up as a *disagreement*, a false `unverified`
   (exit 5): safe-failing but noisy.
3. **Interpreter divergence** (§3). Probing xdist with the verify venv but running the flake with
   the system Python would request `-n` from an interpreter that lacks it, giving exit 4 and `absent`
   every time. That is silent loss of the check, though `_measured` keeps it from becoming `verified`.
4. **Fake-runner sensitivity collapse.** Existing controls were written against a sequential runner
   (shared counter). A thread-pool port can leave them green while results are mis-assigned to runs.
   They need the deterministic index-keyed control from §4.3, which must go red when results are
   collected in completion order.
5. **The 3x may be unreachable on #1550 without per-run workers.** Theory gives 469 s per serial run
   against a 470 s target. The PR may land under the "or the PR says why not" branch if the load-derived
   bound gives no more than 3.
6. **Resource safety.** Peak children = runs × per-run workers. This must be derived and also clamped
   to at most `runs × (cpu_count // runs)`, never a constant. Each run needs a timeout or kill story:
   today a hung run hangs verify, and concurrency does not change that. Out of scope, but name it.
