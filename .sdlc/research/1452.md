## Design pitfalls to carry into the plan
- `input_tokens` already includes `cached_input_tokens`; never sum them. `output_tokens` already includes `reasoning_output_tokens`; record reasoning for reporting only. `tokens_out` stays `sum(output_tokens)`; `tokens_in` stays `sum(input_tokens)`; add `tokens_cached_in = sum(cached)` and `tokens_reasoning_out = sum(reasoning)`. Budget ceiling `tokens_in + tokens_out` unchanged. A test should show a fixture where adding either new field would change the ceiling (value-distinguishing, not zero).
- Cross-stream refusal compares `[:3]`; decide whether the new fields are also compared (a stricter refusal changes behavior for existing partial writes, recommend leaving it at [:3]. Compare cached too only if a red test justifies it).
- De-dup fingerprint should stay `(pair, cumulative)`; if `_codex_usage_pair` now returns a richer value (tuple of 5 or dict), the fingerprint still works but the cumulative call must tolerate a `total_token_usage` that lacks the new fields (cumulative from a legacy-ish row), i.e. the fingerprint must not become `None` just because `total_token_usage` has no `cached_input_tokens`. Safest: keep a separate request-pair and cumulative fingerprint over `(input_tokens, output_tokens)` only, as today.
- The unknown-model flag (`unknown_model_turns`) and `models` list must be preserved; per-request rows carry `model` (None when unknown) so #1666 can refuse to price unknown-model requests.
- Do not write new fields for Claude phases or unmeasured phases (fabrication).
- Keep the `cost: unavailable on this host (Codex model absent from bundled rate card)` string verbatim (quoted by output-contract; `test_phase_report.py:3034`).

## Open decisions for PLAN (flag to plan-review)
1. "Modern shape" is undefined in the design. Existing modern-KIND fixtures (record/event) carry no cached field, and the legacy kind carries none either. Cheapest consistent reading: modern = kind in {record, event} (default 0 for the three new fields when absent); legacy = new fields reported as absent/0 but flagged, or defaulted to 0 too. Spec says defaults apply "only on the modern shape", but making legacy absent-field rows return `None` would break `:774` and `:993` (which exist and pass today). Recommend: legacy kind keeps the two-field pair (cached=reasoning=0, noted in the row as `split_reported: False`); modern kinds default absent fields to 0; any present-but-malformed field returns `None`. Plan-review must confirm this reading against the acceptance text ("missing new fields default to 0 only on the modern shape").
2. Return shape of `_codex_usage_pair`: tuple of 5 vs dict. A dict is clearer (`{"input_tokens", "cached_input_tokens", "output_tokens", "reasoning_output_tokens", "cache_write_input_tokens"}`); only one internal caller so it is free to change.
3. Row timestamp form (raw string vs `norm_ts` epoch) - pick what `price_turn` consumes (`select_rate` is by ts), recommend `norm_ts` output to match Claude turns.
4. Whether `cache_write_input_tokens` also gets a total (`tokens_cache_write_in`). Slice text lists only two new event fields and the four phase totals; keep cache-write per-request only, not a totals/event field.
5. Whether the `phase` event also records the new fields when the totals are zero ("0" vs omit). Recommend writing them (as "0") for Codex-measured phases only so that a zero is a measured zero.

## Risks
- Exact-dict-equality assertions at `test_phase_report.py:774` and `:862` need the new keys; this is intended breakage to update, not regress.
- Contract bump: forgetting `contract/vocabulary.json` regeneration fails `test_contract_generation.py`; forgetting NUMERIC/NON_PROSE entries fails at import (loud, good).
- Silent-skip semantics: a malformed new field drops a whole request from the totals, undercounting `tokens_in` and the budget ceiling (existing behavior for bad input/output, but now a new way to trigger it). Mitigation: treat only wrong-typed present values as malformed; absence on a modern row defaults to 0. Consider a count of skipped rows for later; out of scope here.
- Scalability: per-request rows are an in-memory list bounded by the rollout size (measured about 1,670 rows over 8 rollouts, so about 200 per phase). Rows must NOT be written into the ledger event (only totals), so no unbounded growth. At 100x (20k rows) it is still a single linear pass of a file already read once.
- Host-agnostic: pure Python on Codex's own rollout files, no hook involved.
- No live runs; all fixtures offline.
- Not measured: row-count/size figures above come from design 1379 PC-3/PC-12 (their measurement), not re-measured here.
