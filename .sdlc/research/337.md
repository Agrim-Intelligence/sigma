# Research: #337 flake census (PR A: workflow, script, tests, docs)

Phase P2 RESEARCH. Base `e18e7d0` (origin/main). The issue was parked because the Linux half is a
`workflow_dispatch` workflow, and GitHub accepts a dispatch only for a workflow that already exists on
the default branch (the earlier attempt measured `GET .../actions/workflows/flake-census.yml?ref=sdlc/337`
as 404). Decision recorded on the issue: split into two merges. PR A lands the workflow, the census
script, hermetic tests and docs, and claims no census result. PR B dispatches the merged workflow,
downloads the artifacts and commits the evidence.

## Facts (measured here, 2026-10-04)

- `.github/workflows/` holds `ci.yml` (push to main, pull_request, workflow_dispatch; 5 legs) and
  `windows.yml`. No workflow named `flake-census.yml` exists; `gh workflow list` shows two.
- `ci.yml` setup steps to copy: checkout, git identity, setup-python, `pip install pytest`.
- `tests/test_ci_matrix.py` parses `ci.yml` as text (no PyYAML in the suite), so a workflow test here is
  also text based.
- The issue fixes the design: N = 10 per OS; Linux on `ubuntu-latest`, Python 3.12 only, 10 parallel
  matrix jobs, each `python -m pytest tests/ -q -p no:randomly --junitxml=junit-<run>.xml`; macOS runs
  locally with `$HOME/.sigma-venv312/bin/python -m pytest tests -q -n 4 -p no:cacheprovider`; no retries.
  `docs/launch/definition.md` lists Python 3.10 to 3.13 as supported, but the issue names 3.12 and the
  census is one leg, so the other versions are not run (stated as a limit, not hidden).
- Classification per node id: `flaky` (passed in at least one run and failed or errored in at least one),
  `always_failing`, `skipped_only`, `missing` (absent from some runs).
- pytest writes a collection error as a `<testcase>` whose `classname` is empty and whose `name` is the
  module path, carrying an `<error>` child. A parser that insists on a classname rejects exactly the runs
  where something broke, so the node id must be `classname::name`, or `name` alone when the classname is
  empty.
- Write-surface inventory (`tools/readiness/write_surface.py check`) is green on the base; a new writer in
  `tools/readiness/` is a new fs-write site and must be reflected in the inventory.
- `red_green.observe` counts only an `AssertionError` as red, so each test reaches the tool through a
  helper that asserts the file exists (a missing module is then a red assertion, not an ImportError).

## Cost (stated, not measured)

Linux leg: 10 jobs x one full suite on ubuntu-latest. Per `ci.yml` experience a full leg is about 15 to
21 minutes, so about 150 to 210 Linux runner-minutes per dispatch (Linux minutes are billed 1x; GitHub
rounds each job up to a whole minute). macOS is local, 10 x about 5 minutes (a measured verify of 273 s on
this machine) with no Actions minutes. PR A's own CI is the normal 5 legs; the new workflow does not
trigger on push, pull_request or schedule, so it adds nothing to them.

## Risks carried into the plan

1. A mislabeled classification (b reported flaky). Control: classify by "failed at least once" only and
   see the test red.
2. A dispatch-only guarantee that silently erodes. Test: the workflow's `on:` block names
   `workflow_dispatch` and nothing else, with a mutated copy refused by the same validator.
3. Evidence overwritten. The writer creates a file exclusively and refuses to replace one.
4. A result that claims more than it measured. N runs cannot prove zero flaky tests; the docs and the
   JSON say so, and `combine` refuses anything other than 10 runs per OS.
5. Host paths or secrets in evidence. Metadata values that look like absolute paths are refused.

# Research: #337 merge 2 (dispatch, evidence)

Phase P2 RESEARCH for PR B. Merge 1 (PR 519) is on the default branch, `flake-census.yml` is listed by
`gh workflow list`, and the issue was reopened after the merge step closed it.

## Facts (measured here, 2026-10-04)

- The workflow was dispatched once from the default branch at commit
  `c82e3dfa7420e92465a7cf991a1dcf5166403973`: Actions run 37187467571 (event `workflow_dispatch`,
  head sha read back over REST from the run).
- The macOS half is run locally from a detached checkout of that same commit with the verify interpreter
  (`-n 4 -p no:cacheprovider`), ten sequential runs, using the merged `flake_census.py run`. One full-suite
  run under load measured 13m30s on this machine in an earlier probe (12,088 test cases); the issue's own
  unloaded figure is 273 s.
- Ten runs of the Linux leg cost about 150 to 210 Linux runner-minutes (estimate from CI legs; the
  per-job minutes are read from the run once it ends).
- `docs/launch/flake-census.md` still says the change records no result; once evidence lands that sentence
  is false and must change, and the test that pins the sentence changes with it.

## Risks

1. A result stated more strongly than ten runs support. The doc and the JSON carry the limits.
2. Evidence that does not match the commit it names. The macOS checkout is detached at the dispatched sha,
   and a test checks the filename's sha12 against the file's own `sha`.
3. A partial run aggregated as a full one. `per_run` counts and the exit codes of `run` are read first.
4. Host paths in evidence. `--meta` refuses them; the evidence test also scans the file.
5. Filing noise. Only a real defect becomes an issue, grouped into one, queued, never promoted.
