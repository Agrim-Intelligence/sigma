# Research: #1210 ledger publish never retries a failed push until a new entry is written

Base: `origin/main` at 57d810a. Lane: small (one function, two wording sites, tests).

## The defect, measured

`skills/sigma-loop/scripts/sync.py` `publish()` (ledger channel) returns `"nothing to publish"` when
`git diff --cached --name-only` is empty. It never asks whether HEAD is ahead of `<rem>/<branch>`. Reproduced
with real git: two clones of a bare origin, both bootstrapped, then clone A writes a note and publishes
through a `run` wrapper that raises on `push`:

```
publish #1 (push fails): publish deferred (will retry next tick): git push: simulated network blip
ahead after #1: 1
publish #2 (no new entry): nothing to publish
ahead after #2: 1
origin sdlc-ledger log: ['ledger: ben', 'ledger: ana', 'ledger: scaffold the ops branch', 'ledger: start the ops branch']
```

The stranded second `ledger: ana` commit never reaches origin. The watcher calls `publish` once a tick, so
"will retry next tick" is false until some later entry gets staged.

## Blast radius

- `sync.publish()` is the only defective function. Its callers are `watch_daemon.py` (once a tick, through
  `sync.py publish`), `bootstrap()`, `publish_after_write()` (hand-typed writes) and
  `loop._ensure_ledger_delivery()` (pick-time backlog check). Every caller treats the result as a string, and
  `publish_after_write` and `_ensure_ledger_delivery` each wrap the call in their own `try`.
- Knowledge-channel precedent: `_publish_knowledge` stages and commits inside one `try`, then
  `if _ahead(...) == 0: return "nothing to publish"`, and pushes otherwise (P4 finding B1). `_ahead` returns
  `None` for an absent ref and never raises.
- Since #1142 (on origin/main), `_fetch` writes `refs/remotes/<rem>/<name>` explicitly and `_record_push`
  updates it after every successful push, including in single-branch clones. So an absent tracking ref means
  "never fetched a remote branch and never pushed from here". It does not mean "this clone's refspec is
  narrow", which would otherwise turn "push when absent" into a push on every tick.
- **Adjacent contract break, measured.** `publish()`'s docstring says it never raises (#2449), but `git add`
  and `git diff --cached` sit outside any `try`. A `run` wrapper raising on `add` (a held `index.lock`) gives
  `RAISED: RuntimeError git add: fatal: Unable to create '.../index.lock': File exists.`
- Wording that becomes untrue once the fix lands: `loop.py` `_ensure_ledger_delivery`'s docstring (lines
  145-149) and its stderr line (191-192) say publish only pushes what the current call staged, and that a
  persisting backlog after "nothing to publish" "likely" means an earlier commit failed to push.
- Wording that becomes TRUE with the fix: `_push_with_retry(..., retry_hint="next tick")`, which gives
  "publish deferred (will retry next tick)". Once the fix lands, the next tick's `publish` pushes the stranded
  commit, so this wording stays.
- Stub test affected: `tests/test_watch.py::test_publish_is_a_noop_when_nothing_changed` stubs every git
  call as `""`. Under the fix, `rev-list --count` returning `""` is unparseable, so `_ahead` returns `None`
  and the fix pushes. The stub must answer `rev-list` with `"0"` to keep meaning "nothing ahead".

## Constraints
