# Research: Planned-test proof, flake check and witness accept only pytest, so every UI (vitest) goal ships under --no-tests
**Goal**: [#2084](https://github.com/Agrim-Intelligence/sigma/issues/2084) · **Lane**: medium · **Date**: 2026-10-29

## Goal in one paragraph
A `## Tests` bullet today must be one backticked pytest selector (`red_green.selectors`), so a UI goal whose planned test is a vitest case cannot be proven: `loop.py red` and `verify` find no proof, the flake check and witness print `skipped (non-fatal)`, and `work.py pr` needs `--no-tests`. The goal adds runner-named bullets (`` `vitest: path.test.tsx > suite > test` ``) mapped to a command template at config `tests.runners.<name>`. Red and green are read from the command's exit status. The command is a repository shell string, so it runs only under the same trust as `verify.command` (git-local grant or the environment approval). An unapproved runner is refused and never run, and an unknown runner is an error naming the config key. Acceptance: `.sdlc/acceptance/2084.md` AC-1..AC-5.

## Constraints & unknowns
- Unverified: an end-to-end run against a real vitest project. No vitest is installed here. AC-5 asks for a stub command; any "works with vitest" claim must carry the "unmeasured" label AGENTS.md demands.
- Unverified: whether a cloud environment can ever set an approval covering a runner (see Q-1). docs/cloud-sessions.md already says cloud behaviour is measured on fixtures only.
- North-star: `north_star.py` printed `absent` (drop-in project). No early warning.
- **Blocking (Q-1): what "same trust as verify.command" means under the environment approval.** The approval is one hash of exactly one command (shell_policy.py:105-111, 281-286: `all(approval_value(identity, c) == value for c in commands)`, one 64-hex value enforced at 261-263). If the runner template joins the command list, then in the exact scenario of the source report (a cloud run with `SIGMA_TRUSTED_VERIFY_SHA256` set and no git-local grant) it always reads `mismatch`, so the cloud case still ends up on `--no-tests`. AC-1/AC-2 would then be reachable only under the git-local grant. Options: (a) git-local only for runners; the env approval is refused with the git-local gesture named (smallest, safe, satisfies AC-3, but leaves the cloud case unfixed and says so); (b) redefine the approval as a canonical hash over verify.command plus sorted runner templates (re-approval for every adopter that adds a runner, a change to `doctor.py verify-approval`, to docs and to the pinned tests); (c) a second variable (new operator surface, contradicts the "one value" tests in tests/test_shell_policy.py). Recommendation: (a) for this goal, document the ceiling, and ask the owner whether (b) is wanted as a follow-up. Trust surface decision: owner's.
- **Blocking (Q-2): what counts as "red" for a non-pytest runner.** pytest red is credited only for an attributed `AssertionError` in pytest's summary (red_green.py:200-216), precisely so a compile, import or setup error cannot be laundered into a STRONG `assertion` witness (witness.py:13-35, `classify` ordering). A runner command exposes only an exit status, so a nonzero vitest exit cannot distinguish "assertion failed" from "file does not compile". Options: (a) exit-status only, with a distinct provenance (e.g. `planned-runner-v1`) and documented as weaker; (b) an optional per-runner `red_pattern` regex that the output must match for red to be credited, otherwise the nonzero exit is recorded as `other` (not credited); (c) exit decides green, red needs the pattern when configured and is marked weaker when not. Recommendation: (c). The issue says "read its exit status", so confirm the owner accepts a weaker red when no pattern is set.
- Non-blocking (Q-3): when a runner command is not covered, refuse the whole `loop.py verify` (exit 2, like an uncovered `verify_command`) or run the proving command and refuse only the planned proof? AC-3 says it "SHALL NOT run" and is "refused with a message naming the trust gesture". Recommendation: `loop.py red` exit 2 (as today), and `loop.py verify` also exit 2 before anything runs, because silently dropping the test-first proof repeats the `skipped (non-fatal)` failure this goal removes.
- Non-blocking (Q-4): flake check and witness for runner nodes. pytest shuffling does not apply. Options: re-run the runner command 3 times unshuffled (3x the vitest cost, same trust) or report `absent` with a stated reason. The issue asks both to "run that command". Recommendation: flake = 3 sequential runs of the exact command with the existing verified/unverified/absent vocabulary; witness = file-bytes hash (BR-11/12). Cost: 3 extra runner runs per bullet, bounded by the existing 25-bullet cap.
- Non-blocking (Q-5): the acceptance `verify_command` names a file that does not exist; new tests belong in `tests/test_red_green.py`, created by this goal. Also, #2085 `goal-command`: the goal's own `verify_command` is outside an environment approval, so verifying this goal needs the git-local grant or clearing the record's command.
- Non-blocking (Q-6): placeholder safety. `{file}` and `{name}` come from plan text and reach a shell (the template needs `&&`). Values must be `shlex.quote`d, `{file}` validated like the pytest path (relative, no `..`, no leading `-`, no backslash), unknown placeholders in a template rejected. Decide how ` > ` splits (suite titles may contain `>`: split on first for file, remainder is the name) and whether `-t` receives `suite > test` or only the leaf.
- Non-blocking (Q-7): config shape. `tests.runners.<name>` as a plain string (as in the issue) vs an object if Q-2 needs `red_pattern`. Recommendation: accept a string now, allow an object later.
- Non-blocking (Q-8): the runner's working directory and timeout. pytest `_run` has neither and runs at the goal worktree root. The template does its own `cd` (issue example). A hung runner blocks verify; consider `verify.timeout_minutes` (loop.py `_verify_timeout_seconds`).
- Overlap with #2083 (area:work, branch `sdlc/2083`, worktree exists): #2083 concerns `work.py merge` landing and cloud-session behaviour. Likely shared files: work.py (different functions: `merge` vs `_test_first_refusal`/`pr`), docs/cloud-sessions.md, CHANGELOG.md. Expect textual conflicts in CHANGELOG.md and docs/cloud-sessions.md only; rebase on whichever lands first. loop.py, red_green.py and shell_policy.py should not collide.
