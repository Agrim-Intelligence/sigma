# #144 research — upkeep silently deletes branch content when the base holds a revert of it

## Symptom
`work.py start` printed `upkeep: feature/<x> brought forward onto main (0 replayed, 0 conflicted,
0 skipped)`. That pass force-pushed the feature branch and deleted 72 files (10,985 lines). The new
tip kept the old subject, so `git log -1` looked healthy.

## Root cause
`main`'s tip was a revert of the branch's own commits (the work had been moved off `main` onto the
branch). Those commits are in `main`'s history, just reverted, so git treats them as already
present. `git rebase origin/main` then replays only the branch's later commits on top of the
revert, and nothing restores the reverted content. No existing check could see it:
- `rev-list --count` said "behind", so the pass ran;
- `direct_commits` (the first-parent walk) passed, because every commit on the branch carried a
  pull-request trace;
- the rebase succeeded, so there was no conflict;
- `_pushed` pushed under a correct lease; `0 replayed` counts GOAL branches, not content.
A history-shaped check cannot tell this from a legitimate upstream change: a merge would drop the
content too. It shows up only in the tree the push would publish.

## Blast radius
- `skills/sigma-loop/scripts/feature_rebase.py`: `_rebase_feature` (the replayed head is computed
  there, just before `_pushed`), `_rebase_pass` (outcome handling, filing), `clause`/`_WORDING`,
  `OUTCOMES`/`IN_CLAUSE`, CLI `main`.
- `skills/sigma-loop/scripts/work.py`: `_rebase_upkeep` only relays `report["note"]`. It needs no
  change, because adding the outcome to `IN_CLAUSE` puts it on the start line.
- `skills/sigma-doctor/scripts/doctor.py`: had no upkeep row at all. It cannot import sigma-loop
  (architecture rule 3), so it can see the refusal only through a state file.
- `docs/branching-model.md` §3 (the new §3b), §6e (the measured call count changes by one local
  `git diff`, pinned by `tests/test_docs.py`), §15.
- `slack_commands_listen.py` reuses `worktree_path`/`lock_path`/`rebase_stopped` only, not
  `_rebase_feature`, so it is unaffected.

## Discriminator, and the false positive it carries
Pre-tree = the feature tip the replay started from. Post-tree = the replayed HEAD. Finding = a
tracked path in pre that is absent from post.
- The branch's own deletions are never in pre, so they can never be a finding.
- Base renames are excused with `-M`. A rename beyond git's rename budget degrades to a deletion and
  is refused, towards safety.
- A plain upstream deletion of a file the branch carries unchanged is identical to the revert case
  as a tree. Excusing it would need history semantics (detecting reverts by patch-id or message),
  which is fragile against squashed multi-commit reverts. Decision: refuse it too. That costs an
  upkeep pass and a human decision, never data. It is documented and pinned by a test.
- Not seen: a revert that edits a surviving file back. Documented in §15.

## Scale
One extra local `git diff --name-only -z` per pass that actually replays. Its cost is linear in
changed paths, and it is skipped entirely on `current` (the common case). The listing is capped at
20 in the report, the issue and the marker. The count is always exact. The marker is one bounded
file per unit, overwritten in place and removed by the next clean pass.
