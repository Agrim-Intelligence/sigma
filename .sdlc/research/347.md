# Research: #347 shared `.sdlc` paths with the predecessor, and a guard

Phase P2 RESEARCH, lane medium. Base `4c8562f` (origin/main), worktree `.sdlc/work/347`. Inputs: issue #347, #314 (closed:
Sigma runs alongside and replaces the predecessor; notice, not refusal), `docs/upgrading.md`, `docs/launch/decision-rule.md`
(B1 = "confirmed data loss or corruption of user data, git history, or GitHub state"), `tools/readiness/growth_audit.py`.
Everything below was measured in this phase with scratch code under `~/.sigma-ops/s347/` (never repo code) against the
predecessor's installed copy, picked as the latest version directory of the installed set (1.3.7, 1.4.16, 1.4.20, 1.4.21,
1.4.22, 1.4.24, 1.4.27, 1.4.28): **1.4.28**. Only a COPY of it was ever executed.

## What #314 makes "compatible" mean
Both plugins run on one repository, and Sigma replaces the predecessor in place. So a shared path is compatible when
either plugin can write it without destroying what the other holds there. Reading the other's spelling is Sigma's job
(`legacy.py`, `migrate.py`); the predecessor cannot be changed (out of scope), so a path the predecessor cannot read is a
different format and the question is whether the predecessor then DESTROYS what Sigma wrote.

## Measurements
- The two code bases share a lineage: of 170 `.sdlc` patterns the predecessor's `skills/` writes (growth_audit's own
  scanner) and 167 Sigma's, 142 coincide before directory/prose rows are dropped; after restricting to code writers under
  `skills/` and `hooks/` and merging directory rows, the shared set is about 95 patterns (31 are directories).
- growth_audit misses writers whose destination parameter is not named `sdlc_dir` (`<features_dir>/index.json`,
  `<goals_dir>/<gid>.md`, `<sdlc>/state/...`) because `_row` keeps only `.sdlc/`-prefixed patterns. A relaxed `_row` plus an
  alias table recovers them; the registry shard writer (`feature_registry.write_unit`, destination built in a helper) is
  still unreachable and is pinned by name as a supplementary writer.
- Black-box samples (both sides' own CLIs in scratch repos, one fixed command list, fake HOME): 13 two-writer paths have
  equal key sets; the other differences are additive (Sigma adds `generation` to session markers, `pid` to the phase
  marker, `op`/`path` appear in action-log lines from a step the predecessor did not log).
- Key sets alone say nothing about corruption. Two cross-write probes do: (1) each side's `setup.py configure` over a
  config the other wrote loses no top-level key in either direction (config.json differs in keys, both are additive,
  measured, no corruption); (2) **a registry `index.json` Sigma wrote (schema id `sigma/features@1`, one unit, no unit
  shard) is replaced by the predecessor's own `feature_sync.py fold` with an empty registry in the predecessor's schema id;
  Sigma then reads zero units**. The predecessor prints that it "read none of it", exits 0 and writes anyway.
- Mitigations on Sigma's side exist (`docs/upgrading.md`): a one-time copy of `.sdlc/features` before Sigma's first write
  where the predecessor can still run, and the shard-wins reader. They do not stop the predecessor's fold: the copy is
  once-per-repository, machine-local, and a registry duplicated into a sibling repository (`index.json` only, no shards)
  has no shard to fall back on. The registry is committed team data, so this is the B1 candidate; whether it counts as
  confirmed corruption (git history and the copy can restore it) is the owner's call.
- Direct module call, not a CLI path: the predecessor's `write_unit` overwrites a Sigma-schema unit shard. Not filed as a
  second finding; the registry finding covers both and the shard case is stated as not probed through a CLI.

## Cross-run on one repository
Sigma then predecessor then Sigma, and the reverse, on one scratch repo with the same command list: no exit code differs
from the solo run (0 anomalies of 10 steps x 2 orders). This covers start, next, agent-start, phase markers, note, log,
record, session-end and the setup wizard; it does not cover work.enabled (git worktrees), ledger, features, GitHub mode.

## What a static scan cannot see (carried into the doc)
Paths built from run-time data; destinations passed through a helper parameter not named like a store directory (found and
pinned only where this phase found them); writes by a subprocess the source merely names; `insight/`, `install.sh` and
other trees outside `skills/` and `hooks/`; paths the predecessor's source holds in config it reads from the host.

## Risks for the build
1. growth_audit refactor (`function_table`) must not change its output: measured equal on this tree.
2. The predecessor tree has 1,700 files; hashing is sub-second. Executing it only from a temporary copy keeps
   `__pycache__` out of the original (also `PYTHONDONTWRITEBYTECODE`).
3. Names: the predecessor's name must not appear in committed files; probe output is sanitised using the manifest's own
   `name` at run time, never a literal in code.
4. Version strings of the predecessor in docs need `VERSION_ALLOW` entries in `tests/test_readme_first_run.py`.
