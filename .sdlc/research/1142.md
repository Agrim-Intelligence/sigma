# #1142 research: ledger bootstrap starts an orphan ops branch when the fetch refspec omits it

## Root cause (reproduced, not inferred)
- `sync.init` (sync.py:365-383) runs `git fetch <rem> <name>`, then `git branch --force <name> <rem>/<name>`. A bare `git fetch <rem> <name>` writes `refs/remotes/<rem>/<name>` ONLY when `remote.<rem>.fetch` maps `refs/heads/<name>` (git's "opportunistic remote-tracking update"). Otherwise it writes `FETCH_HEAD` and nothing else.
- With `remote.origin.fetch = +refs/heads/main:refs/remotes/origin/main`, `branch --force` fails on the missing ref. The `except` path cannot tell "remote has no such branch" from "this clone cannot see it", so it runs `commit-tree` on the empty tree, which starts a new history.
- Measured on git 2.46.2 (scratch, two clones, bare origin): clone B made with `git clone --single-branch` then `sync.py bootstrap .sdlc` gives `ledger: start the ops branch -> scaffold -> ledger: bo`, `publish deferred (will retry next tick): ... [rejected] (non-fast-forward)`, and `git merge-base` reports `refs/remotes/origin/sdlc-ledger` as not a valid object. Same shape as the field report.
- `git clone --depth 1` writes the same single-branch refspec AND is shallow (probed). An explicit `git fetch origin +refs/heads/sdlc-ledger:refs/remotes/origin/sdlc-ledger` in that shallow clone fetched the full 3-commit unrelated history with its true root. `.git/shallow` held only main's boundary.

## Blast radius (every bare ops-branch fetch in sync.py)
- `init` :366, `pull` :459, `_pull_knowledge` :485, `_push_with_retry` :568, `publish_receipt` :778 and :786. Each later reads `<rem>/<name>`, which a single-branch clone never has. `pull` therefore rebases onto a STALE or absent ref: "pulled" without the teammates' new entries, or "pull deferred" forever.
- Other modules' fetches (work.py, feature_rebase.py, drift_watch.py, ...) fetch the integration/base branch, which a single-branch clone normally tracks. They are out of scope (noted as residual).
- Consumers of the status strings: `publish_after_write` (sync.py:1202) appends "will retry it". `loop._ensure_ledger_delivery` prints the result and points at /sigma-doctor. `watch_daemon` logs it. Nothing parses the "deferred" prefix (grep).
- Doctor: `_ledger_delivery_state` (doctor.py:3512) cross-loads `sync.unpublished`. It is local-only (no fetch), and a missing tracking ref reads "COULD NOT COMPARE".

## Facts that shape the fix
- With ONLY the fetch fixed, the publish retry's `rebase -X theirs <rem>/<name>` would GRAFT an orphan onto the remote. Add/add conflicts on README.md/.gitattributes/TEAM.md resolve to the LOCAL copy, which silently overwrites shared scaffold and adds an empty "start the ops branch" commit to everyone's history. So detection must run BEFORE that rebase, not on its failure.
- "No common ancestor": `git merge-base` exits 1, but `_run_git` raises on any non-zero exit, so 1 vs 128 cannot be told through the injected `git` callable. Disjoint TRUE root sets (`rev-list --max-parents=0`) prove it exactly. In a shallow repo a root may be a shallow boundary (read `$GIT_DIR/shallow`); then it cannot be told.
- `ledger.read_all` sorts by `(ts, actor, seq)`, so line order inside an entries file does not matter. An append-only union is safe for jsonl.
- Entries file names are `<actor>-<hosthash>.<pid>.jsonl`, so an orphan holds only this machine's files. A same-name collision with the remote needs pid reuse (rare).
- `refs/sigma/claims/*` is claim_refs' namespace (fetched/pushed/pruned with that exact prefix). `refs/sigma/orphaned/*` is outside it, and nothing pushes `refs/sigma/*`.
- Existing tests: stub-based (`tests/test_watch.py`: stubs return "" for every git call), real-git (`tests/test_ledger_publish.py`, `tests/test_hardening_698.py` #592 cases, `tests/test_kg_sync.py`). All use `git remote add`, i.e. the default `refs/heads/*` refspec, so none exercises this case.
- `docs/launch/write-surface.json` inventories every fs/git write per function (`tools/readiness/write_surface.py`). New writes need rows.

## Out of scope, noted
- The ledger `publish` returns "nothing to publish" when nothing new is staged, so a committed-but-unpushed commit is not re-pushed until the next write. The "will retry next tick" wording is therefore only true when a new entry arrives. This is a separate defect.
