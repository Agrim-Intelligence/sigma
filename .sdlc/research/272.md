# Research — #272

Acceptance intent currently lives in mutable issue text or local goal frontmatter. `state.declared_verify_command` selects a local override or repository command; `loop.verify_goal`, done, and merge share that resolver. `work.pr` already gates plan/research before pushing. `review_context.brief` fetches current issue text, so retro cannot reliably recover the original intent. Contract 1.2.0 freezes ledger kinds but supports additive minor releases.

The bounded implementation adds a write-once Markdown acceptance artifact, shared command resolution, a pre-push presence/shape gate, and verbatim review context. Existing records remain authoritative on retry even if an issue changes. Missing or malformed records fail closed when enforcement is enabled. Drafting is an agent decision in P1, never fabricated by a parser. Draft issue comments use a stable hash marker and strict comment reads; the existing source writer has bounded retries and can duplicate after an ambiguous acknowledgement, which is documented rather than claimed exactly-once.

Acceptance reads are O(1) files per goal, with a 32 KiB protocol bound and 3–7 criteria of at most 1024 characters. No fleet scan, background process, resource quota, global lock, or network access is added to verify/PR/review. Capture performs one source read and, only for GitHub drafts, one comment read plus bounded existing note retries. At 10x/100x goals this scales linearly in explicitly invoked captures, with no per-invocation growth. Local atomic create uses a temporary file and create-only hard link; unsupported filesystems refuse visibly and leave no partial record. Retrying a crash is safe for the local artifact. Ledger publication remains opt-in and only records the artifact path/hash, never the command.

Verification evidence must bind the acceptance bytes separately because `.sdlc` bookkeeping is excluded from code fingerprints. A changed/deleted acceptance record invalidates a prior green run. This records the P1 workflow intent and enforces presence; it does not prove when a human first started writing code. Commands are trusted project configuration, as with the existing local-goal command seam.

## Measured controls and cost (macOS, Python 3.9.6)

Sequential bounded local-record reads in a temporary copy on this host: 1 record 0.446 ms;
10 records 3.228 ms; 100 records 33.569 ms. These are one warm local sample, not fleet or Windows
measurements. Branch fallback adds at most four existing timeout-bounded Git calls across local
and remote refs (40 seconds worst-case timeout budget); acceptance blob size is checked before
reading. Branch lookup wall time was not benchmarked. Listing is linear in acceptance filenames.

Review caught shell grouping disabling `set -e` and absent branch-only criteria. Controls saw both
fail, then separate command subprocesses and validated/verbatim branch fallback repaired them.
The actual #272 source exposed trailing epic/blocker metadata after the checklist. Capture now
allows that footer but refuses any subsequent checklist item before the next H2, so criteria
cannot silently disappear. Empty checkbox-only lines also refuse. Existing local malformed
records remain authoritative failures instead of being hidden by a valid branch copy.

The local record is the durable source of truth; optional ledger metadata is best-effort, like
existing ledger writes. A crash after file publication and before ledger append can omit that
metadata; it cannot erase the record. A crash before atomic linking can leave a hidden temporary
file, which is not a valid acceptance record; remove that temporary file during normal cleanup.
If the canonical main-checkout record is lost, restore it from its committed goal branch before
verify/PR, instead of redrafting from changed issue text. Review/retro have a read-only branch
fallback. No GitHub write was made while implementing this issue; actual body capture used one
read-only fetch and the source seam.
