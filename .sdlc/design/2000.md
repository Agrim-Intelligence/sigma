## Intent

From the next minor release (1.1.0), Sigma runs every new goal on the lean route:
- **Work found mid-goal stays in the goal.** It becomes a slice of the goal it was found in. Only
  deferred, urgent-unrelated or exempt work becomes a new issue. Objective: agent filings never
  raise the count of loop-armed goals in the current release.
- **One PR per slice.** A goal with slices ships one pull request per slice, and stays claimed until
  its last slice merges.
- **Lighter phases per slice.** Each slice skips the goal-level research, plan and plan-review, and
  runs tests-first, then review.
- **Small goals are fast-tracked**, sized by the agent's own judgment with a recorded rationale
  (R10), backed by a mechanical check at `work.py pr`.
- **Measured, not A/B'd.** A baseline taken before the release is compared afterwards, with a
  stated revert trigger.

Corrected premises carried from earlier revisions:
- Sigma has no PR size cap (PC-1).
- One goal is one PR today, but a Refs-not-Closes path already exists (PC-8).
- In-goal slices exist but are unused: 0 of 394 local plans declare one (PC-28).
- Follow-up growth is real: 107 created and 22 closed in the last 14 days (PC-7, PC-29).
- An "awaiting merge" state with age reporting already exists and is the between-slices precedent
  (PC-30).

**Owner rulings (2026-10-23; they supersede the source prompt where they differ).**
- **R1 (as changed by the owner).** No flag: there is no `lean_goals` key and no off path. The lean
  route is how Sigma works from 1.1.0, for new and existing repositories alike.
  - This **consciously overrides AGENTS.md's SAFETY opt-in default** ("nothing ... without the
    operator opting in") for this change, by owner decision.
  - Rollback is to pin the previous plugin version (1.0.x). Nothing in the config turns it off.
  - The change is announced by the minor version bump (1.1.0) and the release notes.
  - Compatibility is an upgrade requirement (FR-31 to FR-35): no manual config edit, and a one-time
    cutover keyed on recorded state.
- **R2.** While working, agent filings never increase the count of loop-armed goals in the current
  release. Work found while working goal N becomes a slice of goal N, executed in the same
  iteration. Exceptions that create an issue:
  - (a) not needed for the current release: created deferred (no `sdlc:goal`, lowest priority,
    deferred-from marker as a bare number);
  - (b) priority P3 or P4 by the `sigma-triage` rubric: deferred the same way;
  - (c) an urgent unrelated defect (P0, in code goal N does not touch): its own armed goal, shown
    loudly as "scope grew";
  - (d) the existing exemptions: hard-stop or needs-owner parks, `upkeep_finding`, `blocks_goal`
    hand-offs, other-unit filings, and `goal=None`.

  A filing refused at `create_tracked_issue` converts to "add as slice". With no release source
  configured, priority alone decides: P0-P2 stay, P3 and P4 are deferred. Cursor and Codex can
  bypass this through a raw `gh issue create` (D-21).
- **R3.** Multi-PR goals are core: one PR per slice, claimed until the last slice merges, through
  the Refs-vs-Closes path. They need an aged between-slices state and a timeout.
- **R4.** Slices declared at plan time skip research, plan and plan-review. Each slice runs: write
  tests (red), implement (green), test review, code review, recorded per slice.
  - Retro runs once per goal, and is waivable for small goals.
  - A slice discovered after plan-review needs a delta plan (files and tests) and a delta-only review.
  - The manifest fingerprint covers scope fields only, never `status` (G-1).
- **R5.** Small goals skip research and retro automatically.
  - Their plan-review folds into the mandatory pre-implementation test review.
  - `work.py pr` checks that the change stayed small; if not, the goal goes back to full plan-review.
  - Tests, implementation, test review and code review are never skipped.
  - The `WAIVABLE` meaning changes on purpose. The trivial, small, standard and heavy profiles are
    defined here from code signals (D-20).
- **R6.** Dossier child goals skip Research, and keep plan and plan-review unless small.
- **R7.** Measure instead of A/B: take a baseline before merge, compare after launch, and define a
  revert trigger.
- **R8.** A one-time triage of the existing armed follow-ups, as a dry-run list the owner approves
  before any write.
- **R9.** Must not break: the action log, ledger, phase-record gate, plan sha256 binding, labels,
  branching registry, doctor, status and DAG.
  - Phase-prose ceilings are down-only, so the new route replaces prose, budgeted in tokens (G-7).
  - G-4 to G-10 are folded in. The TEST-MAP check becomes part of the pre-implementation test
    review. Feature 1 is cut to what multi-PR slices still need.

- **R10.** The goal profile (trivial, small, standard or heavy) is the agent's own judgment. It is
  made with full understanding of the goal, the project and the feature, the way an architect, senior
  engineer or PM would make it. It is not a fixed checklist and not defensive over-classification.
  The agent records a short rationale. There are two safety nets:
  - the Python check at `work.py pr` that a goal called small stayed small, failing closed;
  - the baseline report showing the profile distribution, so fear-driven over-classification is visible.
- **R11.** `review.test_review` stays as configured (false here) and governs only today's
  post-implementation test review. The pre-implementation test review that replaces plan-review for
  small goals is part of the lean route, independent of that key.
- **R12.** Host parity: behaviour is identical on Claude Code, Cursor and Codex, and enforcement never
  depends on the Claude Code hook.
  - A Python reconcile step in the loop's existing tick and pick path finds issues created during a
    goal that bypassed the filing route, and applies the same slice, defer or urgent rule after the
    fact. The hook stays only as an accelerator.
  - Bypasses are counted in the baseline report.
- **R13.** AGENTS.md is updated in the same release to describe the lean route as Sigma's standard
  workflow, with no opt-in and no exception wording. Its SAFETY opt-in clause is unaffected: the route
  spawns no new background process (the reconcile step runs inside the existing pick and tick), sends
  no data beyond the GitHub writes Sigma already makes, and consumes model quota only inside loop runs
  the operator starts, as today.
- **R14 (supersedes cross-machine resume).** The owning machine keeps the goal between slices.
  - The goal keeps `sdlc:in-progress` between slices, so no machine (1.0.x included) picks it.
  - The between-slices overlay is informational only. Status, the DAG and the board read it; it
    changes no pick eligibility. It still needs seeding, strip-on-close and reconciler wiring.
  - **Dead-owner recovery.** After the 72-hour timeout, or the existing dead-claim detection, the goal
    goes through the existing reclaim path. The new machine runs a fresh, recorded plan-review that
    re-binds the plan sha256 and the manifest fingerprint locally before continuing. Gate evidence is
    never shared across machines.
  - **PR keywords.** Slices before the last write `Refs #N`. The last slice's PR writes `Closes #N`,
    so GitHub closes the issue whoever merges it. A slice discovered while that last PR is open
    switches it to `Refs`.
- **R15 (supersedes R14's owner-only rule and re-plan-review recovery).** Slice checkpoints live on
  GitHub, and any machine can resume.
  - **Goal-level evidence** is published once on the goal issue by Sigma's Python, through `gh_api`:
    research done, the plan path and plan sha256, the plan-review verdict, and the manifest scope
    fingerprint. Plans are tracked in git, so a resuming machine reads the same plan file and checks
    its sha before trusting the verdict.
  - **Per-slice evidence:** a slice is done when its PR is merged and carries its review verdict
    marker. Progress is derived from GitHub, and the ledger is optional.
  - **Resume:** any machine resumes at the first slice without a merged PR. It reuses an open slice
    PR and branch rather than duplicating them, and never re-runs research, plan or plan-review. The
    phase gate at `done` accepts GitHub-recorded evidence for work done on other machines.
  - **Forced takeover:** `resume --force` takes the claim even if the prior one looks alive. Every
    claim or takeover bumps a claim epoch recorded on GitHub. Before each slice starts, and before
    each PR create, push or merge, a machine checks that the epoch is still its own; if it has been
    superseded, it stops cleanly. The takeover actor and reason are recorded.
  - **Forced restart:** `resume --restart` closes open slice PRs with a comment, deletes their
    branches and restarts from research. Merged slices stay merged.
  - **Automatic recovery:** a ledger-independent stall sweep marks a goal stalled after 72 hours
    without slice activity (a slice start, a PR push or a review). The goal then becomes resumable by
    any 1.1 machine through the normal pick, with an epoch bump. What 1.0.x machines do with it is
    stated and closed (FR-86).
- **Defaults stated by the owner.** A goal between slices is marked stalled after 72 hours without
  slice activity, and parked for resume under R15 and D-53. The revert trigger is follow-ups citing a merged goal rising more than 25
  percent over the baseline within 14 days. It flags the goal for the owner and never auto-reverts.

## Detailed design

**Where it is built (H7, FR-72).** The Epic declares the unit `lean-goals`
(`Feature: lean-goals`, `docs/branching-model.md`). Every child goal lands on `feature/lean-goals`
through its own `sdlc/*` branch, and nobody commits to the unit directly. Main never carries a
half-activated route. The unit reaches main through one human-approved landing as 1.1.0, after
slice 13. Until then, main and every release cut from it behave as 1.0.x.

The landing has a measured cost: main moved 219 commits in 14 days, 39 of them on `work.py`
(PC-48). So the unit is synced with main weekly through `/sigma-rebase`, and its owner resolves
conflicts. The landing is tracked by an `sdlc:checkpoint` issue and preceded by a serial full-suite
verify of the landing tip (FR-78, D-47). Slice 13 prepares the landing; a human performs it.

**The route, per goal (lean/1).**
1. **Pick.** The agent records the profile with a rationale (R10, FR-53). Python writes the route
   marker on the work record, in the action log and as a timeline marker (FR-34, H6). Trivial and
   small goals, and dossier children, get research waived through the existing `phase_waived` kind
   (FR-54, FR-56).
2. **Plan.** It writes the plan, and the slice manifest when there is more than one slice.
3. **Plan-review.** It binds the plan sha256 and the manifest scope fingerprint (FR-40), and Python
   publishes the goal evidence on the issue once (FR-79), with the claim epoch (FR-81). Small and
   trivial goals skip it. Their pre-implementation test review writes the same gates record, marked
   as the fold, so `_hard_plan_gate_refusal` and `_plan_review_refusal` accept it (BR-55).
4. **Per slice:**
   - write the tests and record them red, assertion-only (FR-45);
   - pre-implementation test review: the map half of `review_tests` against existing red tests
     (FR-46), plus a standalone max-tier review for heavy goals (FR-57);
   - implement to green;
   - code review with the post-implementation test review, which follows `review.test_review` per R11;
   - open the slice PR: `Refs #N` before the last slice, `Closes #N` on the last (FR-36).

   The slice's records are checked at its own `pr` push and `merge` (FR-70, M3).
5. **Between slices (R15).**
   - **Claim and labels.** A non-final slice PR keeps `sdlc:in-progress` and adds the informational
     overlay (FR-37). The overlay is seeded outside `overlay_labels()`, stripped by `complete()` and
     the reconciler (FR-75), and its seeding pins change on purpose.
   - **Close gates.** On its merge, neither `merge()` nor the merge-reconcile pass closes the issue
     or records `done` (FR-63). The pass keeps the claim and checkout and records the slice merge
     (FR-85).
   - **Continue.** The owning machine's next pick continues the goal before `next_pending`
     (FR-84).
   - **Resume anywhere.** Any 1.1 machine resumes at the first slice without a merged PR, reusing an
     open PR and branch (FR-64). It enters through the resume lane, or through any pick that finds
     trusted published evidence (FR-90).
     - **Slice state:** merged PRs on work.py slice branches carrying a trusted review marker (FR-65).
     - **Goal evidence:** the plan is read with `git show` from the open slice PR's head, or else from
       `origin/<slice base>` (`feature/<unit>` or the default branch), never the local root copy that
       `plan_copies` prefers (Q4). Its sha must match the published evidence (FR-74).
     - **A slice reused mid-flight** passes FR-70 through the slice evidence published on its PR: the
       red-witness digest, the pre-implementation test review and the code review verdicts. Where
       those are missing, the resuming machine re-records red against the PR base with the PR's test
       files, using the git-archive overlay the sealed tests already use (FR-92, Q2).

       Publishing is the primary path: it costs no test run and matches R15's model. The re-record is
       the honest fallback when the owner died before publishing.
     - **A discovered slice** carries its published delta-only review verdict (FR-76, Q6).
     - **Never re-run:** research, plan and plan-review.
     - **Publication (F4):** goal evidence is published when the first slice push carrying the
       approved plan lands, inside `pr()` (`work.py:4458-4462`), and again on every later approval.
       The newest trusted publication wins (FR-79). If the owner died before that first push, a resume
       refuses and names `loop.py resume --restart`.
     - **Local gate inputs (F1, FR-94):** the resuming machine imports the acceptance record (from the
       same ref as the plan, sha checked against the evidence) and a plan-review gates record marked as
       imported into its state directory, so `pr()`, `verify` and `record done` pass under
       `verify.enforce` and `gates.plan_review`. Nothing is written into the main checkout.
     - **Generations (F2, FR-95):** slice branches and markers carry the plan generation, and only the
       current generation counts. A restart cannot count an earlier generation's merges.
     - **Small goals:** they publish no evidence; continuing on another machine means `--restart`
       (D-56).
   - **Fencing (FR-81, Q1).** Before every GitHub write for a lean goal, the machine reads the newest
     trusted epoch (FR-93). That covers slice start, PR create, push and merge, the merge-reconcile
     pass including its closed-PR park, and every terminal `_record`.
     - A machine that sees a newer epoch writes nothing, and retires its local work record,
       `awaiting_merge` flag and worktree, keeping the local branch as `finish()` does (D-57).
     - After every fence check, slice state is re-derived, so a slice the other machine already merged
       counts as done (L-2).
   - **Stall.** With no slice activity for 72 hours, the stall sweep parks the goal as lean-stalled.
     - Activity is a slice-start marker, a PR push or merge, a review marker or an epoch bump, from
       trusted authors only, all carrying the `sigma:` prefix (FR-93).
     - A goal whose open slice PR carries a published approving verdict and awaits a human merge
       (`work.auto_merge` off, or `protected` where protection stops Sigma merging) is waiting on a
       human, not stalled (D-57, F8, delta N1).
     - The sweep is ledger-independent and bounded per pass. It runs beside
       `_reconcile_awaiting_merges`, inside the budget gate (`loop.py:2665-2672`), because it writes
       (L-1).
     - Any 1.1 pick resumes the goal with an epoch bump and an unpark in one step; 1.0.x never picks
       it (FR-38, FR-86).
     - On 1.1, a lean goal hit by a blocking hand-off or by a ledger reclaim is parked the same way,
       and resumed only once its blockers close (FR-91).
     - The park carries the `lean_stalled` qkind and `sigma:keep-parked`, so no automatic unpark frees
       it (F5). Its note names `loop.py resume`.
   - **Restart (F2).** `--restart` first clears its own work record and `awaiting_merge` flag, so its
     reconcile pass cannot park the goal when the old slice PRs close (`loop.py:4975`). It then starts
     a new plan generation (FR-83, FR-95).
   - **Operator verbs.** `loop.py resume <sdlc> <goal> --force --reason R` takes over a live claim
     (FR-82). `--restart` discards unmerged slices and restarts from research (FR-83).
6. **Last slice.** Its PR writes `Closes #N`, so GitHub closes the issue whoever merges it. On a
   `feature/<unit>` base, Sigma's close step does it once every recorded slice is merged (D-41). A
   resuming machine that finds all slices merged and the issue open records `done` (FR-87). The phase
   gate at `done` accepts the GitHub goal and slice evidence (FR-80).
7. **Retro** runs once per goal, waived for small goals.
8. **Parked mid-slices.** This covers the review-cycle cap, the slice cap and a human park. Unparking
   resumes at the first slice without a merged PR, reusing an open slice PR (FR-66).

**Discovered work (H2, FR-47, FR-67).** Filed work from goal N is handled by the goal's state:
- **Before plan-review:** it goes into the plan.
- **From plan-review until the issue closes or final done is recorded** (implementing, at review, PR
  open, awaiting merge): it becomes
  a discovered slice. It gets a delta plan and a delta-only review (FR-43), and is capped by
  `ai_filed.max_per_goal` (FR-44). If the open PR is the last slice's (it says `Closes`), it is
  switched to `Refs` through a new `gh_api.edit_pr_body` helper (BR-68), so its merge cannot orphan
  the new slice.

  Where the slice is written (FR-76):
  - always in the **manifest of record** on the goal issue, which both close gates count (FR-63);
  - also as an action-log row;
  - into the manifest file in the goal worktree, on the next slice's branch, by whichever machine
    continues the goal.

  It is never written onto an open PR's branch, and never into the main checkout.
- **After the issue closes, or after final done:** it is a new filing under the deferral rules
  (FR-67, F3). This covers retro's follow-ups, which arrive after a `Closes` merge.

**Filing route (R2).** In `create_tracked_issue`, in this order:
1. **Exemptions keep today's path (FR-50).** These are parks, upkeep findings, blocking hand-offs,
   other-unit filings, filings with no goal, and pipeline filings. A pipeline filing is recognised
   from the caller's `pipeline=True` keyword (decompose and design-check meta-issues) or from the
   filing goal's decompose-of marker (decompose children). Filer text never grants it (FR-68, H4).
2. **Urgent unrelated (FR-49, H5).** It is declared with `track --urgent-unrelated --paths ...`. Python
   then checks two things: the urgent triage pattern matches, and the paths are disjoint from the
   goal's planned files, manifest files and changed files (`zones._diff_counts`). Only then is it armed
   at the urgent bucket (D-39), with a loud scope-grew row.
3. **Deferred (FR-48).** Work outside the release, or triaged P3 or P4, is filed unarmed, at the lowest
   priority, with a bare-number marker.
4. **Otherwise it becomes a slice (FR-47).** The result is durable as a manifest entry plus an
   action-log row.

**Routed set and bypass reconcile (R12, FR-71, FR-77, FR-88, FR-89, M1).** There is no marker to
forge. `create_tracked_issue` records every issue number it files in a local routed set:
`state/routed/<goal>.json`, bounded to the claim and pruned at `done` (FR-77). One function then finds issues created during the goal's claim window that are not in that
set:
- It runs on the owning machine from `_next` (every pick, every host) and from
  `reconcile_tick.tick`, ungated by `discovery.reconcile.mode`.
- Issues that reference the goal get the same rule, applied as a relabel plus a comment, never a
  close.
- All others are counted as unrouted.
- Each pass examines a bounded number of goals and issues, and every write sits inside the budget gate
  (FR-88).
- A converted issue is closed, with a comment, when its slice merges (FR-89).

The residual window is stated in D-21.

**Upgrade compatibility and cutover (FR-31 to FR-35, FR-33).** A goal with an approving plan-review
record and no classification record finishes under the 1.0.x rules. Everything classified after the
upgrade is lean/1. New fields are additive. The one new label is additive and documented (BR-59).
