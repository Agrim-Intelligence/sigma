## Decisions (for plan-review)

- **D1 — the multiple is 3 (provisional, D-1).** Cost model per orchestrator turn: a cache read of
  the whole context at 0.1x input price (`rates/anthropic_list_prices.csv`); a hand-off costs the
  successor's fresh start written at 2.0x (1h cache) plus its startup turns, call it O = 2s..4s,
  where s is the start size. A session growing r tokens per turn from s to T costs, per turn,
  0.05(s+T) + O·r/(T−s), minimised at T − s = sqrt(2·O·r / 0.1). Measured on this machine
  (2026-10-24): s about 88k (84,392..95,573 over 8 main transcripts; goal-slot subagents 71k),
  r = 0.9k..3.1k per turn (same 8). That gives T = 1.7s..2.7s. Rounded **up to 3** because the
  model does not price what a hand-off also costs — every hand-off drains live slots with no new
  claims — and 3 sits inside the design's 2–4x band. At s = 71k / 88k / 150k: 213k / 264k / 450k.
  **Caveats written into the constant's comment and the config note:** s was measured at each
  session's FIRST TURN, not at its first pick (a first pick follows the skill load and `start`, so
  it is somewhat larger, which makes the derived threshold larger, not smaller); r was measured on
  general sessions in this repo, not on loop orchestrators; orchestrator growth per goal is
  unmeasured. Re-derived from Epic 2018's baseline and FR-8's report (D-6).
- **D2 — the cap is 45% of the host window (F2).** `threshold = min(3 × first_pick, ⌊0.45 × window⌋)`.
  On a 1M window: 450,000. Host compaction measured at 966,939 (about 0.967W), so at the cap there
  are ≥ 517k tokens of drain headroom: 167 turns at the highest measured mean growth (3.1k/turn),
  ~430 at the median (1.2k/turn); at the 264k default it is ~703k. **Relationship to slice 3,
  corrected:** a DERIVED threshold gets no slice-3 window at all — slice 3 sets a compaction window
  only when `handoff.after_context_tokens` is explicitly set (and max(2a, 420000) < 900000, i.e.
  a < 450000). The cap is chosen equal to that bound so the derived and explicit paths share one
  ceiling, but on the derived path the only compaction is the host's own (~967k). **The design's
  cost bar is not met at the cap:** the cap binds only when first_pick > 150k; there the threshold
  is 450k, and 450k plus any drain puts the orchestrator's peak above 50% of the window, so the
  design's "peak below 50 percent of the host window" row is NOT met for such sessions. At the
  264k default it is met only while the drain adds under 236k, which is unmeasured (D-6).
  Codex: window 258,400 → cap 116,280 (Codex's own compaction point is unverified; assumed above it).
- **D3 — where the window comes from (into the reading, so the resolver stays pure).**
  `context_reading` puts `window` in the block: Claude branch — `CLAUDE_CODE_AUTO_COMPACT_WINDOW`
  when it is a positive int (the host's own compaction point, set by an operator or by slice 3's
  daemon); Codex branch — the rollout's `model_context_window` (slice 1 drops it as `_info`).
  Neither present → `_context_threshold` uses **1,000,000, the largest host window**. Why that is
  safe: the cap only binds when 3 × first_pick > 450k, i.e. first_pick > 150k, which only a window
  above 200k can hold. **Documented limit** (ponytail comment + configuration row): on a 200k-window
  Claude model the derived 3 × s (≥ 213k) is above the window, so host compaction and the goal count
  stay the bound there; the operator sets `handoff.after_context_tokens` (or the env var). A host
  fact, not a machine-resource constant, and named as such.
- **D4 — M4 headroom, no second check.** The trip is evaluated before each claim. Batched path:
  peak ≈ threshold + the drain of ≤ `parallel.goals.max_concurrent` live slots. Inline path (no
  subagents, `references/picking.md:43-45`): peak ≈ threshold + one whole goal. Both ride the D2
  headroom (≥ 517k on 1M). A second check at `phase_report end` is declined: it cannot stop a
  running goal and would make a second chokepoint the design avoids. If D-6's measurement shows
  peaks above host compaction, the follow-up lowers the fraction.
- **D5 — `_explicit_context_tokens(handoff)` (shared rule, slice 3 uses the same).** Returns a
  positive `int` or `None`. Positive `int` → itself. **JSON `300000.0` is accepted**: a float with
  `is_integer()` and > 0 → `int(value)`, because JSON tools legitimately emit integral floats and
  rejecting one would silently fall back to derived. `None` for: absent, `null`, `0` (context trigger
  off), `bool` (checked before `int`, since `True` is an `int`), negative, non-integral float,
  string, anything else. `_context_threshold` distinguishes `0` (off) from malformed (derived) by
  reading the raw value, not by a second rule: `0`/`0.0` → off; any other `None` from the helper →
  derived. The template ships `null`. The doctor row shows a malformed value as
  `derived (ignored: <v>)`.
- **D6 — `_context_threshold(handoff, context)` and `_explicit_context_tokens(handoff)` are PURE and
  module-level in `loop.py`** (contract with slice 4, which calls
  `_context_threshold(config.get("handoff"), baseline)`). No I/O, no env, no clock. `handoff` may be
  `None` or a non-dict (read as `{}`). **`context` is the BASELINE reading, not the current one**: the
  function reads only its `first_pick` and `window` keys and ignores `tokens` and `source`, so a
  heartbeat block whose latest reading is `unavailable` but carries a `first_pick` still yields a
  threshold. Returns `None` when `handoff.enabled is False` (mirroring `_handoff_ceiling`,
  `loop.py:376`), `None` when the explicit value is `0`, and `None` when there is neither a baseline
  (`context` is `None` or its `first_pick` is `None`) nor an explicit key; an explicit key with no
  baseline returns the explicit value. Output `(threshold, basis)`. Everything impure (env, rollout)
  is read by `context_reading` into the block. The CURRENT reading is judged only in
  `_session_count_stop` (D7): it trips only on a `source == "host"` reading with `tokens`, so "meter
  unavailable → goal count only" lives there, not in the resolver.
- **D7 — trip rule.** HANDOFF when the CURRENT reading is `source == "host"` with `tokens`, `tokens >= threshold` **and `tokens > first_pick`** (every session
  does at least one goal). Without the second clause an explicit value below a fresh start, or the
  Codex cap on a big repo (first pick above 116k), would HANDOFF at the very first pick with zero
  claims, and the supervisor would relaunch every 60 s forever. The first pick of a session sets
  `first_pick = tokens`, so it can never trip; the next pick can. The huge-baseline case (first
  pick 400k, reading 460k) still trips.
- **D8 — finding 4 is bounded by the cap, not fixed with new state (YAGNI).** `session_end` unlinks
  the heartbeat, so an end + start in the same transcript re-baselines `first_pick` at the current
  context. The new threshold is min(3 × C, 450k on 1M), so the session still hands off by 450k with
  ≥ 517k headroom. Cost: such a session runs to the cap instead of 3 × its true start. Documented in
  the constant's comment and the configuration row; pinned by one test (Task 5).
- **D9 — meter read once, passed in (M5).** `_record_context` returns the block it built (`{source,
  tokens?, session, first_pick, window?, at, ...}`) or `None`; it already reads outside the lock.
  **On a lock or heartbeat-write failure it still returns the in-memory block** (slice 1's fallback
  at `loop.py:3179-3182` returns only a bool): the block is computed by one helper that reads the
  old heartbeat for the carried `first_pick`; `_write` = helper + write under the lock; the fallback
  = helper without the lock + the plain heartbeat refresh slice 1 already does. `_next(...,
  context=None)` / `_next_untraced`: a standalone pick (`refresh_heartbeat`) takes the block from its
  own `_record_context`; `next_batch` passes its prologue block to every slot. The three gates
  (`:2667`, `:2789`, `_reserve_goal_slot` → `:3691`) receive that one object.
  `_session_count_stop(..., context=None)` never reads the meter or the heartbeat. One transcript
  cannot change inside one `loop.py` invocation, so one reading is exact, not stale.
- **D10 — check order.** Inside `_session_count_stop` the context check runs **first**, before the
  `not ceiling and not iterations` early return (F2), so it fires with `after_goals: 0` and no
  `max_iterations`. Both are HANDOFF; the order changes only which reason prints; the
  resource-budget precedence above it is untouched. `_reserve_goal_slot`'s lock requirement stays
  keyed on goal-count ceilings: the context check reads only the passed-in reading.
- **D11 — the reason line.** `context 264,512 tokens >= handoff threshold 264,000 (3x first pick
  88,000, cap 450,000)`, or `(... handoff.after_context_tokens)` when explicit. Stdout stays the bare
  `HANDOFF` (`_print_pick`, unchanged); `_emit_run_stop_once` gets the same reason.
- **D12 — enforcement row with its own hosts value.** `enforcement_table.HOSTS` gains
  `"claude-code-codex": "Claude Code, Codex (Cursor: goal count only)"` (no test pins the key set;
  `_validate` only checks membership). New registry row "Session hand-off on measured context"
  (`_session_count_stop`, `python-gate`, hosts `claude-code-codex`, `enabled_by: ("handoff.enabled",)`,
  `settings: ("handoff.after_context_tokens",)`). The generator allows one function in two rows (it
  rejects only a duplicate control). The goal-count row is unchanged.
- **D13 — skill prose is this slice's (Epic 2025 rule), near net-zero.** Exact rewrites in Task 6.
  The orchestrator budget is 32,400 / 32,422 est-tokens and 19,336 / 19,527 words
  (`python3 evals/phase_context_budget.py`, 2026-10-24); the edits add ~17 words, paid for by
  removing the `_handoff`-comment pointer in `stopping.md:30-32`. A ceiling is never raised.
