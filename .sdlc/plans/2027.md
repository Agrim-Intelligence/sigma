## Decisions (for plan-review)

- **D1 — the multiple is 3 (provisional, D-1).** Cost model per orchestrator turn: a cache read of
  the whole context at 0.1x input price (`rates/anthropic_list_prices.csv`); a hand-off costs the
  successor's fresh start written at 2.0x (1h cache) plus its startup turns, call it O = 2s..4s,
  where s is the start size. A session growing r tokens per turn from s to T costs, per turn,
  0.05(s+T) + O·r/(T−s), minimised at T − s = sqrt(2·O·r / 0.1). Measured on this machine
  (2026-10-24): s about 88k (84,392..95,573 over 8 main transcripts; goal-slot subagents 71k),
  r = 0.9k..3.1k per turn (same 8). That gives T = 1.7s..2.7s. Rounded **up to 3** because the
  model does not price what a hand-off also costs — every hand-off drains live slots with no new
  claims — and 3 sits inside the design's 2–4x band. At s = 71k / 88k / 150k: 213k / 264k / 450k.
  Unmeasured: orchestrator growth per goal; the number is re-derived from Epic 2018's baseline and
  FR-8's report (D-6). The derivation is written into the config note and the constant's comment.
- **D2 — the cap is 45% of the host window (F2).** `threshold = min(3 × first_pick, ⌊0.45 × window⌋)`.
  On a 1M window: 450,000. Host compaction measured at 966,939 (about 0.967W), so at the cap there
  are ≥ 517k tokens of drain headroom: 167 turns at the highest measured mean growth (3.1k/turn),
  ~430 at the median (1.2k/turn); at the 264k default it is ~703k. Relationship to slice 3: slice 3
  applies a compaction window max(2a, 420000) only when that is < 900000, i.e. a < 450000; the cap
  equals that bound, so every derived threshold is one slice 3 would also protect with a 2× window,
  and 2 × cap = 900k < 967k. Codex: window 258,400 → cap 116,280 (Codex's own compaction point is
  unverified; assumed above it).
- **D3 — where the window comes from.** Codex: the rollout's `model_context_window`, carried by
  `context_reading` as `window` (slice 1 drops it as `_info`; one line). Claude: transcripts carry
  no window (research: no field, bare model ids, no env), so a missing window reads as **1,000,000,
  the largest host window**. Why that is safe: the cap only binds when 3 × first_pick > 450k, i.e.
  first_pick > 150k, which only a window above 200k can hold. Known ceiling (ponytail comment): on a
  200k-window Claude model the derived 3 × s (≥ 213k) is above the window, so host compaction and
  the goal count stay the bound there; the operator sets `handoff.after_context_tokens` (the docs
  say so). Not a machine-resource constant: it is a host fact, named as such.
- **D4 — M4 headroom, no second check.** The trip is evaluated before each claim. Batched path:
  peak ≈ threshold + the drain of ≤ `parallel.goals.max_concurrent` live slots. Inline path (no
  subagents, `references/picking.md:43-45`): peak ≈ threshold + one whole goal. Both ride the D2
  headroom (≥ 517k on 1M). A second check at `phase_report end` (M4's alternative) is declined: it
  cannot stop a running goal, and it would make a second chokepoint the design avoids. If D-6's
  measurement shows peaks above host compaction, the follow-up lowers the fraction.
- **D5 — explicit key semantics.** `handoff.after_context_tokens`: a positive `int` (not `bool`) is
  the threshold, uncapped (the operator measured); `0` turns the context trigger off (mirrors
  `after_goals: 0`); absent, `null` or any other value reads as the derived default (the template's
  convention: "Wrong-typed values read as these defaults"). The template ships `null`, so slice 3's
  "only when that key is set" stays false by default.
- **D6 — meter read once, passed in (M5).** `_record_context` returns the block it wrote
  (`{source, tokens?, session, first_pick, window?, at, ...}`) or `None`; it already reads outside
  the lock. `_next(..., context=None)` / `_next_untraced`: on a standalone pick (`refresh_heartbeat`)
  the block comes from its own `_record_context`; `next_batch` passes its prologue block to every
  slot. The three gates (`:2667`, `:2789`, `_reserve_goal_slot` → `:3691`) all receive that one
  object. `_session_count_stop(..., context=None)` never reads the meter or the heartbeat itself.
  One transcript cannot change inside one `loop.py` invocation, so one reading is exact, not stale.
- **D7 — check order.** Inside `_session_count_stop`, the context check runs **first**, before the
  `not ceiling and not iterations` early return (F2), so it fires with `after_goals: 0` and no
  `max_iterations`. Both are HANDOFF, so the order changes only which reason prints; the
  resource-budget precedence above it (`_budget_resource_reason`) is untouched. `_reserve_goal_slot`'s
  lock requirement stays keyed on goal-count ceilings: the context check reads only the passed-in
  reading, so it has no race to lock against.
- **D8 — finding 4: a per-transcript baseline file.** `session_end` keeps unlinking the heartbeat
  (liveness readers rely on that). When `_record_context` sets a *fresh* `first_pick` from a host
  reading, it also writes `.sdlc/state/context-baseline/<session>.json` = `{"first_pick": N}`
  (through `state.session_write`, atomic, under the stripe lock `_write` already holds), only if
  absent. When the heartbeat carries no baseline for this transcript (after `end` + `start`, or any
  heartbeat loss), `_write` adopts the file's value before taking a fresh one. `<session>` is the id
  `context_reading` already validated (slice 1 returns only safe ids). Growth: one ~20-byte file per
  host transcript that ever picked; the same writer unlinks siblings older than 7 days when it writes
  a new one (one directory scan per new transcript, not per pick). A transcript resumed after 7 days
  re-baselines; the cap bounds that (ponytail comment). Why not keep the heartbeat: every heartbeat
  reader (doctor, `log.py`, `status.py`, `resource_liveness.py`) treats the file as a live session.
- **D9 — the reason line.** `context 264,512 tokens >= handoff threshold 264,000 (3x first pick
  88,000, cap 450,000)`, or `(... handoff.after_context_tokens)` when explicit. Stdout stays the
  bare `HANDOFF` (`_print_pick`, unchanged); `_emit_run_stop_once` gets the same reason.
- **D10 — enforcement table: a sibling row, same function.** New registry row "Session hand-off on
  measured context" (`_session_count_stop`, `python-gate`, hosts `all`, `enabled_by:
  ("handoff.enabled",)`, `settings: ("handoff.after_context_tokens",)`, condition naming that only
  Claude Code and Codex measure; Cursor falls back to the goal count). The generator allows a
  function in two rows (it only rejects a duplicate *control*). The goal-count row is unchanged.
