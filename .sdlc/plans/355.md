## Design

1. `evals/bench/tasks/manifest.json` in the harness's own format (`sigma.benchmark-tasks/v1`), derived from the per-task
   `task.json` files by `bench_tasks.py build-manifest`; `check` refuses drift and runs the harness's own `_load_tasks`
   (external `repo/` is git-ignored, so the load runs over a copy with stand-in empty directories) and, given a hidden
   root, its `_validate_inputs` over the ready tasks. Rows carry `hidden_sha256` and `tree_sha256` (internal: digest of
   the committed starting repo; external: of the fetched base tree), so editing a bundle or a starting tree changes the
   manifest and its hash.
2. Per task: `task.json` (harness fields plus `kind, origin, trap, status, visible_expected, hidden_sha256, hidden_files
   {path: sha256}, tree_sha256`). Internal: `repo/` committed. External: `fetch.json` only (repo URL, base and fix sha,
   PR and issue, license, stars, non-test line count, dependencies, base-tree digest, the issue title and the sha256 of
   its body as fetched, dependencies, hidden test paths); the prompt must be exactly that title and body plus the one
   closing line. `source` is pinned to `<id>/repo` so `task.json` and `fetch.json` never enter an arm's tree.
3. Visible tests. External: the project's existing tests, which pass at the base commit (the pre-registered
   construction). Internal non-trap: one visible test fails on the starting tree for the task's headline behaviour and
   passes on the reference fix, so a retry-until-visible-passes arm has a signal; `verify` requires pytest exit 1 for
   that failure (never a collection error). OWNER DECISION, not made here: with the pre-registered external
   construction the matched-spend arm (A3) stops after its first attempt on every external task, because the visible
   suite already passes; the options are to accept that, or to add the issue's reproduction as a failing visible test
   on external tasks. Filed as a follow-up.
4. Hidden bundles only under the operator's hidden root: `files/` (overlaid at their own relative paths, so sibling
   fixtures still apply), `reference/` (internal), `hidden.json`, the generic `run_hidden.py`, `verify.json`; a trap's
   bundle also holds `obvious/` (the implementation that falls into the trap; hidden tests must fail on it),
   `expected_catch.txt` and `author.json`. Bundle digest = sha256 of sorted "path sha256" lines; per-file hashes are
   committed so CI sees a hidden file copied into the repo (files under 16 bytes ignored; the scan covers
   `evals/bench/`). With a hidden root, `check` also refuses hidden test names found in the starting repo or an
   internal prompt, a bundle for a task still awaiting its author (the harness would run the placeholder), and a
   ready trap without an author, expected catch and obvious tree.
5. One scoring environment. The harness resolves every task's argv on one PATH, so `lock` resolves the union of the
   external tasks' requirements plus pytest once (binary wheels only, scrubbed environment), commits the result as
   `environment.lock`, and binds its hash and the interpreter into the manifest. `verify --external` builds that
   environment from the lock and scores every task in it. This biases the pool toward projects that publish wheels
   for their test dependencies (stated).
6. `tools/readiness/bench_tasks.py`: `check` (static, hermetic), `verify` (internal offline, external over network
   into a scratch directory), `seal`, `build-manifest`, `lock`, `hidden-from-pr`, `materialize [--cache DIR]`,
   `manifest-sha [--rev]`. Scoring is the harness's own `_command_passed` and `_hidden_passed` behind a pass-through
   launcher with `isolated_env`; a second plain run must agree; the hidden run on the starting tree must exit with
   pytest status 1 (a collection error does not count as failing for the right reason); each run is in its own
   process group killed on timeout (and the runner is exercised in a child with its own deadline so a broken runner
   fails instead of hanging the suite). Third-party code (dependency install, project tests) runs under `clean_env`
   (no secret-shaped variables, fresh HOME and TMPDIR): a scrub, not a sandbox. POSIX only. The issue's limits are
   checked: at most 3 tasks per repository, at most 300 non-test lines, a task scores inside the harness's 600 s.
7. Traps: three `awaiting-author` slots (two spec contradictions, one plan defect; the owner may change the split)
   with a placeholder skeleton, and `docs/bench/trap-author-brief.md` holding only the pre-registration's
   definitions, the delivery format and the rules. A spec-contradiction trap's reference resolves it in the one
   direction `expected_catch.txt` states.
8. `docs/bench/task-sourcing.md`: queries, every candidate considered or rejected with its reason, the selected tasks,
   the measured verification (also committed as evidence under `docs/launch/evidence/` naming the base commit and the
   tool's hash), the cutoff and its source, and the exact freeze procedure.

## Test notes

Every test starts with an assertion that the tool and task files exist, so against origin/main each fails on an
assertion, not a missing import; that red proves only absence, so each guard's own control is a separate deliberate
break of the tool (step 4). The leak control copies bytes under a synthetic task (CI has no hidden root); the same
check runs over the real task directory in the first test. Network use is confined to `lock`, `verify --external`,
`hidden-from-pr` and `materialize`, none of which a test calls except against a local repository.

## Risks and limits (stated)

- Pool: eight external tasks were found from about 25 probed candidates (a convenience sample of libraries I named,
  not a draw from all repositories) and are verified only once `verify` has run in step 5; PR sizes 2 to 45 non-test
  lines, so a ceiling effect (all arms pass, almost all ties) is likely and no difficulty check was run: nothing
  claims these tasks discriminate. With four or fewer discordant tasks the pre-registered rule is always
  INCONCLUSIVE.
- Each result is one run: flakiness, network-denied runs and a real isolation launcher are not measured.
- The cutoff is a month; the rule date is the next month's first day. The owner's model pin is still open.
- External trees are fetched from a mutable remote: the base sha and tree digest are pinned, availability is not
  (mitigation: `materialize --cache`, and the freeze step keeps a copy).
- Verification ran under one CPython 3.12 on one macOS machine; the run-time environment must be built from the
  committed lock, which the harness does not enforce.
- An external task can be fetched by any arm with network access (the fix is public); the post-cutoff rule protects
  against model memory only, and containment is the launcher's job.
- An arm can write a `conftest.py` or pytest configuration that the hidden run then reads (the same for every arm;
  follow-up). Checks on external trees are local-only because CI has no fetched trees; the hidden-names checks
  apply to internal tasks only; exact-hash and name checks do not catch a paraphrased copy of a hidden test.
