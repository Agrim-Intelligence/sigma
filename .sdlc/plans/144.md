# #144 plan — refuse a net-destructive feature-branch replay before the push

Decisions (recorded; nobody available to ask):
- D1: a tree comparison, not history. Finding = the tip has a tracked path that the replayed head
  lacks (`git diff -M --diff-filter=D -z <tip> <replayed>`). Renames are excused. Plain upstream
  deletions are refused like reverts (research: the two are indistinguishable as trees).
- D2: stable outcome constant `WOULD_DROP = "would-drop"`. Evaluated in `_rebase_feature` right
  after the replayed head is read and BEFORE `_pushed`, so any later replay strategy or
  acknowledgement logic sits inside it (the outer guard).
- D3: fail closed. If the diff cannot run, the outcome is `FAILED` and nothing is pushed.
- D4: loud on every channel: the `IN_CLAUSE` wording ("was NOT rebased … would remove N tracked
  path(s) (a, b, c and K more)"), a tracked issue (slot `would-drop:<branch>`, key
  `<tip>#<count>`), CLI exit 1, and a per-unit marker `state/features/<unit>.rebase-blocked.json`
  that the doctor reads (dashboard row plus a failing `check` row only while blocked). The marker is
  removed on `current` or `rebased`.
- D5: the listing is capped at 20 (`DROPPED_LISTED`), 3 in the clause, and the count is exact.
