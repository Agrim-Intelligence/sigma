## 1. What changes, in one paragraph per gap

**Gap 1 (AC-1).** `sync.py` gets one kernel `flock` file, `.sdlc/state/ledger-sync.lock`, mirroring `_knowledge_lock`. Every code path that rebases, resets, aborts or creates the ledger worktree takes it: `publish` (a locked wrapper over a new unlocked body `_publish_ledger`), `pull`, `publish_receipt`, `_reroot_guarded` (ledger channel), and `publish_entry` around `_abort_stale_rebase` + `init` + re-root + publish. Tick callers (the watcher's `sync.py publish`/`pull`, `_ensure_ledger_delivery`, the Slack listener, `dag_lease`, `bootstrap`'s publish) take it NON-blocking and get a deferral string. `publish_entry` WAITS (polling `LOCK_EX|LOCK_NB` against the same shared deadline as its git calls) and then publishes; on timeout it prints `NOT published (another publisher holds the ledger worktree: pid N (verb), held Ns)`. The lock file carries a one-line holder record (pid, verb, start time) so a waiter can say who holds it and for how long. With `_abort_stale_rebase` now running only while the lock is held, a live rebase of another Sigma PROCESS is never aborted. A SIGKILLed holder's lock is released by the kernel and the next `publish_entry` clears the rebase it left. **Two limits the first draft overstated (review F3, F4):** (i) the `git` the holder started runs in its own session (`_run_git_bounded`, `start_new_session=True`), so a SIGKILL of the holder can leave a live ORPHAN git (and its `rebase-merge` directory) behind a free lock; the next publisher's abort can then meet a live git, and the likely outcome is an `index.lock` deferral, not loss (mechanism MEASURED, outcome reasoned; Section 0). (ii) "both entries reach origin" holds for the shape where each process appends once before it publishes; a process that APPENDS AGAIN while another's publish is running dirties a tracked file that the other staged (residual (a)), and that shape is not proved here.

**Gap 2 (AC-2).** `loop.py` arms ONE `atexit` hook, lazily, from the first `_mark_publish` of the process (D-3: no "is a `main` frame active" test and no depth counter). At exit it flushes every key that still has marks, through the same `_flush_pending_publish` `main` uses (so the same `publish_entry` gates apply), skipping a key whose `config.json` is gone without printing. `main` still flushes `argv[2]` and pops it, so after `main` the hook finds nothing for that key (a no-op, never a second publish), and it also catches every key `main` did not flush (a different directory, a symlink-spelled path, a second `loop` copy). `_PENDING_PUBLISH[...]` stays a list of strings (BR-22 pins it) but is capped per key, which closes the unbounded growth in the Slack listener (D-10). The hook keeps a STRONG reference to the module that armed it, deliberately: `work.py`'s stale-resume loads its own `loop` copy as a function local, and that copy's marks must survive until exit. The cost is in the test suite, not in production: `tests/conftest.py` gets an AUTOUSE FIXTURE (D-9) that wraps `atexit.register`, remembers any callable defined in `sigma-loop/scripts/loop.py`, and unregisters it at test teardown, so the suite's own in-process `_claim` calls neither publish at exit nor keep a dead `loop` copy alive per test (about 6 MB each, Section 0: 272 MB to 646 MB over 59 tests).

**Gap 3 (AC-3).** `ledger.py` stops asking `tempfile` for the directory. On POSIX the id lives in a fixed machine-level directory, `/tmp`, then `/var/tmp` (module constant `CONTAINER_ID_DIRS`, built by the pure function `_container_id_dirs_for`), file name unchanged (`sigma-container-<uid>.id`). `container_id()` reads EVERY candidate before writing one, so a reader and a writer that disagree about which directory they can write still agree on the id. **Exception (D-1b, review F7): on a non-POSIX platform `CONTAINER_ID_DIRS` stays `(tempfile.gettempdir(),)`, today's behaviour, so AC-3 ("does not depend on `TMPDIR`") is a POSIX / cloud-container guarantee and the docs say so.** `_container_id_path()` stays zero-argument (four tests patch it); when it is patched, only that path is consulted.

**Gap 4 (free).** `_bounded_git` returns a runner that carries its `deadline_at`; `publish` hands it to `_jitter_sleep`, which caps the pause at `max(0, deadline_at - now)`.

## 2. Decisions taken without the owner (each can be overturned at Plan-Review; the lever is the last column)

### Decisions a human may want to veto (read these first; each keeps the plan's choice and names its lever)

1. **D-4 / D-4a: no `fcntl`, or a filesystem whose `flock` is unsupported, FAILS OPEN, loudly (one stderr line per process).** This departs from AGENTS.md SAFETY ("refuse loudly rather than proceeding weakly"). Kept because a refusal would wedge the publish path the lock protects (a container filesystem without `flock` would defer EVERY publish forever, a worse outage than the race this goal closes), and the harm of an unserialised publish is exactly today's behaviour. The review finds this defensible. Lever: return a `publish deferred: no fcntl ...` string instead of `True` (D-4), and treat every `OSError` as held (D-4a).
2. **D-1 / D-1a: no adopt of the old id.** A container whose `TMPDIR` was not `/tmp` and that upgrades mid-life reads its own earlier claim as another machine's until the lease TTL lapses (default 12 h) or an operator runs `loop.py release`. Kept because an adopt would read `tempfile.gettempdir()`, which AC-3 forbids. Lever: a read of the old path inside `container_id()` (about 6 lines), after which AC-3 holds only for NEW ids.
3. **D-2: `publish_entry` waits up to 90 s and now queues behind unbounded tick callers** (`loop.py:234`, `slack_commands_listen.py:967/983/1015`, `dag_lease.py:121-122`; ticket T3). Lever: make `publish_entry` non-blocking (one `if`); then AC-1's second half needs the next flush.
4. **D-13: AC-1's "both entries reach origin" is proved for the single-append shape, not for a second append during another process's rebase** (review F4). `rebase.autoStash` is deliberately NOT added. Lever: D-13's last column.
5. **D-1b: AC-3 is a POSIX guarantee.** On a non-POSIX platform the id path still follows the temporary directory (today's behaviour, kept so a working id is not replaced by a constant).
6. **D-14 (the cut order).** If the revised plan proves too large, Step 3 (gap 2 and its test-suite fixture) is cut first and AC-2 is met by its documented alternative.

## 6. The five properties, explicitly

**RELIABILITY.** Claims in the docs carry the measurement that produced them (Step 4). Nothing is called working that only a stub run: the lock is proven with real `flock` in real processes (tests 13, 14, 26, 27), real git for the deadline (12) and for first creation (20), the exit publish from three real subprocess gestures including `work.py`'s own stale-resume caller (28), and the test-suite fixture by a real pytest subprocess (38). What those do NOT prove is named in the AC-1 row of Section 5 and in residuals (a) and (f). The not-measured list stays in the docs: a real container's filesystem, a real sandboxed shell's write access, the real-remote queue time, Windows. The smoke test is labelled a smoke test; its sensitivity is measured, not assumed. The one thing the review reproduced against this plan's FIRST draft (the suite-exit guard) is replaced by a design whose before and after were measured (Section 0).

**SCALABILITY.** The new ceiling is ONE ledger-worktree mutation at a time per checkout, enforced by one lock file that never grows. Numbers: a publish with one new entry took a median 0.236 s (max 0.255 s) against a local bare origin on macOS; a publish with nothing new, 0.095 s (the researcher's `latency.py`, one machine, NOT a real remote). The default `goals.max_concurrent` is 3, so the queue at 1x is about 0.7 s worst case. At 10x (30 verbs flushing together) the worst case is about 7 s if every waiter still has something new to push (30 x 0.236), about 3 s if the first publisher carried them all (30 x 0.095). At 100x (300) the worst case is about 71 s (300 x 0.236), which is inside the 90 s deadline only barely: past about 380 concurrent flushes at local-git speed the last waiters print `NOT published` and their entries ride the next flush. A real remote multiplies every term by its round-trip time and is UNMEASURED. There is no FIFO fairness: a waiter polls (0.05 to 0.1 s with jitter) and may lose several rounds; the deadline bounds it. Polling cost at 300 waiters is about 3,000 to 6,000 non-blocking `flock` calls a second in total, which is negligible but is named. `_PENDING_PUBLISH` is capped at 64 strings per key; the exit flush walks the keys once. A waiter also queues behind tick callers that have no deadline of their own (D-2, ticket T3), so the 90 s bound is on the WAITER, not on the holder. In the test suite the cost of the exit hook is memory, not time: one retained `loop` copy per marking test (about 6 MB each, 272 MB to 646 MB over 59 tests) is exactly what the D-9 fixture removes (281 MB measured with it).

**RESILIENCY.** Each failure and its recovery:

| Failure | Recovery |
| --- | --- |
| Holder SIGKILLed or the machine loses power mid-publish | the kernel drops the `flock` with the process (test 27 proves "free the instant it is killed"); the next `publish_entry` aborts the stale rebase and publishes (test 13, second phase, with a plain flock-holding child); a tick caller only defers. **Not "no sweep, no human" in every case (review F3):** the holder's `git` runs in its own session (`_run_git_bounded`, `start_new_session=True`), so SIGKILLing the holder frees the lock while an ORPHAN git can keep running (MEASURED mechanism: lock free, orphan alive, `rebase-merge` present). The next publisher's `_abort_stale_rebase` can then hit a live git; the likely outcome is an `index.lock` deferral, not loss (reasoned, NOT run; test 13 cannot show it because its holder has no git). Recovery is by retry: the orphan ends when its git command finishes or its remote call fails (a hung remote can take long: nothing bounds it once its parent is gone), and the next flush publishes. Lever for a git that does not end: end it, then `python3 sync.py publish .sdlc` (docs residual (f); ticket T7) |
| Reboot | same as SIGKILL for every holder; the lock file remains, empty or with a stale record that the probe-first rule never reports |
| Restore-from-backup of `.sdlc/state` | the lock lives in the kernel, not in the file's contents; a restored file is just a file. Deleting the file while it is held (`git clean -fdx`) admits a second holder on a new inode: the same stance as every other never-deleted flock file, stated in the docs |
| Lost ack (push landed, connection dropped) | unchanged by this goal: the next publish fetches, finds its commit already on the branch and answers published/nothing to publish; no new retry or lever |
| Waiter times out | prints `NOT published (another publisher holds the ledger worktree: pid N ...)`; the entry is on disk; the next flush (or `python3 sync.py publish .sdlc`) carries it. The lever is polite: it takes the same lock non-blocking and cannot stall anyone |
| Filesystem without `flock` | fails open with one stderr line (D-4a), so the new lock cannot wedge the publish path |
| Process exits normally with unflushed marks | the exit hook publishes them (bounded 90 s); SIGKILL / `os._exit` skip it: the entry is on disk and the next flush carries it |
| `.sdlc/state` cannot be created or the lock file opened | the verb returns its deferral (`publish deferred ... cannot take the lock: <error>`); never raises |

**SAFETY.** Nothing spawns, sends or consumes quota without the operator's opt-in. The exit hook makes processes that never published before (`work.py start`'s stale resume, `/sigma-scope` assign, the liveness-prune CLI) publish as they exit; it calls the same `publish_entry` `main`'s flush calls, which is gated by `ledger.enabled` and `ledger.publish_on_write` (the operator's opt-in) and, on a laptop, defers to a live watcher; the lock is a local file. No `SIGSTOP`. No secret enters a file, log or shell history: the lock record holds a pid, a verb and a time; the stderr lines carry no URL (they pass through `_scrub` where git text is involved). Limits derive from the machine or are bounded by the deadline: the poll interval and the 64-mark cap are small fixed numbers, not machine-sized resources. Where a guarantee cannot be made, the code says so loudly: the no-`fcntl` line and the non-POSIX id behaviour (D-1b) are documented, and **D-4 is flagged as the one decision that departs from "refuse loudly"**. The id file keeps mode 0o600 and the read-only-32-hex rule.

**LIVENESS.** A holder that has died is distinguishable from one with nothing to do because the lock is a kernel object: dead means free, and there is no state that can read "held" after the owner dies (test 27). A holder that is alive but wedged is distinguishable from a busy one by AGE: the waiter's timeout line prints `pid N (verb), held Ns`, and past 300 s (several times the 90 s `publish_entry` limit and the watcher's 120 s call limit) adds "end that pid and any git it started". The same record is readable without any tool by `cat .sdlc/state/ledger-sync.lock`, and an idle lock file is empty (test 25). The exit hook and the lock are not long-running components; the existing watcher heartbeat and `/sigma-doctor` row are untouched. No doctor check is added here (ticket T6 offers one). Revival is layered: a missed flush costs latency, never data (the entry is on disk; the exit hook, the next `loop.py` call, the watcher tick and `sync.py publish` are four independent triggers).

## 9. What could go wrong

1. **Self-deadlock from a nested acquire.** An `flock` is per open file description, so `publish_entry` holding the lock and then calling the locked `publish` would refuse itself. Mitigations: `publish_entry` calls the UNLOCKED `_publish_ledger` and `_reroot`; the locked wrappers are non-blocking, so a mistaken nesting returns a deferral instead of hanging; `publish_entry` itself is never nested (the flush calls it once per key, sequentially). Tests 21 and 22 pin both halves. On a filesystem where `flock` is emulated with per-PROCESS `fcntl` byte-range locks (some NFS), a nested acquire in one process would silently succeed and closing any descriptor would release the lock; none of our flows holds the lock across such a nesting, but this is why "flock on the container filesystem" is on the NOT MEASURED list.
2. **The `atexit` publish in the test process, and the memory it pins.** The suite loads a FRESH `loop` copy per test and calls `_claim`/`_record`/`_release` in-process in many files (about 448 test functions, the review's lower bound). `atexit.register(fn)` pins `fn.__globals__`, so each marking test would leave a dead copy's whole namespace alive until exit (MEASURED: peak RSS 272 MB to 646 MB over 59 tests, and `tests/conftest.py:120-127` records that a constant worker count already OOM-killed a 24 GB Mac) AND publish its marks when pytest exits (MEASURED: `ledger: published (claim of 10)` after `1 passed`). **The first draft's guard (a `pytest_sessionfinish` gc scan) did not work (review F1; Section 0).** Mitigation: the D-9 autouse fixture (unregister at teardown), with controls 38 (a pytest subprocess: no `ledger:` line, the dead copy's namespace is freed, other atexit callbacks untouched) and 39 (the opt-out). Residual: marks made outside a test function are not covered (none known); a library that caches `atexit.register` before the fixture wraps it would bypass the wrapper (`loop.py` calls `atexit.register` at call time; 38 goes red if that changes).
3. **flock on the container filesystem is unverified**, overlay and network mounts included. D-4a keeps an unsupported `flock` from wedging publishing; a filesystem that SILENTLY does not exclude would give back today's behaviour. Unmeasured; documented.
4. **A sandboxed shell that cannot write `/tmp` or `/var/tmp`** (dossier D-7). The pinned design handles the REVERSE disagreement (a process that cannot write the first directory but can write the second; readers see both). It does NOT handle neither being writable by one process while another can write: that process falls back to the kernel-derived id, which differs from the file's id. Documented as a residual, ticket T4. Unverified that `/proc/1/stat` is the same inside a sandbox PID namespace.
5. **Tests that patch `_container_id_path` or the shape of `_PENDING_PUBLISH`.** The seam rule (D-11) and "dict of lists of strings, capped at 64" are the compatibility contract; the BR-22 pin `== ["claim of 10"]` and the four patching tests are the guards. A future change that makes `_PENDING_PUBLISH` empty at mark time breaks the pin by design.
6. **A held lock turns a previously-published tick into a deferral.** The watcher's `sync.py publish` now defers (once) if a loop `publish_entry` is mid-publish, so a tick's pull or publish can slip 15 minutes. Cost: bounded latency, no loss. A short bounded wait for tick callers was considered and left out (D-2).
7. **The exit flush can delay process exit by up to 90 s** when the remote is down and keeps `work.py start` or `liveness_prune.py` from returning promptly; `main`'s flush has the same cost today. Ctrl-C interrupts it.
8. **The hook is armed in every process that marks, including one whose `main` flushes (D-3, review F2).** Cost: one `atexit` registration per `loop.py` process and an empty walk at exit; benefit: no mark is stranded by a key, a thread or a second `loop` copy that `main` did not flush. In the Slack listener (a long-lived, multi-threaded process that never calls `main`) the hook runs once at shutdown over a capped list (D-10). It holds a strong reference to the module that armed it on purpose (see item 12).
9. **Wall-clock test 12** can be flaky on a very slow or loaded machine; its margin is chosen from a measured gap, and its deterministic seams (9 to 11) are the system of record. The smoke test (26) can pass by luck on the unfixed code; it is demoted to a smoke test in its docstring and test 13 is the system of record.
10. **`write-surface` ratchet and growth-audit.** A new `fs-write` site without a row fails `check` in CI; Step 4 adds the rows from the scanner's own messages. The growth-audit gap is pre-existing (Section 0, item 3).
11. **Public repository.** No private deployment's name, path or count appears anywhere in the diff; the leak scan over the changed files is a Step 4 check.

12. **Retention in production (the price of the strong reference).** `work.py`'s `_load` re-executes a module on every call, so each `_stale_resume_refusal` call that marks creates a `loop` copy with its own flag and its own hook, and each such copy is kept until the process exits (about 6 MB each, the figure MEASURED for a test-time copy). `work.py start` is a short-lived command that calls it once per start, so the retention is bounded in practice; no long-lived caller of `_stale_resume_refusal` is known, but that was not exhaustively checked. A weakref hook would remove the retention and lose the mark, which is the AC-2 failure for exactly this caller (test 28, `work-stale-resume`).
13. **AC-3 is a POSIX guarantee (D-1b, review F7).** A non-POSIX platform keeps `tempfile.gettempdir()`, so there the id path can still follow the temporary directory. Cloud sessions are Linux containers and `container_id()` is read only under `cloud_session()`; the exception is stated in the docs and the PR body rather than papered over.
14. **A SIGKILLed holder with a live orphan git (review F3).** Mechanism measured (Section 0), outcome reasoned: the next publisher's `_abort_stale_rebase` can hit a live git; the likely result is an `index.lock` deferral, not loss. Test 13 cannot show it (plain flock-holding child). Docs residual (f), ticket T7, RESILIENCY row in Section 6.
15. **AC-1's second half has a named shape (D-13, review F4).** A second append by a process during another's rebase makes the other print `NOT published`; the entry is safe on disk. The PR body and the docs say the proof is for the single-append shape.
