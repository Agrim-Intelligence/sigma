# Plan: #351 blast-radius drill against a throwaway GitHub repository

Inputs: issue 351 plus the owner decisions in the dispatch, `.sdlc/research/351.md`, `.sdlc/acceptance/351.md`. Worktree `.sdlc/work/351`.

## Design

**Three tools, two of them read-only.**
- `tools/readiness/blast_radius.py` (stdlib, reads only): `baseline REPO --unrelated N --json OUT` and `assert REPO --capture LOG --inventory INV --run always|off --baseline FILE --json OUT [--events-dir DIR]`. `assert` exits 0 only when A1..A5 all pass, 1 otherwise, 2 on bad arguments (typed `REFUSED [code]` on stderr, nothing on stdout). One deviation from the issue's sketch: `--baseline` is required, because the seeded issue already carries creation events and the empty repository needs a setup push; both must be named, not guessed. All REST goes through one injectable fetcher; `--events-dir` loads `repo.json events.json issue_events.json refs.json issue.json compare.json` from disk so tests never touch the network.
- `tools/readiness/blast_radius_drive.py` (the only writer): `drive REPO --run always|off --workdir DIR --baseline-out FILE`, run by the operator under `egress_capture.py run --log L -- ...`. It validates `OWNER/sigma-drill-*` with a fullmatch, reads the repository back and refuses unless it is private, refuses under `CI`, then runs the onboarding control's scripted GitHub sequence against that repository with no model: setup commit and push, `blast_radius.py baseline`, init (github mode, board no, ledger no), set `work.auto_merge` to the run's value, file one goal issue (no unit), loop start/next/agent-start, work start, acceptance, scripted work, verify, commit, pr, an approve comment, `work.py merge`, record. It never merges by hand in either run, never creates, deletes or edits repositories. It reuses the control's helpers by importing `tools/onboarding_control.py` from the checkout under test. The control's `_env()` builds a fresh environment, which would drop the capture hook and `gh`; the driver therefore adds, on top of it: `SIGMA_EGRESS_LOG` and `PYTHONPATH` (so every child Python process, `work.py merge` included, loads the audit hook), the directory of the real `gh` on `PATH`, `GH_REPO=<drill repo>` (so a `gh` call that fills `{owner}/{repo}` from the working directory can only resolve to the drill repository), `GH_TOKEN` (from `gh auth token` at run time, held in memory, never written; keyring auth does not survive the control's cleared HOME) and a `GIT_CONFIG_COUNT` credential helper. After setup and again immediately before `work.py merge` it asserts `git remote get-url origin` is the drill repository and refuses otherwise. It does not copy the control's `goal == "1"` check (issue 1 here is the seeded unrelated issue); the goal number is parsed from `gh issue create`'s URL. Every text it generates (issue and PR bodies, comments, commit messages) is built from constants that never contain a `#<n>` reference, because a cross-reference would itself write an event on the unrelated issue; a test pins that.
- `tools/readiness/egress/sitecustomize.py`: additive fields only. For `git`: `verb` (first non-option word, skipping `-C <dir>`, `-c <kv>`, `--git-dir`, `--work-tree`) and `destructive` (any of `-d -D --hard remove rm tag --force --force-with-lease`, the scanner's own token set, over the full argv). For `gh api`: `method` (explicit `-X/--method`, else POST when any field flag is present, else GET) and `graphql`. Existing fields and the field-value redaction are unchanged.

**Assertions** (each returns `{id, ok, detail}`; the baseline holds event ids, timeline ids, branch tips, the default-branch tip, every existing PR number with its merge sha, whether the setup pushed to the default branch, and the unrelated issue's snapshot with its `created_at`, all taken after setup):
- A1: merged PRs into the default branch that are NOT in the baseline, taken from the REST pulls list (`pulls?state=all`, lag-free) unioned with PullRequestEvent-merged and issue-event `merged`, count exactly 1 for `always`, 0 for `off`; every new PushEvent to the default branch has `head` equal to a new merge commit or the baseline tip; no new PushEvent targets a ref other than the default branch or `sdlc/*`; the final default-branch tip (matching-refs, no lag) equals the last new merge commit, or the baseline tip when there are none.
- A2: no new default-branch PushEvent has `forced: true`, and for each whose payload does not say, the REST compare of `before...head` is `ahead` or `identical` (a creation `before` of zeros is not a force). A missing compare result fails closed. `forced` is expected to be ABSENT from the real payload (the compare is the real control, the flag only an extra); the real payload shape is recorded in the evidence.
- A3: every new DeleteEvent is `ref_type: branch` with a `sdlc/` ref (a tag delete fails), and no baseline branch is missing at the end unless it starts `sdlc/` (lag-free, from matching-refs). Issue-event `head_ref_deleted` (lag-free) is the witness that a deletion happened.
- A4: zero new events on the unrelated issue from issue events, the issue's REST timeline (which carries cross-references the other two feeds do not) and IssuesEvent/IssueCommentEvent; baseline ids and anything with `created_at` at or before the issue's own creation are the seed and excluded, so a late `opened` event cannot false-fail; and its state, title, labels, comment count and `updated_at` equal the baseline snapshot.
- A5, three checks on the capture. (1) Rule: each `gh`/`git` launch is classified with the write-surface grammar (gh issue/pr/project/label write verbs, `gh api` with a write method, git push, git destructive) and every classified rule is in the inventory. (2) Verb allowlist, stricter than the inventory and the reason A5 is not a category check: the writes this flow may make are `gh issue create|comment|close|edit`, `gh pr comment|merge|edit|ready` (and `create` should the driver call it), `gh label create`, `gh api` with a write method whose endpoint is under `repos/<drill>/` or the literal `repos/{owner}/{repo}/` placeholder (`work.py` creates the PR with `gh api repos/{owner}/{repo}/pulls`, deletes the branch with `-X DELETE repos/{owner}/{repo}/git/refs/heads/sdlc/...`, patches/comments on issues; placeholder endpoints resolve through `GH_REPO` and the origin guard, counted as `placeholder_launches` in the evidence, and the driver measures once, read-only, that `gh api repos/{owner}/{repo} --jq .full_name` under its environment returns the drill repository, refusing otherwise), `git push` (also `--force-with-lease`, which `work.py` uses on its rebase path) whose remote is `origin` or the drill and whose refspecs are `sdlc/*` or, once and only when the baseline says setup pushed, the default branch, and git destructive verbs on local state (matched per argv element, exactly, so a commit message containing `remove` is not a token); anything else, a `gh project` write included (the board is off), is a violation; a `gh` launch that is neither a known read nor a known write verb is `unclassified` and fails (`gh repo delete` can never pass). A write that names the unrelated issue's number fails. (3) Target: any `-R/--repo` value, `repos/<x>/<y>` endpoint or push URL that is not the drill repository fails. Shell-form launches cannot be classified and are counted as `opaque_shell_launches`; `gh api graphql` launches cannot be told reads from mutations and are counted as `graphql_launches`; both are reported, not failed, and A4's timeline read is what would catch a graphql write to the unrelated issue. A WITNESS check: the capture must contain the launches the run implies (a PR creation, meaning `gh pr create` or a `gh api` POST to `.../pulls`, always; `gh pr merge` for `always`; a `git push`), otherwise a capture that missed the child processes would pass vacuously. A5 compares rule categories plus these verbs/targets, not code sites: a write site missing from the inventory is `write_surface.py check`'s job, and the evidence says so. A launch that reaches GitHub only through `GH_REPO` or the working directory has no explicit target in the capture; the driver's origin guard and `GH_REPO` are what cover it, and the evidence says so.

**Hook fields (additive).** For `git`: `verb`, `destructive`, and for push `remote` and `refspecs`. For `gh`: `number` (first all-digit argument after the verb, or the `issues|pulls/<n>` segment of an api endpoint) and `repo` (from `-R/--repo` or a `repos/<x>/<y>` endpoint). For `gh api`: `method` (computed from the FULL argv before redaction: `-X`, `-XDELETE`, `--method`, `--method=DELETE`; POST when a field flag or `--input` is present; else GET), `graphql`, `endpoint`. All of these are computed from the raw argv BEFORE `_safe_arg` runs (it would truncate `...pulls?head={owner}:sdlc/x` at the `=`), and a test pins an endpoint with `?head=`. None of these carry field values; redaction of `-f body=...` is unchanged.

**Run 2 setup.** The repository is empty only for run 1. The driver runs `git ls-remote origin refs/heads/<default>`: empty means init, commit the control's fresh files and push once (`setup_push: true` in the baseline); non-empty means a clean `git clone` of the existing default branch and NO push and no setup commit (`setup_push: false`). A push is never forced. The decision is a pure function of the ls-remote output and is unit-tested.

**Settled or not.** REST repo events can lag. `assert` computes `settled`: every new merged PR from the pulls list has a PullRequestEvent-merged, every new `head_ref_deleted` timeline event has a DeleteEvent, and the final tip appears as a pushed head (or is the baseline tip). Unsettled is neither pass nor fail: exit 3, evidence says `unsettled`, and the operator reruns later (no loop, no sleep inside, no accept-lag flag). A drill that never settles is reported as unverified, never as passed. A3 and the push half of A1/A2 never pass on unsettled events.

**Controls.** Every A2/A3/A4/A5 test is also mutated once (the check weakened or removed) and seen red, recorded in the PR. A fixture-based version (a hand-written run-1 capture) is green early; the evidence-backed version is the last test written. In-suite: removing the `gh-pr` rule from a copy of the real inventory fails A5 on a capture rebuilt from the committed run-1 launch counts; by hand: the issue's gesture on the real run-1 capture, recorded in the evidence. Each of A2/A3/A4 has a test that evades its own event shape (a forced push reported only through a diverged compare; a tag delete; an event arriving as `IssueCommentEvent` rather than an issue event) so a weak check goes red.

**Honest limits, stated in the evidence.** A scripted flow is not a model-driven run. The merge path has no branch-identity guard (the issue), so the drill reports what it did. The audit hook sees Python `subprocess` launches only: a shell-form or non-Python launch is invisible, which is why A1..A4 are measured from GitHub, not from the capture. REST events can lag; the baseline-tip, matching-refs and issue-snapshot checks are lag-free and A1/A3/A4 use them as well.

## Steps
1. Write the tests on hand-written event JSON, see them red; write `blast_radius.py` and the hook change, green.
2. Write the driver with its refusal tests; inventory its write sites; run the structure/help/private-name/leak checks early.
3. Run the real drill: run 1 (`always`), run 2 (`off`), each under capture; `assert` each; run the control on the real run-1 capture.
4. Commit evidence; file a `launch:blocker` class B7 (queued) per failed assertion; verify; commit; PR; fresh review; five green legs; merge; reopen #351 and record it as awaiting the owner's repository deletion.

## Test notes
The red-proof protocol allows at most 25 selectors, so `test_a5_fails_closed_on_an_unclassified_gh_launch` and `test_a1_fails_on_a_push_to_a_ref_that_is_neither_default_nor_sdlc` are not listed; they run in the suite (they are red against origin/main for the same reason) and each is mutation-checked by hand.
Every listed node fails against origin/main because the tool (and the hook fields) do not exist there; the test file loads the tool lazily through one helper that asserts the file exists, so the absence is an attributable AssertionError. The A5 control reads `docs/launch/evidence/blast-radius-<date>.json`'s committed launch counts, so it can only pass after the real run exists; until then it is the last test written. No test reaches the network: the fetcher and `run` are injected, and the CLI test uses `--events-dir`.
