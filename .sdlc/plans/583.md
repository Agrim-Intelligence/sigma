# Plan: #583 make the tracked exposure scan usable as a gate without making it blind

## Design
An allowlist entry is scoped to CONTENT, never to a bare path and rule. It carries exactly one of:
- `blob`: the exact reviewed Git blob (existing form; any edit of the file turns it stale), or
- `lines`: the sha256 of every reviewed matched line (the whole of every line a multi-line match spans, so a key
  block is covered in whole), one hash per match, duplicates counted (a multiset).

For a `lines` entry the scan evaluates each (path, rule) in each blob:
- covered only if every match's hash is in the entry, counted. A new finding, a changed reviewed line, or one more
  copy of a reviewed line is NOT covered and is reported as a finding.
- the entry is live only if it equals the observed matches exactly; an edited or removed reviewed line makes it stale
  and the scan fails until re-triaged. An unrelated edit elsewhere in the file changes nothing.
- an entry with neither scope, both scopes, a malformed hash, a draft reason, or a duplicate (path, rule) is refused (exit 2).
  This closes the old blind spot where a path-and-rule-only entry hid any content at that path.
- history mode never applies the allowlist (a reviewed line at HEAD says nothing about an older blob of that path), so
  history findings are reported in full and stay triaged, not touched.
- new `--propose PATH` (tracked only) writes draft entries (path, rule, hashes, a draft reason) for uncovered findings. The
  draft is refused by the loader until a human writes the reason. Hashes never enter the evidence. This is the documented
  re-triage step: the operator runs it after a deliberate change, reads each row, writes the reason.

Failure modes (stated, accepted): content identity is the line text, so a line moved or re-indented elsewhere in the file
keeps its entry (same text, same value, acceptable); an identical line of identical text is the same finding by
construction. What a determined author CAN hide: a change that moves the dangerous value off the matched span while
leaving the matched text and line identical is impossible for single-line matches (the whole line is hashed); for rules that
match only a token (auth, credential-assignment) a secret on a NEIGHBOURING line that matches no rule is not seen by any
rule, allowlist or not, so the allowlist adds no blindness there; a reviewed line replaced by a different secret fails
(hash differs). A malicious reviewer who writes a false reason is the residual risk, as with any allowlist; every entry
names its reason in review.

## Refinements from plan review (round 1, SOUND-WITH-REFINEMENTS), all applied
- Tracked mode reads HEAD blobs but the allowlist from the working tree, so it now REFUSES (exit 2) a tree whose tracked files
  differ from HEAD: a verdict on a tree nobody committed is not a verdict.
- `--list-allowed` prints every finding an entry covers (rule, path, line, blob, redacted preview) so a reviewer reads what an
  allowlist diff hides; the PR review runs it.
- `--propose` also drafts the replacement of an entry whose reviewed lines were partly removed; a stale entry with no finding left
  is deleted by hand (documented). `--propose` refuses a path inside the repository or the evidence path (the draft holds hashes of
  possibly-real lines, so it is never committable).
- Measured on the old tool (origin/main tool, this test file): 13 nodes red, 12 green. The green ones (unrelated edit survives,
  removed finding is stale, CRLF/indent neutrality, another-rule finding, and the pre-existing tests) are regression guards and are
  NOT in the red selector. The real-tree test (acceptance item 3) is red on the old tool; its second control, new tool against the
  OLD allowlist, is run by hand and recorded.
- The history count without the allowlist is recorded as such (the allowlist no longer subtracts blobs in history mode).

## Refinements from plan review (round 2, SOUND-WITH-REFINEMENTS), all applied
- The default allowlist is read from HEAD (`git show`), never from the working tree; an untracked or edited copy cannot make a verdict.
  An explicit `--allowlist` stays for hermetic controls and is recorded as `explicit`.
- The report records the allowlist source, its HEAD blob and `covered_findings` (counts and a blob id, never a value or a line hash),
  so a green evidence file shows what the allowlist covered.
- Stated limits of "exit 0 means clean" that this change neither causes nor fixes (in the tool docstring): skipped blobs (over 2 MiB,
  or holding a NUL byte), an unterminated key block matches nothing, `legacy-issue-reference` is count-only, `private-pattern-N` names
  are line-number based (re-run the re-triage after that file changes), a hash of a short guessable line can be confirmed by guessing.
- The real-tree test skips without a `.git` and does not use the private-pattern file; the manual run at the launch commit with the
  private-pattern file supplied is the recorded control for acceptance item 1.
