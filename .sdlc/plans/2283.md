## Design decisions (each answers a research finding or a brief-vs-code conflict)
- D1 Constants. Add `MAX_BRANCHES = 50` and `MAX_CHANGED_FILES = 200`, each with the comment "a stated ceiling, not a measurement". `MAX_SECONDS = 120` already exists (declared for `rerun`); reuse it, never declare a second one, and extend its comment to say `inflight` shares it (research TD-4). Add `MAX_BLOB_BYTES = 1048576` for the `cat-file -s` check (equal to `MAX_CHARS`; own name because it is a byte count read from git, not a text cap).
- D2 Clock. The issue says `now` is the injected clock for the 120 s limit. Reading chosen: `inflight(sdlc_dir, goal, remote=None, base=None, run=None, now=None, clock=None)`. `now` is a callable returning seconds. When only `now` is injected, BOTH the deadline (`now() + MAX_SECONDS`, checked with `now()`) and the fetch age (`fetch_age(root, run, now)`) derive from it, so one injected clock drives the test. The deadline stays on `clock` whenever `clock` is given. `clock` is an optional extra: when given it drives only the deadline (the monotonic source `rerun` uses). With neither, `now` is `time.time` for the age and `time.monotonic` for the deadline. Verified: `rerun` keeps two clocks, so this is a deliberate narrowing; the PR notes state the reading chosen and the Task 0.2 note records it.
- D3 `base_ref` is shared, not copied (brief: "share that function"). It loads `work.py` internally, so the brief's "do not load `work.py`" can hold only for the own-branch lookup: read `<sdlc_dir>/state/work/<stem>.json` directly with `json.loads` and take `branch`. The stem is made the way `work.record_path` makes it; if that is not reachable without loading `work.py`, rebuild the stem with the same unsafe-goal refusal and have a test that the two agree (see test `test_inflight_own_branch_name_comes_from_the_work_record`). Recorded with `loop.py note`.
- D4 `--remote` vs `base_ref` (verified in its code: it takes no remote parameter, reads the remote from config and the work record, and prefixes an unprefixed `base` with the CONFIGURED remote, never with `--remote`). Exact behaviour: (a) `--base` given and `--remote` absent or equal to the configured remote: `base_ref(sdlc_dir, goal, base)` as is. (b) `--base` given and `--remote` differs: `inflight` prefixes the value with `--remote` itself (unless it already starts with `<remote>/`) and resolves that with `resolve_commit`, without calling `base_ref` (calling it would produce `<configured>/<remote>/<base>`). (c) no `--base` and `--remote` differs: take `base_ref`'s result and, since it is on the configured remote, print one `inflight: base <ref> is not on remote <remote>` note and continue. `base_ref` is unchanged. Tests through an injected `run` only (RU-4 is shared, not copied).
- D5 Remote and prefix: `work.remote` and `work.branch_prefix` from `state.load_config(sdlc_dir)` inside `try/except Exception` (a goal worktree's `.sdlc` has no config: use `{}`), defaults `origin` and `sdlc/` (work.py `DEFAULTS`). Validation reuses `state.safe_ref(key, value)` (as `work.settings` does) instead of a hand-rolled rule: it prints to stderr and returns the inert name for a value that starts with `-` or holds whitespace or control characters; `inflight` treats any changed value as refused and prints one line `inflight: <remote|branch_prefix> is not usable` on stdout, exit 0. An empty prefix is refused the same way (it would match every remote branch, including the base and checkpoints). Measured in a scratch repository: `refs/remotes/origin/sdlc` (no trailing slash) DOES match `sdlc/1` and `sdlc/2` by path component and not `sdlcx/4`; a partial component (`sdl`) and a name-start prefix such as `goal-` match nothing as a for-each-ref pattern, yet `goal-` is a legal prefix (work.py builds prefix + stem). So the prefix is NOT used in the pattern: D6 lists `refs/remotes/<remote>/` and filters in Python.
- D6 Branch list: `git for-each-ref --sort=-committerdate --format=%(refname) refs/remotes/<remote>/` through `_run_git`, then filtered in Python by `startswith(prefix)` on the display name (the refname with `refs/remotes/<remote>/` stripped; newest-first order is kept). The FULL refname is printed and the `refs/remotes/<remote>/` part stripped for display only. Verified in git: with a local branch named `origin/sdlc/1` and a remote-tracking ref of the same short name, `rev-parse --verify origin/sdlc/1` resolves the LOCAL branch (git warns `ambiguous`) while the full `refs/remotes/origin/sdlc/1` resolves the remote one. So `resolve_commit` is always given the full refname, never the short name. Skip the symbolic `<remote>/HEAD`. Only the full commit id travels on. A ref that does not resolve prints `inflight: <name> does not resolve` and is not counted in `k` (D7). Own branch: the record's `branch` field; with no record, BOTH `git rev-parse --abbrev-ref HEAD` in the goal's root AND `<branch_prefix><stem(goal)>` and its retry names `<branch_prefix><stem(goal)>-<n>` (verified: work.py names a retry `<branch>-2`, `-3`, ...; matched by exact name or `-` plus digits, so `<stem>-notes` is not skipped) are skipped, so a pushed branch of this goal is never reported as another goal's. Tests `test_inflight_skips_the_prefix_stem_branch_when_there_is_no_record`; control C27: drop the prefix-stem skip alone -> that test red compared with the display name; skipped before counting toward `n`. Test: `test_inflight_a_local_branch_named_like_a_remote_ref_does_not_shadow_it`.
- D7 What counts toward `<k> of <n>` (the one rule, applied in D6, D12b, D13 and the tests): `n` is the number of other-goal branches found after the prefix filter, own branch excluded, before the `MAX_BRANCHES` cap. `k` is the number of branches that were actually searched: cap not reached, time limit not reached, the ref resolved AND the diff succeeded. A branch whose ref does not resolve or whose diff fails prints its one line and is NOT counted in `k`. A branch with no changed files (after `--diff-filter=d`) succeeded and is skipped quietly; it counts in `k`. Test: `test_inflight_counts_only_branches_whose_resolve_and_diff_succeeded` (one unresolvable and one diff-failing branch through an injected `run`: `k` is `n` minus 2).
- D8 Diff: `git diff --name-only -z --diff-filter=d <base commit>...<branch commit>` (three dots, both resolved ids), split on NUL. Verified: without `-z`, git quotes a non-ASCII name (`"\303\251.txt"`) and it would silently never match. `--diff-filter=d` drops deleted paths (measured: a path added and deleted on the branch is not listed; a deleted dossier would otherwise give a `could not be sized` line for a file that does not exist at the branch tip, and a deleted file has nothing to search). A branch that only deleted files is skipped as having no files. After the split the names are sorted and the first `MAX_CHANGED_FILES` kept; over the cap prints `inflight: <branch> changed <n> files; searched the first <MAX_CHANGED_FILES>` (built from the constant; 200 at the default, as the issue says). A name holding a control character is filtered out before it reaches `git_grep` (it cannot be searched safely) and counted in a one-line note. Test: `test_inflight_searches_a_non_ascii_changed_file` (a changed file named with a non-ASCII character holding a match is found).
- D9 Queries and hits. Queries are read as `rerun` reads them: `parse_reuse(dossier_text(...))`, each query numbered by POSITION over the good queries and `bad_queries` together (exactly as `rerun`'s loop does), so `Q<i>` agrees with `rerun` and with the dossier, capped at `MAX_QUERIES`. Every query goes through the PATTERN part of `_query_problem` (length 1 to `MAX_PATTERN`, no control character; its path check is not applied, because the query's own paths are not used here). Verified: a NUL in an argv item makes `subprocess.run` raise `ValueError: embedded null byte`, which `git_grep` and `_run_bounded` (they catch only `TimeoutExpired` and `OSError`) do not catch, so an unchecked pattern would end the run with a traceback and exit 1. A bad query (unparsable or failing the pattern rule) prints ONE line `inflight: Q<i> skipped: <reason>` (once per run, before the branches, not once per branch) and the run continues; it is never passed to git. As a second layer `inflight` wraps each `git_grep`, `diff`, `cat-file` and `show` call in `except (ValueError, OSError)`, printing `inflight: <branch> <what> failed (<class>)` and continuing, so no exception escapes and the exit code stays 0 (the CLI's own exit-0 promise). `git_grep` itself is left unchanged. Empty path list guard (measured: `git grep ... <commit> --` with no paths searches the WHOLE tree and printed a hit from `main`): after the D8 control-character filter and the D23 directory filter, if the path list is EMPTY, every `git_grep` call for that branch is skipped; the branch still counts in `k` (its diff succeeded) and the declared-additions pass still runs. For each good query `i`: `git_grep(root, pattern, files, ref=<branch commit>)`; a hit prints `INFLIGHT <branch> Q<i> <file>:<line>: <text>` on one line. Per-query output is bounded by `MAX_HITS_PER_QUERY`; the whole output by `_capped`. A query that times out or errors prints the existing `TIMEOUT` / `ERROR` shape, prefixed `inflight: <branch> Q<i>`, and the run continues. "No recorded queries" means no good queries AND no bad queries (as `_source` decides); a goal with only bad queries prints the `skipped` lines and searches nothing but still runs the declared pass.
- D10 Declared additions (per-branch cap `MAX_PLAN_FILES_PER_BRANCH = 10`, a stated ceiling, not a measurement, with the same comment as the other caps; over it prints `inflight: <branch> carries <n> research or plan files; read the first 10`, the files taken in sorted order): when the branch's changed files include a `.md` file under `.sdlc/research/` or `.sdlc/plans/` (the two directories `dossier_text` and `check_plan` read), check its size with `git cat-file -s <commit>:<path>`; over `MAX_BLOB_BYTES` prints `inflight: <branch> <path> is too large to read` (the failed-call case prints `could not be sized` instead, a separate line, so a git failure is not reported as large) and the file is not read; else `git show <commit>:<path>`, `parse_reuse`, and print `DECLARED <branch> <id> <decision>: <capability>` for rows whose decision is in a frozen tuple `("extend", "dependency-new", "new")`. The tuple is checked against `DECISIONS` by a test so a renamed decision cannot silently drop out. Only table rows are read; a plan's bullets are never printed and never reach `parse_reuse` as queries (a plan's `## Reuse` text goes to `parse_reuse` whole; its `bad_queries` are ignored, only `rows` are used). A dossier without `## Reuse` prints nothing.
- D11 One-line quoted text: a new helper `_one_line(text, limit=200)` replaces every control character (including newline and tab), U+2028, U+2029 and the bidirectional override and isolate characters (U+202A to U+202E, U+2066 to U+2069) with a single space (test: `test_inflight_replaces_line_separators_and_bidi_overrides_in_quoted_text`) and cuts to `limit` characters, no ellipsis. `_shown` is left unchanged (every existing line uses it; research TD-3). Applied to the whole quoted text of every `INFLIGHT` and `DECLARED` line, the capability cell included. The branch name and file name in the line are also passed through it (a hostile ref cannot inject a line).
- D12c Output and declared-pass bounds (verified: `parse_reuse._table` caps no rows, so a 1 MiB table of `new` rows gives 33,821 rows and as many `DECLARED` lines; `_capped` only truncates a finished list and its notice reads `rerun: output stopped at ...`, wrong for this verb and left unchanged for `rerun`). New constant `MAX_DECLARED_PER_FILE = 25` (a stated ceiling, not a measurement): at most 25 `DECLARED` lines per dossier or plan, then one line `inflight: <branch> <path> declares <n> additions; printed the first 25` (built from the constant). The body is built through one small appender: once `MAX_OUTPUT_LINES` (1,000) lines are in it, nothing more is appended, one line `inflight: output stopped at 1000 lines` (built from the constant) is added, the loop ends, and the summary is still printed (the stop line and summary are not counted against the 1,000). The deadline is also checked between the declared-pass files, not only between branches and queries. Tests: `test_inflight_prints_at_most_the_per_file_cap_of_declared_rows_and_says_so` (a 1 MiB table of `new` rows; at most 25 `DECLARED` lines plus the notice; wall time stays bounded), `test_inflight_stops_appending_at_the_output_cap_and_still_prints_the_summary` (monkeypatch `MAX_OUTPUT_LINES` small), `test_inflight_stops_the_declared_pass_when_the_deadline_passes` (clock jumps between two files). Controls C28 to C30: remove the per-file slice, remove the output stop (the line count test goes red), remove the deadline check in the declared pass.
- D12 Time limit: `deadline = clock() + MAX_SECONDS` taken before the first git call. It is checked before each branch and before each query; at or past it, stop, print `inflight: stopped after 120 seconds` (built from `MAX_SECONDS`, not the literal), and still print the summary. Each git call takes its timeout from `min(GIT_TIMEOUT or QUERY_TIMEOUT, remaining)` as `rerun` already does for its queries.
- D12b A git failure or timeout on one branch's `diff` (or `rev-parse`) prints `inflight: <branch> diff failed (<first line of why>)`; that branch is NOT counted in `k` (D7), and the run continues with the next branch. A failure of the branch listing itself prints `inflight: could not list remote goal branches (<why>)`, then the summary with `0 of 0`, exit 0.
- D13 Summary (always the last line): `inflight: searched <k> of <n> goal branch(es) (cap 50); <h> hit(s); <d> declared addition(s); remote refs last fetched <age>`; `(cap 50)` is built from `MAX_BRANCHES`. `<age>` comes from a new `_fetch_age_text(seconds)`: `None` gives `never`; under 3,600 s gives `<n> minute(s) ago`; under 86,400 s `<n> hour(s) ago`; else `<n> day(s) ago` (integer floor; 0 minutes is `0 minute(s) ago`). `fetch_age` is reused as built (it takes the newer of the worktree and common-dir `FETCH_HEAD`, which differs from the brief's common-dir-only wording; it was measured in #2281; recorded as a note).
- D14 Two one-line cases. No remote goal branch (own branch excluded; if it is the only one, nothing else exists to search) prints exactly `inflight: no remote goal branches under <remote>/<prefix>` and no summary. No recorded queries (legacy goal: `queries_for` empty) prints `inflight: no recorded queries for goal <goal>`; see D15 for how it combines with branches.
- D15 Order. The branches are listed FIRST, so with no goal branches the no-branches line wins (FR-38: exactly one line, whatever the goal). With branches present and no recorded queries, the declared-additions pass still runs on every branch (a branch's declared `new` rows matter even without queries), the grep pass is skipped, and the `inflight: no recorded queries for goal <goal>` line is printed before the summary. The issue's two "print only" rules conflict for "branches exist and no queries"; this is the resolution, recorded as a conflict with `loop.py note` in Task 0.2 and stated in the PR. This DEPARTS from the issue's literal "print only" for the no-queries rule (the other "print only" is the no-branches rule, which is kept literally); the departure is stated in the PR notes, and the legacy-goal test asserts exactly this behaviour (the no-queries line, any `DECLARED` lines, then the summary; no `INFLIGHT` lines). Under `--at-research` a new-format dossier with `none:` has no queries, so it prints the no-queries line plus declared additions.
