# Plan: opt-in merge through the account's ruleset bypass (`work.merge_bypass: "ruleset"`)
**Goal**: #2092 · **Lane**: medium · **Acceptance**: `.sdlc/acceptance/2092.md` (AC-1..AC-6, unchanged)
**Verify**: `python -m pytest tests/test_work_merge_bypass.py -q`

One subsystem: `work.py merge()`'s landing path. Default off: every existing behaviour is byte-identical. When
`work.merge_bypass` is the exact string `"ruleset"`, a PR that `gate()` reports `BLOCKED` with nothing failing and
nothing pending (GitHub withholding the merge for a rule, which is the whole case #2090 measured) may merge by the
REST `PUT pulls/N/merge` carrying the vetted head sha, but only when four conditions hold. Anything unreadable
parks. Classic protection, a failing or missing required check, and a ruleset the account cannot always bypass are
never bypassed.

**Honest limit (stated in the docstring, the docs and the PR body):** whether GitHub's REST merge honours a
ruleset bypass for the cloud proxy's token is UNMEASURED (AC-5 stays open; the PR says `Refs #2092`). The tests
drive a fake GitHub and prove Sigma's reads, its decisions and its argv, never GitHub's behaviour.

## Decisions taken (conservative defaults; PROVISIONAL, owner to ratify)
- **D-1 setting.** `work.merge_bypass`, only the exact string `"ruleset"` enables it. Not in `DEFAULTS` (absent means
  off), not set in the template, never set by `tools/cloud/setup.sh`: the owner adds it by hand.
- **D-2 where it enters.** `gate()` stays strict (CLEAN only). It tags its "not a check problem at all" verdict with a
  named constant (`_WITHHELD`) so `merge()` can tell a BLOCKED-with-nothing-failing-or-pending PR from every other
  non-ok verdict without parsing prose. A failing check still goes to `ci_repair`; a pending check still waits and
  arms/parks as today; only the withheld shape reaches the bypass check.
- **D-3 order inside `merge()`.** The bypass check runs after the review gate (condition 3 is therefore known) and
  after the `auto_merge: off` return, BEFORE the protection stops (so a park names its condition instead of reading
  as "yours to make") and the merge. The later protection stops still apply to a bypass that passed.
- **D-4 the four conditions** (`_ruleset_bypass`, all REST, cheapest first, nothing read when the setting is off):
  1. every required context of the base (the rules read's `required_status_checks`) has a rollup entry for the exact
     vetted head that passed, and no check at all is pending or failing;
  2. `GET rules/branches/<base>` is a readable list below the 100-item page, non-empty, with no merge-queue rule,
     every rule carries an integer `ruleset_id`, classic protection answers exactly `Branch not protected`, and
     every distinct ruleset (at most 10) reads with `current_user_can_bypass == "always"`;
  3. the review gate passed (re-asserted here, not trusted from the caller), and when a ruleset requires approving
     reviews, `work.require_review` is not `off` (otherwise no review of any kind would have stood in for them);
  4. `mergeable` is `MERGEABLE`, and when a required-checks rule is strict (or does not say it is not), the head
     contains the base: `compare/<base>...<head>` reads `behind_by == 0`.
- **D-5 evidence.** The merge's ledger/journal `why` carries the bypassed rules; the merge line says so; the existing
  `gate=merge` action-log row reads `warn` (proceeded with a caveat), because the action log's gate names are a closed
  set and a new one would be a contract-vocabulary change (out of scope). After a confirmed merge one PR comment names
  the bypassed rules (fail-soft: a failed comment is named on the merge line, never turns a landed merge into a
  failure). The merge line still opens `PR #N merged (<method>)`, so the caller's routing is unchanged.
- **D-6 a refused bypass merge.** If GitHub's REST merge refuses (the UNMEASURED case) the existing PARK line is
  used with one added clause saying the ruleset bypass was attempted.
- **D-7 ceilings.** One bypass check costs 3 + (distinct rulesets, <= 10) + 1 REST reads, only on a BLOCKED PR with
  the setting on; at 10x/100x PRs per hour that is linear and bounded per PR. The rules read is one page (100); a full
  page fails closed.
