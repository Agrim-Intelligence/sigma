## Design

Reality at main: the false "85% coverage floor" README claim was already removed by #277; the README says CI
measures no coverage. Measured (research, run 2): **90.91%** line coverage of `skills/` and `hooks/`, coverage.py
7.16.2, Python 3.12.13, macOS, 37,806 statements, 3,436 missed, 11,569 passed.

The first plan added a floor of 85 on the ubuntu 3.12 leg. Its first CI run (research addendum) measured the cost: the
step took 3,154 s against 1,481 s plain (2.13x), the job 3,166 s of a 3,600 s limit, and one test with a 15 s
subprocess timeout failed under tracing before any Linux percentage printed. The acceptance criterion says to add a
threshold only if the runtime cost is acceptable. It is not, so the smallest correct change is:

1. `.coveragerc` (test-only, no `fail_under`): `source = skills, hooks`, `parallel`, `patch = subprocess`,
   `data_file`. It is the config the documented commands use; nothing in CI reads it.
2. `.github/workflows/ci.yml`: **unchanged** (reverted to main). No CI cost is added.
3. `docs/launch/coverage.json` (the record: tool, versions, python, platform, revision, commands, counts,
   `line_percent`, `enforced_in_ci: false`, `candidate_floor_percent: 85` explicitly not enforced, the Linux trial
   with its numbers and `line_percent_on_linux: null`, and the not-measured list) and `docs/launch/coverage.md` (the
   commands, versions, figures, the not-measured list, the trial and why it is not a gate, refresh, recovery).
4. `README.md` Dev/test paragraph: replace "CI measures **no** code coverage ... adding one is issue #194" with: CI
   neither measures nor enforces code coverage; a one-off local run gave last measured line coverage of **90.9%**
   (macOS, Python 3.12, understated, caveats named); the Linux trial doubled the leg and tripped a timing test, so it
   is not a gate; link to the doc. The claim names its platform and its own limits.
5. `tests/test_coverage_record.py` (new): the README's figure equals the record, the README still says CI neither
   measures nor enforces, the record's arithmetic adds up, `patch = subprocess` is present, and neither the rc file nor
   ci.yml contains a coverage enforcer (`--cov`, `fail_under`, `coverage run|report`, `pytest-cov`) while the record
   says nothing is enforced. The day a gate is added, the test is red until record, README and doc agree.
   `tests/test_readme_first_run.py` gains four `VERSION_ALLOW` entries (with reasons) for the measured tool, pytest,
   Python and Darwin versions the doc quotes; its existing coverage-claim guard is untouched and still holds.
6. CHANGELOG entry (names no docs/launch or tests path). A queued follow-up: a non-blocking scheduled Linux run that
   measures the figure and decides whether a floor is justified.

## Failure modes and recovery

- The record goes stale as code changes: the README says "last measured" with platform and revision; the doc's refresh
  gesture reruns the commands and the test names whichever of README or record disagrees. The number is a dated fact,
  not a gate, so staleness cannot fail anything or mislead beyond its stated date.
- Coverage tooling absent on a contributor's machine: nothing in the suite imports it; the guard reads files only.
- A later gate: adding any enforcer to ci.yml or `.coveragerc` turns the guard red until `enforced_in_ci`, the README
  and the doc are updated together (a partial claim cannot land).
- Nothing here spawns background work, sends data, changes a CI leg, or ships new runtime code.
