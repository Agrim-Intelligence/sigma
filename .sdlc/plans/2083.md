# Plan: Cloud --land: work.py merge parks whenever the base's CI outlasts the 450 s pending-check wait
**Goal**: #2083 · **Lane**: medium · **Research**: `.sdlc/research/2083.md` · **Acceptance**: `.sdlc/acceptance/2083.md` (AC-1..AC-4, unchanged)
**Worktree**: `.sdlc/work/2083` (branch `sdlc/2083`, base `6df8c2b9`) · **Verify**: `python -m pytest tests/test_work_merge_pending_wait.py -q`

One subsystem (the merge gate's pending-check path), one plan. Three behaviour changes plus their prose:
(1) the pending-check wait becomes `work.merge_pending_wait_s` (default 450, clamped); (2) with GraphQL refused,
a pending set that the base itself requires, on a repo that allows auto-merge, is armed through the CCR REST route
and the arm is CONFIRMED by a REST read-back before Sigma says `auto-merge armed`; (3) the not-armable cloud case
prints one instruction that landing.md repeats verbatim. The GraphQL-available path stays byte-identical.

**Honest limit, stated in the code docstring, docs/cloud-sessions.md and the PR body:** the CCR `PUT/DELETE
.../pulls/{n}/ccr/auto_merge` payload and reply are UNCONFIRMED (no occurrence in the repo; the only source is the
proxy's 403 text quoted in the issue). Tests prove our argv and our handling of fake replies, not the proxy. What
makes this safe without that confirmation is the read-back (D-5): the arm is reported only when `GET pulls/{n}`
(a documented REST field, already modelled by `tests/rest_merge_support.py`, see `tests/test_rest_merge_substrate.py:54-59`)
shows `auto_merge` set, with our merge method, on the vetted head. Anything else disarms (best effort) and parks.

## Decisions taken (defaults; each flagged for Plan-Review)
- **D-1 (AC-4 direction): "re-run work.py merge", never a bare `record parked`.** One instruction string,
  `_PENDING_PARK_INSTRUCTION` in work.py, used by the PARK line and copied verbatim into landing.md's bullet:
  `re-run work.py merge to wait again (work.merge_pending_wait_s sets how long one call waits); if the re-run returns this line too, record parked`.
  **D-1b (flag):** the trailing "if the re-run returns this line too, record parked" is the plan's addition: without
  it a required check that never reports (a workflow that never triggers) makes the loop re-run forever. It bounds
  the gesture at two calls (2 x the configured wait) and is the same words in both places, so AC-4 still holds.
  **Honest limit (RF-4), stated in the plan, in landing.md's bullet and in the PR body:** this bound is PROSE-ONLY and
  lives in the orchestrator's memory. It holds within one turn; a resumed or fresh orchestrator has no memory of the
  first call, so a never-reporting required check costs one extra full wait per resume (up to 2 h at the cap), and
  that is unbounded across resumes. No code enforces it. Machine bound, a follow-up for retro `Deferred roots`
  (not filed): record the head sha of the last not-armable pending PARK in the work record, and make a second
  same-head line end `record parked` in code.
- **D-2 (clamp):** `merge_pending_wait_s` accepts a real finite number (bool rejected); absent/invalid -> 450 (the
  constants' product, read at call time); `0 < v < PENDING_INTERVAL` -> 45; `> 7200` -> 7200 (`MERGE_PENDING_WAIT_MAX`).
  Rounds = `ceil(wait / PENDING_INTERVAL)`, interval stays the flat 45 s; the message reports the real
  `rounds * interval`. 10x/100x: at the 7200 cap one call re-reads the PR 161 times (one `view_pr_gh` + one rollup
  REST read each, ~322 REST calls per 2 h), and `merge_budget_seconds` at the cap is about 4 x 7215 + 615 s ~ 8.2 h,
  under `MAX_RUN_SECONDS` 86400. 7200 is a judgement (a 30-min CI x 4 margin), not a measurement.
  **Rate ceiling (RF-6):** one goal waiting at the cap costs about 161 rounds x 2 REST reads per 2 h, so about 161
  reads/h plus UNKNOWN retries. That is about 3% of a 5000/h primary REST limit, which puts the ceiling at about 30
  goals waiting concurrently on one token at the cap. This is a derived figure, not a measurement. It is named in
  `docs/configuration.md`'s row and in the template comment.
- **D-3 (sibling gate): stays on the constants (450 s).** Minimal; `_sibling_gate` (`work.py:7053-7056`) waits on a
  DIFFERENT repo's CI. Its comment "The SAME budget `gate()` spends" becomes "the DEFAULT budget gate() spends; it
  does not follow `work.merge_pending_wait_s` (#2083 D-3)". The docstring at `work.py:6913` keeps "450s".
  Follow-up, not filed: retro `Deferred roots`.
- **D-4 (when to arm; B1, RF-3):** arm only when ALL of these hold, ANDed, none standing in for another:
  (a) the pending-name set is non-empty; (b) every pending rollup entry has a name. **R1:** the shared builder
  is `_pending_check_names(data) -> (names, unnamed_pending)`. `names` is exactly gate()'s current list (the
  `and n` filter, work.py:4589), so gate()'s message stays byte-identical. `unnamed_pending` counts the pending
  entries with an empty or missing name/context. gate() and merge() both call it. An unnamed pending entry
  (no `name`/`context`, which `_pending_check_names` drops just as gate() does at `work.py:4589`) makes the PR
  NOT armable, because it could be a non-required check that `ci_required: true` says to wait on (RF-3);
  (c) `pending <= required`, where `required = c_checks | r_checks` from the same protection read `merge()`
  already does (`work.py:4846-4847`); (d) **`final_data["mergeStateStatus"] == "BLOCKED"`** (B1). This is GitHub's
  own verdict: `UNSTABLE` means only NON-required checks are failing or pending (`work.py:4581-4585`), so GitHub
  would merge that PR right now. (d) guards against protection() OVER-reporting (bypass actors, `evaluate`-mode
  rulesets: `work.py:4836-4840`), which is the unsafe direction here. (d) never replaces (c), because BLOCKED
  alone can mean a required review. Neither clause does I/O. `ProtectionUndetermined` already stops `merge()`
  before this branch (`work.py:7843-7849`), so an undeterminable set never arms; a test pins that order for the
  cloud path. An empty required set never arms.
  **Residual, stated in docs/cloud-sessions.md and the PR body:** a bypass-capable token may still see `blocked`,
  and whether GitHub's auto-merge honours that token's bypass is UNMEASURED.
- **D-5 (recognising the CCR arm; B2, RF-1, RF-5, RF-8, RF-9):** the PUT reply body is never parsed for success
  (it is the unconfirmed half). The read-back reuses `gh_api.view_pr_gh(api, pr, ["state", "mergedAt",
  "headRefOid", "autoMergeRequest"])` (REST first; an absent `auto_merge` key RAISES: `gh_api.py:1565-1566,
  1637-1650, 1710-1730`). There is no new reader. The outcomes are decided in this order:
  0. **How the PUT is sent (N1):** `arm_auto_merge_ccr` uses `gh_api._call`, not `_json`. Any 2xx counts as
     "sent" and the body is ignored, so a non-JSON 2xx body can never raise. When the PUT raises, the helper
     re-raises a `GhApiError` whose `.outcome_unknown` is `_merge_outcome_unknown(exc)` (gh_api.py:1455; the
     `merge_pr_gh` split). merge() reads it exactly as it already does at the direct merge:
     `getattr(exc, "outcome_unknown", True)`.
  1. **The PUT is DEFINITELY refused** (`outcome_unknown is False`: 401, permission 403, the proxy's 403, 404, 422,
     other 4xx, a proxy block, a primary rate limit) -> `PARK: could not arm auto-merge on PR #N via the cloud REST
     route (<exc>)` (same opening as `work.py:7883`). No merge and no read-back: nothing was armed.
     **The PUT raises with an UNKNOWN outcome** (5xx, timeout, transport failure, anything unclassified) -> it does
     NOT park here. It goes on to the read-back, outcomes 2-8, exactly like a 2xx, so an arm that took effect is
     confirmed, reported merged, or disarmed and parked, and is never left live under a parked goal.
     `<exc>` rides along: every unconfirmed PARK reached this way says `PUT outcome unknown (<exc>)`.
  2. The read-back raises or is malformed -> best-effort DELETE, then the unconfirmed PARK with why `read-back
     unreadable: <exc>`.
     **Bounded re-read (R4):** outcome 5 (open, no `auto_merge` yet) does not disarm on the first read. The PR is
     re-read once more after `RECONCILE_PAUSE` (5 s), so at most 2 reads, and only the second read's answer is
     acted on. `merge_budget_seconds` adds `RECONCILE_PAUSE` for it. How often the arm shows up late is UNMEASURED,
     and it could make the cloud arm park on most runs in practice. That is stated beside the UNCONFIRMED label.
  3. **The read-back shows MERGED (B2, N3)** -> no DELETE and no `merge-armed` row. On the REST path,
     `view_pr_gh`'s `state` is DERIVED from `merged_at` (`_pr_state`, gh_api.py:1574-1576), so the check is
     `state == "MERGED"`. A `mergedAt` check is kept as a belt and is documented as redundant on REST, not proven.
     It returns `PR #N merged when auto-merge was armed, before the pending checks (<names>) answered — WARNING:
     GitHub did not hold it on them; <gate_detail>`.
     **Why `record review` and not `record done` (R5):** `record done` would ACCEPT a MERGED PR (`done_refusal`
     passes, work.py:4968-4971), so this is not a safety refusal. The line deliberately does not start
     `PR #N merged (` so that the merge-reconcile pass owns the close. That pass is the same path that records
     every armed landing, and it carries the WARNING into the recorded outcome instead of a plain "merged". It
     also keeps this unexpected landing on the one path that reads the issue state afresh. landing.md gets its own
     bullet routing it to **`record review`**.
  4. **The read-back shows CLOSED and not merged (B2)** -> `PARK: PR #N was closed while auto-merge was being armed
     (not merged); reopen it or merge it by hand`. No DELETE: a closed PR holds no live arm to remove.
  5. Open, and `autoMergeRequest` is not a dict on the SECOND read (R4) -> DELETE, then PARK with why
     `no auto-merge on the PR after the PUT`.
  6. Open, and `headRefOid != vetted_head` -> DELETE, then PARK with why `armed on <head7>, not the vetted <vetted7>`.
  7. Open, and `autoMergeRequest.merge_method` (compared case-insensitively) `!= method` -> DELETE, then PARK with why
     `armed with <got>, not <method>`.
  8. Otherwise: confirmed. Write `merge-armed`, then return the `auto-merge armed …` line.
  The unconfirmed PARK is `PARK: auto-merge arm on PR #N could not be confirmed (<why>); disarm <sent|failed:
  exc> — a disarm also removes an auto-merge a human armed on this PR (RF-8); check the PR's auto-merge by hand`.
  Each `<why>` is a distinct clause, and each test asserts its own (RF-2).
  Payload fields (UNCONFIRMED, one module constant in gh_api): `-f merge_method=<method> -f sha=<head>`, mirroring
  REST `PUT pulls/N/merge` (`gh_api.py:1233-1239`) because the route lives under the REST path tree. The sha is
  validated with `_HEAD_SHA_RE` (40 or 64 hex, `gh_api.py:1450`), as `merge_pr_gh` does. It is not validated with
  either of the two `_SHA_RE` definitions (`1250`, `1799`; both 40-hex only), which would stop a SHA-256 repo from
  ever arming (RF-5).
  **Head-pin residual (RF-9), stated beside every UNCONFIRMED label:** even if the proxy honours `sha`, a later push
  by a write-access user keeps a GitHub auto-merge armed. That is the same residual `--match-head-commit` has on
  the GraphQL path.
- **D-6 (wait scope):** the key sets `gate()`'s wait on every path (GraphQL or not), because `gate()` runs before
  `merge()` knows whether it can arm. With GraphQL a larger wait only delays an arm GitHub would hold anyway.
- **D-7 (budget):** `merge_budget_seconds(config=None)`; `None` keeps the constants-only formula
  (`tests/test_long_call_receipts.py:518-541` passes unchanged); `merge_with_receipt` passes `config`, so the
  receipt deadline and `wait-call` follow the configured wait. With a config, the budget also adds one
  `RECONCILE_PAUSE` for the R4 re-read of the PR after the CCR PUT.
- **D-8 (order in the cloud branch):** clauses are evaluated cheapest-first: GraphQL unavailable -> pending
  non-empty -> no unnamed pending entry -> pending subset of required -> `mergeStateStatus == "BLOCKED"` (none of
  these do I/O) -> `_auto_merge_allowed` (one REST read) -> CCR PUT -> read-back. So a non-required pending set, or
  an UNSTABLE PR, still never reads `allow_auto_merge` (an existing assertion kept). The not-armable PARK's reason
  names the first clause that failed: `not required by \`main\`: <names>` | `a pending check has no name` |
  `GitHub reports mergeStateStatus=<s>, not BLOCKED: it does not hold the merge on them` |
  `the repository does not allow auto-merge`.
- **D-9 (AC-2 scope; RF-7, R6):** AC-2 is read as the CLOUD path (GraphQL refused). The plan, the PR body and
  docs/cloud-sessions.md say so. **This reading is NOT settled:** AC-2 as written is host-unscoped. The PR body
  asks the owner to confirm the reading explicitly. It also gives the one-line alternative: apply D-4(d), the
  BLOCKED clause, to the `--auto` arm at work.py:7879-7882 too, which relaxes BR-19. On the laptop path (GraphQL available), `--auto` is still armed for a
  NON-required pending set, which GitHub lands at once, before CI answers.
