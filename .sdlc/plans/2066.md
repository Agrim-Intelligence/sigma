# Plan 2066: approve the verify command once per environment, bound to its repository and exact command

Goal: an operator approves a repository's verify command once per environment (for example a Claude Code cloud
environment) instead of once per checkout. They set one value in the environment's own settings:
`SIGMA_TRUSTED_VERIFY_SHA256=<approval value>`, the sha256 of the repository's identity plus the exact command.

The value grants the verify path only, and only while every command that path is about to run, in this
repository, gives that value. Every failure refuses, and the git-local grant is unchanged.

## Exposure

**What a wrong grant lets run.**
- Everything `loop.py verify` already runs after its trust gate, in every checkout in that environment whose
  repository and command match `[S7]`:
  - the approved command string, in its own shell (with `{workers}` replaced by an integer when the resource
    guard is on, `resource_verify.py:90-94`; the value covers the declared string, before substitution);
  - the goal's planned tests through Sigma's fixed argv: collect-only, the planned run, flake re-runs, the
    diff-revert run and the witness run (`red_green.py:184`, `flake_check.py:144`). A selector with a leading `-`
    is refused (`red_green.py:89-92`).
  - `loop.py red` runs that same planned-test argv.
- The value binds the command TEXT and the repository NAME, not what the text executes. `bash scripts/verify.sh`
  runs whatever `scripts/verify.sh` holds on the branch being verified. pytest runs that branch's `conftest.py`,
  tests and plugins, with the checkout as its working directory. A branch that edits those files runs under the
  approval. The git-local grant has the same property and binds no command at all: running a repository's tests
  means running its code.
- What a branch CANNOT change and still be trusted: the command string, whether `verify.command`, a goal's
  frontmatter `verify_command` or an acceptance record's `verify_command`. Those are refused.
- Repository identity is the `origin` remote's last two path segments, lower-cased (`owner/name`). It is `origin`,
  not `work.remote`, because `work.remote` comes from `.sdlc/config.json` (repository input) and `origin` is set by
  the clone `[R13]`.
  - It is read with `git config --local --get-all remote.origin.url`, never `git remote get-url`. `--local` ignores
    `url.*.insteadOf` and global, system and environment-injected config; more than one value gives
    `no-identity` `[N1]`.
- **Git's own environment cannot steer Sigma's reads** `[N1]`. A committed declarative `env` block can set
  `GIT_*` too. Measured by the re-check:
  - `GIT_INDEX_FILE` hides the tracked file;
  - `GIT_WORK_TREE` points the file read at a decoy;
  - `GIT_CONFIG_PARAMETERS` with `insteadOf` spoofs the identity;
  - `GIT_DIR` reads another checkout.

  So:
  - every git call in the environment check runs with an environment that drops every inherited `GIT_*` variable
    and sets `GIT_CONFIG_GLOBAL=<devnull>` (precedent `feature_upkeep_launcher.py:694`). That also neutralises the
    pathspec variables (`GIT_LITERAL_PATHSPECS` and others), which would otherwise turn `:(top)` into a literal and
    find nothing.
  - **Revision 5:** system config stays ON. It is admin-owned, and a repository cannot write it (`GIT_CONFIG_SYSTEM`
    is among the dropped variables). A container that marks the checkout safe in `/etc/gitconfig`
    (`safe.directory`) keeps working; one that does so only in `~/.gitconfig` reads as `no-identity`. That is
    named in Risks and the docs, and `-c safe.directory=*` is never used;
  - and, as `bounded_run` does (`bounded_run.py:106-108,121-123,466-468`), a location variable (`LOCATION_VARS`:
    `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`,
    `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE`, `GIT_PREFIX`) set in the process environment refuses
    (`location-variable`, names only). The verify command itself would otherwise run git against another
    repository.
  - The set is duplicated in `shell_policy`, which stays standard-library only and cannot import `bounded_run`
    (that module imports `shell_policy`). A test pins the two equal.
  - Not changed here, named as a follow-up: the unchanged git-local read (`shell_policy.py:29-36`) still honours
    an inherited `GIT_DIR`.
  - A different repository opened in the same environment with a byte-identical command gives a different value
    and is refused `[S1]`.
  - An agent that rewrites `origin` to the approved name defeats this. That is the same class as an agent
    exporting the value itself.
- It never grants the other repository commands the git-local opt-in gates. A test pins this, and a ratchet pins
  that only `loop.py`, `doctor.py` and `init_flow.py` call the new predicate `[R11]`. Those commands are:
  - pipeline checks, `review.command`, a custom `knowledge_graph.builder`, `autowatch.drive_cmd`,
    `backlog_check.embed.command`, `.sdlc/risk-detect.conf`;
  - the unit-landing and upkeep rehearsal (`bounded_run.run_verify`), `sigma-rebase`'s verify, and the
    sealed-acceptance PR gate.

**Who can set it.**
- Intended: the operator, in operator-owned environment configuration. For a Claude Code cloud environment that is its
  environment-variables panel at claude.ai/code, which only the owner edits. Everyone using the environment can
  see the value; it is a hash, not a secret.
- **A repository can fill the process environment from committed files** `[S2]`. Sigma refuses the environment
  approval (`repository-sourced`) when a TRACKED file at one of the host's declarative environment-config paths
  names the variable `[B1]`:

  | Path (from the repository top, `:(top)` pathspecs `[B2]`) | Loader |
  | --- | --- |
  | `.claude/settings.json`, `.claude/settings.local.json` | Claude Code `env` |
  | `.devcontainer.json`, `.devcontainer/devcontainer.json`, `.devcontainer/*/devcontainer.json` | devcontainer `containerEnv` / `remoteEnv` |
  | `.vscode/settings.json` | VS Code `terminal.integrated.env.*` |
  | `.env`, `.envrc` | dotenv loaders, direnv |
  | `mise.toml`, `.mise.toml`, `mise.local.toml`, `.mise.local.toml`, `.config/mise.toml`, `.config/mise/config.toml` | mise `[env]` |
  | `.codex/config.toml` | Codex `shell_environment_policy` |

  - The check runs in the verify tree, the project root and the main checkout. The main checkout is found with
    `rev-parse --path-format=absolute --git-common-dir` (precedent `bounded_run.py:445`); a bare main repository
    is skipped `[R3]`.
  - Each root is listed with one `git -C <root> ls-files -s -z --full-name` call. The call carries both the
    `:(top)` pathspecs and the same paths relative to that root, because a project whose `.sdlc` sits in a
    subfolder was probably launched there `[R4]`.
  - **Revision 5, C1:** the listing also carries each parent directory of the list as an exact pathspec
    (`.claude`, `.devcontainer`, `.vscode`, `.config`, `.config/mise`, `.codex`). An entry at a parent-pattern
    path (`.devcontainer/*` included) that is a symlink (`120000`) or gitlink (`160000`) refuses. Other entries
    under those directories are ignored unless they match a listed path.
  - **Revision 5, C3:** each root's `--full-name` listing is joined to that root's own toplevel, from one
    `rev-parse --show-toplevel` per root.
  - Every listed path is joined to the absolute `--show-toplevel`. A resolved path outside the toplevel refuses.
    From a subdirectory, a relative `../../.claude/settings.json` could otherwise reach the user's own
    `~/.claude/settings.json` `[N2]`.
  - A listed entry that is a symlink (`120000`) or gitlink (`160000`), or whose working-tree path is not a regular
    file, refuses `[B4]`.
  - Each file is read (at most 1 MiB; larger refuses) as UTF-8, where invalid bytes refuse. `\uXXXX`, `\UXXXXXXXX`
    and `\xNN` escapes are decoded, so a JSON or TOML key written with escapes is still seen `[B4]`. The text is
    searched case-insensitively for the name.
  - A git call that fails or exits with any code but success refuses `[B3]`.
  - Out of scope, and named as residuals in TM-04 and the docs:
    - **code-execution loaders**: hooks (`.claude/hooks/**`, a SessionStart hook writing `$CLAUDE_ENV_FILE`),
      setup scripts, CI workflows, and an `.envrc` or `.env` that builds the name at run time. A host that runs a
      repository's code has already given it code execution, so the approval adds nothing there. A CI job's
      environment is set by repository workflow files, so the docs say never to rely on the environment
      approval in CI;
    - **a host that loads env from any other committed path**, including the declarative indirections that load a
      file named inside a listed one: mise `env._.file`, a devcontainer `--env-file` run argument, compose
      `env_file` `[N6]`;
    - **a worktree the host was launched from that is none of the three roots** `[R4]`.
- Also able, and indistinguishable to Sigma: anything else that controls the Sigma process's environment. That
  includes an agent exporting it in its own shell, a shell profile, a CI job's env, a setup script. The same
  weakness exists for the git-local grant, which an agent can also type.
- **The doctor, which an agent may run, prints the exact value to set** `[R12]`. The friction below therefore
  makes an agent self-grant deliberate and visible; it does not prevent it:
  - the docs and TM-04 state the operator-versus-agent ceiling;
  - the doctor's hint says "never an agent";
  - no agent-read prose names the variable, including `AGENTS.md` and `CLAUDE.md` (a ratchet) `[S10]`;
  - the loop's refusal never prints the value `[S8]`;
  - every verify records which source granted it, in its evidence `[S10]`.
- An explicit git-local `false`, or a git-local value git cannot read as a boolean, vetoes the environment
  approval for that checkout `[S1 fallback]`. It is a deliberate operator "no", and the environment value never
  overrides it.

| | git-local grant (unchanged) | environment approval (new) |
| --- | --- | --- |
| commands it grants | every repository-configured command in the checkout | the verify path only, every declared command, approved strings only |
| reach | one checkout and its linked worktrees | every checkout of that `owner/name` in the environment |
| survives a changed command | yes | no: refused until the operator sets the new value (a hard cutover across containers `[R9]`) |
| outside a Git worktree, or with no `origin` | never | never (`no-identity`) |
| who can set it | anyone with a shell in the checkout | anyone controlling the process environment; refused when a tracked declarative host-config file names it |

## Alternatives rejected

- **Global git config** (`git config --global sigma.allowRepositoryShellCommands true`). Not bound to any
  repository or command, and it trusts every repository on the machine for every command kind. A fresh
  container's `~/.gitconfig` is not set by the environment panel, so it would need an in-container act, which is
  what we are removing. Sigma reads `--local` deliberately (`shell_policy.py:31`).
- **A trust file in `$HOME` written by a setup script.** A new persisted source of truth, with its own permissions,
  symlink and staleness failure modes. It is written by code running in the container, which an agent can write
  too, so it is no stronger than an environment value. If the repository supplies the setup script, the
  repository authorizes itself.
- **Trust committed in the repository.** The repository authorizing its own shell command is exactly what #422
  forbids (`shell_policy.py:3-11`), and any branch or PR could grant itself. `repository-sourced` refuses the
  declarative environment-file form of this.
- **A bare boolean environment variable** (`SIGMA_ALLOW_REPO_SHELL=1`). Not bound to the repository or the
  command, so a PR that changes `verify.command` to anything runs. It also invites widening to every repository
  command.
- **The sha256 of the command alone** (revision 1). Any repository in the environment with the byte-identical
  command would be trusted `[S1]`. Replaced, by owner decision, with the repository-bound value.
- **Two values at once**, for a cutover when the command changes `[R9]`. The owner's brief says several values
  refuse. Documented as a hard cutover; widening it would be an owner decision for a later goal.

## The value

`approval_value(identity, command) = sha256("sigma-verify-approval/v1\n" + identity + "\n" + command)`, as lowercase
hex over the UTF-8 bytes. A known-answer test pins it `[R2]`.

`identity` is the lower-cased `owner/name` of the single local `remote.origin.url` value: its last two path segments, after
`github.com:` or `github.com/` and an alias `host:`, with `.git` stripped. It must match
`\A[a-z0-9_.-]+/[a-z0-9_.-]+\Z` and must not be `.` or `..` in either part `[R1]`. The identity is only ever
hashed, never used as a path or a key, so the permissive class is safe. The remote URL itself is never printed,
because it can carry a token `[R13]`. A parity test against `feature_sync._slug_from_url` is rejected `[R13]`. The
two diverge on purpose: this parser lower-cases, and it accepts `_` and `.` as a first character, which a registry
key there must not.

The domain prefix means a value made for any other purpose can never match.

The operator gets the value from Sigma, never by hand-hashing `[S4]` `[B6]`:

```
python3 -I <installed-sigma>/skills/sigma-doctor/scripts/doctor.py verify-approval .sdlc
```

Run from the repository root, it prints `repository: <owner/name>` and `SIGMA_TRUSTED_VERIFY_SHA256=<value>`, and
tells the operator to inspect `verify.command` in `.sdlc/config.json` before approving. It never prints the
command. `-I` keeps the current directory, `PYTHONPATH` and the user site off the import path, so a planted
`json.py` or `hashlib.py` in the repository is not imported. A test runs the documented text with planted modules
and `PYTHONPATH=:` to pin this. `/sigma-doctor`'s failing trust row prints the same value.

## The decision, evaluated once `[R5]`

`verify_decision(path, commands, environ=None, roots=()) -> Decision(source, reason, detail)`:

1. git-local first, through `repository_shell_commands_allowed` by module-global name: `source="git-local"`. The
   four tests that monkeypatch it keep working (`test_d7_refusal_fixes_work.py:239`,
   `test_resource_mode_resolver_1759.py:84,103`, `test_work.py:7074`).
2. Otherwise `environment_approval(path, commands, environ, roots) -> (reason, detail)`, which is total (any
   exception gives `error`). In order `[N4]`:
   1. read the variable from `os.environ` directly: `unset`, `empty` or `malformed`. **Nothing spawns when it is
      unset.**
   2. `no-command`.
   3. a location variable set: `location-variable` (detail: the names). Nothing spawns.
   4. `rev-parse --path-format=absolute --show-toplevel --git-common-dir` in `path`; a failure gives
      `no-identity` (not a Git worktree).
   5. the veto, with one `git config --local --type=bool` read:
      - exit 0 with `false` gives `vetoed`;
      - exit 0 with `true` continues (git-local already said no, so only a test double gets here);
      - exit 1 (unset) continues;
      - exit 128 (not a boolean) gives `vetoed`;
      - a timeout or `OSError` gives `error`.
   6. identity, `config --local --get-all remote.origin.url`: none, several or unparseable gives `no-identity`.
   7. `repository-sourced` across the roots (detail: the tracked path, JSON-escaped when printed); a failed listing
      gives `error`.
   8. `mismatch` or `match` (detail: `owner/name`).

   Steps 4–7 use the scrubbed git environment `[N1]`.

`verify_refusal_message(decision)` is built from that same decision. When the reason is `unset` it is
byte-identical to today's `refusal_message()`; otherwise it appends one clause naming the reason (and the tracked
file for `repository-sourced`). It never includes the variable's value or the value to set.

## Test list

Fixtures: a git repo whose `origin` is `https://github.com/Owner/Repo.git`. The variable is set through `environ=`
or `monkeypatch.setenv`. The retired-prefix name is built from fragments (`("LOOP" "SMITH") + "_"`, as
`conftest.py:270` does) `[R13]`.

1. Known answer: `approval_value("owner/repo", "bash scripts/verify.sh")` equals a fixed hex literal `[R2]`.
2. The value for `owner/repo` and the exact command grants, with source `environment` and git-local unset.
3. After the command changes, the old value gives `mismatch`.
4. Unset, empty, uppercase, 63 or 65 characters, leading or trailing space, trailing newline, and non-hex values refuse, each with its reason. When unset, `environment_approval` spawns no subprocess (`subprocess.run` patched to fail; `verify_decision` spawns the git-local read by design) `[N5]`.
5. Several values joined by `,`, ` `, `\n` or `;` refuse (`malformed`) even when every part matches.
6. Every command must match: `[repo_cmd, goal_cmd]` with the repo command's value refuses (`mismatch`); `[]` and `[""]` refuse (`no-command`).
7. Any exception refuses: a lone-surrogate command, or `None` as commands, gives `error`.
8. Identity:
   - a different `origin` gives `mismatch`; no `origin`, or a non-git directory, gives `no-identity`;
   - SSH, HTTPS, a `.git` suffix and a proxy-style URL (`http://proxy@127.0.0.1:1234/git/Owner/Repo`) all give `owner/repo`, case folded;
   - `owner/my_repo` is accepted; `owner/..` is refused;
