## Decisions
Each binds Implement. A deviation is a plan deviation and goes back to plan-review.

- **D1 Baseline (Q1), revised.** `record` stores `criteria_sha256` (sha256 of the normalised ORIGINAL `## Done when` block: the exact bytes from the heading line to the last item) in the record front matter at first record ONLY. There is NO ledger witness and NO ledger change. The guard has three clauses, all in `acceptance.prefix_refusal`:
  - **H** (stored hash): when the record carries `criteria_sha256`, it equals the hash of the current original block.
  - **B** (committed baseline): when a baseline blob exists, the baseline's original criteria are an exact, ordered prefix of the current combined list, and, if both carry a hash, the hashes are equal. The baseline is the blob of the FIRST commit that added `.sdlc/acceptance/<g>.md` in the goal branch's history (T2's `first_added_blob`, `git log --diff-filter=A --reverse`), never the tip. Hash and block rewritten together after a first commit are caught by B.
  - **P** (prefix of own record): the original block is the first 3 to 7 items and added items follow in `## Added criteria` only (structural).
  - **Git unreadable, or no commit yet**: B is skipped and the skip is printed (`baseline: unavailable (<reason>)`); the guard refuses only on a CLEAR mismatch from H or P, never because git could not answer. A false positive stops every goal in the fleet; a printed skip costs only strength, and the strength lost is stated here.
  - **Pre-commit residual, stated plainly.** Before the first `work.py commit` there is no committed baseline, so for a record that carries `criteria_sha256` the guard is H alone, and for a legacy record (no hash) the guard is VACUOUS in that window. An actor who rewrites the root record block and its `criteria_sha256` together before the first commit passes H. What narrows that window: the divergence check at `pr` (T4) for non-drafted GitHub goals whose issue has a criteria section, and B from the first commit onward. Drafted goals and local-file goals have no issue witness, so for them the pre-first-commit window is a residual with no compensating check. Host branch protection is the only hard stop for a history rewrite, as AGENTS.md says for feature branches.
  - Rejected: a ledger witness (the ledger is a per-actor file the agent can write, is off when `ledger.enabled` is false, and `OPTIONAL_FIELDS`/`ENTRY_SCHEMAS`/`append()` drop or reject an unknown field); issue-body-at-record-time as sole baseline (the issue is editable and fetched over the network); a full text copy elsewhere under `.sdlc/` (a second file in the root checkout, which AGENTS.md forbids).
- **D2 Cap vs append (Q2).** Unchanged. The original block keeps the 3 to 7 rule and the 1024-character limit (`criteria()` semantics for `## Done when` do not change). Added criteria live in `## Added criteria` after it. **Ceiling: at most 10 added criteria per goal** (17 total), each at most 1024 characters including its suffix. SCALABILITY: 17 x 1024 is under 18 KiB, inside `MAX_BYTES` (32768, `acceptance.py:23`), and the review brief grows by at most 10 lines. At 10x and 100x goals the guard cost is per goal (one file read, one `git log` bounded to one path, one `git show`), not per fleet. `extend` refuses the eleventh with "a goal that needs more than 10 added criteria is a new goal". `breaker._MAX_CRITERIA` (7) keeps reading only the original block, imported from `acceptance.py`.
- **D3 Reason format (Q3).** `- [ ] <text> (added: <slice>; reason: <why>)`. `acceptance.added(text)` returns `[{text, slice, reason}]`; a line missing the suffix yields `reason: None`. `extend` refuses to write one. A hand-written reasonless line is still parsed so review can see it, and two deterministic seams refuse it (D11).
- **D4 Issue-vs-record divergence, revised.** The guard's real protection is local (D1); divergence is an additional witness for GitHub goals only. The check RUNS only when ALL hold: the goal has an issue (not a local-file goal); the record does NOT carry `drafted: true`; the record carries `criteria_sha256` (a legacy record never gets the new park, so no fleet outage on upgrade); and the issue body has a criteria section (`## Done when` or the alias). Otherwise it is skipped and says why (`divergence: skipped (<drafted|legacy record|no criteria section in issue|local goal>)`). When it runs, it compares the record's ORIGINAL criteria with the issue's criteria after alias normalisation, comparing text only: checkbox state (`[ ]`, `[x]`) is ignored, as are surrounding whitespace and trailing `(added: ...)` suffixes. Existing behaviour, where an existing record deliberately wins over later issue edits (`acceptance.py:158-166`), is unchanged: divergence PARKS for a person, it never rewrites the record. **Fetch failure: fail CLOSED at `work.py pr`** (the hold is retried by the next tick, so no human is needed to recover) **and fail OPEN at `work.py commit`** (offline local work stays possible; the local clauses still run). Both print which way they went. Rejected: fail-open everywhere; fail-closed at commit.
- **D5 `goal_readiness` default `warn`.** Unchanged. `warn` prints missing sections and proceeds; `require` parks with a stated reason; `off` does nothing. Required sections default: `Done when`, plus `Verification command` only when the repo has a configured verify command. A default of `require` would park every existing goal on upgrade (RESILIENCY).
- **D6 The prefix guard is unconditional.** `acceptance.prefix_refusal` runs in `commit`, `pr` and `merge()` whether or not `verify.enforce` is on. The existing presence check at `work.py:4839-4842` stays `enforce_enabled`-gated and is NOT widened (research D-3): pr's acceptance check only runs under `verify.enforce`, so every new clause lives in its own unconditional call, outside that branch.
- **D7 Doctor open-goals read is bounded** at 50 bodies (`N of M checked`, `50+ unchecked`), REST only, no GraphQL. 100x growth costs no more than 50 reads per doctor run.
- **D8 The promote seam is GitHub-only** (`promote.py:130 _github`). Local-file goals get only the pick-time check. Documented in `docs/configuration.md`.
- **D9 No bypass surface, revised.** `prefix_refusal(...)` and every function it calls take no override argument. No flag named force, skip, allow, override or no-guard exists on any `acceptance.py` or `work.py` verb that reaches the guard. The guard path reads NO environment variable, NO config key: it calls neither `state.load_config` nor `config.get` nor `os.environ`/`os.getenv`. Config-gated behaviour (`verify.enforce`, `goal_readiness`, `review.independent`) lives only OUTSIDE the guard path, in callers that decide whether to run an unrelated check. The structural test in T3 walks the AST of `prefix_refusal`, `first_added_blob`, `reasonless_added`, `extend_comment_refusal` and the three call sites' guard lines, and fails on any of those names; its control adds `config.get(...)` to the guard and sees red. `goal_readiness` can never loosen the append-only guard.
- **D10 Normalisation, revised.** `## Acceptance criteria` is read as an alias; `record` writes `## Done when` only. `criteria()` is TWO-PASS: pass 1 looks for the canonical `## Done when` section and returns it if present and valid; only if absent does pass 2 look for the alias. A body with both headings uses the canonical one even when the alias appears first, and the alias block is ignored with a printed note, never merged. After `record`, the original block never changes.
- **D11 Reasonless added criterion has two hard stops.** (a) `reviewer.independent_run_refusal` refuses an approving `review` verdict while any added criterion is reasonless, unconditionally (before its `review.independent` early return, T10). (b) `work.py pr` and `merge()` refuse it through `acceptance.prefix_refusal` (T4). `reviewer.py` has no forced-block path for a brief line, so the brief text is advisory and is never the system of record.
- **D12 Added criteria are in the open, checked at `pr`.** `extend` posts an issue comment carrying the extend marker `<!-- sigma:acceptance-extend <sha256 of "text|slice|reason"> -->` with the text, slice and reason in the body (T9 writes it, T3 defines the constructor `acceptance.extend_marker`). At `pr`, `acceptance.extend_comment_refusal` reads the issue's comments through `fetch_comments_strict` (the read used at `acceptance.py:205-209`) and requires, for EVERY added criterion, a comment containing the marker for that exact text, slice and reason. Unreadable history REFUSES (fail closed; the next tick retries, so no human is needed). Local-file goals have no issue and are EXEMPT: the check is skipped with `extend comment: skipped (local goal)`. Residual stated: an actor who can post issue comments can fabricate the comment, so this is an audit trail a reviewer can see, not a proof of who wrote it.
- **D13 Exits other than `pr`.** `merge()` (`work.py:9096`) gets the same unconditional guard (a tamper or reasonless refusal returns a `PARK:`-prefixed line, the human-needed convention in its docstring; Implement reads the prefix handling first). The checkpoint push (`work.py:5010`) and the rebase `--force-with-lease` (`work.py:6519`) push bytes that `commit` already checked, so they get NO guard; that limit is documented beside the raw-push note (`work.py:275-290`) and in `docs/cloud-sessions.md`, stated as: a raw `git push` or a hand edit after the last `commit` and before `pr` is caught only at `pr` and `merge()`.

## Risks
1. **Baseline strength (D1).** Tamper-evident, not tamper-proof. Before the first commit the guard is H alone (or vacuous for a legacy record); the divergence check narrows it for non-drafted GitHub goals only. After the first commit B reads the FIRST-added blob, so a tampered first blob is the weakest point (an actor who tampers before the first `commit` and commits it passes B forever; the divergence check at `pr` and branch protection are the only witnesses).
2. **Blast radius of a gate every goal passes through.** A false positive in `commit`, `pr` or `merge()` stops the fleet. Mitigated: legacy records are exercised at commit and pr (T3, T4 rollout tests); git unreadable refuses only on a clear H or P mismatch; the divergence park skips drafted, legacy and no-section cases; a guard error is a refusal string, never a traceback.
3. **Performance-boundary port (AGENTS.md).** The guard is in-process Python and not a probabilistic concurrency control, so the sensitivity-collapse rule does not apply; the one atomic-write seam (`extend`) has a deterministic in-process test (`..._write_is_atomic_when_replace_fails`). No `kill -STOP`, no background process, no hook is load-bearing: every guard is acceptance.py, work.py, reviewer.py Python and git.
4. **Divergence check turns an issue edit into a park** for non-drafted GitHub goals with a hash. Intended; the park reason names the gesture (`/sigma-unpark` after the person decides, or `extend`).
5. **Cap interplay.** `breaker.py` and `seal_tests.py` read only the original block; T1 tests that ten added criteria leave `breaker`'s count at the original.
