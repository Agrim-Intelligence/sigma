## Owner ruling on the plan-review verdict word
**Status: RESOLVED (owner ruling 2026-10-10, issue 878 comment; noted on 809). The earlier PARK is lifted.**

The finding it resolves (read from source): `properties.json` property `process.plan_review_verdict_approved` is
HARD and requires `streams.plan_review_verdict.verdict == "approve"` by exact `stream_equals`
(`evals/regression/check.py:156-162`). `record.py` `read_plan_review` (`evals/regression/record.py:269-280`)
copies the last `kind=verdict, phase=plan_review` action-log row verbatim, and the only writer of that row is
`work.record_plan_review` (`skills/sigma-loop/scripts/work.py:1295`), whose vocabulary is `pass`/`warn`/`block`
(`work.py:1207`, `PLAN_REVIEW_VERDICTS`). So an intact run read `pass` and the property failed.

Ruling (option 1): ONE normalization is allowed, in `read_plan_review` in `evals/regression/record.py`, and
nowhere else. For the plan-review stream only: `pass` -> `approve`, `warn` -> `approve` (SOUND-WITH-REFINEMENTS is
an approval), `block` -> stays `block`. Any other value, including an unknown word, is kept VERBATIM. Only the
exact strings `pass`/`warn`/`block` as the gate writes them are mapped; no other stream field (`route`,
`plan_hash`, `verified`, `gate_file_present`) and no other `record.py` behaviour changes.
This amends the design's binding rule against touching `record.py`, FOR THAT SINGLE PURPOSE ONLY.

Untouched: `evals/regression/properties.json`, `evals/regression/check.py`, every other `record.py` function, and
`work.py`/`phase_gate.py`. No property is weakened: the hard property still demands `approve`, and a `block`,
a missing row or an unknown word still FAILs it.

The plan is therefore no longer conditional; the implementer proceeds, with the mapping written FIRST (Steps 1).

## Design

### D1. The selector route for `quality.test_first_passed`
Facts (read): `loop.py verify` calls `red_green.observe` (`loop.py:5328`), which runs
`python3 -m pytest` over the plan's `## Tests` selectors and, on a RED run with an assertion failure, records a
witness row (`red_green.py` `observe`, `w.record(...)`). `work pr` refuses unless the LATEST verify evidence
carries `test_first.passed == true` AND the witness journal holds an assertion-red for each node with
`file_hash == nodes[node]` and `observed_at < started` of the green run (`red_green.refusal`;
`work._test_first_refusal`, `work.py:3192-3216`; `verify.enforce` is ON in the confirm setup). So:
- The test FILE must be byte-identical between the red and the green run (the red row's `file_hash` is the test
  file's hash). The red must therefore come from the CODE UNDER TEST, never from editing the test.
- The red must be an ASSERTION failure (a `FAILED <node> - assert ...` summary line, `red_green.py` the
  `AssertionError|assert` regex), not an error: the test must assert on existence, not read a missing file.

Scratch test (written by the control into the goal worktree, committed by `work commit`):
`test_hello.py` (in the scratch repo's tests directory) with one function `test_hello_written`:
`ROOT = pathlib.Path(__file__).resolve().parents[1]; assert (ROOT / "hello.txt").is_file() and (ROOT / "hello.txt").read_text() == "hi\n"`.
Plan `## Tests` section (the scratch plan, written by the control): one bullet
``- `tests/test_hello.py::test_hello_written` ``. The plan is hashed for plan-review, so `## Tests` is part of
the reviewed bytes.

Red-then-green order, all by Sigma's own writers (`loop.py verify` is the only caller of `observe`):
1. write the test file in the worktree (hello.txt absent); `phase_report start implement`;
2. `loop.py verify` with `ok_rc=None`: RED. Assert `rc != 0`, evidence `test_first.passed == false` and the
   witness journal has an assertion row (read the evidence JSON; if the witness path is not visible, assert only
   through the eventual `work pr` acceptance, see step 3);
3. write `hello.txt` (the scripted work); `phase_report end implement`; review phases not here (they come after PR);
4. `loop.py verify` again: GREEN, evidence `test_first.passed == true` (this is what `record.py`
   `read_verify` reads, `evals/regression/record.py:283-291`);
5. `work commit`. (Order is verify, commit, pr, as the skill says; the research doc's "loop verify after merge"
   is NOT used: after merge the worktree may be gone and `verify` would fall back to the project root.)
Content fingerprint safety: `PYTHONDONTWRITEBYTECODE=1` is already in `_env`, and `.pytest_cache` carries its own
ignore file, so a pytest run adds no untracked path. The implementer confirms at the first run that verify does
not report "repository content changed during verify".

Pytest precondition (SAFETY: refuse loudly). A precondition `_pytest_precondition(env)` runs
`python3 -m pytest --version` with the control's own `PATH` (the one `_env` builds, which is what `red_green`
spawns as `python3`) and returns an error string or "". `main()` calls it ONLY when the process variant is
selected (default `all` included) and prints
`onboarding_control: precondition missing: python3 -m pytest is unavailable (the github/process variant needs it for the test-first proof); install pytest or run --variant confirm` to stderr, exit 2, before any directory work. It never runs the variant without pytest and never downgrades to `--no-tests`.

### D3. Naming the RED
`check_github_process(obs)` returns one assertion per concern, and the property results are turned into
assertions named EXACTLY the property id (`process.review_marker_in_store`, ...), in `check.py` print order, so
`Run.result` (`failed_step = "assert:" + first failing assertion`) prints `RED at assert:<property id>`. Order
inside the list: (1) pre-record facts the control owns (probe refused and store empty; PR opened after the
record; review chain printed `posted sigma:approve`; no unhandled gh call), then (2) one assertion per
`check.py` line (`PASS` ok; `FAIL` or `NOT EVALUABLE` not ok, detail kept), so the FIRST failing assertion is the
first FAIL / NOT EVALUABLE property in the evaluator's own order. Merge/done non-fatal (steps 9 and 10) means a
broken review step cannot abort earlier and mis-name the RED. The printed line is
`onboarding-control: github/process: RED at assert:process.review_marker_in_store (...)`, which the tests'
regex `RED at [^(]+? \(` already parses.

Assertion list `check_github_process` (each seen red once in `GITHUB_PROCESS_BREAKS`):
`negative probe printed the plan-review refusal`, `negative probe left the fake store without a PR`,
`PR opened only after plan-review was recorded`, `review chain posted sigma:approve through post-review`,
`every gh call was one the fake models`, `record build succeeded`, then the parsed property lines.
The soft `outcome.goal_commits_on_main` NOT EVALUABLE (branch deleted at merge) must NOT count as red:
only `FAIL`, or `NOT EVALUABLE` on a hard property, fails an assertion (mirrors `check.py` exit rule).

- `onboarding-control: github/process: GREEN|RED at <id> (<s>s)` uses the existing print loop.

### D5. Scalability / liveness / resiliency / safety (stated, not claimed)
- Cost: serial; roughly 30 to 40 more subprocess calls than `github` confirm. UNMEASURED here; the existing
  `github` variant measured 73 to 77 s for 40 steps on a loaded machine (research section 6). `cli_run` is a
  module fixture with a 600 s subprocess timeout (`tests/test_onboarding_control.py:94`), so adding the variant
  to the default gesture thins that headroom. The implementer MEASURES wall time of the plain gesture before and
  after and reports both; no figure is invented in docs. A ceiling number per CI cell is Slice 5.
- Recovery: every run uses a fresh temp dir, removed in `finally` unless `--keep`; a crash leaves nothing to repair.
- Safety: no secrets; session id is a fixed non-secret test string; the fake gh only.
- The control must stay POSIX and host-agnostic: nothing here depends on a Claude Code hook.
