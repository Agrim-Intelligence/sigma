# Plan: #625 init must never overwrite a corrupt or non-object config.json

Inputs: issue #625. Audit of every config.json writer (grep of skills/, hooks/, tools/):

- `init_flow.apply_config` read through `_read_json` (returns `{}` on a parse error or non-object) then wrote the mutated `{}`: THE BUG.
- `init_flow._set_project`, `board_setup._config` (json.loads, raises), `verify_detect.write_verify` (json.loads, raises), `setup.configure` (`_load_cfg` json.loads, raises): fail loudly with a traceback, never write. No data loss.
- `sdlc_init --cursor` block: reads under `except Exception: pass`, writes only a parsed dict. No data loss.
- Non-atomic writers (truncate-in-place; the way a truncated config is made): `setup.write_cfg`, `sdlc_init --cursor` write_text.

Also audited, read-only or strict (no clobber): `preflight.set_local_only/set_remote`, `migrate._plan_config`, `predict._cfg`, `log.py`, `kg.py`, `tools/readiness/blast_radius_drive.py` (test drill).
Non-goal: `preflight.set_local_only` on a non-object config raises a traceback (no write, no data loss); follow-up, same class as item 3.

## Design

1. `init_flow.read_config_strict(path)`: `{}` only if the file is absent; raises `ConfigUnreadable` naming the file, what is wrong (unreadable, invalid JSON, non-object with its type; an empty or zero-byte file is refused too, and the lever is delete) and the lever (repair by hand, or back up and delete deliberately). `apply_config` uses it, so any caller is protected.
2. `init_flow.main` calls it up front (right after the config is first read) and returns exit 2 `REFUSED ... Nothing was written` before the hook-path install, owner marker, or scaffold: a refusal leaves adoption untouched.
3. `setup.configure` CLI path: catch the same shapes from `_load_cfg` (invalid JSON, non-object) and refuse with exit 2 and the lever instead of a traceback.
4. `setup.write_cfg` and the `sdlc_init --cursor` write go through temp + `os.replace` (verify_detect `_atomic_write_json` where importable) so a crash cannot leave a truncated file.
   Item 3 is UX (traceback to refusal), not data loss. Known ceiling: the atomic write has no fsync, so a power loss can still leave an empty file; this is not claimed crash-proof.
5. No backup: no path deliberately replaces an existing config (writers merge into the parsed dict). A valid config is rewritten only when a value changed, as before.

Scale: one read of a small file per run; O(1). Recovery: the refusal is idempotent, exit 2, file untouched; the lever is manual repair or deliberate delete.
