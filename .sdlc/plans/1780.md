## Honest limits and AGENTS.md properties
- RELIABILITY: this slice delivers prose and tests, not behaviour. REJECT on a failed `quality` check exists only because the reviewing model follows goal-review prose (slice 3, not here); `mark-designed` does not refuse. Nothing in this slice enforces that the design agent runs `quality` before publishing. Form not truth: a digit in a Response measure proves nothing about the number. The `Lane` is self-reported. These are stated in the shipped paragraph and the changelog line.
- Token cost: the extra prose adds roughly 175 estimated tokens to SKILL.md (by the repo's characters-over-four estimate, a unit of the budget test, not a measurement of any host's tokenizer) and the cost of answering eleven rows per design is UNMEASURED (design D-13). No timing is claimed.
- SCALABILITY: per-item cost is a pure text edit; there is no runtime cost in this slice. At 10x or 100x designs the cost is the engine's (slice 1: linear in rows, 1 MiB read cap, 2000-character cell cap, 20-container warning) and is not changed here. The pinning tests read three files of tens of KiB; they scale with file size, not with the number of designs. The only growth hazard is a prose drift between the two skeletons, which the equality test turns into a red test instead of a surprise.
- RESILIENCY: failure of any new test is rerun-safe; the plan is idempotent and the edits are additive. A one-sided future edit of either skeleton, or of the engine tuple, goes red rather than silently diverging. Recovery for a red is to revert the one hunk; no state, no lock, no daemon.
- SAFETY: no process spawned except pytest and the two read-only verbs; no network, no `gh` call, no file written by the verbs; no secret in any file.
- LIVENESS: not applicable, no long-running component is added.
- Host-agnostic: all enforcement is plain Python tests over repo text; nothing depends on a Claude Code hook.
- Existing designs written before this slice have no Quality requirements section; they are read without being re-reviewed or rewritten (same as the Functional requirements precedent).
- Root-checkout rule: the plan and its siblings are written into the root checkout's plans directory only; nothing else is written there, and the landing step copies the plan into the goal branch.
