Decisions this plan adds, each from re-reading code the dossier did not cover:
- **D-11 (dossier miss) The new row is written only while the goal is in flight.** A new INTERNAL kind is a state-machine input: `log.py newest_code_written` / `is_closed` / `marker_state` (`skills/sigma-log/scripts/log.py:502-539`), `retention.py:205` and `goal_state_prune.py:13` all read the NEWEST `INTERNAL_KINDS` row. A row after `recorded` would reopen a closed slot and, for `done`, stop retention pruning that goal's log forever (the newest row is no longer `recorded`); a row after `merge_armed`/`merged` flips 🟢 merging to 🔵 running. So `_log_edit` skips the write when the goal's newest INTERNAL row is `recorded`, `merge_armed` or `merged`; the stderr line and exit code are the trace there.
- **D-12 (dossier miss) The "goal added a command" clause is implied inside `verify_decision`.** With `reason == mismatch` and every repository command hashing to the value, some command in the list cannot hash to it, so it is outside the repository list. A separate predicate there is an unobservable mutant (decoration), so none is written; a matrix test pins the implication. The clause is real in the record-time helper, as a cheap pre-filter that avoids every git spawn when the goal adds nothing; control (b) breaks that one.
- **D-13 (dossier miss, BR-19 reopened) `set-verify-command` keeps the goal worktree's copy of the record byte-identical.** `sigma-brainstorm/SKILL.md:53` copies the record into the worktree at P1, and `work.py commit` is create-only (`work.py:4189-4213`). A root-only rewrite leaves a stale branch copy that lands on the base; `_clean_landed_root_records` (`work.py:4215-4252`) then reports "kept ... differs", and an untracked differing root copy of a now-tracked path makes the next `git pull` refuse. That is the exact state AGENTS.md forbids. So: when `state/work/<stem>.json` names a worktree whose `.sdlc/acceptance/<stem>.md` is byte-identical to the OLD root record, replace it with the new bytes; an absent copy is skipped silently, and a differing copy is left alone with one stderr line naming both paths. No "discard it" command is offered for the differing case (it would throw away someone's edit); the operator copies the root record over it by hand, and the line says which two files differ.
- **D-14 Reuse `state.atomic_write_text`** (temp + fsync + `os.replace`, mode preserved, temp removed on failure, `state.py:1081`) instead of a second hand-rolled idiom; it keeps the write-surface delta to `fs-write` rows. The record path is also checked with `state.refuse_symlinks` first (#708), because `atomic_write_text` follows a symlink.
- **D-15 Two test files, because the test-first gate counts only assertion failures and needs EVERY planned node red.** `tests/test_goal_verify_command.py` holds only tests that are red before the change (file selector in `## Tests`). `tests/test_goal_verify_command_guards.py` holds the boundaries that are green before and after (unset, git-local, every accept case, byte-identical unset text, closed-goal log guard): they are the controls, run in verify, and each is broken once in `## Controls`. Ordering asserts use `str.find`, never `.index`.
- **D-16 The remedy depends on where the goal's command lives.** Record holds it: the concrete gesture. Neither (race): the generic "remove the goal's own verify_command". `test_verify_refuses_a_local_goal_whose_frontmatter_replaces_the_command` has NO record at all, where the gesture would fail with `FileNotFoundError`.

## Risks and limits

- **Best effort at record time.** The check reads the recording process's environment. A person who records in a shell without the variable, then runs the loop in one with it, is accepted at record time and refused at verify, where AC-3's text and the verb recover it. Record time can wrongly accept; it cannot wrongly refuse a command verify would have run (an approval that covers the repository command alone cannot also cover a different goal command).
- **Verify racing a clear.** A verify that reads the record, then a clear, then writes evidence: the evidence carries the old `acceptance_sha256`, and `state.done_refusal` (`state.py:1764-1770`) demands a re-verify. Self-healing; unmeasured as a live race.
- **Crash during the rewrite.** `atomic_write_text` leaves the whole old file or the whole new one; a SIGKILL can leave a random-named `.<x>.tmp` in `.sdlc/acceptance/` (its documented limit). It does not collide with an incoming tracked path, so it cannot make `git pull` refuse; nothing prunes it.
- **Two-step for a local `.md` goal.** The frontmatter must be edited by hand before `--clear` is accepted; the verify text and the `--clear` refusal both say so.
- **`seal_tests.py:386-398`** reads the record's command once at seal time for the pytest check; a replace after sealing can change which command was checked. The sealed gate runs its own pytest (`work.py:4078-4086`); accepted, not changed.
- **Cost / scale.** Per call: record time is at most one `git config` plus the existing identity/veto/sourced reads (a handful of git spawns) and only when the variable is well-formed AND the goal adds a command; verify adds pure hashing. The verb reads one record and one action log (O(rows), bounded by `action_log.retention_days`, default 90) and writes at most one row; no store grows. Not measured at 10x/100x; nothing here is per-item beyond that log read.
- **Unmeasured:** the run in a real cloud container (the source report). Everything here is fixtures and a scratch repository; the CHANGELOG says so.
- **Public repo hygiene:** fixtures use `Owner/Repo`; no private repository, path or count is named. The existing sentence in `docs/cloud-sessions.md:42-43` that carries one measured count is kept byte-for-byte or dropped, not extended.
- **Deferred roots for retro:** TD-4 (`record --verify-command X` on an existing record silently keeps the old value; the new verb is the lever; file a ticket); TD-5 / #2068 (the `goal-command` reason must join the trust-refusal vocabulary in the ledger and action log); #2069 (sealed gate reads only git-local); BR-24 (ledger `acceptance_sha256` is never re-paired with a rewritten record); BR-19 after `work.py commit` (the committed branch copy is not rewritten in git; only reachable if a verb call follows a commit with no evidence, which the loop's order prevents).
