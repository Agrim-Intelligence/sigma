1. **Recorded-red path is a judgement call (P-10).** Calling `red_green.observe` directly reproduces what `loop.py verify` records but is not the documented gesture. Exercised in a scratch repo (red row written, product changed, green observed, `refusal` returned `''`), not yet on this goal: the first `work.py pr` is the end-to-end proof, and a refusal there falls back to a full-suite red via `serial_verify.py` with the product hidden as in Task 9 step 4 (hours, one of two machine-wide slots).
2. **Parametrized attribution.** `observe` credits a node only when pytest's short summary prints `FAILED <node> - AssertionError...` (COLUMNS=400 avoids truncation) or the split-traceback join is unique; a parametrized failure with a truncated or non-assert reason earns no row, and any test that prints to stdout/stderr disables the traceback path entirely (Task 1 step 2 forbids printing). Task 9 step 7 checks every node has a row; unresolved if a node gets none.
3. **Plan and research copies.** `verification_plan` raises if the main and worktree plan bytes differ, and `work.py pr` refuses a plan or research dossier that is on disk but not on the branch. This revision is in the main copy only (no worktree copy exists yet), so the orchestrator publishes identical bytes of both to the worktree before Task 9 (Order of work, item 4); a new plan-review is needed (the plan hash changed). The research dossier was edited in this revision too (private-name and flag-token rewording, and a corrected claim that the public-surface guards read untracked files: they read tracked files only).
4. **The venv is a host dependency of the recorded runs.** Both the red and the green rely on `$HOME/.sigma-venv312/bin/python3` (Python 3.12 with xdist 3.8.0) being first on PATH, because `red_green` invokes the literal `python3`. This is an operator-side fact of this machine, not a property of the shipped code; the defect (a hard-coded `python3` that cannot collect this repo on a stock macOS) belongs to sigmaloop's `red_green.py` and is worth a follow-up issue, not part of this slice.
5. **Committing before the green.** P-16 puts `work.py commit` before the full-suite run. If the green then fails, the branch carries a commit that is not yet green; that is harmless (nothing is pushed until `work.py pr`, which refuses without a green), and the fix is another `work.py commit`.

## Post-ship risk note

1. **A structural check is not a render check.** A document can lint clean and still not render in some host; the docs say so. Mitigation: slice 2 adds a "freshly scaffolded document lints clean" test, and the host render question stays with the Dossier (D-4).
2. **Slice 2 depends on the pinned surface.** `resolve_system_root` / `Resolved` and `REQUIRED_HEADINGS` are imported by sibling path; changing either later is a breaking change for slice 2 and R-04/05/06. `test_resolve_system_root_return_shape` is the guard.
3. **Heuristic false negatives.** The label parser is line-oriented: a node label that spans lines, or a diagram built with a different node syntax, can hide a container. The `second_container_block` and edge-case tests cover what was foreseen; anything else is a follow-up goal.
4. **Mutation control couples to function names and contracts.** Renaming a clause function, or calling a helper outside the place Task 3/4 binds it to, turns the control red by design (P-4); the failure message says which function was not found.
5. **CHANGELOG and docs-table rebase conflicts** with sibling goals (#659/#660); resolve at rebase, oldest PR first.
6. **Root-checkout rule (AGENTS):** the linter is read-only; slice 1 leaves nothing in the root checkout that could refuse `git pull`, `git checkout` or `work.py start`. The witness rows Task 9 appends live under `.sdlc/state/` in the main checkout, the same place `loop.py verify` writes them; nothing new to clear.
7. **Config key is advisory until slice 2 and R-04+ consume it.** Until then only the linter reads it; a user can set a value that nothing else honours.
