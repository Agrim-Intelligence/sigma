# Plan: #2028 Compaction safety net: daemon sets the compact window; rules and live slots re-injected after compaction
**Goal**: #2028 · **Lane**: medium · **Research**: `.sdlc/research/2028.md` · **Design**: `.sdlc/design/2024.md` §3 (FR-5, FR-6; BR-9, BR-10, BR-17) · **Date**: 2026-10-24

## Decisions (for the plan reviewer)
- **D-A. How the window is derived.** It is `compact_window.window(cfg)`, read from the project
  config the launcher already has:
  - `handoff.after_context_tokens = a`, a positive int that is not a bool:
    - `a < 1,000,000` → `min(1_000_000, max(100_000, 2*a))`. That is always above `a` and inside
      the documented range. **2×** is headroom for the drain. The hand-off is checked only at a
      pick. After HANDOFF the session keeps finishing its live slots. The measured growth was
      603,142 tokens over 3 goals (`loop.py:337-344`), roughly one goal's worth per slot. The
      number is provisional, like slice 2's D-1.
    - `a >= 1,000,000` → **not set**. No value in range can sit above the hand-off point, so the
      host default applies, and a log line says so.
  - **Absent, 0, a bool, a non-int or negative** → **500,000**. We use this because the host
    window is not knowable before launch: `claude -p` picks the model, and a gateway alias hides
    it. 500,000 is the design's own cost bound, "orchestrator peak stays below 50 percent of the
    host window" (design, Quality requirements: cost), applied to the largest window the host
    accepts (1,000,000). Claude Code caps the window at the model's own window (model-config
    docs). So on a 200k model this equals the host default and changes nothing. On a 1M model it
    compacts at 500k instead of about 967k. It sits above slice 2's derived default as long as
    D-1's 2–4× of a 70–100k start (at most 400k) holds.
  - **Ceiling**: a derived slice-2 threshold above 500k would compact first. Named on #2027.
  - This is a host-documented range, not a machine resource, so the derived-limits rule does not
    apply. Flagged anyway.
- **D-B. "Operator already set it" covers more than the env.** The docs say the env var
  outranks `/autocompact`, `--autocompact` and the `autoCompactWindow` setting, so a blind
  `setdefault` would silently override them. `compact_window.operator_set` returns true on any
  of these:
  - (a) the key is present in the parent env (exact `setdefault` semantics, an empty value
    included);
  - (b) `--autocompact` appears in the launch command string;
  - (c) `autoCompactWindow` or `CLAUDE_CODE_AUTO_COMPACT_WINDOW` appears in the text of
    `$CLAUDE_CONFIG_DIR|~/.claude/settings.json`, `<repo>/.claude/settings.json` or
    `<repo>/.claude/settings.local.json`. This is a substring check: a false positive only means
    we do not set the window.

  **Limit, stated in the docstring:** managed settings (MDM, server-managed, an embedding host)
  cannot be read, so they are not detected. The cheaper alternative is (a) only, which is the
  acceptance wording read literally. The reviewer may cut (b) and (c).
- **D-C. One shared module**, a new `skills/sigma-loop/scripts/compact_window.py`, used by both
  launchers. It is new rather than added to `loop_session_model.py` because slices 1 and 2
  (running in parallel) touch the loop-session code, and a new file cannot conflict. It only
  ever mutates the child dict it is handed, never `os.environ`.
- **D-D. The `after_context_tokens` key is read, not added.** Slice 2 owns the template and docs
  for it. A missing key is "not set". `handoff.enabled` is not consulted: 2×a (or the
  default) is still a valid net with the hand-off off.
- **D-E. Compact tier gating.** The tier fires on `source == "compact"` in any **adopted** repo
  (`.sdlc/config.json` exists). It does not require `session_start.enabled` and ignores
  `SIGMA_RUN_ID` (FR-6: "including in supervised runs"). It costs about 600 tokens after a
  compaction: the brief is about 500 characters and the slots were 1,603 bytes when measured.
  - It sits after the coexist notice and before the first SIGMA_RUN_ID-gated tier, so a
    compaction never starts an upkeep sweep (`session_start.sh:75`).
  - Every other source (`startup|resume|clear|fork`, missing or malformed input) falls through
    to today's code unchanged.
- **D-F. Bounded stdin read.** The read is `[ -t 0 ] || IFS= read -r -d '' -t 2 HOOK_INPUT`, so
  a tty is skipped, EOF returns at once, and a pipe that is never closed costs at most 2 s.
  `cat` would hang `tests/test_stopfiles.py:32` and `tests/test_hook_setup_wizard.py:26,237`,
  which inherit stdin. Checked on bash 3.2.57 and 5.3.15: the payload is read on EOF, and the
  open pipe returns after 1 s with `-t 1`.
- **D-G. One copy of the rules.** The policy-brief text moves into one exported shell variable,
  `SIGMA_POLICY_BRIEF`, read by both the opt-in brief and the compact tier.
  - The compact tier adds one line: this session was just compacted; if it runs the loop, the
    slots below are in flight and must not be re-dispatched; re-read the sigma-loop skill before
    the next pick. The reason is that skill bodies are re-injected capped at 5,000 tokens and
    `SKILL.md` is 19,137 bytes.
  - `log.py slots` runs with `timeout=5`. Measured 0.30 s warm and 1.29 s cold, so the 20 s hook
    budget holds. On failure or timeout the brief is still emitted, with
    `Live slots unavailable (<why>)`.
- **D-H. The daemon logs its choice**: one `supervisor.log` line per daemon start, giving the
  value and its source, or "left to the operator", or "not set: hand-off at or above the max".
  It goes to the log only, never stdout, following the routing table.
- **Not done (skipped):**
  - A `compact` matcher split in `hooks.json`: not needed, and the timeout stays 20.
  - An opt-out key for the compact tier: add one when someone asks.
  - `feature_judge.py` and `feature_upkeep_review.py` launchers: short single calls.
  - Codex re-injection: Codex has no such hook. This is an accelerator; slice 2's hand-off is
    the load-bearing control.
