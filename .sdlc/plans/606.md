# #606 plan: issue-chooser repo link checked against the public repo at export

## Goal / done_when
The research found the premise stale: `.github/ISSUE_TEMPLATE/config.yml` already names the public repo. The gap is a guard that reads `definition.json` and catches ANY other repo. Done when `build_public_tree.py` reports `scans.issue_template_slug`, and a config.yml naming any repo other than `public_repo` (or naming none, or an unreadable definition) makes the verdict REJECTED (exit 1). The rest of the criteria are in `.sdlc/acceptance/606.md`.

CHECK, not rewrite: the exported tree already carries the public slug, and the private tree's own issue chooser must keep working.

## Files
- edit `tools/build_public_tree.py`:
  - add `ISSUE_TEMPLATE_PATH = ".github/ISSUE_TEMPLATE/config.yml"` beside `DOCTOR_PATH` (l.61).
  - add `_issue_template_slug(partial, definition_raw, blobs)` after `_doctor_slug` (l.844), same return shape `(scan, findings)`. It reads the exported copy and extracts every `github.com/<owner>/<repo>` (regex, `re.I`). Each pair is compared case-insensitively with `public_repo`.
    - `not-applicable`: file absent from the export.
    - `unverifiable`: definition missing or `public_repo` not a string, or the file holds no github.com repo reference (so an edit that drops the link is not silent).
    - `mismatch`: any pair differs; the scan lists the offenders.
    - `equal`: all pairs match.
  - finding rules `issue-template-slug-mismatch` and `issue-template-slug-unverifiable`.
  - call it at l.1274 and extend `builder_findings` with its findings; add `"issue_template_slug"` to `scans` (l.1334).

## Tests
`tests/test_build_public_tree.py::test_issue_template_slug_check`, mirroring `test_doctor_slug_mismatch_rejects` (l.655, `_fixture(extra=...)`). The `-k issue_template` selector matches it:
- equal: public slug (also upper-case variant) -> `equal`, accepted.
- mismatch, third repo: `github.com/other-org/other-repo/...` -> `mismatch`, REJECTED, rule `issue-template-slug-mismatch`.
- mismatch, private-slug-shaped repo: built in the test from the definition's owner plus a different repo name (the private slug is never written as a literal) -> REJECTED.
- two links, one good and one bad -> `mismatch`.
- unverifiable, no definition -> rule `issue-template-slug-unverifiable`.
- unverifiable, no link: config.yml with no github.com repo -> REJECTED.
- not-applicable: no config.yml -> status `not-applicable`, no finding.
Existing `tests/test_release_consistency.py::test_public_tree_names_the_public_repo_not_the_working_repo` stays unchanged and green.

## Ceilings / safety
One small file, one regex pass: O(size of config.yml), no scaling concern at 10x or 100x. Read-only on the export. It refuses loudly (REJECTED) where the claim cannot be verified, never passes silently. It does not catch a legitimate link to a different repo on purpose; the owner must edit `definition.json` or the file, which is the intended friction. It is not a rewrite and does not touch the private tree.
