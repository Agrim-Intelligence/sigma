## Resource, scale and recovery statements
- Growth: one witness row per recorded red node per run, at most 25 selectors per run (`red_green.py:61-62`). Repeats are harmless (`refusal` accepts any matching earlier row) but append. A goal that is iterated N times writes up to 25N rows to its own `witness` journal; the retention gate (`retention.py`, `write-surface.json:1684`) removes a closed goal's witness file after its window, so growth is bounded by goal lifetime, not by the fleet. No new table, no new file.
- Scale: cost is one pytest run over at most 25 selectors, serial, no lock. At 10x goals nothing shared is touched (per-goal journal). Ceiling: pytest startup plus the tests.
- Time saving: the issue's figure (full verify 25 to 50 minutes versus a selector-only run) is NOT measured by this plan. Measured here: one selector-only pytest run for a single existing test (`tests/test_test_first_gate.py::test_plan_scope_reaches_flake_without_rebuilding_node_ids`) took 2.27 s wall, `-rA --tb=short`. That is one test on one machine, not a `red` run and not the full verify. The saving is unmeasured until a real goal records the two.
- Recovery: `red` is read-then-run and idempotent. A crash mid-run leaves at most rows already appended by `witness.record`, which are valid rows. The lever for a stale or wrong red is to edit the tests and run `red` again (a changed test hash invalidates earlier rows by `refusal`'s file-hash check). Nothing to clean up.
- Safety: refuses on missing shell consent, unsafe goal, missing plan; spawns nothing but the pytest `observe` already spawns; no background process.
