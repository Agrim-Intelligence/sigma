# Plan: Follow-ups join their goal as slices; a separate goal only for another feature or past the slice cap
**Goal**: #2224 (Agrim-Intelligence/sigma) · **Lane**: large · **Phase**: P3 PLAN
Worktree `.sdlc/work/2224`, branch `sdlc/2224`, base `524d533` (1.0.32). Research: `.sdlc/research/2224.md`. Acceptance: `.sdlc/acceptance/2224.md` (7 criteria, unmodified).

## Goal
Make "found work stays in its goal" a code-decided rule. One pure function maps recorded facts to `slice` or `separate(different-feature | slice-cap)`. A new verb (`work.py add-slice`) adds the slice to the plan, counts it in a code-owned record, appends criteria through #2222's extend verb (refusing loudly while that verb is absent), and the existing plan-review hash gate forces a fresh review. `handoff.py track` routes every kind and `--blocks yes` through the function. `followups.mode` defaults to `in-goal`. The deferred-comment path and the orchestrator clean-up goals are retired. `/sigma-doctor` reports follow-ups with no recorded reason.

### The routing function (contract)
```
route(goal_unit, item_unit, added, cap) -> ("slice", None) | ("separate", "different-feature") | ("separate", "slice-cap")
```
- Positional facts only; no `**kwargs`, no `reason=` input, no env read, no config read inside. `REASONS = ("different-feature", "slice-cap")` is a module constant and the only values the second element can take (a test asserts the set by exhaustive enumeration over a fact grid).
- Clause order: (1) `item_unit` is None -> it inherits `goal_unit`; (2) units differ -> `different-feature`; (3) same unit and `added >= cap` -> `slice-cap`; (4) else `slice`. `different-feature` is checked first, so a find that is both another feature AND past the cap reports `different-feature` (one named reason; flagged below).
- Goal with no declared unit and an item with a declared (open, registered) unit: units differ -> `different-feature`. Both undeclared: `slice`. Flagged below.
- `cap` is whatever `handoff.max_added_slices(config)` returns (default 10, total parsing unchanged); the function does not read config.

### Handling of decompose children and chain prerequisites
SUPERSEDED by `## Amendment (owner decision, option A)` below. Only proven decompose children (`--kind child` with all four recorded legs) are exempt from routing; `prerequisite`, `cleanup`, `followup` and `--blocks yes` stay routed. No refusal text names `followups.mode: file` as a lever.

### Where the facts come from (`gather_facts`), and what an agent cannot pass
- `goal_unit`: `features.read(source.fetch_body_labels(goal))` (the existing `feature_stamp.unit_of` logic, body wins). A source with no unit surface (`LocalSource`) reads None.
- `item_unit`: read from the item's OWN recorded declaration, i.e. `features.read({"body": <--body-file text or None>, "labels": [<--label values>]})` (a `Feature:` body marker / a `feature:` label, body wins). The unit must then resolve through `feature_registry.resolve_open_unit` to count; a name that is not an open registered unit is NOT a declaration (reads None, so it inherits, with a warning). This is the declaration the item will carry once filed (`create_dependency` stamps the same marker/label), so the fact routed on is the fact recorded on the filed issue.
- RESIDUAL, stated plainly (finding 2): the item's feature is still caller-supplied text (a `Feature:` marker in `--body-file`, a `--label feature:`), and so is the `<goal>` positional. Code cannot prove the agent declared its find's true feature; no flag names a reason, but an agent that writes a registered open unit's marker into the body file buys `different-feature`. What the plan DOES do to narrow it, each with its own control: (a) the declared unit must resolve through `resolve_open_unit` (open, registered) or it reads None and inherits (C24); (b) both body-marker and label are read through `features.read`, body wins, a body/label disagreement is the body's unit (C25 body-file marker, C26 `--label feature:`); (c) goal binding: `gather_facts` scans `.sdlc/state/work/*.json` for the work record whose `worktree` contains the cwd (the existing record shape: `rec["worktree"]`); if one exists and its goal differs from the `<goal>` positional, `track` exits 2 and files nothing (C27); a cwd inside no goal worktree (root checkout, loop orchestrator) has nothing to bind to, and then the positional is trusted: stated residual. The count and the plan are per named goal, so naming another goal at the cap would only move that find to that goal's own slice count, never skip the router.
- `--target-unit` does NOT feed routing. It is not read before the routing decision. What it still does: after a `separate` decision, it overrides which open unit the filed issue is stamped with (existing behaviour in `create_tracked_issue`, unchanged); it cannot turn a `slice` into a filing, because the refusal exits before `create_tracked_issue` is reached.
- `AmbiguousUnit` on the goal or on the item: there is no honest unit and no named reason applies, so `track` refuses with exit 2 and the ambiguity message and files nothing (consistent with `features.read`'s own "treat as unresolvable, never first-wins"). A failed goal read (source error) also exits 2: routing needs the recorded fact; it does not guess.
- `added`: `added_count(sdlc_dir, goal) = max(len(read_record(...)["added"]), number of "## Added slice " headings in the main plan copy)`, the record written only by `add_slice.py`. The record is machine-local (`.sdlc/state`, gitignored): a second machine starts at zero, so the record alone gives a ceiling of `cap x machines`. The heading count travels with the plan (it is on the branch) and can only RAISE the count, so it closes that gap whenever the plan is present; a goal whose plan is absent on a machine falls back to the record. Stated as a ceiling, not a guarantee.
- No flag, environment variable or config key supplies a reason: `--kind` is still validated against `TRACK_KINDS` and still sets nothing about routing (a test routes every kind identically).
- No goal (`nogoal`, a filing with no parent) has nothing to slice into: `track` files as today, no routing (flagged).
- `followups.mode: file` (opt-out): `track` files as before the change; no routing, no reason marker (flagged).

### The code-owned record
`.sdlc/state/followups/<stem>.json` (gitignored state, so no root-checkout file blocks `git pull`):
`{"first_routed_at": "<iso>", "added": [{"slice_id": "<sha256[:16] of goal stem + NFKC-casefolded, whitespace-collapsed title>", "plan_sha256_before": "...", "ts": "<iso>"}]}`. The id is the slice's IDENTITY (goal + normalized title), NOT its criteria text, so a retry with edited criteria cannot count a second slice (finding 5). Two distinct slices must carry distinct titles; a reused title is the same slice by definition.
Written with `state.atomic_write_text` under an exclusive `fcntl.flock` on a sibling `.lock` file (the pattern `dag_store.py` already uses), read-modify-write inside the lock, so two sessions on one goal cannot lose a count. Bounded: the list is capped by `cap` because the verb refuses at the cap (it cannot grow past `max_added_slices`). A corrupt or unreadable record reads as REFUSE (verb) / exit 2 (track), never as zero (a silent zero would reopen the cap).

### The add-slice verb (contract)
`python3 skills/sigma-loop/scripts/work.py add-slice <sdlc_dir> <goal> --title T --criteria-file F [--test SELECTOR ...]`
Order matters for crash recovery. The per-goal exclusive `fcntl.flock` (sibling `.lock`) is taken at the top and HELD ACROSS STEPS 1-6 (finding 3): check, plan edit, extend and count are one critical section, so two sessions cannot both pass the cap check and both write. On a platform without `fcntl` the verb REFUSES (exit 5).
1. Resolve stem (same unsafe-goal check as `acceptance.path`; unsafe -> exit 2, nothing written); take the lock; read the record; compute `slice_id`.
2. Idempotent resume, defined: `slice_id` in the record -> print "already counted" (and, when the plan's heading text for that title differs from the new criteria, say the criteria were NOT replaced) and exit 0. NOT in the record but the main plan already holds a heading `## Added slice <n>: <title>` whose normalized title hashes to this id -> resume: skip the plan write, finish steps 6 and the count. Identity is the title, so edited criteria on retry never duplicate (finding 5).
3. Refuse (exit 3, names the reason) if `route(unit, unit, added_count, cap)` is not `slice` (i.e. `slice-cap`: "file it with `handoff.py track`; it will be filed as a separate goal with reason slice-cap"). The verb adds to THIS goal, so its item feature is the goal's own. Evaluated inside the lock.
4. Probe BEFORE any write: if `acceptance.path(sdlc_dir, goal)` exists and `not hasattr(acceptance, "extend")`: refuse loudly (exit 4), naming `acceptance.py extend` (#2222) as the missing verb, writing nothing. If no acceptance file exists there are no criteria to extend; the verb proceeds and says "no acceptance record: criteria not extended".
5. Append `## Added slice <n>: <title>` (task + steps + done-when from `--criteria-file`) to the plan `.md` in the main copy and, when `work.plan_copies` reports a tracked branch copy, the byte-identical transform in the branch copy (so `record_plan_review`'s every-copy-holds-these-bytes rule holds). `plan_copies` (work.py:4224) returns the branch copy only when it is tracked AND unmodified; a modified tracked branch copy is treated as ABSENT and the main copy alone is hashed. The verb edits the main copy always and the branch copy only when `plan_copies` reports it, so the branch copy is never left half-edited; both states are tested explicitly (finding 4): (i) main edited, tracked clean branch copy edited identically; (ii) branch copy already carrying an uncommitted edit (`plan_copies` -> absent): only main edited, the verb prints a notice that the branch copy was not touched and `work.py commit` will carry main's bytes over. Append `--test` selectors to `## Tests` only when no existing file selector already covers them; refuse before writing if the result would exceed the 25-selector parser ceiling (the message tells the agent to use a file selector; this is a verb refusal, not a routing reason).
6. Call `acceptance.extend(...)` (signature owned by #2222; read at implement time from origin/main, and refuse loudly on a TypeError rather than guess), then append to the record (count bumped LAST, so a crash before it re-runs cleanly).
7. Print the next gestures: record a fresh plan-review of the new plan bytes (`work.py record-plan-review`), re-run implement, review, retro in order, run verify again.
It never touches `<stem>.slices.json` (the plan-review hash excludes it; flagged); when that file exists the verb prints a notice that the parallel manifest was not updated.
Probe-failure cases, each its own refusal: `acceptance.extend` raising `TypeError` -> exit 4 "signature unknown, not guessing", plan and record unchanged (the call is made BEFORE the count and, where the plan was already written in this run, the verb reports the half-state and the re-run resumes it); `.sdlc` acceptance file present but `extend` absent -> exit 4 (C7a); acceptance file absent -> no probe (C7b).

Before: unreadable/invalid config -> `file` (files the follow-up). After: unreadable/invalid -> `in-goal` (refuses and points at add-slice). Stated, not softened. The `followup-mode` verb's `except` arm prints `in-goal`. On the `track` path `ledger._config` raising (OSError/ValueError) -> `track` exits 2 with the config error, files nothing (a filing must not guess the mode); tested.

### Scalability / resiliency / liveness / safety
- Per added slice the goal re-runs plan-review, implement, review, retro (and a re-seal if `gates.sealed_acceptance` is on): at the cap that is up to 10 re-reviews of one growing plan. Stated, not measured. Ceiling on the plan `## Tests`: 25 selectors (parser), so slices rely on file selectors.
- Count ceiling: the record is machine-local, so on its own the cap holds per machine, not fleet-wide (`cap x machines`); the plan-heading count (see `added`) narrows this to the cap wherever the plan is present. Stated as a ceiling.
- Serialised chokepoint: the record flock is per goal and is held across the verb's check, plan edit, extend and count; no global lock. The verb's critical section is local file IO plus one `acceptance.extend` call. Cost per filing: one extra goal read (already paid by `unit_of`) plus one registry read.
- Doctor row: one list call, ceiling 200 open `sdlc:followup` issues; above it the row says so and under-reports (same accepted ceiling as `_dependency_marker_scan`). Fail-open: unreadable -> no row failure.
- Recovery: crash in the verb is resumable by re-running the same command (slice_id idempotency); the lever is polite (re-run, no re-ship); a stuck record has a documented fix (delete `.sdlc/state/followups/<stem>.json` only after confirming the plan's `## Added slice` count).
- Safety: no new background process, no new network call beyond one comment on the parent; limits derived from `max_added_slices` config, not constants.
- Host-agnostic: everything is Python; skills only name the verb.

### First green verify (criterion 5), honestly
No detector exists and none is invented. Every find, at any time, routes through the same function. The "second verify" is forced by existing machinery ONLY WHEN `verify.enforce` IS ON: `work.py pr` / `state.done_refusal` reject verify evidence whose content fingerprint differs from the worktree (`work.py:4402-4410`, gated by `state.enforce_enabled(config.get("verify"))`; with enforce off the function returns "" and nothing forces a re-verify). Criterion 5's second-verify contract is therefore CONDITIONAL on enforce, said plainly here, in the criteria map and in `docs/configuration.md`; no claim beyond that. The test runs with `verify.enforce` ON and also asserts that with it OFF no refusal occurs (so the conditionality is a pinned fact, not prose). The test proves: after a green verify, a same-feature find via `track` is refused with the add-slice gesture (no deferred-comment text anywhere), the verb succeeds, and the stale evidence is refused until verify re-runs. The plan edit alone does not invalidate evidence; the slice's own code change does (stated in the test docstring).
