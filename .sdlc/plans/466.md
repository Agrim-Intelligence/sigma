**Code (two small changes; the first plan version had a third, an inbox cap, withdrawn after review):**
1. `setup_wizard.write_dismissed`: keep only names in `_MODES`. The reader already ignores any other
   name (`wizard_status` checks `name not in _MODES` first), so the filter changes no behaviour and makes the
   file at most `len(_MODES)` names by code instead of by skill prose (`len(_MODES)` is computed in the test
   and the doc test, not quoted: the code comment says seven, the dict holds eight). Version skew, named in the
   doc: a newer plugin that added a mode, then an older plugin rewriting the file, drops that dismissal and
   the user is asked once more.
2. `work.prune_terminal_review_copies`: require `evidence.resolve() == sdlc.resolve()/"evidence"/stem`
   (the symlinked-parent escape confirmed in research: a symlinked `.sdlc/evidence` makes the current code
   `rmtree` a directory outside `.sdlc`; it also covers a symlinked `.sdlc` because both sides resolve) and
   print one stderr line when it refuses, like the neighbouring `except` does, so a deliberately symlinked
   evidence root is not silent. Everything else in the function is unchanged. Its callers invoke it only for
   a goal that has reached a terminal record, so the "never a live or claimed owner's data" rule is the
   caller's gate, unchanged here; the doc says so.

**Inbox, withdrawn cap (plan review round 1, FIX-FIRST):** a hold-at-cap in `watch.tick` is not the small
change it looked like. (a) `tick` saves the cursor BEFORE it writes the inbox, so a crash or full disk between
the two loses that tick's items from the inbox today (they stay in the ledger); a hold would build on that
ordering. (b) A held tick leaves the cursor, so the first tick after a clear writes the whole backlog in one
batch and `loop.py next` prints all of it to stderr: the growth is deferred, not capped; bounding it needs a
partial cursor or print chunking, which touches the delivery invariant. (c) An undecodable byte in
`inbox.md` makes `read_inbox` raise `UnicodeDecodeError`, which `_surface_inbox` swallows, so a stat-based hold
could never release. (d) A hold is only visible in `watch.log`; the age of an unread inbox is not surfaced by
doctor or session start. These are real, out of scope for a classification slice, and filed as ONE queued
follow-up. The row's disposition is the honest one: `inbox.md` grows with ledger items addressed to the
operator until a loop pick reads and clears it; ceiling = 517 B per item measured at one item per tick
(196 B per item in one batch) times the items addressed to the operator since the last pick, about 50 KB per
day at 96 ticks, never more than 2.1x the ledger bytes those items occupy (250 B per entry); reclaim =
`loop.py next` (reads and clears) or deleting the file (the cursor has advanced, so deleted items do not
resurface, and the ledger remains the durable record). A test pins the per-item ceiling and the clear.

**Documented decisions (no code):**
- Singletons and markers (`owner.json`, `drift.meta.json`, `reconcile.meta.json`, `kg-refresh.json`,
  `setup-wizard-cache.json`, `setup-wizard-dismissed.json`, `STATE.md`, the two spend files, the pid,
  heartbeat, stop, `coexist.notice`, `kg-warned.stamp`, `ledger-delivery-attempt`): `capped`, each with its
  one-file size and the writer that bounds it (overwrite in place, window prune on write, 4096-entry cap
  with reset by `start_run`). Spend files are bounded by their time window and the call rate (derived
  ceiling stated, not measured live).
- Cursors (`agent-watch`, `comment-watch`, `channel-notify`): **intentionally unbounded, each with its own
  stated ceiling; no key is retired when a claim closes.** `comment-watch` keys are goals with an open claim
  (at most 20 ids each, replaced per tick) and `channel-notify` keys are ledger candidate ids, so both stay
  at or below the goals or candidates the ledger has ever held. `agent-watch` keys are `goal:thread:pid`
  taken from registered agent marker directories (`loop.agent_threads`), NOT from ledger entries: one claim
  can yield a key per dead respawned agent, and with `notify.email` on no ledger note is written per key,
  so its ceiling is the number of confirmed agent deaths (pid recycling aside), not the ledger. All three
  are off by default (`agent_watch`, `comment_watch`, `ledger.autowatch` need opt-in). 19, 630 per goal and
  45 B per key measured. Reclaim: delete the file (self-healing: one repeat notification per key). The test
  checks bytes per key through each cursor's own `_save_cursor` on synthetic keys, which pins the
  per-key cost, NOT the key-set bound (that rests on the code reading above); its docstring and the doc say
  so. Key retirement for closed claims is part of the queued follow-up.
- `embeddings.json`: `capped` at 2,000 entries (existing `_EMBED_CACHE_MAX_ENTRIES`, existing tests
  cited). The cap is entries, so bytes are 15.6, 62.3 and 124.6 MB at 384, 1536 and 3072 dimensions and
  `json.loads` costs 87, 341 and 687 ms per pick. The honest byte ceiling is stated; a dimension-derived
  byte bound is filed as a queued follow-up (changing eviction can force paid re-embeds, so it is not
  slipped into this slice).
- `inbox.md`: intentionally unbounded between loop picks (above). `.sdlc/config.json`: operator-owned singleton rewritten in place, never
  pruned (it is the configuration). `.sdlc/*`, `.sdlc/.sdlc/`, `.sdlc/state`, `.sdlc/state/`: prose and
  rollups, no writer; `.sdlc/.sdlc/` costs 83,798 B once and a repeat creates nothing (measured).
- `<home>/`: out of scope, host-owned. The scan row is the onboarding control's isolated scratch profile;
  Sigma never prunes a host configuration root. The new control test (below) is the machine check.
- No `unscanned` waiver: the scan produces all 26 patterns. `review-queue.md` is #459's row; reported, not
  claimed.
