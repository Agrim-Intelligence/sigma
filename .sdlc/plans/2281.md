## Design (as built; verify against code, do not rebuild)
- Security: a recorded query is data. Every search is the list `["git", "--literal-pathspecs", "-C", root, "grep", "-n", "-I", "-E", "-z", "-e", pattern] + ([commit] if commit else []) + ["--"] + paths`, `shell=False`, pattern a single list item after `-e`.
- Refs: every ref (`--ref`, `--base`, config, dossier) goes through `resolve_commit(root, ref, run=None)` = `git rev-parse --verify --end-of-options <ref>^{commit}`; only the full hex id travels on. Unresolvable or dash-leading refs are refused in one line.
- Two fixed commits, never HEAD or a merge base: the dossier's `**Searched at:**` commit and the tip of the remote-tracking base ref (`base_ref`, mirrors the work-record / configured-default rule in `work.py`). A hit is `(file, text)`, line number ignored.
- Bounds: `QUERY_TIMEOUT = 30` per query, `MAX_SECONDS = 120` per run (stop line names `<k> of <m>`), plus the judgement caps recorded in the CHANGELOG (200 hits/query, 1,000 lines, 8 MiB read; not measured, labelled as such).
- Exit 0 for every informational case; 2 only for usage (`--ref` with `--new-since-research`, unknown option, missing value). Never fetches, never writes.

## Scale and failure notes
- Cost is per query: two `git grep` runs (base and searched-at) per recorded query, at most 25 queries, bounded by 30 s each and 120 s total; at 10x queries the 25-query cap and the 120 s ceiling hold, the tail is reported as `k of m`. Not measured against a large repository; the limits are caps, not timings.
- Recovery: no state is written, so a rerun after any failure is just a rerun. A stale base is made visible by the fetch-age line, not fixed (the verb never fetches).
