# Plan 2079: run a goal's planned tests with the project's Python

Goal: the planned-test, flake and diff-revert runs use the goal worktree's own interpreter (its `.venv`, else a
one-time uv-built `.venv`, else `python3`), and say plainly which interpreter was tried and why when it cannot run.

## Design
- New module `skills/sigma-loop/scripts/goal_python.py`: `resolve(root, env=None, budget=...)` returns an object with
  `path`, `how`, `notes`; it raises `InterpreterError` (a `ValueError`) naming the interpreter and how it was chosen.
  No config is read: the choice comes from the filesystem and `PATH` only (AC-5, no new tracked setting).
- Order: (1) `<root>/.venv/pyvenv.cfg` present: that venv's interpreter. (2) nothing at `<root>/.venv`, `uv.lock` and
  `pyproject.toml` present, `uv` on PATH, `UV_PROJECT_ENVIRONMENT` unset, no enclosing `[tool.uv.workspace]`: build the
  venv once with `uv run --frozen --project <root> python -c pass`, `UV_PROJECT_ENVIRONMENT=<root>/.venv` in the child's
  environment only, `start_new_session`, killed as a group at the budget. (3) otherwise `python3`.
- Every chosen interpreter is probed once with `-c "import pytest"`. A failure raises; there is no fallback to another
  interpreter. A failed or timed-out uv build removes the venv it made; the failure is cached per process, so uv is
  never run twice. `git status --porcelain` before and after the build: anything new is named.
- The three modules take a `python` argument defaulting to `"python3"` (existing tests unchanged); `loop.py` resolves
  once per process and passes it at every call site: `loop.py red`, verify's planned-test proof, `_planned_scope`,
  `_changed_tests`, `_flake_verdict`, `_diff_revert_verdict`.
- `loop.py red` refuses (exit 2) and verify records no `provenance` (so no green, no red) when resolution raises.
- Not built: the sealed-acceptance runner, init's `verify.command`, #1764's other items.
- Limits stated in the docs, not closed: the diff-revert scratch tree runs under the goal worktree's interpreter, so a
  package installed editable from the worktree or a src layout can import the unreverted code; no real uv build and no
  real container were measured.

## Test list (tests first; each clause broken on its own for the controls)
1. venv present (AC-1): the resolver, `red_green.observe`, `flake_check.check` and `diff_revert.run` all execute the
   venv's interpreter (a fake that records its argv); `python3` on PATH is never called.
2. uv project without a venv (AC-2): a fake `uv` on a temp PATH. Exactly one build; argv is `run --frozen --project`;
   `UV_PROJECT_ENVIRONMENT` is the worktree `.venv`; the child is a session leader; pytest is never run under uv; the
   second resolve does not call uv again. One test per clause that disables the build: `.venv` present, no `uv.lock`,
   no `pyproject.toml`, no `uv` on PATH, `UV_PROJECT_ENVIRONMENT` set, an enclosing workspace.
3. neither (AC-3): `python3` as today, `how` says why uv was not used.
4. broken interpreter (AC-4): `pyvenv.cfg` with no interpreter, an interpreter that cannot import pytest, a uv build
   that exits 1, a build that times out (whole group killed, venv removed), a build that leaves an unignored file
   (named). `loop.py red` exits 2 naming interpreter and how; verify records no `provenance`; no red is recorded;
   uv is not retried in the same process.
5. AC-5: the resolver never reads `.sdlc/config.json`; `shell_policy` is untouched and not imported.
6. Structure: no `"python3"` literal at a pytest call in the three modules; every `loop.py` call site passes `python`.
7. Docs: configuration/verify docs, cloud-sessions and CHANGELOG name the order and the unmeasured parts.
