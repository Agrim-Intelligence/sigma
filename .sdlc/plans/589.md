# Plan: #589 make the commit-time secret scan independent of diff formatting

Inputs: issue #589, `.sdlc/research/589.md`, `.sdlc/acceptance/589.md`.

## Design

Stop reading the diff's display form. `_staged_added_rows` makes two reads with one fixed flag set
(`--cached -M --no-ext-diff --no-textconv --no-color --text --submodule=short --inter-hunk-context=0 -O<null>`): `--raw -z`
for the ordered raw path list, and `--unified=0` for the patch. The n-th `diff --git` section is the n-th raw entry, so
no path is parsed from a header (`diff.noprefix`, `mnemonicPrefix`, TAB after spaced names, quoting all irrelevant). A row
is a header only outside a hunk; hunk extent comes from the `@@` counts, so added rows like `++ x` or `+++ x` are data.
Lines split on `\n` only. `--text` makes binary attributes and NUL bytes produce rows. Anything unaccounted for (count
mismatch, truncated hunk, "Binary files", unmerged entry, git failure) raises, which `_secret_refusal` already turns into
a refusal. `_secret_refusal` also turns any hit whose path the status read did not name into an offender instead of dropping it.
`_diff_header_path` and `import ast` are removed. A type change (file/symlink) is one raw entry and two patch sections, so it counts twice; an unmerged raw entry raises. The patch is streamed, so memory is bounded by the longest line.

`_run` drops repository-location variables (`GIT_INDEX_FILE`, `GIT_DIR`, `GIT_WORK_TREE`, ...) from `git` calls so `add`/`commit` and the scan (which already ignored them) address one repository and one index; found by plan review: with `GIT_INDEX_FILE` exported the scan read an empty index while `commit` committed another.

Cost: two git reads however many files change (300 small files: 0.05 s). Because `--text` makes a staged binary a patch of its own bytes, time is linear in staged bytes (plan reviewer measured about 3.5 s for 14 MB of real binaries, roughly 48 s for 200 MB of random data) where the old scan skipped binaries; at 100x that is the regex scan. Memory is bounded by the longest line, which for a binary or minified file can be the whole file (reviewer measured 2.1 GB peak at 200 MB), so that is the 100x ceiling. Compiled files hit the content rules measurably often (reviewer: 6 of 120 sampled system executables, 2 of 86 compiled .pyc), and the old scan skipped them. `work.allow_secret_paths` clears a name only and must keep doing so (an allowlisted `.env` still has its added lines scanned; plan review caught a draft that widened it), so a compiled file that hits has no in-loop lever: it is committed by hand outside the loop or kept out of the repo, stated in docs/enforcement.md and queued as one grouped follow-up (a separate content-allowlist key, doc drift in the allowlist wording).

Stated residual limits, unchanged by this goal: text in UTF-16 is not matched; the scan and `git commit` read the index separately (a pre-commit hook that re-stages could commit unscanned bytes); the risk detector (`_risk_categories`, journal only) still sees the caller's `GIT_INDEX_FILE`; a dangling `diff.orderFile` fails `commit()`'s own earlier `--name-only` read loudly before the scan runs.
