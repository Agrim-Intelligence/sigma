## Risks (the five properties)
- RELIABILITY: only a positively confirmed `merged: true` or non-empty `merged_at` claims merged (existing function); an unreadable PR is UNKNOWN and falls through, never merged. Unmeasured: live GitHub's response to `GET pulls/<n>` for a PR merged by a different actor, and live latency of the extra read. The fixtures are derived from the documented REST body, not captured.
- SCALABILITY: O(1) per `merge` call. Cost claim, measured only by the fake runner's call list and not live: exactly +1 REST read (`GET pulls/<n>`) on every `work.py merge`, bounded, no retry. On a merged PR it saves the gate's 4 UNKNOWN retries with 3, 6, 12 s backoff. REST core budget impact at 100x merges per hour is +100 reads against the 5,000 per hour primary limit; not measured live. The merge-reconcile pass (10 PRs per pass) does not call `merge()`, so it is unaffected.
- RESILIENCY: a crash after GitHub merged but before `record done` now self-heals by re-running `merge` (idempotent) instead of parking. Replays are deduped by the delivery receipt and stable keys (pinned by the twice test); a later `record done` goes through `done_refusal`'s own read, unchanged, and replays the same keys. Not self-healing, unchanged from today and pinned rather than fixed: a delivery-receipt key conflict raises `ValueError` from `_record_confirmed_merge`, so `work.py merge` exits 1 with `work: merge delivery receipt key conflict` and an empty stdout, on the short-circuit exactly as on the direct path; this plan names no new lever for it (none is documented today, and adding one is outside this goal's scope; it is a pre-existing gap on the direct path, not one this change opens). With the goal's worktree deleted, the remote branch delete and the issue close both fail inside the vanished cwd and are caught: the line still says merged, the close clause says it could not close and names `record done`'s retry, and `finish()` deletes the remote branch again once it confirms MERGED; until then the remote branch remains.
- SAFETY: the closed-unmerged branch performs no deletion and no issue close. The merged branch runs the same post-landing helper as the direct path, with the same raising behaviour (only the key conflict above escapes). Not host-specific: pure Python in `work.py` plus a doc, REST only, no GraphQL, no hook dependence.
- LIVENESS: no new background work, no new trigger. `_upkeep_merge_trigger` stays the last effect on both paths (pinned). The test-trust advisory is NOT skipped for a merged PR (orchestrator ruling); it is skipped only for a closed-unmerged PR, which has no landing, and for a missing worktree, where the old code would have recorded a false `pass`.
