## Design

**1. Gate-only value filter, `skills/sigma-loop/scripts/scrub.py` (BR-1, BR-2).** `_SECRET_PATTERN_SPECS`,
`SHAPE_RULES` and `COMMIT_SHAPE_RULES` keep their source and contents byte-identical (BR-3, BR-4, BR-5), so
`scrub()`, `tools/leak_scan.py` and `tools/readiness/exposure_scan.py` see no change (BR-13, BR-14, TD-8).
The post-filter lives in a new gate-only `commit_secret_findings(text)`, which `commit_secret_hits` wraps
(see "Code files" below); nothing outside the commit gate calls either.

- **Which match is filtered.** A `credential-assignment` match whose group 1 starts where the match starts:
  that is the anchored legacy rule (group 1 is the key). The quoted `SHAPE_RULES` instance captures the
  value in group 1, so it never qualifies and stays exactly as today. No identity or index coupling to the
  table, and nothing that can fail at import (scrub.py is imported by the research hook and both scanners).
- **Parse the line, not the match.** `_ASSIGNMENT_SEPARATOR = re.compile(r"[\"']?\s*([:=])\s*([\"']?)")`
  matched at `match.end(1)` yields the separator and the character after it. A non-empty quote group means
  quoted, and a quoted value is ALWAYS refused (the anchored match's own optional quote hides this, so it is
  read from the line). No separator match (cannot happen for the anchored rule) means refuse. The value is
  `text[sep.end():match.end()]`, the rule's own `[^\s"'<>&]{4,}` run.
- **One predicate, `_secret_like(token)`**, used for every token the filter judges. True when the token:
  - starts with a prefix in the closed tuple `_SECRET_PREFIXES = ("ghp_", "gho_", "ghu_", "ghs_", "ghr_",
    "github_pat_", "sk_live_", "sk_test_", "rk_live_", "rk_test_", "AKIA", "ASIA", "AIza", "eyJ", "xox")`;
  - has 3 or more letter/digit alternations between adjacent ASCII characters (a random run alternates
    constantly);
  - holds a run of 24 or more ASCII letters and digits (`[A-Za-z0-9]{24,}`; an underscore breaks the run,
    so long snake_case names pass);
  - or is 6 or more characters holding both an ASCII letter and a digit, unless the whole token is an
    upper-snake name `[A-Z][A-Z0-9_]*` (the env-name and `HS256` shape).

  Hyphenated provider prefixes (`sk-`, `glpat-`, `pypi-`, `xoxb-`) split into segments whose body the
  other clauses refuse; `hf_`/`npm_` are left out of the tuple because `hf_hub_download(` is ordinary code
  and their real tokens are long random runs the 24-run clause refuses.
- **Rest-of-line scan, before any exemption (closes the head-only hole).** The filter judges every
  `[A-Za-z0-9_]+` segment from the separator's end to the end of the line, and every whitespace-separated
  word inside each quoted literal (`"..."`, `'...'` or a backtick string; escape-aware, single line, paired
  left to right from the start of the line) that ends after the separator. If any of them is
  `_secret_like`, the hit stays, whatever the value looks like. That covers every segment of a dotted value
  (the `SG.`, `sk.eyJ`, `hvs.`, `ya29.` and `dp.st.` shapes), a literal inside an expression (a getenv
  default, a `SecretStr(...)` or `b64decode(...)` argument), a literal after an annotated default, and a
  run after a boolean or after the value. A quoted literal that straddles the separator counts as after it
  (fail closed). Cost: `_last_secret_like_end(text)` makes ONE pass over the line and returns the largest
  end offset of a secret-like token; it is computed lazily, at most once per line, and only when an
  anchored match has an unquoted value. Each match then compares one offset with its separator end, so a
  line with k anchored matches costs O(line) + O(k), not O(k x line).
- **Assigned-literal guard, also before any exemption (revision 3; strict form in revision 4; the whole
  rest of the line in revision 5).** `_ASSIGNED_LITERAL =
  re.compile(r"(?<![=!<>])=(?![=>])[\s(]*(?:\\?$|[bBrRuUfF]{0,2}[\"'`])")` is an assigning `=` (not part
  of `==`, `!=`, `=>`, `<=` or `>=`, which are comparisons and arrows) whose right side, after spaces and
  opening parentheses, either STARTS a quoted literal of any length (any quote character, so a
  triple-quoted `"""..."""` or `'''...'''` too, with an optional `b`/`r`/`u`/`f` prefix) or is empty or a
  lone continuation backslash (the literal is wrapped onto the next line).
  `_last_assigned_literal_start(text)` makes ONE `finditer` pass over the line and returns the largest
  start offset of such an `=`.
  Like `_last_secret_like_end`, it is computed lazily, at most once per line, and only when an anchored
  match has an unquoted value. A match keeps its hit when that offset is at or after its separator's end:
  some `=` after the separator assigns a literal. That is the spaced annotated default (`: string = "..."`
  in TypeScript, `: String = "..."` in Kotlin, `: Optional[str] = "..."`, `: bytes = b"..."`), the same
  without spaces, parenthesised (`= ("...")`), triple-quoted, wrapped (`: Optional[str] = (` at the end
  of the line), a concatenation that starts with a short literal (`: string = "ab" + "..."`), a chained
  assignment `= cfg.x = "..."` and a keyword argument `(name="...")`. **New in revision 5** (review
  refinement 1): each of those after an annotation that holds a space, and a no-space `=` that sits
  inside the value run without ending it. Examples: `: string | undefined = "..."`, `: bytes | None =
  b"..."`, `: Annotated[str, X] = "..."`, `: Optional[str]=("...")` and `: Optional[str]=b"..."`.
  Revision 4 checked only two fixed positions (the end of the value run, or the run's own final `=`), so
  it passed all five, while the old gate refuses all five (measured). Both of revision 4's positions lie
  after the separator, and neither is preceded by `=`, `!`, `<` or `>`. So the scan refuses everything
  revision 4 refused (measured too: no anchored match revision 4 refuses passes revision 5 in any of the
  four census trees), and the fixed-position code and its run-final special case are removed. It applies
  after either separator, since a chained `=` assigns the literal too. The right side is revision 4's,
  NOT the review's narrower "a quote holding 4+ characters": a 4+ count inside one quote passes
  `"""..."""` and `'''...'''` (the second character closes the first quote) and the wrapped form,
  reopening revision 4's own findings mid-line. Revision 3 required 4+ characters inside one
  unparenthesised quote. That passed the triple-quoted and parenthesised forms the old gate refuses
  (review finding), and dropping the count also closed the wrapped and short-concatenation forms.
  Measured cost of the whole-line scan against revision 4's fixed positions (Limits): 1 of this repo's
  28 passes, 0 in the stdlib and npm's global modules, 34 of 1,478 in site-packages. Every one is a
  call or signature where a LATER argument or parameter has a quoted literal, e.g. `KEY = x.y("...",
  kw="...")`. The review's census of the same form found the same losses. Linear: see "Linear time".
- **Then exempt ONLY these unquoted values**, each tagged with where it applies (anything else keeps the
  hit). Every whole-value form is a `fullmatch` that allows only trailing closers `[,;:)}\]]*`:
  - an expression, in a CODE file only: `_EXPRESSION = r"[A-Za-z_][A-Za-z0-9_]*(?:[(\[]|\.[A-Za-z_])"
    r"[A-Za-z0-9_.()\[\],;:?!=*+-]*(?:\}[,;:)}\]]*)?"`, a `fullmatch` against the WHOLE value run
    (revision 3): an identifier head that starts a call, a subscript or an attribute read whose dot is
    followed by an identifier start, then only expression characters (identifier characters and `. ( ) [
    ] , ; : ? ! = * + -`), then optionally a `}` and closers. Covers R1, R2, `getenv(...)`, `settings.x`,
    `cfg[0]`, `Optional[str]`, a TypeScript `x!`. A dotted value holding any other character, such as
    `Pa.ss@word!`, is refused. **Revision 4 folds the closers in** (review finding): revision 3 appended
    the closer class `[,;:)}\]]*` after a body class that already holds `, ; : ) ]`, so a failed
    `fullmatch` tried every split of a closer run between the two, and `a(` followed by 32,768 `)` and
    `@` took 6.9 s (measured; 7.3 s through the whole filter). Every closer except `}` is already a body
    character, so the closers reduce to the optional `}` tail above, which no body character can match:
    the same language (0 differences over 300,000 random strings against revision 3's form, measured)
    matched in one greedy pass, 1.3 ms for that line.
  - a boolean or null word, whole, in EVERY file: `True False true false None null nil undefined` plus
    closers (R4, and a `None` default closing a signature, `None):`, measured in the stdlib). A word
    followed by anything else (`True,` then a run) is refused.
  - after a `:` separator only, in a CODE file only, a type from the closed set `str bytes bool int float
    Any SecretStr string boolean number any unknown String`, optionally a `|` union of set members and
    `None`/`null`/`undefined`, plus closers (R3, TypeScript `string;`, `string|null;`). No `=` may follow
    a type inside the run. Capitalised words are not inferred to be types; the three capitalised entries
    are exact names, so a YAML word such as `Summer` stays refused.
  - one of `COMMIT_PLACEHOLDER_VALUES`, in EVERY file: a new public exact frozenset beside
    `COMMIT_FIXTURE_VALUES` holding `[REDACTED]` (the anchored rule's own `scrub()` replacement) plus
    `[REDACTED:<name>]` for every rule name in `_SECRET_PATTERN_SPECS`, i.e. Sigma's own redaction markers,
    exact, plus closers. No structural `${...}`/`{{...}}`/`<...>` forms. Its comment records the
    deliberate divergence from leak_scan's broader `_PLACEHOLDER_VALUE` (TD-5): a gate's false-positive
    budget differs.
  - Numbers and bare identifiers are NOT exempt, in any file.
- **Code files: a CLOSED suffix set (revision 4; replaces revision 3's config-like mirror).** Only a code
  file gets the expression and type exemptions. In any other file (config, data, docs, an unknown or
  missing suffix) a value is treated as a literal, so the DOTTED sample there is a credential value, not
  an attribute read. `COMMIT_CODE_SUFFIXES` is a new public frozenset in scrub.py: `.py .pyi .js .jsx .mjs
  .cjs .ts .tsx .mts .cts .vue .svelte .java .kt .kts .scala .groovy .gradle .go .rs .rb .php .cs .swift
  .dart .c .h .cc .cpp .hpp .m .mm .lua .ex .exs`. `commit_code_path(path)` is True only when the
  basename has a non-empty stem and its last `.suffix`, exactly as git stores it (case-sensitive, so
  `a.PY` is not code), is in the set.
  - **Why closed.** Revision 3 treated every path outside leak_scan's config-like list as code, so
    `.md`, `.txt`, `my.cnf`, `Makefile`, `.xml` and any unknown suffix got the code exemptions (review
    finding). A closed set fails closed: a file nobody listed keeps every hit the old gate gives it except
    the boolean/null and marker ones. Widening it is a deliberate one-line change that test 25 pins. It
    also makes revision 3's machinery redundant, so `COMMIT_LITERAL_SUFFIXES`, `commit_literal_path` and
    test 25's mirror of `tools/leak_scan.py` are dropped: one list, no mirror to keep in step.
  - **Measured cost (revision 4 prototype, `5f25b99`):** 0 exemptions lost in this repo (all 28 passes
    are `.py`) and in npm's global modules (`.js`, `.py`, `.ts`); 2 of 93 in the stdlib (`.stp` probe
    files) and 7 of 1,485 in site-packages (5 files with no suffix, 1 `.rst`, 1 `.css`).
  - Outside a code file only the boolean/null and placeholder exemptions apply; the rest-of-line scan and
    the assigned-literal guard still run first.
  - `commit_secret_findings(text)` returns `[(rule, column, code_exempt)]`, where `code_exempt` is True for
    an anchored hit that only a CODE exemption clears; it knows no path. `commit_secret_hits(text,
    path=None)` keeps its `[(rule, column)]` shape and drops the `code_exempt` hits only when
    `commit_code_path(path)` is True.
  - **Missing path, deliberately fail closed:** `None` or an empty path is not a code path, so a caller
    that cannot say which file a line came from gets only the boolean/null and marker exemptions.
    `commit_secret_hits(line)` called the old way therefore still refuses R1-R3 and now passes R4. Its
    only production caller, `work.py`, moves to `commit_secret_findings` and always knows the path (git's
    raw name; `_staged_raw_paths` never yields an empty one for a staged file).
  - **Why a tag rather than handing the path to the filter.** `_staged_added_rows` attributes rows to paths
    only after the whole patch is parsed, by position (`work.py:2735-2767`), and its `keep(line, text)`
    callback is shared with `tests/test_work.py`'s `_fake_rows` (984-991) and the two-argument lambda at
    `tests/test_work.py:1363`; changing the callback's arity breaks both. The tag leaves the streaming
    parser, the callback and both test helpers untouched and costs one boolean per hit.
- **Linear time, every added pattern (revision 4; revision 5 adds the line scan).** The gate runs on every
  staged added line, so no added pattern may backtrack quadratically. `_ASSIGNMENT_SEPARATOR` matches at
  one fixed position; `_EXPRESSION` is a `fullmatch` whose adjacent runs share no character (closers folded
  in), and the type, word and marker forms are fixed words (a type may be a `|` union of them) followed by
  one closer run, so nothing can be split two ways; `_last_secret_like_end` is one pass. So is
  `_last_assigned_literal_start`: an attempt fails in O(1) anywhere but at an `=`, and an `=`'s `[\s(]*`
  run stops at the next `=`, so no two attempts rescan the same run. Measured on the revision-4 prototype
  over 14 pathological shapes of about 32,768 characters each (closer, union, comma and bracket runs, quote
  and backslash runs, long dotted chains, 23-character runs, repeated separators, `=` runs, spaces and
  parentheses before a literal): 11 to 49 ms each, against 12 to 28 ms for the old gate on the same lines.
  Three of them (the closer run, the type union, the dotted chain) re-measured at 10x length (about 330 KB)
  took 0.18 to 0.58 s, and at 100x (about 3.3 MB) 2.0 to 4.6 s against 1.2 to 2.9 s for the old gate:
  linear, at most about 3.5x the old gate's per-byte cost. **Revision 5, re-measured** on its prototype
  over those 14 shapes plus 7 aimed at the line scan (an `=` run, ` (` pairs after an `=`, a `:` chain,
  thousands of anchored matches on one line with and without an `=`, runs of `=` with spaces between,
  repeated `= (`), each against the rule table's own scan of the same line (every
  `scrub.COMMIT_SHAPE_RULES` pattern's `finditer`, which is the old gate's cost), best of 3, interleaved:
  7 to 52 ms at about 32,768 characters (65,536 for three), 1.0x to 3.3x the table scan, and the same 1.0x
  to 3.3x at 10x length (0.08 to 0.59 s). Linear. Test 26 pins it relative to that scan (Test notes).
- **TD-1:** identical `(rule, column)` pairs are reported once (R5 is currently listed twice), tracked in a
  `seen` set: a list-membership check made a 10,000-hit line take 1.17 s against 0.19 s with a set
  (measured on the revision-2 prototype). The first-seen entry of a duplicate is always the strictest: the
  quoted `SHAPE_RULES` instance comes first in the table and matches only a quoted value, which the anchored
  instance never exempts. Checked: no test pins a duplicate (`tests/test_scrub.py:45-51`,
  `tests/test_work.py:1602` are single hits), and the refusal header counts paths, not hits.

**2. Content allowlist and path classification, `skills/sigma-loop/scripts/work.py` (BR-7..BR-12).**

- `_line_sha256(text)`: `hashlib.sha256(text.strip().encode("utf-8", "replace")).hexdigest()`, the recipe
  of `tools/readiness/exposure_scan.py:148`, used by both the gate and the helper below.
- `_allowed_secret_content(config) -> (paths, line_hashes, ignored)`, a sibling of `_allowed_secret_paths`
  (unchanged) with the same defensive reading: a non-dict `work` or non-list value reads as empty. An entry
  counts only when it is a dict whose `"rule"` equals `credential-assignment` exactly, whose `"reason"` is
  a non-empty string, and which carries exactly one of `"path"` (non-empty string, compared exactly against
  git's raw repo-relative path, so `*`, `./a.py` or a different case never match) or `"line_sha256"` (64
  lowercase hex). Every other entry (other rule, wildcard rule, missing or empty reason, both or neither
  key, a malformed hash, a non-dict) is ignored and counted in `ignored`. Never raises; never a bypass.
- `_row_hits(line, text, line_hashes=frozenset())`: calls `scrub_module.commit_secret_findings(text)` and
  returns `[(rule, line, column, code_exempt)]` or None. When `line_hashes` is non-empty and the row has a
  `credential-assignment` finding and `_line_sha256(text)` is in the set, the `credential-assignment`
  findings are dropped. Other rules on the same row stay. The text is still never kept.
- `_added_secret_hits(path, allowed=None)`: `allowed` is the reader's triple; the default keeps the
  one-argument call the existing tests make (`tests/test_work.py:1535-1633`). It passes the hash set to
  `_row_hits` through the `keep` callback. Per path, it drops the `code_exempt` hits when
  `scrub_module.commit_code_path(name)` is True, drops `credential-assignment` hits for a path in the
  path set, strips the tag, and drops a path whose hit list becomes empty. The returned tuple arity
  `(rule, line, column)` is unchanged (BR-21).
- `_secret_refusal`: reads the allowlist inside the existing `try` (a reader bug becomes the fail-closed
  "could not be scanned" refusal) and passes it to `_added_secret_hits`, so allowlisted hits are gone
  BEFORE the ordinary-path early return: a fully allowlisted commit makes the pinned three calls (BR-10,
  BR-20).
- Content-hit refusal text (AC-4, TD-6; reordered in revision 4): keeps `<rule> at <path>:<line>:<col>`
  and "no matched value is shown"; drops "committed by hand outside the loop". The loop's docs say "do
  exactly what the refusal prints", so the refusal states the AGENT's move first and never offers the
  allowlist as that move. For a path with a `credential-assignment` hit, in this order:
  1. **The agent's move:** "Remove the literal or replace it with a read from the environment or a secret
     store, then re-run `work.py commit`. If the line holds no secret and cannot be rewritten, park the
     goal: `record parked "<why>"`, naming this rule and location."
  2. **Whose ruling an entry is:** "An allowlist entry is an OPERATOR ruling: an agent never writes one
     itself, attended or not." (Precedent: `references/running.md`'s "Never self-grant" for
     spend-approval.)
  3. **For the operator, narrowest first:** one line in `work.allow_secret_content` in `.sdlc/config.json`
     as `{"rule": "credential-assignment", "line_sha256": "<printed hash>", "reason": "<why>"}`, where
     `python3 <this work.py, absolute> line-hash <worktree>/<path> <line>` prints the hash without showing
     the line. The file argument is the goal WORKTREE's copy (`_secret_refusal`'s `path` joined with git's
     raw path, `shlex.quote`d), so the hash is taken from the staged bytes, not from the main checkout's
     copy; when `_diagnostic_path` redacted the path itself, `<file>` stands in for it. One recipe per
     path, at its first `credential-assignment` line, with "repeat for each listed line". Then the WIDE
     form, labelled as wide: `{"rule": "credential-assignment", "path": <json path, or a placeholder when
     the path itself was redacted>, "reason": "<why>"}` clears every current AND future
     `credential-assignment` hit in that file, a real literal added later included, so it is for a file
     of fixtures only.

  For a path with any other rule: "Remove the value or keep the file out of the repository, else park the
  goal (`record parked`)"; `work.allow_secret_paths` clears a path's NAME, never its content, and
  `work.allow_secret_content` clears only `credential-assignment`. When `ignored > 0` and a
  `credential-assignment` hit remains, one footer line says how many entries were ignored and what a valid
  entry needs. The refusal never contains a line hash.
- `line_hash(file, line_number)` and the CLI verb `work.py line-hash <file> <line>` (no config, dispatched
  before the `_COMMANDS` block like `root`; added to the `--help` map and the usage text): reads the file in
  binary, splits on `\n` only (as `_parse_added_rows` does), decodes that line with `utf-8`/`replace`, and
  prints `_line_sha256` of it. A missing file, a non-integer or non-positive line, or a line past the end
  goes to stderr with exit 2 and nothing on stdout. It prints only the hash, never the line, and the line
  never touches the command line or shell history. No new name ends `_refusal`/`_gate`/`_guard`/`_hold`.
- `ENFORCEMENT_GATES` `_secret_refusal` row (BR-12): `settings` gains `work.allow_secret_content`; the
  mechanism names the value classes the anchored rule now passes, that outside a code file (the closed
  suffix set) only boolean and null words and Sigma's redaction markers pass, that quoted values, any line
  with an assigning `=` after the separator that starts a quoted literal or wraps, and any line with a
  secret-like token after the separator stay refused, the new key as an operator ruling (line-hash form first; an agent
  removes the literal or parks, never adds an entry), `work.py line-hash`, and that a compiled file that
  hits is kept out of the repo (no hand commit).

## Limits stated

- **What "quoted values stay refused" means, exactly.** A quoted value directly after the separator is
  ALWAYS refused, and so is any value with an assigning `=` anywhere after the separator whose right side
  starts a quoted literal or wraps (revision 5: the rest of the line, not only the end of the value run).
  Any other quoted literal after the separator (a positional call argument, a getenv default) keeps the
  hit only when one of its words is `_secret_like`. Measured on 2,000 random letter/digit runs per length
  (revision 2's prototype; revisions 3 to 5 only add refusals, so these are lower bounds for a code file), a run
  placed as a getenv default is refused 56% of the time at 6 characters, 70% at 8, 80% at 10, 89% at 14, 97%
  at 20 and 100% at 24 or more; the same run as a dotted segment of an unquoted value is refused 56%, 70%,
  79%, 90%, 97% and 100% in a code file and always outside one. The misses are runs under 24 characters that
  hold no digit at all (a random 6-character run has none about 42% of the time), plus upper-snake runs with
  fewer than 3 alternations.
- **Now passing `credential-assignment` (residual false negatives, stated):** in a CODE file, an unquoted
  expression or closed-set type after `:` where no token after the separator is secret-like and no assigning
  `=` after it starts a quoted literal or wraps; in EVERY file, a whole boolean/null word or exact Sigma
  redaction marker. Examples: the DOTTED sample in a `.py` or `.ts` file (syntactically an attribute read),
  a dotted value made only of expression characters such as `Pa.ss!word`, a dictionary-word credential as a
  positional call argument or getenv default (letters only), a digit-only one under 24 digits (a numeric
  PIN), an upper-snake run with fewer than 3 alternations, a
  passphrase of plain words with spaces inside quotes, and the random-run misses above. Only the closed code
  suffix set gets the expression and type exemptions: `.xml`, `.plist`, `.tf`, `.tfvars`, `.hcl`,
  `Makefile`, docs, every unknown suffix and `a.PY` get the non-code treatment. Provider rules (`aws-key`,
  `gh-token`, `stripe-key`...) still fire on their own shapes in the same line.
