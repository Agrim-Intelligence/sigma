## Design

**Verifier** `tools/readiness/verify_repo_settings.py OWNER/NAME [--team SLUG] [--fixture FILE]`, stdlib only.

- One choke point, `request(method, path)`: refuses any method but `GET` (raises `RefusedWrite`, exit 2 path), refuses any
  path not matching an allowlist of the exact endpoint shapes below, refuses a slug that is not `[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+`
  (no `..`, no query string, no `graphql`). It is the only place `subprocess` is used, with argv
  `gh api --include --method GET <path>` and nothing else (no `-f/-F/--input/-X`). `--include` gives the HTTP status, so a
  404 is read as a status, not guessed from stderr. `--fixture FILE` reads recorded responses from disk and never
  starts a process.
- Endpoints (GET only): `repos/{r}`; `repos/{r}/branches/{branch}/protection`; `repos/{r}/private-vulnerability-reporting`;
  `repos/{r}/actions/permissions/workflow`; `repos/{r}/teams`.
- Settings judged (PASS or FAIL, closed set), each FAIL printing the command that fixes it:
  `branch-protection` (200, not 404), `required-checks` (the five CI check names all present in `contexts` or `checks[].context`),
  `enforce-admins`, `no-required-reviews` (absent or count 0, so the loop can keep merging), `no-force-push-or-deletion`,
  `auto-merge-allowed` (`allow_auto_merge`, which the loop's arm path needs), `secret-scanning`, `push-protection`,
  `private-vulnerability-reporting`, `workflow-token-read-only` (`default_workflow_permissions: read` and
  `can_approve_pull_request_reviews: false`), `maintainers-team` (slug present on the repository with permission `maintain` or `admin`).
  A missing or unreadable answer is FAIL, never PASS. Exit 0 all PASS, 1 any FAIL, 2 bad arguments, a refused request,
  or a repository that cannot be read at all (nothing is judged).
- Required names are a constant in the verifier, equal (asserted) to the names derived from `.github/workflows/ci.yml`
  (`test (<os>, <python>)` for each matrix `include` entry of job `test`).

**Document** `docs/launch/repo-settings.md`: who runs it and with what token rights; the five check names between
`<!-- required-checks:begin/end -->`; one numbered command block per setting (`gh api -X PUT|PATCH|POST`, JSON via `--input -`);
the verifier gesture; what each setting changes in the loop (required checks make `mergeStateStatus` BLOCKED while CI is
pending so `work.py merge` polls then arms `--auto` only if `allow_auto_merge`, else parks, instead of landing a pending PR;
`enforce_admins` because an admin merge otherwise bypasses required checks; no required reviews because the loop reviews and
cannot satisfy a human approval); evidence for why (2 of 12 merges before CI finished measured 2026-10-01, and a later slot
merged with all five legs pending, because the base had no protection); the REST docs checked with URLs and the date
2026-10-03; what is unverified (the PUT shapes were not applied to any repository, which is item 4's job); out of scope
(rulesets, `strict`, Windows leg). Team membership is never written to a file.

## Test notes
The unprotected fixture is a real 404 `Branch not protected` plus disabled scanning, PVR off, workflow token `write`,
no team. The protected fixture is the same repository with everything on. `test_each_missing_setting_fails_alone` mutates
the protected fixture one setting at a time and requires exactly that setting to FAIL. The CLI tests run the documented
`--fixture` gesture as a subprocess. No test calls GitHub.

## Risks
The PUT body shapes are from the REST docs, not from an applied run (item 4). Fixture shapes for the protected case are
the documented GET shape; a live-shape difference would show in item 4. `contexts` is documented as the required field
of the PUT; `checks` is accepted on read.
