## Design (binding)

### D1. `PR_FIELDS` grows by two; the rollup is its own read
`gh_api.PR_FIELDS` += `mergeable`, `mergeStateStatus`. `statusCheckRollup` is NOT added: it is served only by
`pr_check_rollup_gh` (D2), keyed by an explicit head sha, so `view_pr_gh(..., ["statusCheckRollup"])` still
raises `ValueError` before any call. Still unmapped and refused: `statusCheckRollup` (for `view_pr_gh`),
`reviewDecision`, `latestReviews`, `files`, `changedFiles`, `isDraft`, `url`, anything else.

`to_gh_pr_shape` rules (fail closed; never CLEAN or BEHIND by default, because BEHIND triggers a force-push
rebase in `_reconcile_behind`):

| gh field | REST source | rule | evidence |
|---|---|---|---|
| `mergeable` | `pulls/N .mergeable` | `true` -> `MERGEABLE`, `false` -> `CONFLICTING`, `null` -> `UNKNOWN`; key ABSENT or any other type (incl. the string `"true"`) -> `GhApiError` (kind other). If `mergeable_state == "unknown"` the result is `UNKNOWN` whatever `mergeable` says, so the gate's existing UNKNOWN retry runs and the park reads "mergeability unknown" (research C3) | true/false/null MEASURED 25/25 (orchestrator live parity) |
| `mergeStateStatus` | `.mergeable_state` | accepted ONLY when it is a `str` exactly in `{clean, dirty, unstable, blocked, behind, draft, has_hooks, unknown}` (lowercase, exact): emitted upper-cased. Absent, null, non-string, upper-case (`"CLEAN"`), or anything else (`"ok"`, `"queued"`) -> `GhApiError`. When `mergeable` is null the emitted value is forced to `UNKNOWN` (both fields agree) | `blocked`, `unknown` MEASURED; the other six DERIVED from GitHub docs |
| `headRefOid` | `.head.sha` | unchanged (4a-1): missing/non-str -> `""`, the gate parks `_PARK_NO_REMOTE_HEAD` | 4a-1 |

The field is validated whenever requested, so a request for `mergeStateStatus` alone still raises on a bad
`mergeable_state`, and a request for `mergeable` alone validates `mergeable_state` too (it can force UNKNOWN).

### D2. `pr_check_rollup_gh(run, number, sha, repo=None, *, gql_run=None, env=None, sdlc_dir=None, now=None)`
Returns the `statusCheckRollup` list in gh's shape for exactly commit `sha`. `number` coerced with `int(str(.))`;
`sha` must match `^[0-9a-f]{40}$` else `ValueError` before any call (an empty or branch-name ref can never be
queried). Named limit: a SHA-256 repository's 64-hex head is refused (fails closed: the gate parks unreadable),
although `work.py:5996` accepts 64-hex heads elsewhere; UNMEASURED, documented. ONE `rest()` closure, all-or-nothing, through the existing `_rest_first` (op `pr_rollup_read`):
1. Check runs: `GET repos/{owner}/{repo}/commits/<sha>/check-runs --method GET -f per_page=100 -f page=k`
   (REST default `filter=latest`), `CHECK_RUN_PAGE_CAP = 10` (1000 runs). Each page must be an object with an
   int (not bool) `total_count` and a list `check_runs`, else `GhApiError`. Stop when fetched >= the page's
   `total_count`. A short page while fetched < `total_count`, or the cap reached with fetched < `total_count`,
   RAISES (a missing failing check must never read as green). Never "stop at the first short page" alone.
2. Statuses: `GET repos/{owner}/{repo}/commits/<sha>/status --method GET -f per_page=100 -f page=k`,
   `STATUS_PAGE_CAP = 5`; same `total_count` rule over `.statuses[]`; `statuses` absent / non-list RAISES. The
   combined `.state` is never read (an empty set reports `pending`, MEASURED).
3. Shape, check runs first then statuses (gh order; consumers are order-insensitive except `ci_repair` taking the
   first failing, which this preserves):
   - CheckRun row -> `{"__typename": "CheckRun", "name", "status": upper, "conclusion": upper or "" when null,
     "detailsUrl": details_url}`. Row not an object, `name` not a str, `status` not a str -> `GhApiError`.
     `status == "completed"` with null/empty conclusion -> `GhApiError` (research C6: `work._check_verdict`
     reads empty conclusion + `COMPLETED` as ok, so passing it through would turn "unknown" into a pass).
   - StatusContext row -> `{"__typename": "StatusContext", "context", "state": upper, "targetUrl": target_url}`.
     Row not an object or `context` / `state` not a str -> `GhApiError`.
Fallback (ONE, only on `rate_limit` / `server` / `transport`, never in a cloud session or with
`SIGMA_GH_GRAPHQL=off`, never on 401/404/422/permission-403/proxy, shared breaker and log): the existing
`_pr_fallback(gql_run, str(n), ["statusCheckRollup", "headRefOid"], repo, rest_err)` (it already raises when a
requested key is missing). The result is accepted only if `headRefOid == sha` and `statusCheckRollup` is a list;
otherwise `GhApiError` (kind other): a rollup for a different head is never attached. Cost: 2 calls typical
(`ceil(runs/100) + ceil(statuses/100)`), ceiling 15 calls at the caps.

### D3. `open_pr_for_branch_gh(run, branch, fields, repo, *, gql_run=None, env=None, sdlc_dir=None, now=None)`
For R10. `repo` (`owner/name`) REQUIRED, `ValueError` otherwise (doctor already returns None without one).
`fields` must be a subset of `PR_FIELDS` and may not include `comments` (`ValueError`). REST leg: ONE
`GET repos/<repo>/pulls?head=<owner>:<quote(branch)>&state=open&per_page=1 --method GET` with `<owner>` =
`repo.split("/")[0]`, the same construction as `pr_for_branch_gh` (NOT gh's `{owner}` expansion: research
MEASURED that `{owner}` expands in a query string, but it expands from the process cwd's remote, which may not
be `repo`; doctor's `_real_run` sets no cwd). Body not a list of objects (incl. empty output) -> `GhApiError`;
`[]` -> `None`; `rows[0]["number"]` not a non-bool `int` -> `GhApiError` (kind other, no fallback); else
`view_pr(run, rows[0]["number"], repo)` (list rows carry `mergeable: null` and no
`mergeable_state`, MEASURED) -> `to_gh_pr_shape(pull, fields)`. Op `pr_open_branch_read`. Fallback: ONE
`["pr", "list", "--repo", repo, "--head", branch, "--state", "open", "--limit", "1", "--json", ",".join(fields)]`
built in gh_api: not JSON / not a list -> `GhApiError`; `[]` -> `None`; a row lacking any requested key ->
`GhApiError`. Named difference (DERIVED, not re-measured): `gh pr list --head X` matches any owner, REST
`head=<owner>:X` same-owner only; a fork landing PR becomes invisible (advisory row: no alarm).

### D4. `gate()` wiring (R1) and when the rollup is fetched
Decision: the rollup is fetched AFTER the UNKNOWN loop settles, once per pending round, and only when the
settled read carries a non-empty `headRefOid`. Inside the loop each attempt is
`gh_api.view_pr_gh(_pr_api_run(run, rec["worktree"]), rec["pr"], ["mergeable", "mergeStateStatus", "headRefOid"],
sdlc_dir=sdlc_dir)` (1 REST call). After the loop (on every path that reaches today's
`remote_head = ...` line) and BEFORE the local-head read, if `remote_head`:
`data["statusCheckRollup"] = gh_api.pr_check_rollup_gh(_pr_api_run(...), rec["pr"], remote_head, sdlc_dir=sdlc_dir)`,
RETRIED on the same budget as the pull read: up to `UNKNOWN_ATTEMPTS` attempts with
`sleep(UNKNOWN_BACKOFF * 2 ** attempt)` between them; only after the last attempt fails ->
`return False, f"{_PARK_PR_STATE_UNREADABLE} ({exc})", {}` (today's read-failure posture). The retry is
load-bearing: in a cloud session or with `SIGMA_GH_GRAPHQL=off` there is no fallback, so without it one 502 on
check-runs or status would park the goal (stripping `sdlc:goal`, i.e. needing a human). Why before the
stale-head and verdict branches: every returned `data` (stale head, UNKNOWN, CONFLICTING, BEHIND, non-CLEAN,
CLEAN) keeps today's four keys, so `_behind_transient`, `normalise_ci_rollup` -> `ci_observed`,
`_ci_failed_check`, `ci_repair` (`detailsUrl` -> `_ci_run_id`) see an identical shape. The sha queried is the
very `headRefOid` the stale-head check then compares with local HEAD, so a rollup can never describe a head
other than the one judged (research C8). Two-read window (named, not new): REST reads pulls then check-runs
non-atomically; a push in between leaves the rollup describing the older, compared head, and the merge itself
is guarded by `--match-head-commit` (slice 4b, unchanged).

VERDICT PRECEDENCE CHANGE (stated, not hidden): today one atomic read can never be "pull readable, rollup not".
Now a rollup that is still unreadable after its retries PRECEDES and HIDES the STALE HEAD, `_PARK_NO_LOCAL_HEAD`,
UNKNOWN, CONFLICTING and BEHIND verdicts: the gate returns `could not read PR state (...)` with `{}` instead.
It still fails closed (a park, never a merge), but a BEHIND PR then parks instead of rebasing, and a stale head
is reported as unreadable rather than STALE HEAD. Chosen over reordering because reordering would hand
consumers a `data` with no rollup on those paths. Pinned by a test (Task C 9, "rollup-unreadable precedence").
Only `_PARK_NO_REMOTE_HEAD` (empty head, no rollup read) is unaffected.
Unchanged: merge only on `MERGEABLE` AND `CLEAN` AND remote == local head; UNKNOWN_ATTEMPTS / backoff /
PENDING_ATTEMPTS; the verdict strings themselves. Gate docstring gains a short "REST first (#895 4a-2)"
paragraph that states the precedence above.
Cost (DERIVED from the call shapes; nothing timed): clean PR 3 calls vs 1 GraphQL; +1 per UNKNOWN retry;
worst merge() 11 rounds x (<=4 + 2) = 66 vs 44; ceiling ~230 worst-case merges/h on one 5,000/h token
(documented limit, UNMEASURED). With the breaker OPEN both the pull read and the rollup read go straight to
their GraphQL fallback: 2 GraphQL calls per round (not 1), i.e. up to 2x today's GraphQL cost while the breaker
is open.
