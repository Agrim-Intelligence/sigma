## Design (binding)

### D1. One write-policy table, in code
In `gh_api.py` a module constant, the single source of truth that the code reads and the tests
iterate (no parallel prose copy to drift). Columns: case_id, description, fallback for an
idempotent write, fallback for a non-idempotent write.

```
WRITE_POLICY = (
  ("primary_rate_limit",   ..., True,  True),   # HTTP 429, or 403, whose hint says rate limit and NOT secondary/abuse
  ("secondary_rate_limit", ..., False, False),  # 403 or 429 whose hint says secondary|abuse
  ("server_5xx",           ..., True,  False),  # 500-599: may have committed -> idempotent only
  ("transport_ambiguous",  ..., False, False),  # timeout / connection reset after send: NEVER
  ("auth_401",             ..., False, False),
  ("not_found_404",        ..., False, False),
  ("invalid_422",          ..., False, False),
  ("permission_403",       ..., False, False),
  ("proxy_block",          ..., False, False),
  ("refused",              ..., False, False),  # the feature-label guard; not a classify kind
  ("other_unparsed",       ..., False, False),  # includes malformed 2xx body
)
```
HTTP 429 decision: a 429 whose hint carries no secondary/abuse wording is a PRIMARY rate limit and
falls back (row 1); a 429 or 403 whose hint mentions secondary or abuse is the secondary limit and
never falls back (row 2). A primary-limit rejection is returned by GitHub before the request is
executed, so a create or comment may safely fall back on it (no duplicate possible); this is
documented GitHub behaviour and is UNMEASURED here (see Unmeasured). A test pins it with a create
(`create_issue` on a primary 429 falls back exactly once).

`_write_fallback_ok(exc, idempotent)` is DERIVED from this table (lookup by case), not a second
if-chain. Mapping from `classify` kind to case_id: `rate_limit` (+ `_is_secondary`) ->
primary/secondary; `server` -> server_5xx; `transport` -> transport_ambiguous; `auth`, `not_found`,
`invalid`, `permission`, `proxy`, `other` -> their rows. `refused` is NOT a `classify` kind
(`GhApiError(kind="refused")` is raised by the guard): `_write_fallback_ok` returns False for it via
its own row, with a test. The table test asserts case ids are unique and that every `classify` kind
plus `refused` maps to exactly one row. Cloud session / `SIGMA_GH_GRAPHQL=off`
(`graphql_available(env)["available"]` false): no fallback for any row. A fallback is attempted at
most once and never retried. Idempotent ops: `add_labels`, `remove_label`, `close_issue`,
`edit_issue(body=)`, `add_assignees`. Non-idempotent: `comment_issue`, `create_issue`.

Classification input for writes is STRUCTURED ONLY. `classify()` falls back to `str(exc)`, which
embeds argv and therefore the write BODY; a comment saying "rate limit" or "timeout" must never be
read as a fallback-eligible failure. The write layer adds `_write_kind(exc)`: it reads `exc.status`
and `exc.kind` set from the `.hint` (gh stderr, no argv) ONLY. When the exception carries no `.hint`
and no parsed `HTTP nnn`, the write kind is `other_unparsed` (never fall back); the `str(exc)`
wording branches of `classify` are not consulted for writes. `_write_kind` re-runs the structured
part of `classify` on `hint` alone (proxy check on hint, `HTTP nnn`, `TimeoutExpired` cause chain)
and never regexes `str(exc)`. Test: a comment/create whose BODY contains "rate limit", "abuse",
"timeout", "HTTP 502" and "dial tcp", failing with an unrelated hint, raises with zero fallback
calls; the same wording in the hint behaves per the table. `classify` itself and the read path are
unchanged. `_is_secondary(text)` (`secondary|abuse`, case-insensitive) is applied to the hint only.
The wording is INFERRED (no live capture): stated as a ceiling.

### D2. `_rest_write` (new, separate from `_rest_first`)
`_rest_write(op, number, what, cmd, rest, fallback, *, idempotent, env, sdlc_dir, now)`:
try `rest()`; on `GhApiError` raise unless the table says fallback OK and GraphQL is available;
else log once and run `fallback()` once (any exception from it propagates, no second try).
Logging reuses the bounded `state/gh-fallback.json` (cap 200, no text/argv/body) when an
`sdlc_dir` exists; it NEVER opens, closes, or consults the read breaker
(`state/gh-rest-breaker.json`). The log cap is now shared with reads: the docstring says so. stderr
line `fell back to <cmd> once` as `_rest_first` does. Fallback argvs are today's exact
`gh issue ...` argv, built inside `gh_api.py` (exempt from the ratchet), and are sent through the
same injected `run` (= `GitHubSource._run`) so recording fakes and the chokepoint seam still see
them.

### D3. Feature-label refusal, two layers; non-feature label minting
- Layer 1, inside `gh_api`: `create_issue` and `add_labels` raise `GhApiError(kind="refused")`,
  BEFORE any `run` call, for any `feature_labels.is_feature_label(name)` unless the caller passes
  `feature_labels_exist=True`. Loaded lazily with the existing `_load("feature_labels")` idiom.
- Layer 2, in `GitHubSource`: `_require_feature_labels(names)` does one REST
  `GET repos/R/labels/<quoted>` per feature-prefixed name via new `gh_api.label_exists` (404 ->
  False). Any False, or any failed lookup (fail closed), raises `RuntimeError("refusing to create
  the label ...")` with `_run`'s existing stderr wording. Only when it passes does the wrapper call
  the helper with `feature_labels_exist=True`. On refusal ZERO REST write calls are made (the
  existence GET is the only call, and it is a read); a test asserts it.
- Non-feature labels: REST `POST /issues` and `POST /labels` mint missing labels where gh failed.
  This also reaches `priority:P*` (`_write_priority_label`) and arbitrary triage labels
  (`triage.py` add-label). Per path:
  `create_dependency`/triage create: labels are pre-created by the existing `label create` steps
  (sources.py:3746, triage.py:2267), which stay, so REST never meets an absent label there (test:
  the recording fake shows `label create` precedes the write). `_write_priority_label`: the
  `priority:P*` label is a canonical vocabulary label (`priority_prefix + canon`); REST minting a
  missing one is ACCEPTED, documented behaviour, pinned by a test asserting the add call is
  `priority_prefix + canon` only. Triage `add-label` of an arbitrary label (`triage.py:2280`):
  accepted and DOCUMENTED divergence (gh failed, REST mints a colourless label), pinned by a test
  naming it; it is not "fixed" here (non-goal; REST auto-create is documented GitHub behaviour and
  is listed under Unmeasured).

### D5. Label atomicity (documented, nothing changes for lifecycle)
No lifecycle swap site (promote/park/unpark/mark_in_progress/complete/assign `_promote_to_goal`/
triage `swap-label`) is in this slice; all stay on `GitHubSource._swap_labels` (one aliased GraphQL
document). Triage single-label sites (7-9) and site 10 are single-label operations: atomicity N/A.
`_write_priority_label` (site 17) goes from UNORDERED parallel (`gh issue edit --add-label X
--remove-label Y...`, 4 parallel requests) to add-first-then-removes, SEQUENTIAL; it is still NOT
atomic; a partial failure leaves two priority labels, visible. Self-heal is NARROW:
`_priority_name` takes the MIN rank (sources.py ~4241). If the new label is LOWER priority than the
stale one (a demotion), the stale higher label still wins, the field/label disagreement persists
and the next pass retries the remove. If the new label OUTRANKS the stale one (a promotion) and the
remove fails, the effective priority is already correct, no disagreement is detected, and the stale
lower label is NEVER removed by the loop (visible, harmless to ordering, needs a human or a later
write). Documented as such; tests cover both directions. `PUT /labels` is NOT used (replace-set
lost update, reproduced earlier, see the sources.py block comment). Stated in docs and CHANGELOG.
In a cloud session lifecycle swaps still need GraphQL: unchanged, owner decision D-4 (801 plan).

2. Duplicate comments/issues if an ambiguous failure or a 5xx on a non-idempotent write is ever
   replayed (C1-C3).
3. Assignee silently dropped or `@me` sent literally (C18, C19).
4. Policy wording is INFERRED (403 decided by hint text only; secondary-limit wording and the
   pre-execution guarantee of a primary-limit rejection were not captured live).

   per-file run and the vacuity control C23.
6. Scanner / issue-creation-boundary blindness to migrated writes; mitigated by steps 15-17, and
   the blind spot is stated.
7. `GhApiError.__str__` embeds argv with the issue BODY (as `RuntimeError` does today); `.hint`
   stays the short form and classification never reads `str(exc)`.
8. Shared 200-entry fallback log now also carries writes; a write burst can push read entries out.
9. Priority promotion with a failed remove leaves a stale lower label that nothing removes (D5).
