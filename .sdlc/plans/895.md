## Design

### D1. `gh_api.merge_pr_gh(run, number, method, sha, repo=None, *, fallback_run=None, env=None, sdlc_dir=None, now=None)`
- Validate BEFORE any call: `number` coerced with `int(str(number))` (as `view_pr_gh` does; `rec["pr"]` is a string; not `isdigit()`), a failure is invalid; `method in {"merge","squash","rebase"}`; `sha` matches
  `[0-9a-f]{40}|[0-9a-f]{64}` (lower-case only). Else raise `GhApiError(..., kind="invalid")` with
  `.outcome_unknown = False`, zero runner calls.
- REST: reuse the existing `merge_pr(run, n, method, sha, repo)` (argv `api repos/{owner}/{repo}/pulls/N/merge --method PUT
  -f merge_method=M -f sha=S`) inside `rest()`. Success ONLY when the parsed body is a dict with `merged is True` -> return
  `{"merged": True, "merge_commit_sha": body.get("sha") if str else None, "via": "rest"}`. Empty body (`_json` -> None),
  non-dict, `merged` missing/false/"true" -> raise GhApiError("malformed REST merge reply ...") with
  `.outcome_unknown = True` (R1).
- Wiring: `_rest_write("pr_merge", n, "PR #N merge", "gh pr merge", rest, fallback, idempotent=False, env, sdlc_dir, now)`.
  WRITE_POLICY already lets only `primary_rate_limit` fall back for a non-idempotent op, and only while
  `graphql_available(env)` is available; the fallback runs once, uncaught, logged to `state/gh-fallback.json`.
- Fallback argv built HERE (EXEMPT from the ratchet): `pr merge N --<method> --match-head-commit SHA [--repo R]` via
  `_call(fallback_run or run, ...)`; exit 0 -> `{"merged": True, "merge_commit_sha": None, "via": "gh"}` (today's
  semantics for a CLI exit 0, unchanged).
- Every exception leaving the helper carries a boolean `.outcome_unknown`, set by one private `_merge_outcome_unknown(exc)`
  (a preset value wins): **False** (definite refusal, nothing landed) when `_write_case` is `auth_401`, `not_found_404`,
  `invalid_422`, `permission_403`, `proxy_block`, `primary_rate_limit` (reached when the fallback was not allowed, or when the fallback itself hit it), or
  `_write_status` is any other 4xx (405, 409) and the case is not `secondary_rate_limit`. **True** otherwise: `server_5xx`,
  `transport_ambiguous` (incl. `TimeoutExpired` in the cause chain), `secondary_rate_limit`, `other_unparsed` with no
  status, malformed/empty 2xx.
- DECIDED for the fallback's own failure: it propagates from `_rest_write` untouched and is classified by the SAME rule, so
  a fallback 5xx / transport / no-stderr failure (gh CLI refusals usually carry no `HTTP nnn`) is outcome-unknown ->
  reconciled; one with a 4xx status is definite. Never a second fallback, never a re-PUT.

### D2. `work.merge()` direct-merge site
`api = _pr_api_run(run, rec["worktree"])`; `gh_api.merge_pr_gh(api, rec["pr"], method, vetted_head, fallback_run=api,
sdlc_dir=sdlc_dir)`. The `["gh","pr","merge",...]` literal at ~5974 is deleted (ratchet -1).
- `except Exception as exc`: `if getattr(exc, "outcome_unknown", True)` (unknown exception types default to the SAFE
  branch: one read, no write) -> `state, why = pr_landing_state(sdlc_dir, rec, run)` (existing, ONE REST `pulls/N` read,
  no GraphQL, `merged` only on `merged: true`/non-empty `merged_at`):
  - `MERGED` -> fall through to the normal post-landing steps (branch delete, `_close_issue_the_base_cannot`,
    `_record_confirmed_merge`, observe, actionlog `merged`); return line keeps the opening
    `PR #N merged (<method>) — {gate_detail}{closed}` and appends ` (outcome reconciled: the merge call failed
    ambiguously, a REST read shows the PR merged)`.
  - the reconcile read is repeated up to `RECONCILE_ATTEMPTS = 3` (module constant) with `sleep(RECONCILE_PAUSE = 5)`
    between (uses merge()'s injected `sleep` parameter, tests pass NOSLEEP), only while the answer is OPEN/UNKNOWN (GitHub can lag after a 5xx; bounded 10s); MERGED/CLOSED stop it.
  - still `OPEN` / `UNKNOWN` (incl. read error) -> NOT a `PARK:` (plan-review R1: a park is not swept by the
    merge-reconcile pass, which reads only `awaiting_merge` goals set by `record review`). Return
    `merge outcome unknown for PR #N (<exc `.hint` first line, never the argv>; REST read: <state> <why>) -- NOT retried and NOT sent via GraphQL;
    leaving PR #N awaiting merge: the merge-reconcile pass records done if it landed, doctor's stuck-merge alarm covers
    it if not`. SKILL routing: any non-PARK, non-`merged` line -> `record review` (sets awaiting_merge); `record done` is
    refused until a REST read confirms the merge. No branch delete, no issue close, no ledger/actionlog `merged`.
  - `CLOSED` (unmerged) -> `PARK: PR #N was closed without merging (...)`.
  - The `MERGED` branch does not compare the merged head to `vetted_head` (`pr_landing_state` returns no head); the PUT
    carried `sha`, so GitHub merges only that head via THIS call (a human or an earlier arm could have merged a later head; the outcome is safe either way). Stated limitation.
- Definite refusal -> today's `PARK: direct merge of PR #N was refused (<exc>)` (409 head moved included: parks, never
  merges the new head; no reconcile read).
- Validation error (bad method/sha) -> same refused PARK (definite).
- Fake gotcha: `pr_landing_state`'s argv `gh api repos/{owner}/{repo}/pulls/7` is a substring of the PUT line; tests key the
  PUT with `prfake.merge_put(7)` = `"pulls/7/merge --method PUT"` FIRST in the handler list.

### D3. No-GraphQL pending path (before the existing arm branch) -- no extra wait
`if pending_arm and not gh_api.graphql_available()["available"]:` (env/override only, no probe). Do NOT call
`_auto_merge_allowed` and do NOT attempt `--auto`. gate() has ALREADY spent its bounded REST wait (PENDING_ATTEMPTS x
PENDING_INTERVAL = 450s, the stated timeout; the 4a-2 REST check-run reads, all-or-nothing, malformed answers park) and
the checks are STILL pending, so:
`PARK: required checks still pending after 450s and auto-merge cannot be armed without GraphQL; re-run
work.py merge once they finish` (the secs value is computed from the two constants). No merge is attempted (a REST merge
of a PR with pending required checks would be refused by GitHub anyway; never merge around them). When the wait ended
with checks ok, `pending_arm` is False and the flow goes straight to the D2 REST merge with the vetted head, i.e. the
"wait for checks, then PUT with sha" rule is met by gate() itself. GraphQL available: byte-identical to today (arm when
`_auto_merge_allowed`, else direct merge, now via D2). No new wait, so the worst case stays 22.5 min and no host-timeout
number changes (plan-review R2: a longer wait cannot fit the host's 10-minute foreground cap).

## Stated limitations
- **A real cloud session still stops BEFORE the merge call (plan-review round 4, the biggest honesty item).** `merge()` calls
  `merge_rights` first, whose permission read is `gh repo view --json viewerPermission` (GraphQL, work.py ~3589) and
  `protection()` reads `gh repo view --json nameWithOwner` (~3609). Under `CLAUDE_CODE_REMOTE` the first fails, is caught, and
  `merge()` returns `PR #N opened -- could not determine merge rights (...)` (routes to `record review`); nothing merges.
  Moving those two reads to REST is NOT in this slice (every test using `prfake._perm()` fakes `viewerPermission`; too large
  to review here): it is the first item of slice 4b-2. So D2/D3 are reachable only where GraphQL works (including
  `SIGMA_GH_GRAPHQL=off` for the `graphql_available()` branches) -- Goal/Docs/CHANGELOG/cloud-sessions.md/enforcement.md
  must NOT claim a cloud session can now merge. One test drives `CLAUDE_CODE_REMOTE=true` WITHOUT the `_perm()` fake and
  asserts the real current outcome (the `opened -- could not determine merge rights` line, no merge call).
- A secondary rate limit is rejected before the write runs, like a primary one, but is treated as unknown (safe; costs the
  3-day stall). Docs say so.
- docs/skills `landing.md` (~203-208) says a host cut mid-call means "nothing was recorded ... re-run work.py merge": update
  it to name the `record review` lever for a PUT that may have landed.
- D3 parks on pending checks without trying the sha-guarded PUT, so an UNSTABLE PR whose pending checks are NOT required
  (GitHub would merge it) also parks in a no-GraphQL session; cloud previously could do neither (arm and direct merge were
  both GraphQL) -- see the next limitation: a real cloud session does not even reach this point yet. Safe direction; liveness cost named in cloud-sessions.md.
- A gh-CLI fallback refusal (after a primary rate limit, GraphQL available) usually has no `HTTP nnn`, so it reads as
  unknown, reconciles to OPEN and the goal sits awaiting_merge (3-day doctor alarm) where a definite refusal would park at
  once. Documented in the cloud-sessions.md table.
- Number validation is `int(str(n))` only (accepts "-7"); a bad number is a 404, a definite refusal.

## Cost, ceilings, recovery
- Calls per merge (Scalability): happy path 1 REST PUT (was 1 GraphQL `gh pr merge`); + at most 1 gh-CLI fallback (primary
  rate limit, GraphQL available); + at most RECONCILE_ATTEMPTS = 3 REST reads on an unknown outcome. Hard ceiling 5 GitHub
  calls for the landing step, independent of repo size. No new waiting: worst-case wall clock unchanged (22.5 min,
  DERIVED from constants, not timed; the PUT and the reconcile reads have NO per-call timeout because `_run` sets none,
  existing ceiling) plus at most 10s of reconcile pauses. Per-goal, no shared lock; 10x/100x merges scale linearly against
  the REST core budget (5,000/h per token, documented, UNMEASURED here).
- Recovery: definite refusal -> PARK, nothing written, next pass re-gates. 409 moved head -> PARK, next pass vets the new
  head. Unknown + MERGED -> normal post-landing. Unknown + OPEN/UNKNOWN -> `record review` (awaiting_merge): the
  merge-reconcile pass records `done` if it landed; if not, doctor's stuck-merge alarm names it; a re-run's PUT carries
  `sha` so it cannot land a different head. Primary rate limit on cloud -> PARK (definite). Fallback failure ->
  classified like REST. Host cuts the call mid-PUT -> nothing recorded locally and the PR may or may not have merged; the documented lever is `loop.py record review` (sets awaiting_merge), after which the merge-reconcile pass records `done` once a REST read shows MERGED (`record done` stays refused until then). How the next `work.py merge` reads an already-merged PR is not changed by this slice and not re-measured. Cloud pending checks -> PARK, re-run `work.py merge`.
