## Design decisions
1. `check-tests` always runs the plan input check (no `verify.enforce` condition, as `tests_section_error` today); the verdict refuses only with `verify.enforce` on (TD-2), stated in the `main` docstring.
2. Warnings (legacy goal) go to stderr only; `check-tests` stdout stays the single success line.
3. The refusal text in `work.py`: `the plan's inputs are incomplete, so Plan-Review cannot pass it: <errors joined by "; "> (fix <reviewed.as_posix()>, then run a fresh plan-review)`. `ValueError` makes the verb print it and exit 2 with nothing written, as the neighbouring refusal does. `reviewed` is the plan copy the verdict binds to, passed as `check_plan`'s third argument.
4. Registry row (read `enforcement_table._validate` first, line 288; required keys `control`, `function`, `kind`, `hosts`, `enabled_by`, `mechanism`): control `Plan inputs are complete before Plan-Review passes`, function `_plan_inputs_refusal`, kind `python-gate`, hosts `all`, `enabled_by` `("work.enabled", "verify.enforce")` (spelling as the Test-first row), `settings` `()`, a `mechanism` naming `work.py record-plan-review` and `red_green.py check-tests`, and a `condition` (legacy goals pass with a warning; `check-tests` checks whatever `verify.enforce` is). No `|` and no newline in text fields; pure literals. Name ends `_refusal` so it must be registered (it is).
5. Scalability and resiliency: cost is one `check_plan` call per `check-tests` or approving verdict, ceilings in `reuse.py`'s docstring (1 MiB plan cap, linear); the gate cost was not timed here and the PR says so. No state is written by either check; a refusal is retried by fixing the plan and running again. Not measured: an end-to-end run in a real goal worktree with a new-format dossier (tests use temp projects); the PR says so.
