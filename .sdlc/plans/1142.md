# #1142 plan: ledger bootstrap must join, never fork, the remote ops branch

## Goal / done_when
See `.sdlc/acceptance/1142.md`. Research: `.sdlc/research/1142.md`.

## Design

D1 `_fetch(git, cwd, rem, name)` runs `git fetch <rem> +refs/heads/<name>:refs/remotes/<rem>/<name>`. The destination is explicit, so the tracking ref exists whatever `remote.<rem>.fetch` says. `+` mirrors git's default refspec, so a force-pushed ops branch still updates. It replaces all six bare fetches in sync.py (init, pull, `_pull_knowledge`, `_push_with_retry`, `publish_receipt` x2). `name` is already `_ref_value`-validated, and git refnames cannot contain `:`.

D2 init never forks. On a failed fetch with no local branch, `_remote_branch_state` runs `git ls-remote <rem> refs/heads/<name>` (no `--heads`: renamed in 2.46) and exact-matches the ref column:
- absent: start from the empty tree, as today;
- present: raise `RuntimeError("REFUSED: <rem> has <name> but it could not be fetched (...); refusing to start a second, unrelated history (#1142) ...")`;
- ls-remote fails: if `git config --get remote.<rem>.url` is set, refuse the same way (the remote cannot be read, so it might have the branch). If it is unset, start fresh as today (a local-only setup has nothing to diverge from).
No local branch is created on refusal. The existing local-branch-present paths (#592) are unchanged.

D3 `_shares_history(git, cwd, rem, name)` returns True, False, or None:
- `git merge-base HEAD refs/remotes/<rem>/<name>` succeeds: True. This is the fast path, O(distance to the base).
- Otherwise read both root sets (`rev-list --max-parents=0`). Return None if either is empty or unreadable, if a missing tracking ref raises, or if any root is a shallow boundary (`rev-parse --is-shallow-repository`, then `$GIT_DIR/shallow`). Otherwise return True if the sets intersect, False if they are disjoint.
Disjoint true roots is exactly "no common ancestor". Stubs that return "" read as True or None, never False, so the stub suites keep their meaning.

D4 detection, BEFORE any rebase. Grafting via `rebase -X theirs` would overwrite shared README/.gitattributes/TEAM.md with this clone's copies.
- `_push_with_retry`: after the post-rejection `_fetch`, if `_shares_history is False`, return `_UNRELATED.format(verb="publish", ...)`. This covers both channels.
- `pull` and `_pull_knowledge`: after `_fetch`, the same check with `verb="pull"`.
- Message: `"{verb} refused: {name} here shares no history with {rem}/{name} -- it was started on its own (#1142), so no retry can land it; run `sync.py bootstrap .sdlc{--channel knowledge}` to re-root it onto {rem}/{name} (local files are kept)"`.
- `publish_after_write`: a result starting `publish refused` drops the "will retry it" tail and points at the lever instead.
- `publish_receipt` gets D1 only. Its retry is bounded and already says "pending", and its open defects are #211's.

D5 `bootstrap` re-roots an orphaned worktree. `_reroot(git, ch)` runs after `init` and before seeding. The knowledge channel holds `_knowledge_lock` for it and releases it before `publish` (flock is per open file description, so a second acquire in the same process would conflict). Steps:
1. `_fetch`. On failure return "" (cannot decide; publish reports the push).
2. If `_shares_history` is not False, return "".
3. Back up: `git update-ref refs/sigma/orphaned/<channel>/<YYYYmmddTHHMMSSZ> HEAD`. This is outside `refs/sigma/claims/`, and nothing pushes it.
4. `git ls-tree -r -z --name-only <tracking>` gives R. For each path:
   - root scaffold (ledger: README.md, TEAM.md, .gitattributes; knowledge: .gitattributes, .gitignore), or absent on disk: add it to the checkout list;
   - present on disk: union it. `_append_missing_lines` appends the branch copy's lines the local file lacks. It is append-only (O_APPEND), so a concurrent `ledger.append` is never truncated, and it is idempotent.
5. `git checkout <tracking> -- <paths>` in chunks of 100, while HEAD is still the orphan.
6. `git reset -q --mixed <tracking>`: the branch and index move to the remote tip, and the working tree is untouched.
Then publish stages exactly what it always does (my entries + TEAM.md; knowledge: every note, through the secret gate). The re-root stages nothing itself, so a teammate's stale file is never republished on my behalf. Returns `"; re-rooted <name> onto <rem>/<name> (old tip kept at <ref>[; N file(s) merged])"`.
Crash safety: every checkout precedes the single reset. A crash before the reset leaves HEAD on the orphan, and a re-run converges (existing files union with themselves as a no-op). After the reset, the state is consistent. A concurrent watcher can make a step fail on `index.lock`; bootstrap then exits 1 with the git error, and re-running converges.

D6 doctor: `sync.history_shared(sdlc_dir, config, run=None)` is the public wrapper of D3 for the ledger worktree. It is local-only and never fetches. `_ledger_delivery_state` returns `" -- DIVERGED: this clone's <name> shares no history with <rem>/<name>, so no publish can ever land; run `sync.py bootstrap .sdlc` to re-root it (local entries are kept)"` ahead of every other clause when it is False. That precedence is right: it is the one state no tick fixes.

## Revisions from plan-review round 1 (SOUND-WITH-REFINEMENTS): all taken; these OVERRIDE D1-D6 above where they differ

- R1 (finding 1, wedge). D5's union applies ONLY to `entries/*.jsonl` (ledger) or `*.md` (knowledge). Every other path in R is checked out from the tracking ref: README, TEAM.md, .gitattributes, .gitignore, `receipts/*.json`, anything else. Their committed orphan copies are in the backup ref. A ledger file the union actually changed is `git add`ed after the reset, whatever actor's name it carries: its content is a superset of the branch copy, which is what `merge=union` would have committed. The knowledge channel stages nothing; publish's secret gate does that. After the reset, `status --porcelain --untracked-files=no` is read. Any unstaged tracked change that publish will not stage is NAMED in the return string, never silent. `_append_missing_lines` prefixes a newline when the local file lacks a trailing one.
- R2 (finding 5, actor drift). After the reset, the ledger re-root also stages untracked `entries/*.jsonl` whose name carries THIS machine's host token (`-<_host_token()>.`). That covers the clone's own writes under any earlier actor resolution (#488), and never another machine's files. That matters when the remote branch was deliberately recreated: re-root does not republish teammates' old files.
- R3 (finding 2, shallow). The shallow file comes from `git rev-parse --git-path shallow`, made absolute against cwd. Probed: from a linked worktree it is the common dir's `shallow`. D4 changes: when `_shares_history` is NOT True (False or None), no rebase runs. False returns the permanent `refused` status. None returns `{verb} deferred: no common ancestor with <rem>/<name> is visible in this clone (a shallow cut or an unreadable repository); not rebasing onto it`. The graft is then unreachable from every path. Stubs return "" for merge-base, which reads as True, so they keep rebasing.
- R4 (finding 3, URL or path remotes). `_fetch`, and so the tracking ref, needs a NAMED remote. When `rem` contains `/`, `:` or `\` and is not in `git remote` output, it raises `ValueError("REFUSED: ledger.remote <rem> is a URL or path; ...")`. Probed: `git remote` lists pushurl-only remotes and names containing `/`, and a URL-shaped string is not a valid remote name. `name` may not contain `* ? [ \ ^ ~ :`; `ledger.branch="*"` would otherwise fetch every head. `init` lets that REFUSED propagate (exit 1). Today such a config already forks or wedges on the second machine. D2's "configured" test is `rem in git remote`, not `remote.<rem>.url`.
- R5 (finding 4). `merge_observation.resolve_remote_snapshot` (merge_observation.py:405) does a bare `fetch --no-tags <remote> <branch>`, then `rev-parse <remote>/<branch>`. Once D1 creates the ref in a single-branch clone, it would pin a STALE commit. It gets the same explicit refspec, with a test that pins the moved ref.
- R6 (finding 6). The message names both causes and the consequence: `"{verb} refused: {name} here shares no history with {rem}/{name} (it was started on its own -- #1142 -- or {rem}/{name} was deleted and recreated), so no retry can land it; `sync.py bootstrap .sdlc{flag}` re-roots it onto {rem}/{name} and republishes this clone's own entries"`.
- R7 (finding 11). If bootstrap's publish returns `publish refused`, which happens when two first-ever bootstraps race against an absent remote, bootstrap re-roots and publishes ONCE more. Bootstrap is the consented gesture; bounded at one retry.
- R8 (finding 12). Doctor: when the tracking ref is missing and `remote.<rem>.fetch` maps nothing matching `refs/heads/<name>`, the row adds that this clone's fetch refspec does not cover the branch and that `sync.py pull .sdlc` fetches it by name. That is the pre-fix orphan with a dead watcher. Local config read only. The matcher handles exact and single-`*` globs, skips `^` negative refspecs, and treats an unparseable entry as "covers" (no false alarm).
- R9 (finding 13). `publish_receipt` stops before its rebase when `_shares_history` is not True. It is gated off today, but the graft must be unreachable from every path.
- R10 (findings 9, 10). init's empty-tree branch is reached ONLY from `_remote_branch_state` = absent or no remote. Any other exception with no local branch refuses. If the knowledge lock is held, re-root returns `"; re-root deferred: another knowledge sync holds the lock"`. Re-root never calls `is_worktree`.
- R11 (findings 7, 8). Measured D3 (git 2.46.2, one laptop, best of 5, no commit-graph, 32,500-commit branch): `merge-base` on related histories 24.8 ms; root walk 245.6 ms; `merge-base` on unrelated histories 321.4 ms (exit 1). The re-root's chunked checkout is measured in P5 at 10,000 files and recorded in the CHANGELOG. Write-surface rows are REGENERATED with `tools/readiness/write_surface.py scan`, never hand-written (the scanner does not tag reset or checkout).
- Ceiling added: D3 None (shallow cut) never rebases. Such a clone defers until its history is deepened (`git fetch --deepen`/`--unshallow`). That is stated in the message, not hidden.

## Revisions from plan-review round 2 (SOUND-WITH-REFINEMENTS): all taken; these OVERRIDE R1/R2 where they differ

- R12 (round-2 finding 1). The ledger re-root splits by HOST TOKEN, not by "the union changed it". An `entries/*.jsonl` in R whose name carries this machine's `-<_host_token()>.` and exists locally is unioned and then staged (always, changed or not). EVERY other path in R is checked out from the tracking ref, including a teammate-named file this clone carries; the orphan's committed copy stays in the backup ref. So the purge case never republishes a teammate's line, and the superset case never leaves a modified tracked file. After the reset, `status --porcelain -z --untracked-files=no` is parsed by whitespace split (round-2 finding 6) and must show only staged entries under this host token. Anything else is named in the return string as a defect, never ignored. Knowledge has no host token in note names. It keeps "union every `*.md` in R that exists locally", and publish stages notes through the secret gate. The refusal message's "republishes this clone's files" is the warning for the purge case. That asymmetry goes in the docs.
- R13 (round-2 finding 2). After the reset, the ledger re-root lists untracked `entries/*.jsonl` (via `git ls-files --others -z -- entries`). Files with this host token are staged (R2). Every other leftover (another host, a pre-hostname-change token, a legacy `<actor>-<pid>` name) is MOVED to `<sdlc>/state/orphaned/<stamp>/ledger/<path>` when it is byte-identical to its blob in the backup ref. That is lossless twice over: the backup ref has it, and the moved file does too. It stops `unpublished()`/`pending_entry_count()`/`read_all()` from counting it forever. One `ls-tree -r <backup> -- entries/` plus chunked `hash-object` compares them. A leftover that differs from the backup, or is absent from it, is left in place and NAMED in the return string. The return string reports the moved count and the directory.
- R14 (round-2 finding 3). The R7 test injects the interleaving: B's runner runs A's bootstrap at B's first `push`, so B's re-root has already passed. Removing R7 must turn it red; this is checked in P5.
- R15 (round-2 finding 4). The shallow file path is resolved against the `-C` directory passed to the git callable, never the process cwd. In a main checkout `--git-path` prints a relative `.git/shallow`.
- R16 (round-2 finding 5). `merge_observation.resolve_remote_snapshot` refuses a URL or path remote by the same named-remote rule before building the refspec.

## Ceilings / recovery
- D3 costs one `merge-base` per pull and per rejected push: O(commits since the merge base). The roots walk (O(ledger history), measured in R11) runs only when merge-base fails.
- Re-root is operator-run, O(|R|) stats plus ceil(|R|/100) checkouts, once. One backup ref per re-root; nothing prunes them (rare, and deliberately kept).
- Why not auto-re-root in the watcher: an unrelated history also arises when someone deleted and recreated the remote branch, possibly to purge it. Silently republishing onto it is a SAFETY call a human makes. After D1/D2, new orphans cannot form from a narrow refspec.
- Recovery from a mistaken re-root: `git -C .sdlc/ledger reset --hard refs/sigma/orphaned/<channel>/<stamp>`.
