# Plan 2228: two resource-lease tests establish their own pid premise

## Approach
Cause (confirmed, research `.sdlc/research/2228.md`): `test_peak_taken_while_the_session_runs_is_what_release_records`
and `test_ring_unit_is_bytes_per_sizeable_process_of_the_run` rewrite the lease record's `pid` to a fake 100 but
leave `admit`'s `pid_start` (the real test process's start). Where a real process 100 exists that started more than
`START_TOLERANCE` (2.0 s) from the test process, `reused()` is True and `note_peak` returns False. Production code is
correct (a different process at a recorded pid IS reuse, #1715). No production change, no loosening.

Fix at the cause (research option 2): a test helper `_take_over(lease, got, pid)` rewrites `pid` AND `pid_start`
together (`pid_start = lease.process_start(pid)`), so the record says which process it claims to be. Both tests call
it instead of their inline `path.write_text(dict(record, pid=100))`. With no process 100, `pid_start` is None and
`reused` is False (as today). With an occupant, `pid_start` equals that occupant's start and `reused` is False.
`reused`, `START_TOLERANCE`, `note_peak` and every assertion (`is True`, `procs == 5`, `[414]`, `[100]`, `[500]`) are untouched.

## Amendment 1 (found by the full verify, run 2 of `loop.py verify`): a third container-sensitive test
The full verify (`1 failed, 25096 passed, 89 skipped, 9 xfailed in 3405.98s`, evidence `.sdlc/state/verify/2228.json`) failed
`tests/test_run_with_timeout.py::test_a_hung_commands_grandchild_process_is_also_terminated_not_orphaned` (line 137, "not terminated
within 2s"). Same family as #2225's fix, never applied to this test. Measured here, on the two-test fix's own branch:
- 3 isolated runs of the file: 1 failed, 2 passed. A 40-iteration loop of the test's own scenario: 6 of 40 still answered
  `os.kill(pid, 0)` at the 2 s deadline.
- Cause: the killed grandchild is reparented to PID 1 (`process_api`), stays a ZOMBIE (`/proc/<pid>/stat` state `Z`, ppid 1 in
  60 of 60 samples) until PID 1 reaps it on a ~2 s poll (lifetime observed 1.98 to 2.0 s, i.e. right at the test's own 2 s
  bound), and `os.kill(pid, 0)` succeeds on a zombie. The group kill itself worked every time. This is the README's existing
  row for "PID 1 reaps orphans on a ~2 s poll" and failure family "tests that kill a timed-out process group" (#2225); the fix
  there was `alive()`/`gone()` in `tests/unattended_support.py`, which read the process state and treat a zombie as gone.
- Fix (test only, no production change, no loosening): the test's own poll loop (lines 128-137) is replaced by
  `support.gone(child_pid, limit=2.0)` (import `unattended_support`, as `tests/test_bounded_run.py:20` does): same 2 s bound,
  same assertion message, and a zombie is correctly "terminated" because it is dead. A grandchild that is truly still running
  at 2 s still fails.
- Test-first: there is NO deterministic red at base for this one (the failure depends on when PID 1 reaps), and the helper
  already exists, so a new test of it would be green at base. It is NOT added to `## Tests`. Evidence instead: (i) the verify
  failure above; (ii) before/after on the same loop, N runs each: base leaves some at the deadline, fixed leaves 0; (iii) the
  documented gesture `python3 -m pytest tests/test_run_with_timeout.py -q` repeated 10 times after the fix: all green;
  (iv) control: with a deliberately naive `run_with_timeout.py` that does not kill the group (scratch copy only, never in
  the tree) the fixed test still goes red, so the 2 s bound still bites; (v) control: restoring the raw `os.kill` poll goes
  red again in the loop. The post-PR review judges this; if the gate refuses the extra file, say so, do not hide it.
- Files: `tests/test_run_with_timeout.py` (modify, test file), plus a README sentence in the existing failure-family row
  naming this test as a second site (#2228). Guards: `tests/test_run_with_timeout.py`, `tests/test_cloud_setup_script.py`,
